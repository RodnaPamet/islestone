# Scheduling and working calendars

Roadmap 3.1 (`docs/porting/maps/3.1.md`), [ADR 0010](adr/0010-scheduling-and-working-calendars.md), owner decisions 182 to 203. This page describes what the three sub-phases built: the scheduling engine, working calendars, review steps on calendars, the project's due date and the start-after-due rule (3.1a), the timeline with the critical path (3.1b), and changing dates and dependencies from the timeline, with "Also move the N items it pushes later" (3.1c).

## The engine

`src/app-layer/domain/schedule/` is pure and client-safe: plain data in, plain data out, no database, no clock, no time zone, no `@/env`. The server and the browser run the same module (the timeline's cache re-runs it after a write, 3.1b; the drag preview, 3.1c); there is no second implementation.

| File | What it holds |
|---|---|
| `calendar.ts` | Epoch days (`toEpochDay`, `fromEpochDay`, `epochDayToDate`), `compileCalendar`, `isWorkingDay`, `nextWorkingDay` / `previousWorkingDay` (the day itself when it works), `addWorkingDays` / `subtractWorkingDays` (`n ≥ 0`, counting from the first working day on or after the day), `workingDaysInclusive`, `workingDayDiff`, `workingDaysAfter` (a review step's due day: the day itself never counts), `todayIn` (the only function that reads a zone, through `Intl`), `isKnownTimeZone` and `copyHolidaysToYear` ("Copy last year's"). |
| `types.ts` | `ScheduleInput`, `ScheduleItem`, `ScheduleEdge`, `ItemSchedule`, `ScheduleResult`, `SCHEDULE_ITEM_LIMIT` (20,000). |
| `engine.ts` | `computeSchedule(input)`. |
| `span.ts` | The spans (3.2c, decision 215): `spanOf` (the earliest start to the latest end of several spans: the one summary rule, which the engine's summaries and the roadmap's bars both use), `plannedSpanOf` (one item's stored dates as the engine reads them: both dates, start to due; a due date alone, one working day ending on it; a start alone, one working day from it; start after due, as a due date alone), and `boundsOf` / `mergeBounds` / `spanFromBounds` (the same span from the four boundary dates an aggregate returns per group, property-tested equal to `spanOf` over every item; `tests/unit/domain/schedule-span.test.ts`). |

An epoch day is a whole number of days since 1970-01-01: a civil date, never an instant. A calendar compiles to a weekday mask and its holidays on working weekdays, sorted; a count over a span steps whole weeks, the remainder and the holidays in range by bisection, so it is O(log h).

### The rules (ADR 0010 §2 to §4)

1. **Validate.** A duplicate item or calendar, an unknown calendar or an edge to an unknown item throws (a programmer error). Over 20,000 items returns `TOO_LARGE` before any work.
2. **Summaries** (decision 186). An item with sub-items in the input is a summary, not scheduled itself; a blocks relation into it applies to every leaf sub-item and one out of it leaves from every leaf. A relation between an item and its own sub-item is left out and named (`EDGE_INSIDE_SUMMARY`). A summary's result spans its leaves (`spanOf`, shared with the roadmap since 3.2c); `SUMMARY_OUTSIDE_PLANNED_DATES` names one whose leaves run past its own dates.
3. **Duration** on the item's calendar (decisions 184, 185): both dates, the working days between them (at least 1); one date, 1; neither, 0 and `unscheduled` ("No dates"); start after due, `DATES_REVERSED` and 1 day at the due date. An undated item inside a chain counts zero days and is named (`UNSCHEDULED_IN_CHAIN`).
4. **Order.** Kahn's sort with the ready set ordered by id. A remainder is `CYCLE`, naming one cycle in blocks order from its smallest id; it answers exactly when `wouldCreateCycle` would (a property test).
5. **Forward pass** (decision 187). Done: fixed at its actual dates (`startedAt`, `completedAt` in its calendar's zone, else its planned dates); it holds nothing back after it finished and is never critical. Started: from its actual start, never finishing before today. Open: not before today, its start date or the day after each blocker's earliest finish, on its own calendar's next working day, so a cross-team relation needs no common unit. `STARTS_BEFORE_BLOCKER_FINISHES` when its plan (the start date, or a due-only item's due day) is before an open or started blocker's finish.
6. **Backward pass.** The latest finish is the earliest of the finish in view, the item's milestone's due date, its project's due date (decision 188) and the day before each open successor's latest start. A successor already started or done bounds nothing.
7. **Float** in working days on the item's calendar: total float from earliest to latest finish (negative when a deadline is missed: `lateDays`, "Late by N days"), free float to the earliest successor start, never negative nor more than a positive total float. `MISSES_MILESTONE_DUE_DATE` and `MISSES_PROJECT_DUE_DATE` are reported each on its own.
8. **Critical** (decision 198): the open and started items with the least total float in view, when that is 0 or less, and the input edges between two critical items that leave no gap. An undated item with no relation is never critical.

Results are sorted by id; every number is an integer. Nothing here writes a date (decision 184).

`tests/unit/domain/schedule-engine.test.ts` (vectors written by hand: the float vector, a weekend, a holiday inside a duration, two calendars across an edge, a started item past its due date, a done item, deadlines earlier, later and equal, summaries, a cycle), `schedule-properties.test.ts` (cycles refused exactly when the relation usecase would, reordering, idempotence, monotonicity in edges, today and holidays, the critical path, no date of an open item on a non-working day), `schedule-calendar.test.ts` (the arithmetic against a day-by-day reference; `todayIn` one second either side of every offset change of six zones from 2020 to 2030, the date line and Apia's skipped day), `schedule-timezones.test.ts` (byte-equal results under five process time zones, each in its own process) and `schedule-performance.test.ts` (5,000 items and 10,000 relations; about 20 ms median and 30 ms p95 alone in Node on the development machine; the test fails at four times the 50 ms p95 budget).

## Working calendars

`WorkingCalendar` and `WorkingCalendarHoliday` (`prisma/schema/scheduling.prisma`, migration `20261212120000_working_calendars`): one workspace calendar (`teamId` NULL) and at most one per team (two partial uniques), each a name, an IANA time zone, working weekdays (ISO 1 to 7: non-empty, ascending, unique, by CHECK) and a `version` every change moves; holidays a date and a name, unique per calendar. Names are plaintext workspace configuration, sanitised, at most 80 characters (CHECK); not personal data, so not encrypted. A team's deletion removes its calendar.

- **Which calendar** (decision 189): an item's team's, else the workspace's. A workspace with no row counts Monday to Friday, no holidays, in `NOTIFICATIONS_TZ`; Settings shows that default, and the first save, or the first holiday added, stores it.
- **"Today"** (decision 191) is today in the calendar's zone (`todayIn`); the nightly jobs keep firing in `NOTIFICATIONS_TZ`.
- **Holidays** (decision 190) are entered by hand. "Copy last year's" and "Copy the workspace's holidays" are computed in the browser (`copyHolidaysToYear`; 29 February becomes 28) and posted to the add route, which skips a date already there and answers `added` and `skipped`. At most 500 holidays per calendar (`TOO_MANY_HOLIDAYS`), 100 per request, in the years 2000 to 2199.
- **Keys** (decision 193): read under `projects.view`, written under `admin.manage` (`workConfigAffordances().manageWorkConfig` on the page).
- **Routes:** `GET`/`PUT /working-calendar` (the workspace's, with which teams have their own), `POST /working-calendar/holidays`, `DELETE /working-calendar/holidays/:holidayId`, `GET`/`PUT`/`DELETE /teams/:teamId/working-calendar`, `POST /teams/:teamId/working-calendar/holidays`, `DELETE /teams/:teamId/working-calendar/holidays/:holidayId`. Refusals: `TIME_ZONE_UNKNOWN` (a zone both `Intl` and `pg_timezone_names` must know), `WEEKDAYS_INVALID`, `NAME_INVALID`, `HOLIDAY_DATE_INVALID`, `NO_TEAM_CALENDAR` (a team holiday before the team has its own calendar).
- **Audit** (`category: 'entity_lifecycle'`): `WORKING_CALENDAR_SET` (scope, team, zone and weekdays, before and after), `WORKING_CALENDAR_HOLIDAYS_CHANGED` (the dates added and removed, never the names), `WORKING_CALENDAR_REMOVED`.
- **One read for arithmetic:** `resolveWorkingCalendars(db, ctx, teamIds?)` (`usecases/working-calendar.ts`) returns the workspace's calendar and `forTeam(teamId)`, compiled; every caller that counts working days uses it.
- **Settings → Working calendars** (`settings/working-calendars`, and a team's at `settings/working-calendars/[teamId]`; `WorkingCalendarSettings.tsx`): the zone, the weekdays, the holidays, the teams. Removing a holiday and taking a team back to the workspace's calendar go through the undo toast (`use-undo-delete.ts`). Copy is `settings.workingCalendars.*`.

Changing a calendar changes no stored date (ADR 0010 §5).

## Review steps on calendars (decision 192)

A step opened from 3.1a stores its due day as `workingDaysAfter(calendar, today in the calendar's zone, n)` on the item's team's calendar, else the workspace's (`openStepInTx` in `review-engine.ts`). With no calendar edited that is exactly 2.8's Monday to Friday in `NOTIFICATIONS_TZ` (`tests/integration/working-calendars.test.ts` proves it). A stored `dueOn` never moves (ADR 0009 §13). The 08:00 job reads the same calendar for "today" and "the next working day" of each pending reviewer's item. `src/app-layer/domain/working-days.ts` keeps 2.8's `Date` signatures over the calendar module, Monday to Friday when no calendar is given.

## The project's due date (decision 188)

`Project.dueDate` (migration `20261212120100_project_due_date`), optional and date-only, set on `POST /projects` (`projects.create`) and `PATCH /projects/:id` (`projects.edit`), returned as `YYYY-MM-DD`, audited by naming the field in `PROJECT_CREATED` / `PROJECT_UPDATED`. It is a deadline for the schedule and nothing else: it moves no item or milestone, is never refused against them and rings nothing (ADR 0002 §16). A project template carries it as `projectDueInDays` (an offset from the day the template is saved), dated from today when used, unless the create names a due date (`null` included). UI: the create dialog's Due date, Settings → Projects' "Change due date" and column, the Projects list's column and the project page's header (`ProjectDueDate`, offered with `editProject` on an unarchived project). Copy is `settings.projects.dueDate*` and `workItems.projects.dueDate.*`.

## Start after due (ADR 0010 §3)

A write that would leave an item's start date after its due date is refused, 400 `START_AFTER_DUE` (`assertStartNotAfterDue` in `work-item-shared.ts`): every create (`createWorkItemInTx`, so the dialog, the API, intake accept, templates and repeat copies), an edit of either date (`updateWorkItem`), and the bulk due-date change (naming the items in `details.workItemIds`). A write that touches neither date is not refused, and rows written before are never rewritten: the schedule reports them (`DATES_REVERSED`). A repeat whose source has its start after its due date makes copies without a start, named `startDate:afterDue` in `skipped`.

## The timeline (3.1b)

The `TIMELINE` layout (decisions 182 to 203): read in 3.1b; changes from it are 3.1c's (below). The layout switcher offers List, Board and Timeline on the Work items page, a project's page, a cycle's page and a milestone's page; a saved view stores `TIMELINE` and its `timeline` settings (`zoom`, `showCriticalPath`, `showNoDates`). My Work offers no timeline (decision 54).

### The read

`GET /api/t/:slug/work-items/timeline?<the list's filters>` (`requirePermission('work_items.view')`, a `route-permissions.ts` rule and a `tenant-crud-authz-coverage` pin), usecase `getWorkItemTimeline` (`usecases/work-item-timeline.ts`):

1. **The scope** is the list's own `where`: the filters are resolved by `resolveListFiltersInTx` (the list's `q` key hit and full-text matches, `cf.<fieldId>` conditions, `cycleId=current`) and read by `WorkItemRepository.listForTimeline`, so a timeline and a list with the same filters hold the same items. The list's order, page size and cursor do not apply.
2. **At most 5,000 items** (`TIMELINE_ITEM_LIMIT`, decision 196). The read asks one past the limit; over it, it counts and answers 422 `TIMELINE_TOO_LARGE` with `details: { count, limit, what: 'items' }`, and the page says "Narrow the filter: 7,214 items match". Never a cut-off list. The same refusal, `what: 'relations'`, guards more than 25,000 blocks relations (`TIMELINE_EDGE_LIMIT`).
3. **Blocks relations** with either end in the scope (`WorkItemRelationRepository.blocksTouching`). An end outside the scope that the caller sees (a live item in a project it sees, archived included) is a **context row**: greyed, read-only, in a group of its own at the end, at most 500 in id order (`TIMELINE_CONTEXT_LIMIT`; the rest counted in `omittedContextRows`, their relations left out). An end the caller cannot see (a deleted item; from 8.4 a project a guest has not been granted) is dropped and counted in `hiddenDependencies`, never named; the page says "n dependencies to items you cannot see are not shown".
4. **Calendars** from `resolveWorkingCalendars` for the teams in view (every holiday they hold, at most 500 each); **deadlines**: each project's due date and its milestones'. `asOf` is today in the workspace calendar's zone (decision 191); an item's `startedAt` and `completedAt` are read as dates in its own calendar's zone (decision 187).
5. **The engine runs on the server** (decision 197): `computeTimelineSchedule` (`src/lib/work-items/timeline.ts`, client-safe) builds the engine's input from the read (cancelled items and their relations left out, decision 187; a parent counts only when it is a scope row, decision 186; a context row never parents) and calls `computeSchedule`. The response is the read and the result. Nothing is stored and nothing is audited; no description, comment or field value is read.

Every read carries `tenantId`, `deletedAt: null` and the visibility fragment (`tests/unit/repositories/work-item-repository-predicates.test.ts` holds the three new methods). `tests/integration/work-item-timeline.test.ts` drives it against Postgres: the context row, the hidden relation, the cancelled item, the critical path and the missed project due date; the list's filters; a guest; the 5,001-item refusal; the route as every role and a role without the key.

### The browser

- **One read, one cache.** `useWorkItemTimeline` (`components/work-items/data/`) reads the route through `use-tenant-swr.ts`. It registers with `work-item-cache.ts`: a write in any view places the changed row in the cached timeline and re-runs the engine there (`placeRowInTimeline`, the same module the server runs); a row the timeline does not hold, and every list re-read, re-reads the timeline. It does not page through `useWorkItemList`: it needs the whole scope at once.
- **One view model.** `components/work-items/timeline/timeline-model.ts` (pure, unit-tested) lays the answer out; it decides nothing about the schedule. A leaf's bar is its stored dates (decision 184: start to due; one date, one day on it; reversed dates, one day at the due date; a done item, its actual dates). A summary's bar is the engine's span of its sub-items (decision 186). Several projects are grouped under one summary row each; each project's due date and its dated milestones are diamonds at the top of its group (or of the chart on a one-project timeline, decision 188). Neither date puts an item in the "No dates" list beside the chart (decision 185). A cancelled item is in the table, greyed, with no bar.
- **The chart.** `TimelineChart` loads `svar-adapter.tsx` with `next/dynamic` and `ssr: false`, behind an error boundary that points to the table; the region is labelled and described for assistive technology. The adapter is the only file that imports SVAR (see below). Bars carry Islestone's own `data-critical`, `data-late`, `data-conflict` and `data-context` through `taskTemplate`; critical links are one CSS rule per relation id (`[data-link-id=":<id>"]`, a cuid checked against `^[a-z0-9]+$` before it is put in a selector; the CSP allows inline styles). Today and the non-working days are cell classes from `highlightTime`: today's cell at every zoom (its day, week, month or quarter), and at day zoom the days no calendar in view works ("non-working on every calendar in view" when several are). A cycle's page marks the cycle's days. Choosing a bar opens the item's sheet.
- **The schedule table** (decision 203): `TimelineScheduleTable` on the shared `DataTable`, the same rows and the engine's numbers: key, title, start, due, earliest start, latest finish, float ("Late by N days" when a deadline is missed), critical, conflicts. "Chart / Table" is remembered per viewer; the table is the timeline's accessible view, not a fallback. From 3.1c a row offers "Change dates" and "Dependencies" (below).
- **The summary line**: "Finishes on 14 Mar · 3 items on the critical path · none late", and on a one-project timeline with a due date "Due 10 Mar · late by 4 days" (working days on the workspace calendar from the due date to the finish). With no dated open item: "Add dates to see the critical path", never an empty path presented as a result.
- **Copy** is `workItems.timeline.*`; the words are decision 201's (Timeline, Critical path, Float, "Late by N days", Earliest start, Latest finish, No dates).

### SVAR React Gantt (decisions 182 and 199)

- **The package**: `@svar-ui/react-gantt` 2.8.3, pinned exactly; its tree is 27 `@svar-ui` package versions (30 lockfile entries) and a nested `date-fns` 3.6.0, every one MIT. The licence gate passes with no exemption. `tests/guards/svar-core-only.test.ts` holds the lockfile to the pinned list (MIT, no `wx-react-gantt`, no `-pro` or `-trial` name, `package.json` exact), `src/` to importing SVAR only in `svar-adapter.tsx` and only `@svar-ui/react-gantt`, `@svar-ui/react-gantt/style.css` and `@svar-ui/react-grid/style.css`, the adapter's theme to `fonts={false}`, the widget element to a closed list of props (none of PRO's), and the word "Gantt" to the widget's import (ADR 0006). The adapter imports the widget as `TimelineWidget`.
- **No vendor request.** `fonts={false}` stops the theme's `cdn.svar.dev` icon font. `all.css` and `@svar-ui/react-core`'s stylesheet carry `@font-face` rules naming that CDN, so neither is loaded: the two plain stylesheets are, and `timeline.css` defines the base `--wx-*` variables the core stylesheet would have, mapped to Islestone's tokens for both themes, and draws the tree's expand and collapse with CSS. `timeline.css` is unlayered on purpose: SVAR's stylesheets are unlayered and would beat a layered override whatever its specificity; every rule is scoped under `.isl-timeline`, so none competes with a utility on Islestone's own elements.
- **The widget never writes.** No toolbar, editor or context menu is rendered, and every action that would change a task or a link is refused in `init`: `REFUSED_ACTIONS` (`add-task`, `delete-task`, `copy-task`, `move-task`, `indent-task`, `split-task`, `update-link`, `show-editor`, `schedule-tasks`, `undo`, `redo`) always, and `READ_THEN_REFUSED_ACTIONS` read by Islestone (3.1c, below): `update-task`, `add-link` and `delete-link` always refused after they are read, `drag-task` refused for a bar that may not move. A caller who does not edit work items gets `readonly`.
- **The CSP needed no change.** Production `script-src` is unchanged (no `unsafe-inline`, no host); the widget's inline styles and the critical-link `<style>` element fall under `style-src 'self' 'unsafe-inline'`, which has no nonce; nothing requests `cdn.svar.dev` (the E2E spec records every request). The widget's chunk still contains the theme's font link as a string, in the `fonts` branch that `fonts={false}` never runs.
- **The bundle.** The widget's code ships only on a timeline: the E2E spec checks that the list's scripts hold none of it and that opening the timeline fetches it.
- **Jest** maps SVAR's React packages to their ES builds (their `require` entry, `dist/index.cjs.js`, is not in the published files) and compiles every `@svar-ui` package (`ESM_PACKAGES`).
- **The notice (decision 199).** SVAR's MIT notice travels only in the licence files installed with the packages. Checked in 3.1b: the worker image's pruned production tree holds every `@svar-ui` package with its `license.txt`. The app image's standalone trace (`.next/standalone`) holds no `@svar-ui` package and so no `license.txt`: SVAR is a client package the server never reads, so Next's trace leaves it out; the browser bundle carries its code and no notice. Recorded as decision 199's known risk; nothing about licence policy changed.

## Changing dates and dependencies (3.1c)

Decisions 194, 195, 197, 201 and 203; ADR 0010 §6. A person changes dates from the timeline; the timeline asks first, and every change is the API's (field sets, permission, audit, reminders). Agents never use this path: an agent's schedule change is a proposal (ADR 0003, roadmap 7.5) that reuses the engine, never the confirmation.

### Who may change what

`editableRows(resp, { canEdit, hiddenDates })` (`timeline-model.ts`, pure) answers two sets of row ids once per answer. `canEdit` is the client permission `work_items.edit` the board reads too (`usePermissions().work_items.edit` in `WorkItemsView`); `hiddenDates` resolves each type's built-in start and due rules with `resolveFieldSet` over the view configuration's `fieldSetEntries` (built-in rules are a type's across the workspace, 2.4b-b), never restated.

- **Dates** (step 6 of the map): an open or started item of the scope, not a context row, a summary, a done or cancelled item or one in an archived project, whose type shows every date it carries and at least one. Its bar can be dragged (`data-draggable`); every other bar's `drag-task` is refused, so it does not move.
- **Dependencies**: any item of the scope in an unarchived project (`data-linkable`; the link handles show only there). The relation route decides the rest.

### A dropped bar

1. **Intercept.** The adapter's `update-task` intercept reads the drop (`dropFromWidget`: `diff` in day cells, `lengthUnit="day"`; both dates named is a move, one is a resize; anything else, a progress drag or an editor's save, is refused silently), refuses it, and hands it to `onDateDrop`. The widget had moved the bar's pixels during the drag, so the adapter hands it a fresh tasks array at once: every bar is drawn again from the cached rows (the widget re-initialises on a new array). The rendered test drives the intercepts through a recording stand-in; the E2E spec drags a real bar.
2. **The proposed dates** (`proposeDates` in `src/lib/work-items/reschedule.ts`, pure): a move keeps the working-day duration on the item's own calendar (the new start snaps forward to a working day, the due date is `addWorkingDays(start, duration − 1)`); a one-date item moves that date (snapped forward); a resize changes the one date it drags, the start snapped forward and the due date back to a working day, never past the other date. A start-only bar resized at its end gains a due date, and the reverse.
3. **"Change dates for ISL-123"** (`ChangeDatesDialog`): the dates now, the new start and due in the product's `DatePicker`s (a date the item's type hides is shown, not offered), and the preview from `planDateChange`, the engine re-run in the browser on the cached rows with the new dates (decision 197): items whose earliest start moves, by working days on their own calendar; items that become or stop being critical; the conflicts the change brings. Each named item opens its sheet (the dialog closes first). A start after the due date cannot be confirmed; unchanged dates neither.
4. **Confirm, unticked**: `PATCH /work-items/:id { startDate, dueDate }` with `If-Match` (`useTimelineWrites().changeDates`), the same write the detail makes. The decision the map left open (a single-item drag through the existing versioned write or through the new route) is the existing write: it already carries every rule, and the bulk route stays the narrow tool decision 194 describes. Optimistic over the cached timeline; the answer is placed in every mounted view; a refusal re-reads the timeline and shows the server's sentence, a 409 "Someone else changed this work item".

### "Also move the N items it pushes later" (decision 194)

**The set** (`planDateChange(...).push`): the items downstream of the changed one through the timeline's blocks relations (context rows included) that are open and not started (Backlog or Unstarted), have a date, sit in an unarchived project, whose type shows the dates they carry, and whose planned start the change puts before a blocker's finish: `STARTS_BEFORE_BLOCKER_FINISHES` that the change brings, or worsens (its earliest start moves later). Each moves later only, to its earliest start, keeping its working-day duration on its own calendar; an item with only a due date moves it to its earliest finish. A date is never moved earlier (a computed date before the stored one keeps the stored one, so a due date on a weekend can lengthen the item by its weekend). The engine is re-run with the pushes until nothing more moves, so a chain moves together. Items the change would let start earlier are never pulled. Started, undated (whose earliest start the change moves later), hidden-date, reversed and archived items are named, "not moved: started", never moved. The checkbox is unticked by default and absent when nothing would move.

**The bound**: at most `RESCHEDULE_MAX` (100, `BULK_MAX`) items in one confirmation, the changed one included. Above it the checkbox is disabled and the dialog says "143 items would move; move fewer at a time": the set is never cut.

**Undo**: ticked, "Change dates" closes the dialog, places every new date in the cached timeline and holds the write five seconds behind `useToastWithUndo` ("Moving ISL-12 and 6 items."), sent from inside the toast's action (`use-timeline-writes.ts`, in `SITE_CONTRACTS`). Undo sends nothing and puts the old dates back. A refusal when it is sent (a 409 because someone changed an item meanwhile) refuses the whole change: the timeline is read again and the reason shown. After the commit the lists and the details of the items are read again; there is no undo but moving the dates again, and each item's entries keep its old dates.

**The route**: `POST /api/t/:slug/work-items/bulk/dates` (`requirePermission('work_items.edit')`, a `route-permissions.ts` rule, a `tenant-crud-authz-coverage` pin, permission-matrix rows), body `{ dragged: { id, version, startDate, dueDate }, pushed: [...] }` (`RescheduleWorkItemsSchema`: each item once, at most 99 pushed), usecase `rescheduleWorkItems` (`work-item.ts`). All or nothing, in one transaction, in this order:

1. `lockWorkItemGraph` first, then every item locked in id order (`WorkItemRepository.lockForWrite`, decision 173), then the rows read; an item missing or not visible is 404.
2. Each item's version equals the one sent, else 409 `VERSION_CONFLICT` with `details.workItemIds` and their current `versions`, nothing written.
3. Each pushed item is reached from the dragged one through BLOCKS relations between live items (`WorkItemRelationRepository.liveBlocksReach`, the cycle check's recursive `UNION` walking only relations whose far end is not deleted: a deleted item relays nothing), else 400 `NOT_DOWNSTREAM`. Each pushed item's dates only move later: a date it has moves to the same day or later, at least one strictly, and none is added or cleared, else 400 `PUSH_NOT_LATER`.
4. Every item open (409 `ITEM_CLOSED`), in a writable project (409 `PROJECT_ARCHIVED`), its field set showing the dates written (`checkWrite` per item: 400 `FIELD_HIDDEN`; the dragged item's required date cleared, 400 `FIELD_SET_UNMET`), and its start not after its due date (400 `START_AFTER_DUE`).
5. `WorkItemRepository.setDatesOfLocked`: one versioned write per item over the locked rows (each version increases once; `sortKey` untouched); a count short of the items is a conflict.
6. One `WORK_ITEM_UPDATED` per item (`changedFields` the dates that changed; `metadata` both dates `{ from, to }`, the change's `rescheduleId` and, on a pushed item, `pushedBy`: the dragged item's id), so every item's Activity says its dates moved; one `WORK_ITEMS_RESCHEDULED` on the dragged item with `rescheduleId`, `pushedIds` and `pushedCount` (not an Activity entry: Activity reads `WORK_ITEM_*`).
7. After the commit: one watcher entry per item (`emitWatcherActivity`, kind `updated`, discriminator the `rescheduleId`) and each item's due bell for today's window (`emitDueBell`), as the bulk due-date change does; no notification for "pushed".

The answer is `{ rescheduleId, items: [{ id, version, startDate, dueDate }] }`. `tests/integration/work-item-reschedule.test.ts` holds every refusal, the audit rows, the untouched sort keys and two overlapping changes at once through PgBouncer (no deadlock: the graph lock serialises them; one applies, the other is refused for the versions it read).

### Dependencies (decision 195)

- **Drawn on the chart**: SVAR's MIT core draws links from a bar's end handle to another's start handle; no PRO feature is used. A drawn end-to-start link between two linkable items opens "Add dependency: ISL-1 blocks ISL-2?" (`AddDependencyDialog`); confirming calls the existing `POST /work-items/:id/relations { type: 'BLOCKS', toId }`, whose graph lock refuses a cycle (409 `RELATION_WOULD_CYCLE`), shown in the dialog. The link appears only after the server accepts (the timeline is read again). Another link type (`s2s`, `e2e`, `s2e`), or a link to an item that may not be joined, is refused with a sentence.
- **Removed on the chart**: a selected link's delete button removes it from the chart at once and sends `DELETE /work-items/:id/relations/:relationId` (from the blocker) when the undo toast closes; Undo puts it back.
- **By keyboard**: the schedule table's "Dependencies" on a row (`DependenciesDialog`) lists its "Blocked by" and "Blocks" relations on the timeline, each removable through the same undo toast, and adds one by choosing the relation ("ISL-2 is blocked by" or "ISL-2 blocks") and the other item: the dialog names the relation it will create ("ISL-3 blocks ISL-2?") before "Add dependency" sends it.

### The schedule table and "No dates"

A row a person may change offers "Change dates" (the same dialog, opened with its own dates for the date pickers) and "Dependencies" (decision 203): every change the chart allows by pointer is possible by keyboard. Each undated item in the "No dates" list offers "Set dates", which opens the same dialog. The widget's drag-in of an unscheduled item (`locateTask`) is not used.

## The calendar view (3.3a)

The `CALENDAR` layout ([`docs/work-items.md`](work-items.md), "The calendar view (3.3a)"; decisions 241 and 242) reads the scheduling module twice and writes through 3.1c alone: its shading is the scope's working calendar (one team's, else the workspace's; holidays and non-working weekdays), its "today" is today in that calendar's zone (decision 191), and moving an item opens `ChangeDatesDialog` over the item's project's timeline, with the due date moved and the start by the same number of calendar days. Who may move an item is `editableRows`; the preview and the push set are `planDateChange`; the writes are `useTimelineWrites`. There is no calendar-only rule for dates.

## The roadmap's bars (3.2c)

The roadmap (`docs/goals.md`, "The roadmap") draws plans, not the schedule: a project's bar is `plannedSpanOf` over its items' stored dates through `spanFromBounds` on its team's calendar, an initiative's the `spanOf` of its projects', and the engine's pass is never run there (decision 215, read as the engine's span over stored dates). Goal and initiative due dates are diamonds, never deadlines (decision 210; ADR 0010 §3 unchanged). The chart is drawn through the same adapter (decision 216), read-only, with its own row model (`roadmap-model.ts`); a bar opens the timeline above (decision 217).
