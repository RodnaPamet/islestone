# Search

Sub-phases 2.7b and 2.7f, built by [`docs/porting/maps/2.7.md`](porting/maps/2.7.md) (parts 2 and 3) under owner decisions 124 to 147 (`docs/HANDOFF.md`) and [ADR 0008](adr/0008-search-over-encrypted-fields.md). This page records what they built: 2.7b's indexes over work-item titles and project names, the workspace search route, the command palette's entity search and the list's `q` filter; 2.7f's Bulgarian and English text-search configuration `islestone_bg_en`, Islestone's own Postgres image that carries its dictionary, the stored vectors of descriptions and comments (`SearchVector`), their one write seam and rebuild job, and the search over them.

## What is searched

| Searched | How | Index |
|---|---|---|
| A work item's title | Substring (`ILIKE '%q%'`, case-insensitive) or every word of the query in any order (`simple` full text) | `WorkItem_search_title_trgm`, `WorkItem_search_title_fts` |
| A work item's key (`ISL-12`) | Exact, in any case: the current prefix, a retired one, or a key left by a move (`WorkItemKeyAlias`), as `GET /work-items/by-key/:key` resolves it | The unique `ProjectKeyPrefix (tenantId, prefix)`, `WorkItem (tenantId, projectId, number)` and `WorkItemKeyAlias (tenantId, projectId, number)` |
| A project's name | As a title | `Project_search_name_trgm`, `Project_search_name_fts` |
| A project's key prefix (`ISL`) | Exact, in any case | The unique `Project (tenantId, keyPrefix)` |
| A work item's description (2.7f) | Its stemmed words (`websearch_to_tsquery`: words, `"a phrase"`, `or`, `-word`) | `SearchVector_search_lexemes` over the stored vector |
| A live comment's body (2.7f) | As a description | The same |

Since 2.7f every full-text match (titles, project names, descriptions, comments and the query) goes through `islestone_bg_en`, so `задача` finds `задачата` and `run test` finds `running tests`.

Never searched: intake requests, template text and project-template content (decision 124), and any personal data.

Titles and project names are plaintext already (ADR 0002 §11), so indexing them adds no exposure. **Descriptions and comments are encrypted, and their search vectors are not**: by owner decision 124 the stemmed words of every description and comment, with their positions, are readable in the database, in its dumps and in the off-host backups (ADR 0008 D1). The exact text, punctuation and stop words stay encrypted.

## The migration

`20261203120000_search_titles`:

- `CREATE EXTENSION IF NOT EXISTS pg_trgm` and `btree_gin`. Both are contrib extensions, trusted since PostgreSQL 13 and shipped in the `pgvector/pgvector:0.8.7-pg17-trixie` image that production, CI's Integration and DAST services and the local `docker-compose.yml` run. Migrations run as the database's superuser (the one-shot `migrate` service in production, the `islestone` login in CI and locally), as `btree_gist` did in 2.5a; the runtime role (`islestone_app`, a member of `app_user`) never creates an extension. They are created in `public`, where the app's `search_path` finds `similarity()` and the operator classes.
- Four GIN indexes, each leading with `tenantId` (`btree_gin` lets a GIN index lead with a scalar) and covering live rows only (`WHERE "deletedAt" IS NULL`): a trigram index (`gin_trgm_ops`) and a full-text expression index (`to_tsvector('simple', …)`) on `WorkItem.title` and on `Project.name`.
- The `simple` configuration does not stem. 2.7f replaced the two full-text indexes with `islestone_bg_en` ones (decision 126, ADR 0008 D2), so titles, stored vectors and queries stem alike.

Prisma cannot declare these indexes; they live in the migration, and `npm run db:check-schema-drift` passes with them (Prisma's diff ignores partial and expression indexes, as it ignores 2.1's partial uniques), so the residue file is unchanged. `tests/integration/search.test.ts` checks the catalogue and that the planner uses them.

## The configuration and the image (2.7f)

`islestone_bg_en` (migration `20261207120000_search_configuration`) is a copy of PostgreSQL's `english` configuration whose other-letter words (Cyrillic and accented Latin: the parser's `word`, `hword`, `hword_part`) go through `bulgarian_hunspell`, then `simple`; Latin words keep `english_stem` and its stop list; numbers and the other token types keep their defaults. A word the Bulgarian dictionary does not know is indexed as typed.

- **The dictionary** is bgOffice's Bulgarian spelling dictionary, OOo-spell-bg 4.3, used under MPL-2.0 (owner decision 145, [ADR 0007](adr/0007-third-party-licence-exceptions.md) E10), re-encoded to UTF-8 and changed in no other way. It is in the repository at `deploy/postgres/tsearch_data/` with its licence, copyright statement and statement of change; `deploy/postgres/dictionary.json` records its source and hashes, and `tests/guards/postgres-dictionary-pinned.test.ts` holds the files to that record and the record to ADR 0007 E10.
- **The image** is `ghcr.io/rodnapamet/islestone-postgres` (owner decision 146), built from `deploy/postgres/Dockerfile`: `pgvector/pgvector:0.8.7-pg17-trixie` by its index digest, plus the two files in `$SHAREDIR/tsearch_data`, checked by `sha256sum -c` while it builds. Nothing else changes (the same PostgreSQL 17, pgvector, entrypoint and data directory). Production pins it in `deploy/docker-compose.prod.yml`; the local `docker-compose.yml` builds it; CI's Integration, E2E and DAST jobs build and run it from the pull request (`scripts/ci-postgres.sh`); the release workflow publishes it under the Dockerfile's version tag when that tag is new (`tests/guards/postgres-image-pinning.test.ts`). `docs/deployment.md`, "The Postgres image", is the rollout.
- **Fail closed** (decision 126). The configuration migration raises when the dictionary cannot be loaded (on the stock image: "the Bulgarian dictionary could not be loaded … This server is not running Islestone's Postgres image"), then asserts by query that 17 fixtures stem as pinned (`SEARCH_CONFIGURATION_FIXTURES` in `src/lib/search/configuration.ts`, the same list). In production the app (`src/instrumentation-node.ts`) and the worker (`scripts/worker.ts`) run the fixtures at startup and refuse to start on a miss, and `/api/readyz` runs them on every probe, answering 503 with `search: { error: 'search_configuration' }`. No code names another configuration (`tests/guards/search-vector-write-seam.test.ts` holds every `to_tsvector`, `plainto_tsquery` and `websearch_to_tsquery` in `src/` and in the migrations since to the literal `'islestone_bg_en'`), and nothing falls back to `simple` or `english`.
- **Cost** (measured): the loaded dictionary is about 9.3 MB in each database backend that uses it, about 100 ms on first use. PgBouncer's pool of 20 bounds it near 190 MB of the database's 1536 MB `mem_limit`.

## Stored vectors (2.7f)

`SearchVector` (migration `20261207120100_search_vectors`) holds one row per indexed source: an item's description (`commentId` NULL) and each live comment, unique each way by two partial indexes. `lexemes` is the `tsvector`, built with `configName` (CHECKed to `islestone_bg_en`) at `revision` (`SEARCH_VECTOR_REVISION`). The GIN index `SearchVector_search_lexemes` leads with `tenantId` (`btree_gin`) and is partial on the configuration, which every match names. Row-level security, its grants and a two-tenant test as for every workspace table. The item, the comment and the workspace cascade, so the 30-day purge, a comment's hard delete and a workspace's delete take the vectors with the text. The encryption-manifest guard lists the column as a deliberate plaintext derivative of `WorkItem.description` and `Comment.body` (`PLAINTEXT_DERIVATIVES`, citing ADR 0008).

- **One seam.** `SearchVectorRepository` (`src/app-layer/repositories/SearchVectorRepository.ts`) is the only module that issues SQL against the table. `replaceForSource` writes `to_tsvector('islestone_bg_en', $1)` with the sanitised plaintext as a bind parameter, in the caller's transaction; an empty text removes the row. It is called by `createWorkItemInTx` (so a create, an intake accept, a repeat copy and a project template's starter items), `insertTemplateItemInTx` (template sub-items), `updateWorkItem` (a description change; a cleared one removes the row), `addComment` and `editComment`; `deleteComment` calls `removeForSource`. `tests/guards/search-vector-write-seam.test.ts` finds every function that writes a description or a comment and fails when one does not call the seam. A write that rolls back rolls its vector back with it.
- **What is vectorised.** `searchableText` (`src/lib/search/configuration.ts`): the stored, sanitised text, mention tokens (`<@userId>`) taken out, at most 100,000 characters. Soft-deleting an item keeps its rows (a restore needs nothing); every read filters `deletedAt` and visibility instead. A moved item keeps its rows.
- **The rebuild.** `search-index-rebuild` (02:40 in `NOTIFICATIONS_TZ`) rewrites, in every live workspace and as its system user, each source whose vector is missing or older than the revision. It walks each kind of source in id order, one page of 500 at a time, each page in its own transaction: a page reads the next 500 sources after its cursor and probes each one's vector by its own key (`SearchVector_one_per_description`, `SearchVector_one_per_comment`), so a page reads only its own rows and a run is linear in the workspace (issue #79; before it every page hash-joined the workspace's whole vector table, so a forced rebuild was quadratic, finding F2). It writes at most 100,000 sources of each kind a run (200 pages' worth); it removes any vector of a deleted comment and writes a counts-only `SEARCH_INDEX_REBUILT` entry. It is the backfill on first deploy and the rebuild after a change to the configuration, its dictionary or `searchableText` (bump `SEARCH_VECTOR_REVISION`; never a data migration). An admin can force one for their workspace: `POST /api/t/<slug>/admin/search-index/rebuild` (`admin.manage`, audited `SEARCH_INDEX_REBUILD_REQUESTED`, 5 an hour), run by the worker as that admin, re-resolved when it runs (refused if they left or lost the key).
- **Private.** The plaintext reaches PostgreSQL only as a bind parameter of the write and of the query, and is never logged by the application; the database keeps its defaults that keep parameters out of its own logs (`docs/deployment.md`). Key rotations need nothing: the vectors are not encrypted. Workspace exports (when they exist) leave the table out: it is rebuilt from the encrypted text.

## The search functions (decision 245)

Under row-level security a full-text (`@@`), `ILIKE` or trigram condition cannot be an index condition: those operators are not `LEAKPROOF`, so PostgreSQL applies the policy's qual first and only then the search condition, and every search read the workspace's whole entry of its tenant-leading GIN index (H2a's finding F1, `docs/performance.md`; issue #78). Owner decision 245 fixed it without relaxing row-level security and without marking anything `LEAKPROOF`: each search read is a `SECURITY DEFINER` function (migration `20261214120000_search_definer_functions`).

| Function | Read by | Index searched |
|---|---|---|
| `search_work_item_titles(p_query, p_contains, p_prefix, p_key_hit_id, p_all_projects, p_project_ids, p_limit)` → `(id, ordinal)` | `WorkItemRepository.searchTitleIds` (the palette) | `WorkItem_search_title_trgm`, `WorkItem_search_title_fts` |
| `search_work_item_title_words(p_query, p_all_projects, p_project_ids, p_limit)` → `(id)` | `WorkItemRepository.titleFullTextIds` (the list's `q`) | `WorkItem_search_title_fts` |
| `search_work_item_title_substring(p_contains, p_all_projects, p_project_ids, p_limit)` → `(id)` | `WorkItemRepository.titleSubstringIds` (the list's `q`) | `WorkItem_search_title_trgm` |
| `search_project_names(p_query, p_contains, p_prefix, p_all_projects, p_project_ids, p_limit)` → `(id, ordinal)` | `ProjectRepository.searchNameIds` (the palette) | `Project_search_name_trgm`, `Project_search_name_fts` |
| `search_page_titles(p_query, p_contains, p_prefix, p_all_projects, p_project_ids, p_limit)` → `(id, ordinal)` (4.1a) | `PageRepository.searchTitleIds` (the move dialog's parent search; 4.1f's palette group) | `Page_search_title_trgm`, `Page_search_title_fts` |
| `search_item_contents(p_query, p_all_projects, p_project_ids, p_limit)` → `("workItemId", "commentId", rank, bounded)` | `SearchVectorRepository.matchItems` (the palette and the list's `q`) | `SearchVector_search_lexemes`, and `SearchVector_search_recent` for the walk (decision 250, below) |

Every one of them:

- is owned by `app_search_definer`, a role the migration creates: it cannot log in, is not a superuser, inherits nothing, is a member of nothing and has no members, owns no table, and holds `SELECT` on exactly the columns the functions read (`WorkItem`: id, tenant, project, title, `deletedAt`; `Project`: id, tenant, name, key prefix, `deletedAt`, `archivedAt`; `Comment`: id, tenant, `deletedAt`; `SearchVector`: tenant, item, comment, lexemes, configuration), never a description, a comment's body or anything encrypted. It is `BYPASSRLS`, which is what lets the planner use the index inside the function: no policy qual is applied there, so the function applies the workspace itself;
- reads the workspace from `current_setting('app.tenant_id', true)`, the setting every policy reads and `runInTenantContext` binds, and never takes it as an argument; with the setting unset or empty it returns no rows, as the policies return none. A caller that names another workspace's context still gets its own transaction's workspace;
- filters the workspace, the item's `deletedAt`, a comment's `deletedAt`, the project's `deletedAt` and `archivedAt`, the configuration and project visibility in its own `WHERE` (visibility is the input `projectVisibilitySql` took before: every live project, or the granted ids; an empty grant matches nothing);
- is bounded by its `p_limit`, clamped in the body to a hard cap (100 for the palette's two, 1,000 for the rest);
- returns ids and the candidate order or the rank only, never text (`search_item_contents` adds one boolean about the caller's own result, `bounded`, decision 250): the usecase reads the rows it shows by id, under row-level security;
- sets `search_path = pg_catalog, public, pg_temp` and names every table with its schema, so nothing a caller creates (a temporary table) can shadow what it reads (`search_item_contents` also sets `plan_cache_mode = force_custom_plan` and `jit = off`, below, and nothing else);
- is executable by `app_user` alone (`EXECUTE` revoked from `PUBLIC`).

The liveness checks of a broad content match (its item, its comment) read two narrow partial indexes index-only, `WorkItem_search_live_ids` (`tenantId, id` with the project, live items) and `Comment_search_live_ids` (`tenantId, id`, live comments), from the same migration. Row-level security stays enabled and forced on every table.

Guards: `tests/guards/search-definer-functions.test.ts` pins each function's body by hash and holds it to `definerProblems` (`tests/helpers/search-definer.ts`: the tenant from the setting and never an argument, the empty-setting return, every table qualified and tied to the workspace, `deletedAt`, visibility, the configuration, the cap, the returned columns, the fixed `search_path`, never `LEAKPROOF`), its owner, its grants and the role's attributes, and each function's one calling repository; `tests/guards/search-vector-write-seam.test.ts` keeps `search_item_contents` in `SearchVectorRepository`, the table's one module; `tests/integration/search-definer.test.ts` holds the same against the catalogue (`pg_proc`, `pg_roles`, the column grants, forced row-level security, no `LEAKPROOF` operator) and drives every function through `runInTenantContext` in two workspaces (the other workspace, an invisible project, a deleted item or comment, an archived project and an unset setting all return nothing). `docs/rls-tenant-isolation.md` lists the functions as a named exception.

## The bound on content matches (decision 250)

A common word can match a large share of a workspace's descriptions and comments, and ranking every match before the limit made the search grow with its matches (H2b's finding F3, `docs/performance.md`: 33,356 matching vectors at 100k, the palette and the list's `q` at 0.85 to 1.2 s p95; issue #89). Owner decision 250: content search ranks only a bounded candidate set. Migration `20261217120000_search_recent_candidates` replaces `search_item_contents`:

- **The candidates** are the caller's 2,000 most recently written live, visible matching vectors (`CONTENT_CANDIDATE_BOUND` in `SearchVectorRepository`), read one past the bound: the workspace, the item's and a comment's `deletedAt`, the project's liveness, project visibility and the configuration apply before the bound, as before. They are ranked with `ts_rank`, each item once with its best source, best first; then the cap (`p_limit`, at most 1,000) applies as before.
- **Two ways to the same candidates**, chosen by measurement rather than by the planner's estimate (which multiplies the words' frequencies, so a phrase whose words go together is under-counted several times over: 15,970 estimated against 33,130 for the measured query):
  - **the walk**, in a large workspace (at least 100,000 vectors, counted index-only and capped) for a query that matches at least 100 of the workspace's 2,000 newest vectors (5 %): the newest 50,000 vectors are walked on `SearchVector_search_recent`, newest first, filtered by the query and every predicate, and the walk stops at 2,001 matches. When it reaches them nothing older can be among the newest 2,001; it reads at most half of the workspace;
  - **every match**, otherwise (a smaller workspace, a sparse query, or a walk that stopped short): the matches are read on `SearchVector_search_lexemes` with `@@` in the index condition and the workspace's live, visible items index-only (`WorkItem_search_live_ids`), each in a materialised step (so the matches are never reached by probing every item, and the items are hashed once rather than probed per match), and the newest 2,001 live, visible matches kept. A small workspace never reads the 2,000-vector sample.
- **The flag.** `bounded` is true on every row when the 2,001st candidate existed. Because the predicates apply before the bound, it counts only what the caller may see: another workspace's vectors or an invisible project's never cut a read or set it. `matchItems` returns `{ matches, bounded }`; `GET /search` answers it as `meta.contentMatchesBounded`, and `GET /work-items` as `contentMatchesBounded` beside `items` (false without a `q`). The palette then says it is showing the best of the most recent matches under its hits (`commandPalette.recentMatches`), and the list layout of the Work items, project, cycle and milestone pages and each My Work section say they are showing recent matches (`workItems.list.recentMatches`, `RecentMatchesNote`). Titles, keys and project names are never bounded: their functions are unchanged.
- **"Most recently updated" is the vector's own `updatedAt`**: the time its description or comment was last written. `replaceForSource` stamps it in the transaction that writes the text; the rebuild (`search-index-rebuild`), which re-vectorises text nobody changed after a revision bump or a forced run, keeps an existing row's time (`{ keepTime: true }`), so a rebuild never makes everything look new. It lives on the matched row, so one index orders the walk; the item's `updatedAt` would move with every state, assignee or field change (unrelated to what matched) and would need a join to the item before the bound. A row the rebuild inserts because it was missing takes the time of the rebuild.
- **The index.** `SearchVector_search_recent` on `("tenantId", "updatedAt", "id") WHERE "configName" = 'islestone_bg_en'`, tenant-leading and partial on the configuration like `SearchVector_search_lexemes` (SQL only; the drift check ignores partial indexes). The owner role gains `SELECT` on `SearchVector.id` and `updatedAt` for it, and nothing else. The function also sets `plan_cache_mode = force_custom_plan`, so each call is planned with its query folded to a constant (a pooled connection takes a cached generic plan after five calls, and a generic plan parses the query again for every row the walk filters: 300 ms instead of 70 at 100k), and `jit = off`: the walk's estimated cost is far above `jit_above_cost`, and compiling its plan took longer (about 240 ms) than the read.
- **The guards.** `definerProblems` holds the walk as pinned (`candidates` on the spec: the five literal limits in order, newest first, both the walk and the full match carrying every predicate and join, every read of the vectors naming the workspace and the configuration, the size and density gates, the fallback, the flag, at most 2,000 ranked) and the two settings (`planSettings`); `tests/guards/search-definer-functions.test.ts` pins the new body's hash; `tests/integration/search-content-bound.test.ts` drives a workspace past the bound (the newest matches returned, older better-ranked ones not, the flag set, the palette and the list carrying it, a title still found), one under it (every match ranked, unbounded), the isolation of the bound between two workspaces and from invisible projects, and a large workspace of 100,000 vectors whose dense query is walked on the recency index and whose sparse query is read on the vector index.

## The route

`GET /api/t/<slug>/search?q=<query>[&limit=<n>]` (`src/app/api/t/[tenantSlug]/search/route.ts`) answers a `SearchResponse` (`src/lib/search/types.ts`): hits ranked highest first, each with its type, title, subtitle (the item's key, the project's prefix), href and score, and `meta` with the query used, per-type counts, the cap and whether any type was cut.

- **Key.** A literal `requirePermission('projects.view', …)` with its rule in `route-permissions.ts`; the usecase asserts the same predicate (`assertCanReadWorkConfig`). Every built-in role holds it. Work items are a second domain: a caller without `work_items.view` (a custom role) gets project hits only and a work-item count of zero, never a refusal (inflect's per-domain skipping, `mayReadWorkItems`).
- **Visibility.** `visibleProjects(ctx)` goes to every read: to the search functions as two bind parameters (`projectVisibilityArgs`: every live project, or the granted ids), which each function applies itself, and to the reads of the matched rows by id as `projectVisibilityWhere`. A deleted item, a deleted or archived project, and a project outside a GUEST's grant (every project until 8.4) never match. The reads run in `runInTenantReadContext`, as `app_user` with the workspace set: the matched rows are read under row-level security, and each search function reads the workspace from the same setting (see "The search functions").
- **Bounded.** Description and comment matches are ranked among the 2,000 most recently written (decision 250, above; `meta.contentMatchesBounded`). `q` is trimmed and cut to 200 characters (a parameter longer than 1,000 is a 400); `limit` is the hits per type, 5 by default, at most 25 (`MAX_PER_TYPE_LIMIT`; more is a 400). Each read fetches at most three times the cap, and never more than 100 rows (`SEARCH_ROW_CAP`).
- **Private.** The query is a bind parameter, never part of the SQL text, and is never logged. `%`, `_` and `\` in a query match themselves (`escapeLike`, `src/lib/search/query.ts`).
- The read tier's rate limit applies at the edge, as for every workspace GET.

Since 2.7f the route also returns work items found by their description or a comment (`SearchVectorRepository.matchItems`: the live, visible items whose description or a live comment matches, each once with its best source, ranked by `ts_rank`). An item already found by its title keeps its title hit. Every hit says where it matched (`matchedIn`: `title`, `key`, `description` or `comment`); the best five description and comment hits that survive the cap carry a `snippet`, a window of at most 120 characters of the matched text around the first word of the query, without mention tokens, decrypted and read under the caller's visibility in the same transaction, never stored.

### Ranking

Each match is one search function (`WorkItemRepository.searchTitleIds`, `ProjectRepository.searchNameIds`, `SearchVectorRepository.matchItems`), because Prisma cannot order by a rank, and returns ids in candidate order (or with their `ts_rank`); the usecase then reads the matched items' rows in one read by id (`WorkItemRepository.findSearchRows`) and the projects' in another (`ProjectRepository.findSearchRows`). The database orders candidates so the best make the cut: a typed key first, then an exact title, a title prefix, the full-text rank (`ts_rank`) and the trigram similarity, then the id. The usecase then scores each row with `computeRankScore` (`src/lib/search/rank.ts`, pure): an exact title or code (a key, a project's prefix) 100, a prefix 60, a substring 30, plus a baseline of 1 for a work item, so a typed key ranks first and a word match found in another order ranks below every substring hit. `sortHits` orders by score, then type, then id (by code unit), and `capPerType` keeps the best of each type. A description or comment match scores `computeContentScore` (0.5 to 0.9 by its `ts_rank`): below every title match, a title word match included.

## The command palette

`ENTITY_SEARCH_AVAILABLE` is true (`src/components/command-palette/use-entity-search.ts`): from two characters, and 180 ms after the last keystroke, the palette sends one request to the search route of the workspace in the URL and lists work items and projects under their headings, each with its key, and opens the hit's page on select. A failed request says so rather than "No results found". Outside a workspace the palette says search is available after sign-in. A description or comment hit says so under its title ("In the description", "In a comment") with its snippet, rendered as text.

## The list's `q` filter

The Work items page, a project's page and My Work send the filter popover's search box as `q` to `GET /work-items`. It matches a title substring or an exact key, as before, and since 2.7f the title's stemmed words (`WorkItemRepository.titleFullTextIds`) and the description and live comments (`SearchVectorRepository.matchItems`), each through `islestone_bg_en` and at most 1,000 items, under the same visibility; the list keeps its own sort and its other filters. The description and comment half is bounded as the palette's is (decision 250): the answer's `contentMatchesBounded` says so, and the list shows its note.

The title substring (decision 245) is read by `search_work_item_title_substring` on `WorkItem_search_title_trgm`: at most 1,000 ids, which the list then matches by id (`WorkItemFilters.titleSubstringMatchIds`, set by the usecase, never the request). When the 1,000 come back full the query is broad, and the list filters by `title ILIKE '%q%'` itself instead: under row-level security that is a filter, not an index condition, but a broad `q` matches so many items that the list finds a page of them quickly in its own order, and the answer stays complete (a cut list of ids would hide matches). A caller that does not resolve the ids (none does today) gets the same filter. A query of fewer than three characters has no trigram, so the index then reads the workspace's whole entry; that is still bounded.
