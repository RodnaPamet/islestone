## Summary

- **What moves.** The NextAuth v4 layer (`src/auth.ts`, the `[...nextauth]` route) and the parent's hardened code around it: credentials sign-in with the lockout ladder and timing equalisation, bcrypt with the pre-hash, the HIBP breach check, email verification, password change and reset, Google and Microsoft sign-in with the OAuth email-trust rule, `UserSession` rows with revocation, MFA (TOTP) asked per workspace, tenant and org invites, the edge middleware's public-path, MFA, tenant-access and org-access gates, `requirePermission` with its `AUTHZ_DENIED` row, the route-permission map, and member, session and MFA admin routes. SSO (SAML and OIDC through the hand-off) and SCIM 2.0 move behind one feature flag.
- **What is rewritten.** `src/lib/permissions.ts` keeps its mechanism: the `PermissionSet` shape, `PERMISSION_SCHEMA`, `getPermissionsForRole`, the custom-role parser and `permissionsExceeding`. Its 18 compliance domains, 2 DSAR keys and 11 agent keys are replaced with project-management keys. `src/lib/roles.ts`, the coarse ladders, the SCIM role ceiling and `ROUTE_PERMISSIONS` change from OWNER/ADMIN/EDITOR/READER/AUDITOR/AI_ADMIN to OWNER/ADMIN/MEMBER/VIEWER/GUEST (ADR 0006, decided 2026-11-18).
- **What is cut.** Device-agent tokens, line of defence, auditor independence, trust centre and vendor-assessment public paths, legacy-access edge paths, AUDITOR edge carve-outs, about 155 of the 178 route rules (compliance and agent; another 12 or so move to later sub-phases), the compliance API-key scope rows, the DSAR keys, the task-reviewer picker, `latestSignInByUser` (access reviews), the login page's AISVS badge, and the legacy-access and agent imports of `tenant-security-settings`.
- **What waits.**
  - API keys wait for 5.2 (ADR 0004 A2).
  - Entra group-to-role mapping waits for 8.3 (ADR 0004 A2).
  - AI_ADMIN and every agent key, path and context field wait for Phase 6.
  - The custom-role admin page and the members, SSO, SCIM, security and rbac admin pages wait for 1.7 or 8.3.
  - `tenant-lifecycle.ts`, `org-members.ts`, `org-tenants.ts` and the `/api/admin/tenants` routes wait for 8.3 (enterprise administration). Until then, `/api/auth/register` is the only way to create a workspace.
  - The avatar half of `/account/profile` waits for 4.4 (storage). Help-site guides wait for 8.6.
- **Size.**
  - About 24,200 source lines are in scope: core auth 7,347; permissions and roles 4,951 (2,405 of them `route-permissions.ts`); core usecases about 4,300 (4,015, plus `org-provisioning` at 313, minus `tenant-owner-lock`, which 1.3 brings); core routes about 2,020; SSO 3,522; SCIM 2,344. Another 1,200 are in `tenant-security-settings`, which is rewritten down to its session settings. About 3,200 more are auth and account pages (with `src/lib/account/{profile,sso-scope}.ts` and the profile route). The first ESLint local rule adds 106.
  - Deferred: about 1,460 lines of Entra and 1,670 of API keys.
  - Cut outright: about 560 lines. About 2,150 of the 2,405 lines in `route-permissions.ts` are compliance and agent rules; the mechanism is about 120 lines and the kept rules about 100.
- **Tests.** The tests section names about 240 source test files and helpers (wildcard rows counted once). About 185 port with 1.4 or its pages, as COPY or COPY+EDIT. About 55 wait for 1.3, 1.5, 1.6, 1.7, 5.2, 8.3, 8.6 or Phase 6, or are cut. Another 300 or so source tests only mock `requirePermission` around compliance routes; they stay behind.
- **Sibling maps this one now agrees with.**
  - 1.3 ships `src/lib/auth/session.ts` as a stub, plus `tenant-owner-lock.ts`, `org-roles.ts` and gate-free `context.ts` and `*.server.ts`. It keeps `canExport` and drops only `canAudit`. It drops `TenantMembership.customRoleId` and `Tenant.industry`. It leaves `org-provisioning`, `org-members`, `org-tenants` and `tenant-lifecycle` to 1.4 or 8.3.
  - 1.5 creates `OrgAuditAction` and a slim `TenantSecuritySettings`.
  - 1.6 cuts the API-key and agent parts of `context-system.ts`.
  - 1.7 expects `/account/profile` and `/account/security` from 1.4.
- **Owner decisions this map needed: taken** (ADR 0006, owner decisions of 2026-11-18). The `Role` declaration order is `OWNER ADMIN MEMBER VIEWER GUEST` (see Enums). The standard role is `MEMBER` (M2), not `EDITOR`. A user whose role cannot be resolved falls back to `VIEWER`, never `GUEST`. Public self-signup at `/api/auth/register` sits behind a switch: off by default in production, on in development, and an operator opens it without a code change (`register/route.ts`).
- **Licence and ADR 0004.** ADR 0001 is Accepted (owner decisions, 2026-11-18): D1 allows copying, with a `PROVENANCE.md` row per copied file. ADR 0004 is still Proposed, so get it signed before the first copy lands. Its A3 now allows the pinning guard to be copied (COPY+EDIT) under D1; the "fresh, pattern only" wording came from the retired interim rule.

### Permission set: mechanism and key list

**Mechanism.** Keep each of these, rename nothing.

- `type PermissionSet = { [domain]: { [action]: boolean } }`.
- `PERMISSION_SCHEMA: Record<keyof PermissionSet, string[]>`. It is client-safe, and it is the denominator for validation, parsing and escalation.
- `getPermissionsForRole(role)`: an exhaustive switch.
- `validatePermissionsJson`: rejects missing and unknown domains or actions at write time.
- `DERIVED_FROM`: the split-key migration map. It starts empty.
- `parsePermissionsJson(json, baseRole)`: each missing key falls back to the base role's default.
- `permissionsForMembership`.
- `permissionsExceeding(granted, held)`: you cannot grant what you do not hold.
- `PermissionKey`, a template-literal type in `permission-key.ts`, with `hasPermission`.
- `getOrgPermissions`.
- Downstream: `requirePermission` writes `AUTHZ_DENIED` (through `assert-permission.ts`), and `resolveRoutePermission` and `isRouteCovered` drive the coverage guardrail.

**Source key list, all cut.**

- Domains: `controls`, `evidence`, `policies`, `tasks`, `risks`, `assets`, `vendors`, `findings`, `tests`, `incidents`, `personnel`, `access_reviews`, `identity_reconciliation`, `continuity`, `processes`, `frameworks`, `audits`, `reports`.
- `admin.*` keys: `compliance_dsar_view`, `compliance_dsar_manage`, and the 11 agent keys in `AGENT_ADMIN_KEYS`.
- `tasks` and `processes` are PM-shaped, but they come back as `work_items` (2.1) and `canvas` (4.2).

**Proposed Islestone list**, for the owner to confirm. The domains follow roadmap 1.4; the role names follow ADR 0006 (decided 2026-11-18).

- `Role`: from `OWNER ADMIN EDITOR READER AUDITOR AI_ADMIN` to five values, `OWNER ADMIN MEMBER VIEWER GUEST` (ADR 0006, owner decisions of 2026-11-18). 1.3 writes the enum, in that order.
  - **Why order matters.** The source's job actor pickers (`context-system.ts:548`, `jobs/agentic-evidence-emission.ts:116`, `jobs/agent-kill-switch-drill.ts:560`) `orderBy: { role: 'asc' }` with no role filter to find "the most senior member". The ordinal is read as seniority.

VIEWER reads every project. GUEST is limited to named projects (8.4), so it ranks last although the matrix lets it create and comment on items in those projects. A job that wants "most senior" must never land on a guest.

1. **Canonical three policies on every direct tenant table.** The tables are `UserMfaEnrollment`, `TenantSecuritySettings`, `TenantInvite`, `TenantCustomRole`, `TenantIdentityProvider`, `UserIdentityLink` and `TenantScimToken`; 1.3 covers `TenantMembership`.
