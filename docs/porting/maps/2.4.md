## Summary

- **Nothing is copied.** inflect-compliance has no custom fields and no server-side saved views: its "saved views" are the Epic 53 filter presets, a localStorage list per page (`src/lib/filters/filter-presets.ts`, `src/components/ui/filter/use-filter-presets.ts`), which Islestone already mirrors byte for byte in 1.2 part B and does not change. Teable's `packages/` and Kaneo are read for rules and semantics only (pattern only, no code copied), because both store values in shapes ADR 0002 §7 rejects (Teable: a physical column per field and select values keyed by name; Kaneo: one `value text` column). Everything is written fresh.
- **Custom fields follow ADR 0002 §7 exactly** (Accepted, owner decisions 2026-11-19): `CustomField` per project (name, type, `sortKey`, `archivedAt`), `CustomFieldOption` (name, `sortKey`), `CustomFieldValue` with typed columns, a composite FK to `CustomField(id, type)`, a CHECK that exactly the matching column is set, two partial uniques, a 500-character cap on text and URL values, and **text values not encrypted, because they are filterable** (ADR 0002 §7 and "Consequences"; already decided, so not an open question here). Three refinements, each named under "Prisma models" below: the value row also carries `projectId` under composite FKs so a value can never belong to another project's field (ADR 0002 §10's "wrong shapes unrepresentable"); options get `archivedAt` (Teable study open question 2, Kaneo's hidden options); a checkbox stores only `true`, so unchecked is no row (Teable study open question 3).
- **Saved views follow ADR 0006**: model `SavedView`, enum `ViewLayout` (`LIST`, `BOARD`, `TIMELINE`, `CALENDAR`; only the first two are accepted until 3.1 and 3.3), UI word "View". A view holds a scope (the workspace's Work items page or one project), filters, the board's grouping (swimlanes), the sort, the layout and the visible columns; it is personal (its creator's) or shared.
- **Sorts.** The list gains `created`, `due`, `priority`, `key` and a sortable custom field beside `manual` and `updated`, with an optional direction, nulls last in both directions, under a generalised multi-column keyset cursor (`docs/pagination.md`). Priority sorts by a trigger-maintained `priorityRank` column, because Postgres orders the `WorkItemPriority` enum by declaration (`NONE` first) and Prisma cannot order by an expression.
- **Where custom fields show.** A project's page (`/projects/<prefix>`) offers the project's live fields as list columns (column gear), filters (the filter system), board swimlanes (single-valued types and multi-select), and sorts; the detail (page and sheet) shows and edits them. The workspace-wide Work items page and My Work offer none, because fields are per project (ADR 0002 "What would change": workspace-wide fields are a later decision). The API filters and sorts by a field anywhere.
- **Size.** About 3,000 new lines of source, 1,500 of tests.

## Prisma models and migrations

One migration, `20261120120000_saved_views_and_custom_fields`. The two new enums are created in it with their tables (no `ALTER TYPE … ADD VALUE`, so `migration-enum-isolation` is satisfied). Models go in `prisma/schema/work.prisma`, enums in `enums.prisma`.

```prisma
enum CustomFieldType     { TEXT NUMBER SELECT MULTI_SELECT DATE PERSON URL CHECKBOX }
enum ViewLayout          { LIST BOARD TIMELINE CALENDAR }
enum SavedViewVisibility { PERSONAL SHARED }

model CustomField {        // per project; type immutable; archive, never delete
  id, tenantId, projectId, name, type CustomFieldType, sortKey (COLLATE "C"), archivedAt?, createdAt, updatedAt
  project  Project @relation([projectId, tenantId] -> [id, tenantId], onDelete: Cascade)
  @@unique([id, tenantId]); @@unique([id, type, projectId, tenantId]); @@unique([tenantId, projectId, name])
  @@index([tenantId, projectId, sortKey])
}
model CustomFieldOption {  // a select's choices
  id, tenantId, fieldId, name, color?, sortKey (COLLATE "C"), archivedAt?, createdAt, updatedAt
  field CustomField @relation([fieldId, tenantId] -> [id, tenantId], onDelete: Cascade)
  @@unique([id, tenantId]); @@unique([id, fieldId, tenantId]); @@unique([tenantId, fieldId, name])
  @@index([tenantId, fieldId, sortKey])
}
model CustomFieldValue {   // one row per item and field; one per option for MULTI_SELECT
  id, tenantId, projectId, workItemId, fieldId, fieldType,
  textValue?, numberValue Decimal(15,6)?, dateValue Date?, boolValue?, optionId?, userId?, createdAt
  workItem WorkItem         @relation([workItemId, projectId, tenantId] -> WorkItem[id, projectId, tenantId], onDelete: Cascade, onUpdate: NoAction)
  field    CustomField      @relation([fieldId, fieldType, projectId, tenantId] -> [id, type, projectId, tenantId], onDelete: Cascade)
  option   CustomFieldOption? @relation([optionId, fieldId, tenantId] -> [id, fieldId, tenantId], onDelete: Restrict)
  member   TenantMembership?  @relation([tenantId, userId] -> [tenantId, userId], onDelete: Restrict)
  @@index([tenantId, workItemId]); @@index([tenantId, fieldId, textValue|numberValue|dateValue|boolValue|optionId|userId])
  @@index([tenantId, projectId]); @@index([tenantId, optionId]); @@index([tenantId, userId])
}
model SavedView {
  id, tenantId, name, visibility SavedViewVisibility, projectId?, layout ViewLayout,
  configJson Json, createdByUserId, createdAt, updatedAt
  project   Project? @relation([projectId, tenantId] -> [id, tenantId], onDelete: Cascade)
  createdBy User     @relation(createdByUserId -> id)
  @@unique([id, tenantId]); @@index([tenantId, createdByUserId, projectId]); @@index([tenantId, visibility, projectId]); @@index([tenantId, projectId])
}
// WorkItem gains: priorityRank Int @default(5) and the sort indexes below.
```

What the migration SQL adds beyond Prisma's DDL, each with a catalogue test in `tests/integration/custom-field-sql-constructs.test.ts`:

- `COLLATE "C"` on both `sortKey` columns (ADR 0002 §5).
- `CustomFieldValue_one_column`: a CHECK that exactly the column of `fieldType` is set (`textValue` for TEXT and URL, `numberValue`, `dateValue`, `boolValue` (and only `true`), `optionId` for SELECT and MULTI_SELECT, `userId` for PERSON).
- `CustomFieldValue_text_cap`: `char_length("textValue") <= 500`.
- The two partial uniques: `(workItemId, fieldId)` where the type is not MULTI_SELECT; `(workItemId, fieldId, optionId)` where it is.
- **The project lock.** `CustomFieldValue` references `WorkItem(id, projectId, tenantId)` with `ON UPDATE NO ACTION`, and `CustomField(id, type, projectId, tenantId)`. A value can never sit on another project's item, and a move that changes an item's project fails unless the values were removed first: the move usecase deletes the moved subtree's values in its transaction (fields are per project; ADR 0002 §10 clears a milestone the same way).
- `WorkItem.priorityRank` is set by a `BEFORE INSERT OR UPDATE OF priority` trigger (`work_item_priority_rank`: URGENT 1, HIGH 2, MEDIUM 3, LOW 4, NONE 5), back-filled in the migration. No code writes it.
- Row-level security (`tenant_isolation`, `tenant_isolation_insert`, `superuser_bypass`, FORCE) and `GRANT SELECT, INSERT, UPDATE, DELETE … TO app_user` on the four tables. `app_user` may delete values (a clear), options (an unused one), views; fields are never deleted by the app but cascade with a project's purge, which runs as `app_user`, so DELETE is granted.

Indexes added to `WorkItem` for the new sorts, each tenant-leading and ending with `id` (ADR 0002 §13, `docs/pagination.md` rule 4): `[tenantId, projectId, createdAt, id]`, `[tenantId, projectId, dueDate, id]`, `[tenantId, projectId, priorityRank, id]`; `key` uses the existing `[tenantId, projectId, number]` unique within a project and joins `Project.keyPrefix` across projects. Workspace-wide lists use the tenant-leading indexes the planner picks; H2 measures them and removes any it does not use.

## API

Every route is a literal `requirePermission` with a rule in `src/lib/security/route-permissions.ts`, wrapped in `withApiErrorHandling`, with a Zod schema in `src/lib/schemas/custom-field.ts` or `saved-view.ts`.

| Method and path | Key | Usecase |
|---|---|---|
| `GET /projects/:projectId/custom-fields` (`?includeArchived=1`) | `projects.view` | `listCustomFields` |
| `POST /projects/:projectId/custom-fields` | `projects.edit` | `createCustomField` (with initial options for a select) |
| `PATCH /projects/:projectId/custom-fields/:fieldId` | `projects.edit` | `updateCustomField` (rename, archive, unarchive, reorder) |
| `POST /projects/:projectId/custom-fields/:fieldId/options` | `projects.edit` | `addCustomFieldOption` |
| `PATCH /projects/:projectId/custom-fields/:fieldId/options/:optionId` | `projects.edit` | `updateCustomFieldOption` (rename, colour, archive) |
| `DELETE /projects/:projectId/custom-fields/:fieldId/options/:optionId` | `projects.edit` | `deleteCustomFieldOption` (409 `OPTION_IN_USE` while a value holds it) |
| `PUT /work-items/:id/custom-fields/:fieldId` `{ value }` (`If-Match` optional) | `work_items.edit` | `setWorkItemCustomFieldValue` |
| `GET /work-items` adds `order=created|due|priority|key|cf:<fieldId>`, `dir=asc|desc`, `cf.<fieldId>=<op>:<operand>` | `work_items.view` | `listWorkItems` |
| `POST /work-items` adds `customFields: { [fieldId]: value }` | `work_items.create` | `createWorkItem` |
| `GET /views` (`?projectId=<id>` or `?scope=workspace`) | `views.view` | `listSavedViews` |
| `POST /views` | `views.create` | `createSavedView` |
| `GET /views/:viewId` | `views.view` | `getSavedView` |
| `PATCH /views/:viewId` | `views.edit` | `updateSavedView` |
| `DELETE /views/:viewId` | `views.edit` | `deleteSavedView` |

Every list and detail row gains `customFields: { [fieldId]: value }` (string, number, `YYYY-MM-DD`, `true`, an option id, option ids in option order, or a user id), read in the same query (`workItemListSelect`, bounded). The view configuration the project page reads gains the project's live fields with their live options.

**Concurrency (ADR 0002 §9).** A value write is a single-field change: it increases the item's `version` (a custom-field value is part of what the item shows, as labels are), and `If-Match` is optional (a stale one is a 409 with the current row; without one the last writer wins, audited). It is one versioned `updateMany` (bumping the version), then the value rows replaced, in one transaction. Definition writes (rename, archive, options) do not touch items, so they bump nothing; archiving a field or an option keeps every value. Removing a member clears their person values and increases those items' versions, before the membership row goes (the value's member FK is `RESTRICT`, as the assignee's is).

**Audit.** `CUSTOM_FIELD_CREATED`/`_UPDATED`/`_ARCHIVED`/`_RESTORED`, `CUSTOM_FIELD_OPTION_CREATED`/`_UPDATED`/`_DELETED`, `WORK_ITEM_CUSTOM_FIELD_SET` (changed field id and name, never the value: a text value may hold anything), `SAVED_VIEW_CREATED`/`_UPDATED`/`_DELETED` (a shared view deleted by an admin who did not create it is `SAVED_VIEW_MODERATED`, decision 53's shape). All through `logEvent` with the transaction client and a structured `detailsJson`.

## Sorting and cursors

`src/lib/pagination.ts` gains a multi-column keyset (`SortSpec`: an ordered list of columns, each a Prisma path such as `['project', 'keyPrefix']`, a direction, a kind and whether it is nullable) with `buildSortWhere`, `sortOrderBy` and `computeSortPage`; the cursor is `{ v: [...values], id }`. Nulls sort last in both directions; a cursor whose value is null continues among the nulls by `id`. The single-column `KeysetOrder` stays and is expressed through it, so existing cursors keep their shape.

| `order` | Columns (default direction) | Index |
|---|---|---|
| `manual` | `sortKey` asc (no `dir`) | `[tenantId, projectId, sortKey, id]` |
| `updated` | `updatedAt` desc | `[tenantId, projectId, updatedAt, id]` |
| `created` | `createdAt` desc | `[tenantId, projectId, createdAt, id]` (new) |
| `due` | `dueDate` asc, nulls last | `[tenantId, projectId, dueDate, id]` (new) |
| `priority` | `priorityRank` asc (urgent first) | `[tenantId, projectId, priorityRank, id]` (new) |
| `key` | `project.keyPrefix`, `number` asc | `[tenantId, projectId, number]` (unique) |
| `cf:<fieldId>` | the value column asc, nulls last; a select by its option's `sortKey` | `[tenantId, fieldId, <column>]` |

A custom-field sort is two phases over Prisma (no raw SQL): items with a value, read from `CustomFieldValue` ordered by the value (or `option.sortKey`) and `workItemId`, with the item filters as a relation filter; then, when that phase is exhausted, items with no value (`customFieldValues: { none: { fieldId } }`) by `id`. The cursor carries the phase. The full rows are then read once by id and put in order in memory: three bounded reads, no read in a loop. Sortable types: TEXT, NUMBER, DATE, SELECT, CHECKBOX, URL; not MULTI_SELECT or PERSON (a person's name is encrypted PII and cannot be ordered by the database).

## Saved views: permissions (existing keys only)

1.4's `PermissionSet` has a `views` domain: `view`, `create`, `edit`, `share` (OWNER, ADMIN, MEMBER hold all four; VIEWER and GUEST `view`). The proposal, applied as the narrowest safe default:

| Act | Rule |
|---|---|
| See a view | Your own personal views, and every shared view whose scope is the workspace or a project you can see (`visibleProjects`). Key: `views.view`. |
| Create a personal view | `views.create`. |
| Create a shared view, or share a personal one | `views.create` (or `views.edit`) and `views.share`. |
| Change or delete a personal view | Its creator, holding `views.edit`. Nobody else (it is not theirs to see). |
| Change or delete a shared view | Its creator holding `views.edit` and `views.share`; or a workspace admin (`admin.manage`) for moderation: delete only, audited as `SAVED_VIEW_MODERATED`. Nobody else edits another person's shared view (open question 2). |
| Unshare a shared view | Its creator (it becomes their personal view). |

A project-scoped view is refused (404) when the project is not visible, and its project must be live. **Custom-field definitions** take `projects.edit` (change a project; `projects.view` reads them), because a field is part of a project (ADR 0006: "A body of work … with its own key prefix and custom fields"), and re-prefixing a project already takes `projects.edit` (open question 1: `admin.manage` instead). **Value writes** take `work_items.edit`, as labels on an item do.

## UI touch points

- **Project page** (`/projects/<prefix>`): the server page reads the project's fields (`getWorkItemViewConfig(ctx, { projectId })`) and the affordances (`customFieldAffordances`, `savedViewAffordances`, asked on the server). The header gains a **Views** menu (apply, save, save as, rename, share, delete with the undo toast), a **Sort** picker (list layout) and, for a viewer who may edit the project, a **Fields** button opening the field manager.
- **Work items page** (`/work-items`): the same Views menu and Sort picker (workspace-scope views), no custom fields.
- **Columns.** The list gets the column gear (`useColumnsDropdown`, per-view storage): the six 2.3 columns, plus created, updated, type and labels, plus one column per live custom field (hidden by default). A saved view stores the visible column ids and applies them.
- **Filters.** One filter definition per live field: options and "No value" for select, multi-select (any of) and person; "Checked"/"Unchecked" for a checkbox; "Has a value"/"No value" for text, number, date and URL (richer operators are API-only in 2.4). Keys are `cf.<fieldId>`, synced to the URL like every facet.
- **Board.** Swimlanes by a select, multi-select (first option in option order, as labels), person or checkbox field. Moving a card to another lane of a select, person or checkbox field sets that value; multi-select lanes are fixed (as label lanes).
- **Detail** (page and sheet): a "Fields" section listing the project's live fields with an editor per type, writing through `useWorkItemMutations` (optimistic, `If-Match`, rollback).
- **Field manager** (`CustomFieldsManager`, a modal): list fields in order, create (name, type, options), rename, archive and unarchive, add, rename, archive and delete options. Also reachable from Settings → Projects (a "Fields" action per project), which is the same component. The editor says text values are not encrypted (ADR 0002 §7).
- **Views page** (`/views`, 1.7's placeholder): replaced by the list of views the member can see (name, scope, layout, shared or personal), each linking to its page with `?view=<id>`. The page and its list are new code in `src/components/views/`.
- Rules from 2.3 hold: one list query and one cache (the sort is part of the list's filters, so a re-sort is another cache key); options from the server (field definitions come with the view configuration, never from rows); deletes through `useToastWithUndo`; `h2` under the page's `h1`; every string a `messages/en.json` key (`workItems.fields.*`, `workItems.sort.*`, `views.*`).

## Ordering and risks

1. Schema and migration, then the domain module and repositories, then usecases and routes, then the client; tests with each step.
2. **Risk: the move path.** Every move to another project must delete the moved rows' values first, or the FK refuses the move. Held by the FK itself and an integration test.
3. **Risk: `workItemListSelect` grows** by the values; bounded (`take`) and only for the list's own rows.
4. **Risk: Prisma and the composite FKs** sharing `tenantId`, `fieldId` and `projectId` across relations; Prisma accepts shared scalar fields, and the drift check holds the migration equal to the schema.
5. **Risk: priority rank by trigger.** A trigger is the single writer; Prisma reads it back through `RETURNING`. Catalogue test and a behaviour test.

## Open questions for the owner

1. **Who defines custom fields?** Applied default: `projects.edit` (members hold it), since a field belongs to its project. Alternative: `admin.manage`, like work item types and labels (narrower). Recommendation: `projects.edit`.
