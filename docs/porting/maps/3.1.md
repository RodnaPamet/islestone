## Summary

- **SVAR React Gantt 2.8.3 passes Islestone's licence gate with no exemption.** Re-verified today: the package and its whole dependency tree (25 distinct `@svar-ui/*` packages, 30 lockfile entries with nested copies, plus `date-fns` 3.6.0) declare MIT; the repository's `license.txt` at the v2.8.3 tag is byte-identical to the tarball's. Nothing in this map needs an exemption, and none is proposed. Two traps: the **old package name `wx-react-gantt` is GPL-3.0** (still on npm, 1.3.1), and `@svar-ui/react-gantt` itself was **GPL-3.0 at 2.3.1 to 2.3.4**; the gate refuses both, and a guard pins the namespace (below).
- **The MIT core has no scheduling at all.** The 2026-11-18 study verified that PRO is the same source with its bodies removed and its options forced off at init (`isCommunity()` returns `true`): no forward or backward pass, no float, no critical path, no working calendar, no today line, no undo; links are accepted without validation, cycles included. The core gives bars, links, zoom, a task grid, drag to move and resize, drag-in from an outside list, virtualisation and weekend shading through a callback. Everything the prompt asks for beyond drawing is Islestone's, as the roadmap already said.
- **The engine** is a pure, client-safe module, `src/app-layer/domain/schedule/`, over **date-only epoch days** (whole days since 1970-01-01, never a `Date` with a zone), so daylight saving cannot move a result. Kahn's topological sort with ties broken by id, a forward and a backward pass, total and free float, the critical path, per-calendar working-day arithmetic. It reads only BLOCKS relations as finish-to-start dependencies (ADR 0002 §6), refuses a cycle itself as a second line behind the usecase's graph lock, and returns results sorted by id so input order never matters.
- **No new dates on the item.** `WorkItem.startDate` and `dueDate` exist (date-only, 2.1). The engine treats the start date as "not before" and derives the duration from the two dates on the item's working calendar; it **computes and never writes** (principle 4): earliest and latest dates, float and the critical path are returned with every read, never stored.
- **Working calendars** are new tables: one workspace calendar and optional team calendars (time zone, working weekdays, holidays), managed under `admin.manage`. 2.8's Monday-to-Friday constant (`working-days.ts`, decision 151) moves onto them for review steps opened after 3.1; a stored `dueOn` never moves (ADR 0009 §13).
- **The timeline** is the `TIMELINE` layout (already in `ViewLayout`) on the Work items page, a project, a cycle, a milestone and saved views; at most 5,000 items per scope, refused above with a count, never cut silently. The widget is display and input only: SVAR's own editor, toolbar, context menu, grid editing and task creation are switched off, its icon font is never loaded (the CSP would refuse it anyway), and an accessible schedule table beside the chart shows the same numbers and offers the same date change by keyboard.
- **Dragging a bar never writes.** `api.intercept('update-task')` returns `false`; a "Change dates" dialog shows the old and new dates and what the engine says the change does to other items (re-run in the browser on the same pure module); confirming sends the ordinary versioned `PATCH` with `If-Match`, through every field-set and permission check the API already applies. It is a person's own edit, not a proposal (ADR 0003: proposals are agents'; 7.5's rescheduling proposals reuse the engine, not the dialog).
- **Three pull requests**: 3.1a engine and calendars, 3.1b the read-only timeline, 3.1c changes from the timeline. About 7,500 lines of source and 6,000 of tests.

## The model

### Item dates: nothing new

`WorkItem.startDate` and `dueDate` are date-only (`@db.Date`), both optional, both configurable field-set fields (2.4b). 3.1 adds **no column** to `WorkItem`. It adds two rules:

- **Start after due is refused on write** from 3.1a: 400 `START_AFTER_DUE` in `createWorkItemInTx`, `updateWorkItem`, the bulk due-date path, templates (`dueInDays` against a template's start) and repeats (a copy keeps the distance). No CHECK: rows written before 3.1 may break it, and the engine reports them (`DATES_REVERSED`) rather than a migration rewriting them (2.4b's rule: existing items are never rewritten).
- **The schedule is never stored.** Earliest and latest dates, float and criticality are computed on every read, like the burn-up (2.5a). No column, no cache table, no job.

### Working calendars (new; open questions 8 to 12)

```prisma

  id String @id @default(cuid()), tenantId, teamId String?,
  name String,                   // plaintext, sanitised, <= 80

  holidays WorkingCalendarHoliday[]

model WorkingCalendarHoliday {
  id, tenantId, calendarId, on DateTime @db.Date, name String (plaintext, sanitised, <= 80), createdAt
```

- **Which calendar an item uses:** its team's, else the workspace's. A workspace without a calendar row behaves as Monday to Friday, no holidays, `NOTIFICATIONS_TZ` (the 2.8 default), so nothing changes until an admin edits one; Settings shows that default as editable.
- **A team calendar replaces, it does not add to, the workspace's** (open question 8): its own weekdays and its own holidays, with "Copy the workspace's holidays" as an action.
- **Holidays are dates entered by hand** (open question 9), with "Copy last year's" (same names, the same day of month; a person fixes the moveable ones). No country preset: the obvious library, `date-holidays` 3.39.2, declares `(ISC AND CC-BY-SA-4.0)`, and CC-BY-SA-4.0 is not on `ALLOWED_LICENCES`, so it would need an ADR 0007 exemption.
- **Tenant-table rules** for both: `tenantId`, the tenant-leading indexes above, `tenant_isolation`, `tenant_isolation_insert`, `superuser_bypass`, FORCE and `GRANT … TO app_user` in their migration, two-tenant tests in `ISOLATION_TESTED`. No encryption: a calendar's name and a holiday's name are workspace configuration, not personal data; `encryption-manifest-coverage.test.ts` classifies both columns as plaintext business fields with that reason. Both names go through `sanitizePlainText`.
- **Keys** (open question 12, A): read under `projects.view`, written under `admin.manage` (teams, states and types are configured by admins, owner decision 2026-11-19). Routes: `GET`/`PUT /working-calendar` (the workspace's), `GET`/`PUT`/`DELETE /teams/:teamId/working-calendar`, `POST`/`DELETE …/holidays[/:holidayId]`, each a literal `requirePermission` with a `route-permissions.ts` rule and a `tenant-crud-authz-coverage` pin. ## The engine (3.1a)

Pure TypeScript, client-safe (no `server-only`, no Prisma, no `@/env`, no clock), in `src/app-layer/domain/schedule/`:

- `calendar.ts`: `toEpochDay(dateOnly)`, `fromEpochDay(n)`, `isWorkingDay(cal, d)`, `nextWorkingDay(cal, d)` (`d` itself when working), `previousWorkingDay`, `addWorkingDays(cal, d, n)` (n ≥ 0: the n-th working day after `d`; `n = 0` is `nextWorkingDay(d)`), `workingDaysInclusive(cal, a, b)`, `todayIn(timeZone, instant)` (the only function that touches a zone: `Intl.DateTimeFormat` parts to an epoch day). Holidays are a sorted array searched by bisection; a working-day count over a long span steps whole weeks, then the remainder, then subtracts holidays in range, so it is O(log h) per call, not O(days).
- `engine.ts`: `computeSchedule(input): ScheduleResult`.
- `types.ts`: the shapes below, exported for the server, the browser and 7.5.

```ts
type EpochDay = number;                      // days since 1970-01-01, a civil date; never an instant
interface CalendarSpec { id: string; workingWeekdays: readonly (1|2|3|4|5|6|7)[]; holidays: readonly EpochDay[] }
type ItemStatus = 'open' | 'started' | 'done';        // CANCELLED items are not passed
interface ScheduleItem {
  id: string; calendarId: string; parentId: string | null;
  plannedStart: EpochDay | null; plannedFinish: EpochDay | null;   // startDate, dueDate (inclusive)
  status: ItemStatus; actualStart: EpochDay | null; actualFinish: EpochDay | null;
  deadline: EpochDay | null;                                         // the item's milestone's due date (question 7)
}
interface ScheduleEdge { from: string; to: string }                 // from BLOCKS to: finish-to-start, no lag
interface ScheduleInput { asOf: EpochDay; calendars: readonly CalendarSpec[]; items: readonly ScheduleItem[]; edges: readonly ScheduleEdge[] }
interface ItemSchedule {
  id: string; durationDays: number | null; unscheduled: boolean;
  earliestStart: EpochDay; earliestFinish: EpochDay; latestStart: EpochDay; latestFinish: EpochDay;
  totalFloat: number; freeFloat: number; critical: boolean;
  conflicts: readonly ('STARTS_BEFORE_BLOCKER_FINISHES' | 'MISSES_DEADLINE' | 'DATES_REVERSED' | 'STARTS_ON_NON_WORKING_DAY')[];
}
type ScheduleResult =
  | { ok: true; asOf: EpochDay; finish: EpochDay; items: readonly ItemSchedule[] /* sorted by id */;
      criticalEdges: readonly ScheduleEdge[]; warnings: readonly ScheduleWarning[] }
  | { ok: false; error: 'CYCLE'; cycle: readonly string[] }
  | { ok: false; error: 'TOO_LARGE'; items: number; limit: number };
```

The rules (proposed; open questions 3 to 7 and 17):

1. **Validate.** Unknown calendar ids, edges to unknown items and duplicate ids are programmer errors and throw; over `SCHEDULE_ITEM_LIMIT` (20,000, four times the timeline's scope limit) returns `TOO_LARGE` before any work.
2. **Duration.** Both dates: `workingDaysInclusive(cal, start, finish)`, at least 1. Only a due date: 1 working day ending on it. Only a start date: 1 working day from it. Neither: `unscheduled`, duration 0 (question 4). Start after due: `DATES_REVERSED`, duration 1 at the due date.
3. **Order.** Kahn over the item graph, the ready set kept sorted by id (`<`, never `localeCompare`, as `sortKey` is compared). A remainder means a cycle: a DFS from the smallest remaining id returns it as a path, and the result is `{ ok: false, error: 'CYCLE' }`. ADR 0002 §6 makes a stored cycle impossible; this is the second line, and its answer equals `wouldCreateCycle` on the same edges (a property test ties them).
4. **Forward pass**, in that order. For an item on calendar `c`:
   - `done`: fixed at `actualStart`/`actualFinish` (the epoch days of `startedAt` and `completedAt` in its calendar's time zone; falling back to planned dates); it moves nothing and is never critical.
   - `started`: `earliestStart = actualStart`; `earliestFinish = max(start + duration − 1 working days, asOf)` (work in progress cannot finish before today).
   - `open`: `earliestStart = nextWorkingDay(c, max(asOf, plannedStart ?? −∞, max over blockers b of (b.earliestFinish + 1)))`; `earliestFinish = addWorkingDays(c, earliestStart, duration − 1)`. Each blocker's finish is read on the blocker's own calendar and the successor starts on the successor's next working day, so cross-team edges with different calendars need no common unit.
   - `STARTS_BEFORE_BLOCKER_FINISHES` when a planned start is earlier than a blocker's earliest finish + 1.
5. **Finish.** `finish = max earliestFinish` over the items passed.
6. **Backward pass**, in reverse order: `latestFinish = previousWorkingDay(c, min(finish, deadline ?? +∞, min over successors s of (s.latestStart − 1)))`; `latestStart` = the working day `duration − 1` before it. `done` items take their actuals.
7. **Float.** `totalFloat` = working days from `earliestStart` to `latestStart` on the item's calendar (negative when late); `freeFloat` = working days from `earliestFinish` to the earliest successor start, minus one, clamped at 0 (to `finish` with no successor). `MISSES_DEADLINE` when `earliestFinish > deadline`.
8. **Critical** (question 17, A): an open or started item whose `totalFloat` equals the minimum `totalFloat` over open and started items, when that minimum is ≤ 0; an edge is critical when both ends are critical and the successor's earliest start is exactly the next working day after the blocker's earliest finish. With no deadlines the minimum is 0 and this is the classic longest path; with a missed deadline it is the chain that is most late.
9. **Sub-items** (question 5, A): an item with live sub-items in scope is a **summary**: not a node itself; its bar spans its sub-items' earliest start to their latest finish; a BLOCKS edge into it applies to each of its leaf sub-items, an edge out of it leaves from its latest-finishing leaf. Its own planned dates are shown as a faint outline, with `SUMMARY_OUTSIDE_PLANNED_DATES` when the children run past them.
10. **Unscheduled items in a chain** (question 4, A): duration 0 at their earliest start, so the chain's logic holds, and a `UNSCHEDULED_IN_CHAIN` warning names them.
11. **Output** sorted by id; every number an integer; no `Date`. `asOf` is passed in, never read from a clock.

**Complexity.** One topological sort and two passes: O(V + E) times the O(log h) calendar step. Target: 5,000 items and 10,000 edges in under 50 ms in Node and under 100 ms in a browser on the reference machine (part "Performance").

**Tests (H3's list, made concrete).** `tests/unit/domain/schedule-*.test.ts` with `fast-check` (4.10.2, already a dev dependency):

- **Cycles refused:** for random DAGs plus one random back edge, the result is `CYCLE` and its `cycle` is a real cycle of the input; for random DAGs, never `CYCLE`; `CYCLE` exactly when `wouldCreateCycle` says the last edge closes one.
- **Order independence:** shuffling `items`, `edges`, `calendars` and each calendar's holidays gives a deep-equal result.
- **Idempotence:** writing each open item's earliest dates back as its planned dates and recomputing changes nothing.
- **Monotonicity:** adding an edge never makes any earliest start earlier; moving `asOf` later never makes any earliest start earlier; adding a holiday never makes any finish earlier.
- **Critical path:** with no deadlines it is non-empty when any open item exists, every critical item has float 0, and the critical edges join a chain from an item with no critical blocker to one finishing at `finish`.
- **Calendars:** no earliest or latest date ever lands on a non-working day; `addWorkingDays(c, d, n)` is strictly increasing in `n`; `workingDaysInclusive(addWorkingDays(c, d, n − 1)) = n` for a working `d`; a calendar of seven working days and no holidays equals plain day arithmetic.
- **Time zones and daylight saving:** the engine is run under `TZ` set to `Europe/London`, `America/Sao_Paulo`, `Australia/Lord_Howe` (a half-hour shift), `Pacific/Apia` (it skipped 30 December 2011) and `UTC` (one Jest project per zone, or `process.env.TZ` set before the module loads in a child process): results are byte-equal. `todayIn` is tested at instants one second either side of every DST transition of those zones from 2020 to 2030, against `Intl`'s own answer, and across the date line.
- **Vectors written by hand**, checked against the rules above: the study's float vector (A 2 days, B 3, C 15, no edge between C and the others: A and B float 12, C 0) recast to finish-to-start, a weekend-straddling chain, a holiday inside a duration, two calendars across one edge, a started item past its due date, a done item with an early finish. SVAR's PRO test files are a source of ideas only (study §4): no vector is translated from them, so no NOTICE entry is needed.

## How 2.8's working days move onto calendars (3.1a)

2.8a writes `addWorkingDays(dateOnly, n, calendar)` in `src/app-layer/domain/working-days.ts` with a Monday-to-Friday constant, and computes "today" in `NOTIFICATIONS_TZ` when a step opens (decision 151, ADR 0009 §13). 3.1a:

- moves the arithmetic into `schedule/calendar.ts` and leaves `working-days.ts` as a re-export with the same signature, so 2.8's callers do not change;
- resolves the calendar when a step opens: the item's team's, else the workspace's, else the constant (open question 11, A); "today" from that calendar's time zone (open question 10, A), which equals `NOTIFICATIONS_TZ` until someone changes it;
- **never recomputes a stored `dueOn`**: ADR 0009 §13 says calendars replace the constant "for steps opened after it", and a reviewer's due date does not move under them;
- changes the reminder windows ("tomorrow's working day", 2.8's `WORK_ITEM_REVIEW_DUE`) to the same calendar;
- amends ADR 0009 §13 to say so (drafted below, not applied).

The 08:00 and 08:10 jobs keep running in `NOTIFICATIONS_TZ`: a calendar's time zone decides which day "today" is for its items, not when the deployment's jobs fire (question 10).

The layout switcher (List, Board, Timeline) gains Timeline where Board is offered today. Every filter of the list applies, through the same `list-filter.ts` where clause, so a timeline and a list with the same filters hold the same items.

### The read

`GET /api/t/:slug/work-items/timeline?<the list's filters>` (`requirePermission('work_items.view')`), usecase `getTimeline` in `src/app-layer/usecases/work-item-timeline.ts`:

1. Count the scope with the list's where clause; over `TIMELINE_ITEM_LIMIT` (5,000; question 15) answer 422 `TIMELINE_TOO_LARGE` with the count: the page says "Narrow the filter: 7,214 items". **Never a cut-off list** (zero is never complete; neither is a truncated population).
2. One bounded read of the rows (`take: limit + 1`): id, key, title, type, state category, assignee, parent, sort key, start, due, `startedAt`, `completedAt`, milestone, team, version. Cancelled items are read but not passed to the engine (question 6); they show greyed with no bar.
3. BLOCKS edges with **either end** in the scope (`WorkItemRelationRepository.blocksTouching`, a new bounded read on `@@unique([tenantId, fromId, type, toId])` and `@@index([tenantId, toId, type])`). An end outside the scope but visible becomes a **context row** (greyed, read-only, at most 500 of them, its own dates as fixed constraints). An end the caller cannot see (a GUEST from 8.4; every edge of a deleted item) is dropped and counted: the response says `hiddenDependencies: n`, never which item, and the page says "n dependencies to items you cannot see are not shown". Edges to soft-deleted items are dropped (the cycle refusal keeps walking them; scheduling does not).
4. The calendars of the teams in scope, their holidays within the visible range plus a year.
5. `asOf` = today in the workspace calendar's time zone.
6. `computeSchedule`; the response carries rows, edges, calendars, `asOf` and the result. Description, comments and custom-field values are not read: the timeline shows titles (plaintext by ADR 0002 §11).

Every read carries `tenantId`, `deletedAt: null` and `projectVisibilityWhere` (the repository-predicate test gains the method). The plan check registry of H2 gains the scope read and the edge read.

### The client

- **Data:** `useWorkItemTimeline(scope, filters)` in `src/components/work-items/data/` (the shared-query guard's folder), an SWR read through `use-tenant-swr.ts`. A write through `useWorkItemMutations` updates the timeline cache too (`work-item-cache.ts` learns the timeline's key) and re-runs the engine on the cached rows, so the list, board, detail and timeline agree without a refetch. The timeline does not use `useWorkItemList`: it needs the whole scope at once, not pages of 50.

Rows ordered by `(sortKey, id)` within their parent; a parent's children in its own order.
- **Switched off:** SVAR's `Toolbar`, `Editor`, `ContextMenu`, grid inline editing, `add-task`, `delete-task`, `copy-task`, `move-task` (grid reordering) and its hotkeys, each by `api.intercept(<action>, () => false)` registered in `init`, plus `readonly` for a caller without `work_items.edit` (from `timelineAffordances`, asked on the server). The grid shows key, title, assignee, start, due and float, read-only.

- **Today:** SVAR's markers are PRO, so the today line is Islestone's: an absolutely positioned element over the chart's scroll area at `asOf`, computed from SVAR's scale state (which field exposes it is to be verified in 3.1b), re-placed on zoom and scroll; or a `highlightTime` class on today's column when that proves simpler (3.1b decides by a rendered test).
- **No dates:** items with neither date are listed in a "No dates" panel beside the chart (SVAR's unscheduled tasks are PRO). In 3.1c they can be dragged onto the chart (core since 2.8.0, `locateTask`), which opens the same "Change dates" dialog.
- **Copy** is `workItems.timeline.*` in `messages/en.json`; `h2` headings under the page's `h1`.

## Changing dates from the timeline (3.1c)

1. **Intercept.** `api.intercept('update-task', ev => { openChangeDates(ev); return false; })`. SVAR has already moved the bar's pixels during the drag (study §6.D); the adapter resets the widget by passing the cached `tasks` array again on cancel, on a refusal and on a 409. A rendered test checks that a blocked `update-task` leaves the bar where it was (the study's open point).
2. **The proposed dates.** From the drop: a move keeps the item's working-day duration on its calendar (the new start snaps forward to a working day; the due date is `addWorkingDays(start, duration − 1)`); a resize of the start or the end changes that one date, snapped to a working day. A drag of a summary moves nothing (its dates are derived); 3.1c disables it.
3. **The dialog, "Change dates for ISL-123".** Old and new start and due; and, from `computeSchedule` re-run in the browser on the cached rows with the new dates: items whose earliest start moves (with by how much), items that become critical or stop being critical, new conflicts (a blocker that now finishes after its successor starts, a milestone now missed). Each named item is a link to its sheet. Buttons "Change dates" and "Cancel".
4. **Confirm** sends `PATCH /work-items/:id { startDate, dueDate }` with `If-Match: <version>` through `useWorkItemMutations().update`, the same write the detail makes: field sets (a hidden or required date refuses with `FIELD_HIDDEN` / `FIELD_SET_UNMET`), `START_AFTER_DUE`, `PROJECT_ARCHIVED`, permission (`work_items.edit`), audit (`WORK_ITEM_UPDATED`, fields named), due-date reminders (`emitDueBell` for today's window), watchers, everything. A 409 shows "changed by someone else" and re-reads.
5. **Only the dragged item changes** (open question 13, A). The knock-on effects are shown, not applied: moving a chain is a bulk date change with its own checks, and moving a plan is 7.5's agent proposal.
6. **Read-only bars:** done and cancelled items (actuals are history), items in an archived project, summaries, context rows, and every bar for a caller without `work_items.edit` or whose field set hides the date.
7. **Dependencies from the timeline** (open question 14, A): drawing a link between two bars opens "Add dependency: ISL-1 blocks ISL-2?"; confirming calls the existing `POST …/relations { type: 'BLOCKS' }`, whose graph lock refuses a cycle (409 `RELATION_WOULD_CYCLE`, shown in the dialog). The link appears only after the server accepts. Other link types SVAR offers (`s2s`, `e2e`, `s2e`) are refused in the intercept. Deleting a link goes through `useToastWithUndo` and the existing `DELETE …/relations/:relationId` (`SITE_CONTRACTS`).
8. **Agents never use this path.** An agent's schedule change is a proposal (ADR 0003, roadmap 7.5); the engine is the shared part, the dialog is not.

## The critical path on screen

- **Bars:** `taskTemplate` renders the bar's content as a full-size element carrying `data-critical`, `data-late` and `data-conflict`, styled by token classes (critical: the emphasis border and fill; late: the danger tone; a conflict: a small marker with its reason in the tooltip). ### New: ADR 0010 — Scheduling and working calendars (draft)

> Status: Proposed (roadmap 3.1)
>
> **Context.** Roadmap 3.1 asks for a timeline with a critical path and working calendars. SVAR React Gantt's MIT core draws and edits bars but schedules nothing (its scheduling, critical path and calendars are in the paid PRO edition, removed from the public code). Items have date-only `startDate` and `dueDate` (ADR 0002). Review steps count working days, Monday to Friday until this ADR (ADR 0009 §13).
>
> **Decision.**
> 1. **One engine.** Scheduling is a pure module (`src/app-layer/domain/schedule/`): plain data in, plain data out, no database, no clock, no time zone. Dates are whole days since 1970-01-01. Every caller (the timeline read, the browser's preview, roadmap 7.5's rescheduling proposals, 3.6's forecasts) uses it; no second implementation.
> 2. **Dependencies** are BLOCKS relations read as finish-to-start with no lag. A cycle is refused by the relation usecase (ADR 0002 §6) and again by the engine.
> 3. **Dates mean:** the start date is "not before", the due date is the planned finish, the working days between them are the duration. A done item is fixed at its actual dates, a cancelled item is left out with its edges, an unstarted item cannot start before today, a started one cannot finish before today. A milestone's due date is a deadline for its items.
> 4. **Computed, never stored.** Earliest and latest dates, float and the critical path are computed on every read; nothing writes them. The engine never changes an item's dates.
> 5. **Working calendars** belong to the workspace and optionally to a team (a team's replaces the workspace's): a time zone, working weekdays and holidays entered by hand. An item uses its team's calendar, else the workspace's; with neither, Monday to Friday in `NOTIFICATIONS_TZ`. Changing a calendar changes no stored date: review steps keep their `dueOn` (ADR 0009 §13).
> 6. **A person changes dates; the timeline asks first.** Dragging a bar or drawing a dependency opens a confirmation showing the change and its effects; confirming sends the ordinary versioned write, with every field-set, permission and audit rule the API applies. Only the item dragged changes. It is not a proposal: proposals are agents' (ADR 0003), and an agent's schedule change is a proposal (roadmap 7.5).
> 7. **SVAR React Gantt, MIT core only**, at a pinned version at or after 2.4.3, through one adapter file; no PRO package, no PRO option, no vendor CDN request. The word "Gantt" stays inside that import (ADR 0006).
>
> **Consequences.** The timeline's critical path, today line and accessibility layer are Islestone's own code over the widget. A team's calendar can differ from its neighbour's, so cross-team dependencies are computed per calendar. A scope over 5,000 items is refused, never truncated.
>
> **What would change this decision.** Customers need start-to-start or finish-to-finish dependencies, or lag (a new relation shape and an ADR 0002 amendment); personal time off must shape schedules (roadmap 3.5); automatic levelling or rescheduling is wanted beyond agent proposals; SVAR PRO is bought (an ADR 0007 exemption and a new pin); the engine cannot meet the 5,000-item budget.

## Open questions for the owner

Each question stands alone. The recommended option is first and marked; each option carries its main trade-off.

**The library**

1. **Which version of the timeline library (SVAR React Gantt) do we pin?** Both candidates are MIT and pass the licence gate with no exemption.
   - A (recommended). 2.8.3, the latest (published 17 November 2026). It fixes the library's own missing dependency declarations, which matter for a strict install; only three days in the field.
   - B. 2.8.2 (27 October 2026). Three more weeks in the field; without that fix.
   - C. Whatever is latest when 3.1b starts, re-verified then. Freshest; the licence check and the guard's package list are redone at that point.

2. **Which kinds of dependency does the schedule understand?**
   - A (recommended). Only "blocks", read as "must finish before the other starts", with no lag: what the product stores today, and no change to the work-item model.
   - B. "Blocks" plus a lag in working days (for example, "starts 2 days after"). Common in construction-style plans; a new column on the relation and an amendment to ADR 0002.
   - C. All four kinds (finish-to-start, start-to-start, finish-to-finish, start-to-finish) with lag. The full scheduling vocabulary; new relation kinds, new words in ADR 0006, and more for people to learn.

**What the engine does with dates**

3. **What do an item's start and due dates mean to the schedule?**
   - A (recommended). The start date means "not before", the due date is the planned finish, and the working days between them are the duration. The engine computes the earliest and latest dates from dependencies and today, reports conflicts ("starts before its blocker finishes"), and never changes a stored date. People stay in charge of dates; the timeline tells them what does not fit.
   - B. The engine reschedules: when a blocker moves, its successors' stored dates move with it automatically. The plan always fits, but dates change without a person choosing them, against the principle that people (not code) set dates and agents only propose.
   - C. Ignore start dates; schedule purely from durations and dependencies. Simple and classic, but a person's "not before Monday" is lost.

4. **What happens to items missing a start or due date?**
   - A (recommended). An item with only a due date is one working day ending on it; only a start date, one working day from it; neither, it sits in a "No dates" list beside the chart, and if it is in the middle of a chain it counts as zero days and the chain is flagged. Nothing silently disappears.
   - B. Only items with both dates appear on the chart; the rest are listed. Simpler, but a chain through an undated item breaks.
   - C. Estimate missing durations from the item type's history. Clever, but invented numbers, against "deterministic numbers" until 3.4's estimates exist.

5. **How are sub-items shown and scheduled?**
   - A (recommended). An item with sub-items in view becomes a summary bar spanning them; it is not scheduled itself; a dependency on it applies to its sub-items (into all of them, out of its last-finishing one); its own planned dates show as an outline, flagged when its sub-items run past them. The usual way planners read a breakdown.
   - B. Every item, parent or not, is scheduled on its own dates; sub-items only shown indented. Simpler, but a parent can look on time while its children are late.
   - C. Show top-level items only. Fastest and cleanest; hides the breakdown.

6. **How do done, cancelled and started items count?**
   - A (recommended). Done items are fixed at the dates they actually started and finished; cancelled items, and the dependencies through them, are left out; unstarted items cannot start before today; started items cannot finish before today. The critical path reflects where the work really is.
   - B. Use only planned dates, whatever the status ("plan as entered"). Shows the original plan, but a late open item looks fine because its dates are in the past.

7. **Do milestone due dates act as deadlines?**
   - A (recommended). Yes: an item in a milestone must finish by the milestone's due date; items that cannot are marked "late by N days" and the critical path shows the chain that is most late. Uses data people already enter.
   - B. No deadlines: float is measured only against the latest finish in view. Simpler; a missed milestone is not flagged by the timeline.
   - C. As A, plus a new due date on each project as a deadline for all its items. More complete; a new field on projects and an amendment to ADR 0002.

**Working calendars**

8. **Where do working calendars live?**
   - A (recommended). One workspace calendar, and optionally one per team that replaces it for that team's items. Each has a time zone, working weekdays and holidays. Covers teams in different countries without a calendar per person (personal time off is roadmap 3.5).
   - B. One workspace calendar only. Simplest; a distributed workspace's teams share one set of holidays.
   - C. Per team only, no workspace default. Precise, but every new team must set one up.

9. **How are holidays entered?**
   - A (recommended). By hand, with "Copy last year's" (a person then fixes holidays whose date moves). No new dependency or data licence.
   - B. Country presets from the `date-holidays` package. Convenient; its data is licensed CC-BY-SA-4.0, which is not on the licence allowlist, so it needs an owner-approved exemption (ADR 0007).
   - C. Subscribe to a public holiday calendar feed by URL. Always current; a new outbound request to a URL a person types (a new server-side request forgery surface to guard) and a feed to keep healthy.

10. **Which time zone decides what "today" is for scheduling and for review steps?**
    - A (recommended). Each working calendar has a time zone, defaulting to the deployment's `NOTIFICATIONS_TZ`; the timeline and review steps opened after 3.1 take "today" from the item's calendar. The nightly jobs keep firing in `NOTIFICATIONS_TZ`. Correct for teams abroad; until anyone edits a calendar, nothing changes.
    - B. Keep `NOTIFICATIONS_TZ` everywhere until workspaces have their own time zone setting. One rule; a team twelve hours away sees "today" change at the wrong time.

11. **How do review steps (2.8) use working calendars?**
    - A (recommended). Steps opened after 3.1 count working days on the item's team calendar (else the workspace's); a due date already stored on a step never moves. ADR 0009's own text ("calendars replace the constant for steps opened after it").
    - B. Keep Monday to Friday for reviews. Simpler; reviews ignore holidays the rest of the product knows about.
    - C. Also recompute open steps' due dates when a calendar changes. Most accurate; due dates people were told about would move under them.

12. **Who manages working calendars?**
    - A (recommended). Admins (`admin.manage`), as teams, workflow states and work item types are; everyone who can see projects can read them. Consistent with the other workspace configuration.
    - B. Team calendars by anyone who manages cycles (`cycles.manage`; Members hold it). Teams self-serve; more people can change everyone's dates.
    - C. A new permission key for calendars. Finer control for custom roles; one more key everywhere.

**The timeline**

13. **When someone drags a bar and confirms, what changes?**
    - A (recommended). Only the dragged item. The confirmation shows which other items would now start later or become late, as warnings with links, but does not move them. Each change is one item and one audit entry; moving a whole chain is for a later bulk tool or an agent's proposal (7.5).
    - B. Offer "also move the N items it pushes later" in the same confirmation. Faster replanning; a bulk change of dates with its own checks and a larger undo story.
    - C. No confirmation when the move stays within the item's float. Fewer clicks; contradicts the roadmap's "a change the user confirms".

14. **Can people draw and remove dependencies on the timeline?**
    - A (recommended). Yes, through a confirmation ("ISL-1 blocks ISL-2?"); the server refuses a loop as it does today, and removal goes through the undo toast. Where planners expect to draw them.
    - B. No: dependencies are shown but edited only in the item's detail. Fewer ways to change the plan; slower to build one.

15. **How many items may one timeline show?**
    - A (recommended). 5,000 (the hardening budget's size). Above that the page shows the count and asks to narrow the filter; it never shows a cut-off list.
    - B. 10,000. Bigger scopes; the 5,000-item budget no longer covers the worst case, and the browser does twice the work.
    - C. No limit; page by project. Never refuses; a workspace-wide timeline becomes many charts.

16. **Where does the schedule get computed?**
    - A (recommended). On the server for every timeline read (one answer for everyone), and the same code in the browser to preview a drag's effects before the person confirms. Instant previews; one module to test.
    - B. Server only; previews ask the server. One place runs it; every drag preview is a round trip.
    - C. Browser only. Least server work; numbers in an export or an agent's proposal would need a second path.

17. **What counts as the critical path?**
    - A (recommended). The items with the least float in view (zero when everything fits, negative when a deadline is missed), and the links between them that leave no gap. The textbook definition, extended so it still shows something when the plan is already late.
    - B. Only items with zero or negative float. Same when the plan fits; when it is late, every late item lights up, not only the worst chain.
    - C. Items within N days of float (a "near-critical" setting). Shows what is almost critical; a setting to explain and tune.

**Notices, ADRs and delivery**

18. **The timeline library's MIT licence must travel with the code we send to browsers, and its files carry no licence banner. How do we ship the notice?**
    - A (recommended). Generate a third-party notices file from every production dependency at build time, ship it in both images and serve it at `/licences`. Covers this library and every other bundled package at once.
    - B. Add a section for this library alone to the repository's `NOTICE` file and serve that. Smallest change; the other bundled packages stay uncovered.
    - C. Rely on the licence files inside the installed packages on the server. No work; the browser bundle carries no notice.

19. **Which ADRs record 3.1?**
    - A (recommended). A new ADR 0010, "Scheduling and working calendars" (drafted in the map), plus short amendments: ADR 0002 §6 (blocks read as finish-to-start), ADR 0006 (the new words), ADR 0009 §13 (review working days from calendars). One place for the scheduling rules.
    - B. Fold the rules into ADR 0002 as a new section. Fewer documents; ADR 0002 grows a second subject.

20. **Which words?** A (recommended): "Working calendar" (`WorkingCalendar`), "Holiday" (`WorkingCalendarHoliday`), "Critical path", "Float" (with "Late by N days" when negative), "Earliest start", "Earliest finish", "Latest start", "Latest finish", and "Change dates" for the confirmation; never "Slack" (5.4's chat product), "Gantt" (already banned), "Proposal" (agents' word), "Time off" (3.5's). B: accept with changes the owner names.

21. **How is 3.1 delivered?**
    - A (recommended). Three pull requests: 3.1a the engine and working calendars (with 2.8's working days moved onto them), 3.1b the read-only timeline with the critical path, 3.1c changing dates and dependencies from the timeline. The engine is proved before any interface depends on it.
    - B. Two: 3.1a, then the timeline with editing in one. Fewer reviews; one very large interface pull request.

22. **The timeline library's chart cannot be used with a keyboard or a screen reader. What is the accessible way to use the timeline?**
    - A (recommended). A schedule table beside the chart (a "Chart / Table" toggle) with the same rows and numbers, whose dates are edited with the product's date pickers and go through the same confirmation. Everything the chart does by mouse can be done by keyboard; built from parts that already pass accessibility checks.
    - B. Build keyboard moving of bars into the chart itself (arrow keys move the focused bar a day). Closer to the board's model; deep changes over a third-party widget that does not expose its bars to assistive technology.
    - C. Both. Best experience; the cost of B on top of A.
