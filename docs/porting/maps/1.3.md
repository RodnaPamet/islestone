## Summary

- **What moves.** The Prisma 7 multi-file schema base (`prisma.config.ts`, `base.prisma`), five models (`Organization`, `OrgMembership`, `Tenant`, `TenantMembership`, `User`) and three enums (`Role`, `OrgRole`, `MembershipStatus`) cut out of `auth.prisma` (2,285 lines) and `enums.prisma` (2,477 lines, 170 enums). The RLS data path: `src/lib/prisma.ts` (primary + `prismaRead`), `src/lib/db-context.ts` (`runInTenantContext`, `runInTenantReadContext`, `runInTenantJobContext`, `withTenantDb`), `src/lib/db/rls-middleware.ts` (`runWithoutRls`, `TENANT_SCOPED_MODELS`, the tripwire), `audit-context.ts`, `concurrency-limits.ts`, `kek-bypass-sources.ts`. The request layer: `RequestContext`/`OrgContext` (`src/app-layer/types.ts`), `getTenantCtx`/`getOrgCtx` (`src/app-layer/context.ts`), their page-side twins `getTenantServerContext`/`resolveTenantBySlug` and `getOrgServerContext` (`src/lib/server/*.server.ts`, gate-free in 1.3), `resolveTenantContext` (`src/lib/tenant-context.ts`), and the tenant/org owner advisory-lock helpers.
- **What the database gets.** One fresh migration: tables, `app_user` role grants, Class-A RLS on `TenantMembership`, the org-axis RLS on `Organization`/`OrgMembership`, and the final (serialised, purge-exempt) bodies of both last-owner triggers. No source migration is replayed.
- **What is cut.** Everything compliance on `Tenant` (ISMS scope fields, currency, risk scale, readiness weights, region, the ~230 back-relations), on `User` (~95 back-relations), on `Organization` (agent switches/turn caps, widgets, threat levels, initiatives), `TenantMembership.lineOfDefence` and `accessReviewDecisions`. The audit, soft-delete, field-encryption and PII Prisma extensions are cut from `prisma.ts` and belong to 1.5. Every SSO/Entra/MFA/API-key/agent gate in `getTenantCtx` is cut and belongs to 1.4, 5.2 or 6.x.
- **What is stubbed.** `PermissionSet`/`getPermissionsForRole` (1.4 rewrites `src/lib/permissions.ts`), `getSessionOrThrow` (1.4 ports NextAuth). The logger and request-context store are pulled forward from 1.6 because `rls-middleware.ts` and `prisma.ts` need them.
- **Tests.** The RLS coverage guardrail, the tenant-isolation structural test and the no-direct-prisma allowlist test come over with emptied allowlists and planted-fixture proofs; the two owner-race suites keep only their trigger halves (the tenant one with its `twoOwners()` helper rewritten off the cut `createTenantWithOwner`); the org last-owner trigger cases are extracted from `org-owner-writers`; the RLS integration suite is rewritten against `TenantMembership`; the error-type, pool-limit and enum-in-Postgres suites come too. A new schema vocabulary guard (ADR 0006) is written. A new Jest `integration` project and a test-database helper are required.
- **Size.** About 3,150 source lines land in `src/` after cuts (from about 5,000 read), about 180 schema lines, a hand-written migration of about 270 SQL lines, and about 4,300 test and helper lines.
- **Prerequisites.** ADR 0001 must record the BUSL-1.1 grant before any file is copied (Islestone's `CLAUDE.md` and `PROVENANCE.md` still say "copy no code"; ADR 0001 is still "Proposed"). ADR 0006 must be signed for W1 (`Tenant`/`tenantId` in code) and M1/M2 (the `Role` enum's values), because the migration fixes both.

### Migration — write fresh

Islestone starts with a fresh history, and replaying the source's 443 migrations (`ls -d prisma/migrations/*/`) would recreate the compliance schema. Write one migration, `prisma/migrations/<timestamp>_tenancy_core/migration.sql`. Generate it with `prisma migrate dev --create-only`, then append hand-written SQL in this order:

1. **Enums, tables, indexes and FKs** as generated.
2. **The role and grants.** Taken from `20260323180000_apply_full_rls_setup` L21–36, minus its `GRANT app_user TO postgres`:
   ```sql
   DO $$ BEGIN IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'app_user') THEN CREATE ROLE app_user NOLOGIN; END IF; END $$;
   GRANT USAGE ON SCHEMA public TO app_user;
   GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_user;
   GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_user;
   ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;
   ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT USAGE, SELECT ON SEQUENCES TO app_user;
   ```
   **Then grant every table this migration creates explicitly**, after step 1's DDL:
   ```sql
   GRANT SELECT, INSERT, UPDATE, DELETE ON "Organization", "OrgMembership", "Tenant", "TenantMembership", "User" TO app_user;
   ```
   `ALTER DEFAULT PRIVILEGES` applies only to tables later created by the role that ran it. The source says so itself (`20260422180000_enable_rls_coverage` L526–535) and re-grants table by table for that reason, as `docs/rls-tenant-isolation.md`'s recipe does (L116). Once 1.8 runs migrations as a separate migrator role, a table created without its own `GRANT` is invisible to `app_user`, and nothing in the RLS guardrail notices. So every later migration that creates a table carries its own `GRANT … TO app_user`, and the DB half of `rls-coverage` asserts it (see "Tests to bring").
   Grant `app_user` to the login role outside the migration, in `prisma/init-roles.sh` and the CI step. The source CI does `GRANT app_user TO ci` at `ci.yml` L733–743.
3. **Class-A RLS on `TenantMembership`**, the canonical shape from `20260323180000` L331–338 plus `20260323182100` L112–113. The shape is documented in `docs/rls-tenant-isolation.md` "Adding a new tenant-scoped table":
   ```sql
   ALTER TABLE "TenantMembership" ENABLE ROW LEVEL SECURITY;
   ALTER TABLE "TenantMembership" FORCE ROW LEVEL SECURITY;
   CREATE POLICY tenant_isolation ON "TenantMembership" USING ("tenantId" = current_setting('app.tenant_id', true)::text);
   CREATE POLICY tenant_isolation_insert ON "TenantMembership" FOR INSERT WITH CHECK ("tenantId" = current_setting('app.tenant_id', true)::text);
   CREATE POLICY superuser_bypass ON "TenantMembership" USING (current_setting('role') != 'app_user');
   ```
   `superuser_bypass` must stay keyed on the role alone, with no `WITH CHECK`. The guardrail asserts the exact normalised text `(current_setting('role'::text) <> 'app_user'::text)` (#5314).
4. **Org-axis RLS**, copied from `20260426060000_add_organization_layer_rls` L60–103 (103 lines; COPY the SQL, it is not compliance): `org_isolation` on `Organization` (EXISTS own `OrgMembership` keyed on `app.user_id`), `org_membership_self_isolation` on `OrgMembership` (`"userId" = current_setting('app.user_id', true)`), `superuser_bypass` on both, and ENABLE + FORCE.
   - Note that the source never sets `app.user_id`; `grep -rn "app.user_id" src` finds only a comment. So under `app_user` both tables return zero rows, which fails closed, and every org path uses the global client.
   - Keep that behaviour in 1.3 and record it. Setting `app.user_id` inside `runInTenantContext` is a separate decision.
5. **`Tenant` and `User` get no RLS**, as in the source ("GLOBAL TABLES — no RLS needed", end of `20260323180000`). Because of the grant in step 2, a query on the transaction client inside `runInTenantContext` can read every `User` row in the deployment. Record this as an H1 question (RLS `User` by shared membership, or revoke `app_user` SELECT on `User`), not a 1.3 change.
6. **Tenant last-owner trigger.** Write the FINAL body once: `check_not_last_owner()` from `20261112160000_tenant_owner_guard_serialised` L37–86. That body includes the soft-deleted-tenant exemption (#2747, from `20260922200000_last_owner_guard_allows_purge`) and the `pg_advisory_xact_lock(hashtext('tenant-owner:' || tenantId))` taken before the count (#5388). Add the trigger from `20260424220000_epic1_last_owner_trigger` L48–51: `CREATE TRIGGER tenant_membership_last_owner_guard BEFORE UPDATE OR DELETE ON "TenantMembership" FOR EACH ROW EXECUTE FUNCTION check_not_last_owner();`. Keep the function VOLATILE (the default): its COUNT reads a fresh snapshot only because it runs after the lock. The role literal `'OWNER'` must match the new `Role` enum.
7. **Org last-owner trigger.** The final `check_not_last_org_owner()` from `20261112130500_org_owner_guard_serialised` L32–67 takes the lock `org-owner:<organizationId>` and exempts the organization's own cascade. Add the trigger from `20261030160000_org_owner_backfill_and_guard` L76–79: `CREATE TRIGGER org_membership_last_owner_guard BEFORE UPDATE OR DELETE ON "OrgMembership" FOR EACH ROW EXECUTE FUNCTION check_not_last_org_owner();`. SKIP that migration's backfill `UPDATE` (L19–30); a fresh database has no ORG_ADMIN rows to promote.
8. **How the triggers read under RLS (record this in the migration comment).** Neither function is `SECURITY DEFINER` (both end `$$ LANGUAGE plpgsql;`), so their reads run as the writer and are RLS-filtered when the writer is `app_user`.
   - **Tenant trigger: correct under `app_user`.** Inside `runInTenantContext` the only `TenantMembership` rows a writer can touch are those of `app.tenant_id`, and the trigger counts rows of that same tenant, so the filter hides nothing it needs. Its `Tenant.deletedAt` check reads a table with no RLS.
   - **Org trigger: correct only on the owning role.** Under `app_user`, `check_not_last_org_owner`'s `NOT EXISTS (SELECT 1 FROM "Organization" …)` goes through `org_isolation` (keyed on `app.user_id`). With `app.user_id` unset the organization reads as gone, so the delete is treated as the organization's own cascade and let through. Today that cannot happen, because the same unset `app.user_id` hides every `OrgMembership` row from the writer, so there is nothing to delete. With `app.user_id` set, the `COUNT` sees only the caller's own `OrgMembership` rows, so a second owner is invisible and a legitimate demotion is refused.
   - **So in 1.3 every org-membership write stays on the owning role** (the global client or `runWithoutRls`), as in the source. Whoever later sets `app.user_id` must first fix the function: make it `SECURITY DEFINER` with `SET search_path = public`, owned by a role that bypasses RLS (FORCE applies to a plain table owner, and `superuser_bypass` reads the `role` GUC, which `SECURITY DEFINER` does not change), or give the trigger its own policy. Add a test then, not now.

- **Empty populations break Jest, or pass vacuously.** `it.each([])` throws, and a `describe` whose loop yields no `it` fails the file with "Your test suite must contain at least one test". In 1.3 that hits `database-routing-coverage` (`ROUTED_USECASES = []`) and section 4 of `tenant-isolation-structural` (no `src/app/t`). `no-direct-prisma` does not go empty (its usecase and route loops find the two lock helpers and the `livez`/`readyz` routes), but its repository loop does, and every test it does generate passes trivially. The planted-fixture proof on every guard (see "Tests to bring") covers all three.
- **The import cycle.** `prisma.ts` imports `withRlsTripwireExtension` from `rls-middleware.ts`. `rls-middleware.ts` imports `* as prismaModule from '@/lib/prisma'` and re-exports `db-context.ts`, which imports `{ prisma, prismaRead } from './prisma'`. It works only because every dereference happens inside a function (source comments at rls-middleware L60–70 and prisma.ts L503–512). Keep the namespace import. Never destructure `prisma` at module top level in any of the three files, and never convert `rls-middleware`'s lookup to a top-level `const p = prisma`. The source also reports that Turbopack returned `undefined` for a dynamic `require('./db/rls-middleware')`, which is why the import is static.
- **Two database URLs in tests.** `@/lib/prisma` builds its client from `env.DATABASE_URL` at import, and `prismaTestClient()` resolves its own URL. If they differ, suites that go through `runInTenantContext` fail with a bare `PrismaClientKnownRequestError` while direct-client suites pass (source `resolve-test-database-url.js`, #5567). The integration project's setup must set `DATABASE_URL` to the test URL first.
- **Superuser connections bypass RLS entirely.** Islestone's dev `POSTGRES_USER=islestone` is a superuser. Inside `runInTenantContext`, `SET LOCAL ROLE app_user` drops that, so the isolation tests are valid. But any query outside a tenant context runs unfiltered even on FORCE tables. Production (1.8) must connect as a non-superuser, non-`BYPASSRLS` role that is a member of `app_user`, or `SET ROLE` fails. The H1 test "as the application database role" should assert `current_user = 'app_user'` inside the callback.
- **Do not port `GRANT app_user TO postgres`.** It is why the source needed a placeholder `postgres` role in `init-roles.sh` and CI. Name no login role in a migration.
- **Keep both trigger functions VOLATILE**, and the lock keys byte-equal between SQL and TypeScript (`tenant-owner:` / `org-owner:` + id). Do not reuse the bare `hashtext(tenantId)` key: the 1.5 audit chain takes it, and the two would contend.
- **Teardown versus the last-owner trigger.** `deleteMany` on memberships is refused for a live tenant's last OWNER. Use `TRUNCATE` (no row triggers) or soft-delete the tenant first. `TenantMembership.tenant` has no `onDelete` (`auth.prisma`, `TenantMembership` L47), so deleting a `Tenant` with memberships fails on the FK even before the trigger.
- **The triggers read through RLS.** Neither trigger function is `SECURITY DEFINER`. The tenant guard is correct under `app_user`; the org guard is correct only on the owning role (migration step 8). Setting `app.user_id` anywhere, which the org-axis policies are written for, breaks the org guard in both directions unless the function changes first.
- **Default privileges do not grant future tables to `app_user` for every role.** They cover only tables created by the role that ran `ALTER DEFAULT PRIVILEGES`. Every migration grants its own tables; the RLS coverage suite checks it.
- **The Prisma CLI does not read `.env.local` by itself.** Without `loadEnvConfig` in `prisma.config.ts`, `npm run db:migrate` locally gets an empty URL (the `?? ''` fallback) and fails with a connection error that does not name the cause. CI exports its variables and is unaffected.
- **`next start` validates env.** Once `DATABASE_URL` is required, any job that starts the built app needs a well-formed URL or `SKIP_ENV_VALIDATION`; only the E2E job is affected today.
- **Compose port syntax.** Islestone publishes ports as `'127.0.0.1:${PGBOUNCER_PORT:-6432}:5432'`. The source's `hostPorts()` splits on `:` and reads `'-6432}'` as the host port (`NaN`). Any ported test that parses compose ports must expand `${VAR:-default}` first.
- **No `fail()` in Jest 30.** jest-circus does not define it; `membership-identity`'s three calls must become `expect(...).toEqual([])`.
- **Islestone compiler and lint settings are stricter than the source's.**
  - `noUncheckedIndexedAccess` affects array destructuring in `extractCallerFingerprint`, the regex match groups in `prisma.ts`, and test helpers indexing arrays.
  - `consistent-type-imports` at error affects `db-context.ts` L1 and the `PrismaClient`/`Role` imports across tests.
  - `no-explicit-any` (typescript-eslint `recommended`, on for tests too through `eslint-config-next/typescript`, and set to error in `src/`) affects `prismaTestClient(): any` and the `eslint-disable` `any`s in `rls-coverage`.
  - `no-console` is set only for `src/` in Islestone's config, so `migrateTestDb`'s `console.warn` and the connection-pooling test's `console` calls pass lint; remove the latter anyway with its silent skip.
  - `strict` + `noUncheckedIndexedAccess` with `tsconfig.json` including `tests/`: compiling copies of the 1.3 files against Islestone's `@types` (scratch directory, `_tools/tc13` and `tc13b`) found errors in `source-blocks.ts` (18), `prisma-schema-models.ts` (19), `prisma-enum-order.ts` (17), `membership-identity` (17), `observability-logger` (21), `schema-index-coverage` (6), `connection-pooling` guard (2), `prisma-enum-values-exist-in-pg` (3), `tenant-job-context` (2), `audit-concurrency-limits` (1 in the kept half) and `rls-middleware.ts` (L192).   - No raw `process.env` in `src/` affects `logger.ts` L71–72.
- **`Role` values are a one-way door.** The enum created here is what the last-owner trigger compares against (`'OWNER'`). Removing or reordering a value later is a breaking migration, and adding one must sit alone in its migration (`migration-enum-isolation`). Settle ADR 0006 M1/M2 and 1.4's role list before this migration is applied anywhere shared.

If 1.3 copies the source shape instead, it needs `hashForLookup` and `LOOKUP_HASH_KEY` early, which is 1.5's key hierarchy. Either way, no `@map`.
