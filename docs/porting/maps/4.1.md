## Summary

- **Most of the architecture is already decided.** ADR 0005 (Accepted, 2026-11-19) fixed it: a page's stored Yjs state is the source of truth for its body (§6.4); the collaboration server is its own Node process (§6.1) and the only writer of that state and its projections (§6.6); every connection carries a signed, 60-second collaboration token and is re-checked on every refresh (§6.2); references to work items store the id and nothing else (§6.3); content from a client is untrusted (§6.7); state and snapshots are encrypted under the workspace key (§6.8); page comments are `Comment` rows anchored by a Yjs relative position (§6.10); one audit entry per person per page per 10 minutes (§6.11); agents never connect (§6.12). ADR 0006 already reserves `Page`, `PageContent` and "Projection", and bans "Doc, Document, Wiki, Note, Article" for a page. This map builds on all of it and asks only what is still open.
- **Six things to build.** (1) A page tree per project and one for the workspace, ordered by fractional index, moved, soft-deleted in groups, restored and purged like work items. (2) The editor: Tiptap 3 (MIT) with a schema module shared by browser and server, a slash menu written in-house on `@tiptap/suggestion` (MIT), people and work-item mentions, work-item embeds, page links. (3) The collaboration server: Hocuspocus 4 (MIT) as a new `collab` service from the worker image, its token, its re-checks, its store path (encryption, projections, audit), its caps, and a route through Caddy. (4) Comments on pages on the existing `Comment` table: anchored, with one level of replies and a resolved state. (5) Versions: saved and automatic, viewed, compared and restored as a forward change. (6) Search over pages, if the owner amends ADR 0008 (question 10).
- **Three tensions the owner must settle.** Pages are encrypted at rest (decided), and searching their words means storing a readable derivative, as ADR 0008 did for descriptions and comments (question 10). The stack's six long-running services already use exactly its 4 GB ceiling (`tests/unit/deploy/compose-prod.test.ts`), so the collaboration server needs memory from somewhere (question 20). The `Comment` table is welded to work items (a NOT NULL `workItemId`, a three-column unique key the answer and mention keys point at, the search seam), so "the existing comment model" is a real migration (question 18).
- **What is taken.** From inflect-compliance: its Tiptap editor (`src/components/ui/RichTextEditor.tsx`, 462 lines: the StarterKit configuration, the hardened link, the placeholder, the accessible editor surface, the toolbar, the lazy-load posture), its 16 `richtext` copy keys and its rendered test, copied and adapted; its version diff (`src/components/ui/VersionDiff.tsx`, 284 lines, over jsdiff), copied and adapted. inflect has no Yjs, Hocuspocus, slash-menu, mention or comment-anchor code (ADR 0005, "What inflect-compliance has built"; its `package.json` lines 138 to 142 hold only five Tiptap packages). Everything else is written fresh. No inspiration-only project (Docmost, AppFlowy, Outline, Plane) was read.
- **Licences.** Every package proposed is MIT, apart from `diff` (BSD-3-Clause), both on the allowlist. Tiptap's paid "Pro" extensions (snapshots, snapshot compare, comments, AI, document export and import) are not on the public registry (a 404 for `@tiptap-pro/*`, 2026-11-27) and are not used: comments, versions and export are built in-house, as roadmap §2.3 says. One trap: `@hocuspocus/extension-redis` 4.8.0 and 4.9.0 depend on `@sesamecare-oss/redlock` 1.4.0, whose `package.json` declares `UNLICENSED` while its tarball ships an MIT `LICENSE.md`; the licence gate refuses `UNLICENSED`. One collaboration server needs no Redis extension (question 22).
- **A new permission domain name.** `src/lib/permissions.ts` already holds a `docs` domain (`view`, `create`, `edit`), unused by any route. "Doc" is a banned word for a page, and a permission key is customer-facing (ADR 0006 rule 2), so the domain becomes `pages` with `comment` and `delete` added (question 2).

## What makes the prompt harder than it reads

- **"On the existing comment model."** `Comment.workItemId` is NOT NULL; `Comment` carries `@@unique([id, workItemId, tenantId])` because `WorkItem.answerCommentId` and `Mention.commentId` point at it through that triple; `SearchVector.workItemId` is NOT NULL; and every comment read is by work item. A comment on a page needs a second, mutually exclusive parent, a second unique triple, second keys from `Mention`, and a search row of its own. ADR 0002's sketch already says "roadmap 4.1 adds pageId; a CHECK then requires exactly one parent" (ADR 0002 §12); the cost is in the ripple.
- **A CRDT has no author per write.** Decision 129 records a mention only for "a person's own write". The collaboration server sees merged binary updates from several connections, not form submits. Attributing a mention to the person who typed it needs the Yjs client id of the inserting update mapped to the connection that sent it, and a refusal of updates that claim another connection's client id (below).
- **"Checks … on every connection"** is the easy half. H4 wants a person who loses access disconnected while connected, and ADR 0005 §4 puts the `access` notice on 4.3's Redis channel. 4.1 needs some of 4.3's channel now (question 23).
- **Binary state, encrypted, searchable.** The encryption extension handles strings only (`encryptValue`, `encryption-middleware.ts` lines 250 to 253), so Yjs bytes must become text or the extension must learn bytes (question 9). Searching what is encrypted repeats ADR 0008's trade-off (question 10).
- **History in a garbage-collected CRDT.** A Yjs document with garbage collection on cannot be rewound. A "version" is therefore a stored copy, and a restore is a new change applied on top of the live document, never a rewind (question 11).
- **The memory budget is spent.** Postgres 1,536 MB, PgBouncer 128, Redis 512, the app 1,024, the worker 768, Watchtower 128: 4,096 MB, the ceiling the compose test holds.
- **Sanitising a CRDT.** The server never receives HTML from a client; it receives Yjs structures any client can forge, including a link mark with a `javascript:` URL or an element the schema does not know. Sanitisation happens when projections are built and again at export, and the browser's schema must refuse a dangerous URL when it renders another client's content.
- **Restarts drop every socket.** Watchtower replaces containers on each release. The client reconnects and Yjs resends what was not acknowledged; the server must flush pending stores on shutdown inside the grace period.
- **The words.** The sub-phase is called "Documents", but "Document" and "Doc" are banned for a page in UI text and identifiers, "Space" is banned for workspace and project, "History" and "Thread" are banned in every schema identifier (the schema guard enforces both strictly), and "Draft" is a proposal's word. Hocuspocus's own API says "document"; that stays inside the adapter (ADR 0006 rule 5).

```prisma
  deletedByUserId String?
  deletionId      String?
  createdAt       DateTime  @default(now())
  updatedAt       DateTime  @updatedAt

  @@unique([id, tenantId])
  @@unique([id, projectId, tenantId])   // target for comments and mentions that must match a page
  @@index([tenantId, projectId, parentId, sortKey])
  @@index([tenantId, deletionId])
}
```

- **Two kinds of tree, one table** (question 4). A project's tree (`projectId` set) and the workspace's (`projectId` NULL). The tree read is children of one parent in one scope, in `sortKey` order, through two partial indexes written in SQL (`… WHERE "deletedAt" IS NULL AND "projectId" IS NOT NULL` leading `tenantId, projectId, parentId, sortKey`, and the workspace twin), with a catalogue test; Prisma cannot declare either.
- **Same scope, always.** A page's parent is in its own scope: the usecase checks it under the tree lock and a trigger refuses a row whose parent's `projectId` differs (a composite key cannot carry a nullable scope column). The parent key is `(parentId, tenantId)` → `Page(id, tenantId)`, `DEFERRABLE INITIALLY DEFERRED` like the work-item parent link, so a subtree move is one transaction.
- **Depth at most ten** (question 4), counted by a depth-capped, path-guarded recursive query (the pattern of `WorkItemRepository.ancestry`); a move into its own subtree is `PAGE_WOULD_CYCLE`, past the cap `PAGE_TOO_DEEP`. Every write that changes `parentId` or `projectId`, every delete and restore and every purge page takes `lockPageTree(tenantId)` FIRST (a transaction advisory lock, `page-tree:<tenantId>`), then the page rows in id order (the multi-row rule of decision 173).
- **Waiting a turn.** Tree writes that take `lockPageTree` wait their workspace's turn in the process first, through the one queue implementation (`write-queue.ts`, the pattern of `inWorkItemGraphQueue`, decision 254), so a burst of moves does not hold PgBouncer's connections while it waits.
- **Rows that name a member** (`PageWatcher`, page `Mention` rows) follow CLAUDE.md's "A row that names a member": the people are read `FOR KEY SHARE` through `MembershipRepository.lockActiveUserIds` after the page, a removed person named on purpose is a 400 and one a write brings along is skipped.
- **Order** is `sortKey` from `keyBetween` ("after X, before Y", computed by the server), compared with `<`; the rebalance job learns pages (below). A `sortKey` write does not bump `version`.
- **Moves.** Within a scope: a new parent and a place. Across scopes (a project to the workspace, the workspace to a project, one project to another; question 4): the page and its live subtree move together, each row's `projectId` rewritten in one transaction; comments, versions and mentions follow the page id. Moving into an archived or deleted project is refused (`PROJECT_ARCHIVED`, 404).
- **Visibility** (question 5). A project page is readable exactly when its project is visible (`visibleProjects`, so today every role but Guest) and live; a workspace page by every holder of `pages.view`. An archived project's pages are readable and read-only (writes 409 `PROJECT_ARCHIVED`, connections read-only). No page is narrower than its scope in 4.1: private pages and per-page sharing wait for 8.4's grants.
- **Title** (question 6). A row field, plaintext like a work item's title: it is shown in the tree, the breadcrumb, notifications and search results, none of which should open the document. Renaming is a versioned write (`If-Match` required, 428 without it, 409 `VERSION_CONFLICT` with the current row), audited `PAGE_RENAMED` with the old and new title (titles are plaintext and already audited this way for work items). The editor shows the title as a separate field above the body.
- **Delete, restore, purge** (question 7). Delete soft-deletes the page and its live subtree under one `deletionId` (`PAGE_DELETED`), closes every open connection to those pages, and goes through the undo toast; restore brings the group back through its root only (`DELETED_WITH_PARENT`), under a live parent (`PARENT_DELETED`) in a live scope; a restored row whose `sortKey` collides is re-placed (`planRestoredSortKeys`). The nightly `page-purge` hard-deletes groups deleted more than `PAGE_PURGE_DAYS` (30) ago; content, versions, comments, mentions, watchers and search rows cascade. Deleting a project hides its pages with it, and its purge cascades them. No archive for pages (an archived project archives its pages' writes).
- **Creating a page** writes the row and an empty `PageContent` row in one transaction (`PAGE_CREATED`); the first store fills it. A create names a scope, an optional parent and a place, and a title (default "Untitled").

### Page content: the state and its projections (question 8)

```prisma
model PageContent {
  pageId        String   @id
  tenantId      String
  state         String?  // the encoded Yjs state, base64, then encrypted (manifest) (question 9)
  contentJson   String?  // the ProseMirror JSON projection, schema-validated, encrypted (manifest)
  plainText     String?  // the text projection, encrypted (manifest)
  schemaRevision Int     // PAGE_SCHEMA_REVISION the projections were built with
  stateBytes    Int      // the decoded state's size, for the cap and the dashboards of H4
  updatedAt     DateTime @updatedAt
  // (pageId, tenantId) → Page ON DELETE CASCADE
}
```

- **The stored Yjs state is the source of truth** (ADR 0005 §6.4, decided). Written only by the collaboration server's store path (§6.6); the guard ADR 0005 §8 asks for lists that one writer.
- **The projections written on each store** (question 8): `contentJson` (what agents, export, the version diff and the print view read), `plainText` (for search, if question 10 allows, and for 6.5), and the `PageItemMention` and `Mention` rows (4.1c). **Recommended departure from ADR 0005 §6.4:** sanitised HTML is not stored; it is rendered from `contentJson` with `@tiptap/static-renderer` and passed through `sanitizeRichTextHtml` at each export or email, so there is one fewer encrypted copy and the sanitiser's current allowlist always applies (H4's "sanitised on the server before any export or email" holds at the point of use).
- **Validation.** Projections are built by decoding the state through `@tiptap/y-tiptap` into a ProseMirror document over the shared schema (`src/lib/pages/schema.ts`, below); nodes, marks and attributes the schema does not know are dropped and counted in the store's log line (never their content); a link mark whose URL fails the sanitiser's schemes (`http`, `https`, `mailto`, `tel`) is dropped. Whether `y-tiptap`'s converter throws or skips on an unknown element is verified in 4.1b; either way the store records the drop and never stores an unvalidated projection.
- **Schema changes.** `PAGE_SCHEMA_REVISION` (beside the schema) is bumped by any change to the node set; the `page-projection-rebuild` job re-projects rows at an older revision, and a node rename ships a tested transform of stored states (ADR 0005, "Consequences").

### Encryption (question 9)

- **State, `contentJson`, `plainText` and every `PageVersion.contentJson` are in the encryption manifest** (ADR 0005 §6.8 and open question 6, decided). Titles are plaintext (above). Comment bodies stay encrypted as today.
- **Bytes as text** (question 9, recommended A): the encoded state is base64-encoded and stored in a `String` column, so the existing extension encrypts it unchanged and the key-rotation sweeps (`key-rotation`, `tenant-dek-rotation`) re-wrap it like any manifest field. The cost is size (base64 of the ciphertext of base64: about 1.8 times the raw state) and one large value per page for the sweeps to page through. Teaching the extension a `Bytes` path touches the encryption middleware, both sweeps and the manifest guard, which scans `String` columns only.
- **Write-once rows admit the re-wrap.** `PageVersion` is write-once by trigger; the trigger admits the sweeps' rewrite of `contentJson` from ciphertext to `v2:` ciphertext with every other column unchanged (CLAUDE.md, "Key rotation (1.5b)"), as the review rows' trigger does.
- **In flight.** The state crosses the WebSocket as Yjs updates under TLS from the browser to Caddy, and in clear on the private Docker network from Caddy to the collaboration server, as every API request does today. With one collaboration server no update crosses Redis (question 22).

### Search (question 10; an ADR 0008 amendment either way)

ADR 0008 excludes pages until an amendment ("Pages' plain-text projection … needs its own amendment to this ADR before it is built"). The options, with what each stores:

| | What is searched | What becomes readable outside the application | Cost |
|---|---|---|---|
| **A (recommended)** | Page titles; page bodies; page comments | Titles (already plaintext); the stemmed words of every page body and page comment, in every dump and off-host backup, as for descriptions and comments (decision 124) | A `PageSearchVector` table (`tenantId`, `pageId`, nullable `commentId`, `lexemes`, configuration, revision, `updatedAt`), written in the store's transaction from `plainText` and by the page-comment usecases, through one seam; two new search functions (`search_page_titles`, `search_page_contents`) on the decision-245 pattern with page visibility inside, bounded like decision 250; the palette's "Pages" group; the rebuild learns pages |
| B | Page titles only | Nothing new (titles are plaintext) | An expression index and one search function; bodies are found only by opening pages |
| C | Titles; bodies by keyed word tokens (ADR 0008's option A, never built) | Nothing readable; token frequencies | A second search mechanism beside `islestone_bg_en`: whole words, no stemming, no phrases |
| D | Nothing | Nothing | Pages cannot be found from the palette |

A separate `PageSearchVector`, rather than widening `SearchVector` to two parents, keeps the pinned, plan-checked item functions (`search_item_contents` and its hashes) untouched. A page found in search opens at the top; snippets are built from the decrypted `plainText` under the same visibility, never stored (ADR 0008's rule). The 6.5 embeddings over pages need a further amendment.

### Versions (questions 11 to 13; 4.1e)

```prisma
model PageVersion {
  id            String   @id @default(cuid())
  tenantId      String
  pageId        String
  number        Int                       // per page, from 1; @@unique([pageId, number])
  origin        PageVersionOrigin         // AUTOMATIC, SAVED, BEFORE_RESTORE
  name          String?                   // a saved version's name, plaintext, at most 120
  contentJson   String                    // encrypted (manifest)
  schemaRevision Int
  createdByUserId String?                 // the saver or restorer; NULL for AUTOMATIC
  contributorIds String[]                 // who edited since the previous version
  createdAt     DateTime @default(now())
}
```

- **What a version holds** (question 11, recommended A): the page's `contentJson` at that moment, not a Yjs state. Viewing, comparing and restoring all need the ProseMirror document; a state with garbage collection on records no history that a person could use. **This departs from ADR 0005 §6.9's "full encoded snapshots"**, which the amendment records.
- **When one is made** (question 12): automatically when an editing session on the page goes quiet (no store for 10 minutes, the audit window of ADR 0005 §6.11) and at most once an hour while editing continues; when a person chooses "Save version" with an optional name; and before every restore (`BEFORE_RESTORE`). Identical content makes no automatic version.
- **How long** (question 12): saved and before-restore versions are kept for the page's life; automatic ones are thinned by `page-version-compaction`: every one for 7 days, then the last of each day for 90 days, then the last of each week. 8.3's retention table may later set limits; until then nothing else deletes a version.
- **Restore** is a forward change: the server records a `BEFORE_RESTORE` version, then replaces the live document's content with the version's through the direct connection (question 24), so live editors see it at once and the next store keeps it. Audited `PAGE_VERSION_RESTORED`. The version list and each version's content are read under `pages.view`; save and restore take `pages.edit`.
- **Compare** (question 13): a block-level diff of two versions' Markdown projections (the same serializer as export) with jsdiff, in the copied `VersionDiff`; "Compare with current" diffs against the latest store.

## The editor (4.1b, 4.1c)

### One schema, browser and server

- `src/lib/pages/schema.ts` (client-safe, no React) exports the extension list and `PAGE_SCHEMA_REVISION`. The editor adds the React-only pieces (node views, popups) on top; the collaboration server builds its ProseMirror schema from the same list (`getSchema`), so a node the browser can write is a node the server can project, and nothing else is.
- The editor is loaded with `next/dynamic({ ssr: false })` behind an error boundary (inflect's posture), at `src/components/pages/editor/`; it is never given `content`: the Collaboration extension binds it to the provider's `Y.Doc`, and `immediatelyRender: false`.
- The link extension is configured with Islestone's schemes through `isAllowedUri` (http, https, mailto, tel: the sanitiser's set), so a link another client wrote with another scheme is neither rendered nor followed.

### Blocks and the slash menu (questions 14 and 15)

- **Blocks** (question 14, recommended A): paragraphs; headings 1 to 3; bullet and numbered lists; quote; code block (plain, no highlighting); divider; table (`@tiptap/extension-table`); hard break; marks bold, italic, strike, inline code, link. Islestone's nodes: person mention, work-item mention, work-item embed, page link. Not in 4.1: images and files (4.4 adds them with uploads), external embeds (`frame-src` is not opened), callouts, toggles, mathematics, emoji, a table of contents.
- **The slash menu**, in-house on `@tiptap/suggestion`: `/` at a line start or after a space opens a filtered list of the blocks above plus "Work item" (search and embed), "Mention work item", "Link to page", "Mention person" and "Create work item" (question 15). Keyboard: arrows, Enter, Escape, by the editor's own key handling (no window listener; `useKeyboardShortcut` stays for the shell's shortcuts). Every label is a `pages.editor.slash.*` key.
- **To-dos and principle 3** (question 15, recommended A): no checkbox list block. "Create work item" turns the current line or selection into a new work item in a chosen project (the normal create dialog, prefilled with the text as the title, through `useWorkItemMutations`) and replaces the text with its chip; an untracked to-do would be a second kind of tracked work.

### Work-item mentions and embeds (question 16; 4.1c)

- **Stored as the id only** (ADR 0005 §6.3, decided): `workItemMention { id }` inline, `workItemEmbed { id }` as a block. Typing a known key (`ISL-123`, decision 131's grammar) and a space turns it into a chip; the slash menu's "Work item" searches through `/api/t/:slug/search`.
- **Rendered under visibility.** `GET /api/t/:slug/work-items/refs?ids=` (`work_items.view`, at most 100 ids, one statement over `WorkItem` with `deletedAt` and `projectVisibilityWhere`) answers each id with the chip's fields (key, title, state and its category, assignee id, due date, review mark) or `{ id, access: 'none' }`, the same for a missing, deleted or invisible item (a reader learns nothing from the difference). The chip shows "No access" for those. The read registers with `work-item-cache.ts`, so an item written in this tab updates its chips; other tabs refresh on focus until 4.3's change notices.
- **"Mentioned in pages"** (question 16): on each store the server writes `PageItemMention(tenantId, pageId, workItemId, firstSeenAt)` for the ids the page names, removing the ones it dropped; the item detail lists the pages the caller can read that mention it (`GET /work-items/:id/pages`, `work_items.view`, the page visibility applied, at most 50). Nothing is notified when an item is mentioned in a page.
- **Linking a page from an item** (question 16): "Link a page" on the item's Links panel writes a `WorkItemLink` with type `PAGE` and the page id as its location, rendered as the page's current title, or "No access", under page visibility; ADR 0006's Link row already names pages.

### Person mentions (question 17; 4.1c)

- **In page bodies**: `personMention { id }`, chosen with `@` from `GET /users/assignable` (2.7d's picker, as a Tiptap suggestion). A chip shows the person's current name; the node never stores the name.
- **Recorded on store, as the person who typed it** (decision 129). The collaboration server keeps, per document, the Yjs client ids each connection has used: a client id is claimed by the first connection whose update carries it, and an update carrying a client id another person claimed is refused and its connection closed (so nobody can write as someone else). On store, each mention node new since the last store is attributed to the person whose client id inserted it; `recordMentionsInTx` is generalised to a page source and records a `Mention` row (`pageId` set, `commentId` NULL) for each new person who is an ACTIVE member with `pages.view` and may read the page (`mentionableAmong`'s rules); the rest render as a plain name-less chip ("Unknown person") and notify nobody. Mention nodes removed since the last store delete their rows.
- **Effects** as in 2.7d: the mentioned person becomes a page watcher, gets a `PAGE_MENTIONED` bell and, by preference, an immediate email naming who and which page and linking to it, never the text (decision 130). Audited `PAGE_MENTIONED` with ids.
- **In page comments**: decision 127's `<@userId>` tokens and the comment usecases' existing `recordMentionsInTx` path, with the `Mention` row carrying `pageId` and `commentId`.
- **The model change**: `Mention.workItemId` becomes nullable, `Mention.pageId` is added, a CHECK requires exactly one; the comment key gains a twin `(commentId, pageId, tenantId)` → `Comment(id, pageId, tenantId)` beside the existing `(commentId, workItemId, tenantId)` (each enforced only when all its columns are set, Postgres's MATCH SIMPLE, which the CHECKs make exact).

### Comments (questions 18 and 19; 4.1d)

- **On the `Comment` table** (ADR 0005 §6.10, ADR 0006's Comment row and the prompt; question 18 asks the shape). `workItemId` becomes nullable; `pageId` is added with `(pageId, tenantId)` → `Page ON DELETE CASCADE`; a CHECK requires exactly one; `@@unique([id, pageId, tenantId])` beside the existing triple; `@@index([tenantId, pageId, createdAt])`. Every existing read is by `workItemId`, so page comments never appear on an item; the answer key still requires a comment of the same item, so a page comment can never be an answer.
- **Anchors**: `anchorFrom` and `anchorTo`, the two Yjs relative positions (base64), both or neither (CHECK); NULL is a comment on the whole page. They hold Yjs ids and clocks, not text: classified in the encryption guard's `NOT_SENSITIVE` with that reason. The anchored text itself is not stored; the panel shows the live text at the anchor. The highlight is a decoration drawn from comment rows, never a mark in the document, so commenting writes nothing to the document, a reader who may comment but not edit can comment, and a comment's text never enters the Yjs state (§6.10).
- **When the anchored text is deleted** the comment stays, listed as "The text this comment was on was removed", and can be resolved or deleted like any other.
- **Replies**: `parentCommentId` → `(parentCommentId, pageId, tenantId)` → `Comment(id, pageId, tenantId)`, so a reply is on the same page; one level only (a trigger refuses a reply to a reply); page comments only (CHECK). **Resolved**: `resolvedAt` and `resolvedByUserId` on a root comment only (CHECK), set and cleared by anyone who may comment on the page (`PAGE_COMMENT_RESOLVED`, `_REOPENED`); resolved conversations fold away in the panel.
- **Text** (question 19, recommended A): plain text with decision 127's tokens, sanitised with `sanitizePlainText`, encrypted, edited by its author only and deleted by its author or an admin (`comment.policies.ts`, decision 53, unchanged); deleting a root deletes its replies in the same transaction. Rich text in comments waits with item descriptions (question 3).
- **Usecases**: `addPageComment`, `editPageComment`, `deletePageComment`, `resolvePageComment` beside the item ones, sharing the sanitiser, the policy, `recordMentionsInTx` and (if question 10) the page search seam. The write-seam guards for mentions and search learn the new writers.

## Collaboration (4.1b)

### The collaboration server (questions 20 and 22)

- **A new service, `collab`** (question 20, recommended A): `scripts/collab.ts` bundled by `scripts/build-worker.mjs` into `dist/collab.mjs` inside the existing worker image, started with its own command through `wait-for-migrations.mjs`, named `islestone-collab`, on `islestone_internal` only, watched by Watchtower with the `depends-on` label, `mem_limit` 384m and a stated heap (`--max-old-space-size=256`), `cpus` 0.5. The worker image already carries Prisma, the pruned production tree and the migration head; no third image. The worker import-graph guard gains `scripts/collab.ts` as a root (no NextAuth, no `next/headers`).
- **One instance** (question 22, recommended A), like the one app container (decision 50): documents live in its memory, so no `@hocuspocus/extension-redis` and no `UNLICENSED` exemption. A second instance needs that extension (or a sticky route per document) and is a later decision with its own measurement.
- **Two listeners**: the public WebSocket port that Caddy routes (below) and a private HTTP port on `islestone_internal` for the app's server-side writes (question 24) and the healthcheck. Caddy never routes the private port.
- **Shutdown**: on SIGTERM the server stops accepting upgrades, stores every loaded document with pending changes, then closes connections, inside a budget below Docker's grace period (the pattern of `shutdown-budget.ts`); clients reconnect to the new container and resend what was not acknowledged.

### Authentication: the collaboration token

- `POST /api/t/:slug/pages/:pageId/collaboration-token` (`requirePermission('pages.view')`, through `getTenantCtx`, so the workspace MFA gate applies) mints `v1.<tenantId>.<pageId>.<userId>.<userSessionId>.<sessionVersion>.<access>.<issuedAtMs>.<nonce>.<mac>`, with `mac` an HMAC-SHA256 under `deriveSubkey('islestone-collaboration-token-v1')` and one spelling of the MAC (the H2f lesson in `form-token.ts`); `access` is `write` when the caller holds `pages.edit` and the page's scope is writable, else `read`; it lives 60 seconds (ADR 0005 §6.2). A route that mints for a page the caller cannot read answers 404.
- **`onAuthenticate`** verifies the MAC, the age, that the document name (`<tenantId>/page/<pageId>`) equals the token's, and the `Origin` header (equal to `NEXT_PUBLIC_APP_URL`'s origin, checked at upgrade in `onUpgrade`); then, through `runInTenantContext` as the workspace's system user, re-reads: the `UserSession` row live (not revoked, not expired, its `sessionVersion` current), the membership ACTIVE with `pages.view` (and `pages.edit` for `write`), the page live in a live, visible scope. A `read` connection is read-only (Hocuspocus does not apply its updates). Any failure closes the connection with a generic reason.
- **Refresh**: the provider fetches a new token every 45 seconds and sends it over the open connection (`onTokenSync`); each refresh re-runs every check and may downgrade `write` to `read`. A connection whose token is not refreshed within 60 seconds is closed. So a revocation takes effect within a minute even if its notice is lost (ADR 0005 §6.2).

### Staying authorised: losing access (question 23)

- **Recommended A: the `access` notice now.** The usecases that take access away publish, after their commit, a content-free notice on a per-workspace Redis channel (`ChangeNotice` `{ kind: 'access'; userId }` and, new, `{ kind: 'page'; op: 'delete' | 'move' | 'scope'; pageId }`), through one publish function guarded by a strict Zod schema (ADR 0005 §4); the collaboration server subscribes and closes, or downgrades, the affected connections at once. The publishers: member removal, role or custom-role change, session revocation and "revoke all", page delete and move, project archive (downgrade to read-only), delete and restore. 4.3 builds the SSE stream and every other notice kind on the same function and channel.
- Either way, H4's test: each of those acts closes or downgrades an open connection within the stated time.

### Persistence: the store path

- `onLoadDocument` reads `PageContent.state` (decrypted by the extension), decodes it into the document, and refuses a page whose decoded state exceeds the cap (question 25).
- `onStoreDocument` (debounced 2 seconds, at most 10, the defaults) runs one transaction under the workspace's context as its system user: the new state, the projections, `contentUpdatedAt`, the mention and item-mention rows, (question 10) the search rows, and an automatic version when due. A store with an unchanged state vector writes nothing.
- **Audit** (ADR 0005 §6.11, decided): one `PAGE_EDITED` entry per contributing person per page per 10 minutes, written as that person (`logEvent` with a context resolved for them at store time by `resolveMemberContext`; a contributor who no longer resolves is named by id in the system user's entry, never as the actor), saying who edited, never what. The window lives in the server's memory; a restart writes at most one extra entry.
- **Single write seam** (ADR 0005 §6.6 and §8): only the store path writes `PageContent` and the projections; a guard lists it, and the purge's cascade delete is the only other change to those rows.

### Server-side writes (question 24)

A restore now, and from 6.2 an approved proposal, an import or a template, change page content on the server. Recommended A: the app calls the collaboration server's private port (`POST /internal/pages/:pageId/apply`, a JSON body naming the change, signed with an HMAC under `deriveSubkey('islestone-collab-internal-v1')` and a timestamp, refused when older than 30 seconds); the server opens a direct connection (`openDirectConnection`), applies the change as the acting person, and stores. Live editors see it at once and the next store keeps it. When the server is down the app answers 503 and changes nothing. The app never writes `PageContent` itself.

### Untrusted content (ADR 0005 §6.7)

- Every update's size and rate are checked in `beforeHandleMessage`; `websocketOptions.maxPayload` bounds a frame before authentication.
- The decoded state's size is checked on store; a document past the cap stops accepting updates (its connections are closed with a reason the editor shows: "This page is too large; changes after this point were not saved").
- Projections validate against the schema and drop what it does not know; export and email sanitise again.
- Awareness state is checked in `beforeHandleAwareness`: its user id must be the connection's, its size bounded; names are fetched through the API from that id, never taken from a client.
- Client ids are claimed per person (above).

### Caps and rate limits (question 25; H4 sets the final values)

Recommended values: a decoded page state of at most 4 MB; one WebSocket message at most 1 MB; per connection at most 60 messages a second (bursts to 120) and 4 MB of updates a minute; awareness states at most 2 KB, 20 a second; per person at most 10 connections per workspace; per workspace at most 300 connections; per IP at most 30 upgrades a minute; a page at most ten levels deep; at most 500 automatic versions kept per page after compaction. Over a connection cap the upgrade is refused (HTTP 429 before the socket opens); over a message cap the connection is closed. The limits are counted in the server's memory (one instance, decision 50's reasoning), and every refusal is a metric with the workspace id never an attribute.

### Presence (question 26)

Recommended A: 4.1 ships what collaboration needs inside the editor (each person's caret and selection, labelled with their current name, through `@tiptap/extension-collaboration-caret` and Yjs awareness, throttled as ADR 0005 §5 says); 4.3 ships presence elsewhere ("who is here" on pages, items and canvases, R1's presence-only rooms).

### The route through the edge (question 21)

- **Recommended A: the same origin.** `wss://islestone.cloud/collab/…`: a `handle /collab/*` block in `deploy/caddy/islestone.caddy` routes WebSocket upgrades to `islestone-collab:<port>` (and answers 404 to anything that is not an upgrade), before the app's `reverse_proxy`, with the same `X-Forwarded-For` rule; Caddy's `request_body` limit does not apply to WebSocket frames, so the server's own caps are the limit. The Next middleware never sees these requests: the token, the Origin check and the per-IP upgrade limit replace the edge's checks, and `/collab` needs no `MACHINE_CALLER_PREFIXES` entry because it never reaches the app.
- **CSP**: `connect-src` gains the explicit `wss://<app host>` from `NEXT_PUBLIC_APP_URL` (today it holds `'self'`, `blob:` and `https:`, with `ws:` only in development, `csp.ts` lines 168 to 174), so no browser depends on how it reads `'self'` for WebSocket schemes.
- **Local and CI**: `docker-compose.yml` and the Playwright web server start the collaboration server beside the app; the client reads its URL from a new `NEXT_PUBLIC_COLLAB_URL` (in `src/env-client.ts`, `.env.example`, the compose file and `deploy/.env.prod.example` together).

## Keys and who sees what (questions 2 and 5)

- **The `pages` domain** (question 2, recommended A) replaces the unused `docs`: `pages.view`, `pages.create`, `pages.edit` (body, title, move within what the caller may write, versions), `pages.comment`, `pages.delete` (delete and restore). OWNER and ADMIN hold all; MEMBER holds all; VIEWER holds `view`; GUEST nothing until 8.4 (decision 204). The domain is renamed in `permissions.ts`, `route-permissions.ts`, the role matrix and the permission matrix; stored custom-role `grantsJson` with a `docs` key is rewritten to `pages` by a data migration (`view` → `view`, `create` → `create`, `edit` → `edit`, and `comment` and `delete` taken from `edit`), audited by count.
- Every page route is a literal `requirePermission` with a rule, and every page route and method gets a hand-written permission-matrix row (the H2 rule). Pages read affordances from the server (`pageAffordances` in `page.policies.ts`: create here, edit, comment, delete, save and restore versions); a component never checks a role or a key.
- A workspace page is created by any `pages.create` holder; nothing about a page is narrower than its scope (question 5).

## Export (question 28; 4.1e)

Recommended A: **Markdown** (`GET /pages/:id/export?format=md`, `pages.view`, audited `PAGE_EXPORTED`), written from `contentJson` by an own, pure serializer (`src/lib/pages/markdown.ts`, also the diff's input), with chips written as the item's key and a link and people as their current names, and a **print view** (`/t/<slug>/pages/<id>/print`) rendering the static renderer's HTML through `sanitizeRichTextHtml`, which the browser prints to PDF. ## Jobs

## Performance (H2's rules)

- **Plan checks** (`PLAN_CHECKED_QUERIES`): the tree's children read, the page ancestry (breadcrumb, one recursive statement), the subtree ids for a move or delete, a page's comments, the refs read, "Mentioned in pages", and the page search functions (question 10). `Page` joins the guarded tables once the seed holds pages; the coverage guard already catches the comment and refs reads (they read `Comment` and `WorkItem`).
- **The seed** gains pages: about 1,000 in `perf-10k` and 10,000 in the 100k shape, nested three to five deep, with states generated in bulk through the schema and encrypted for real, a share with comments and item mentions.
- **Statements per request**: the page route (row, ancestry, affordances, counts) in a fixed number of statements whatever the depth.
- **Latency** (proposed budgets, reported and not enforced until the nightly 100k run measures them, as 3.6a's were): `page-open` (the page's HTTP read) p50 60 / p95 150 ms; `page-tree` (the top level of the largest project) p50 80 / p95 200 ms; `page-sync` (mint a token, connect, first sync of a 200 KB page, measured by a Node client with `@hocuspocus/provider` in the harness) p50 300 / p95 700 ms. The editor's chunk is measured in 4.1b's pull request and kept off every other route by the dynamic import.
- **The collaboration server** reports open connections, loaded documents, store duration and size, refusals by reason, and heap; its decrypt and encrypt of a 4 MB state are measured once in 4.1b.

## H4 and 4.1

Tests 4.1 ships for H4's lines (the canvas and upload lines are 4.2's and 4.4's):

- **Losing access disconnects**: a removed member, a narrowed role (losing `pages.edit` downgrades to read-only; losing `pages.view` closes), a revoked session and "revoke all", a deleted page, a page moved out of reach, an archived project (read-only) and a deleted one: each closes or downgrades an open connection within the stated time, by notice and, with the notice dropped, by the token refresh.
- **Tokens**: expired, another workspace's page, another page, a tampered or re-spelled MAC, a wrong `Origin`, a token whose session was revoked after minting: each refused. A read-only connection's updates are never applied.
- **Two tenants**: the server never loads a document whose name's workspace differs from the token's; every new table has its two-tenant test in `ISOLATION_TESTED`.
- **Caps per tenant**: an oversized frame, an oversized document, a message flood, a connection flood from one workspace that leaves another's connections working.
- **Sanitisation**: a forged update with a `javascript:` link, an unknown element, an attribute the schema does not know: none reaches a projection, an export or the browser's rendering; exported Markdown and the print view's HTML pass the sanitiser.
- **Convergence**: two clients editing one page converge; a restore during a live session survives the next store.
- **Attribution**: an update claiming another person's client id is refused; a mention typed by A is recorded as A's.

## ADR impacts (proposed, none applied)

**A new ADR 0015 "Documents and collaboration"** (question 1), Proposed until the owner decides this map's questions. ADR 0005 stays the cross-cutting sync decision; ADR 0015 holds what is page-specific and names where it departs from ADR 0005. Its outline:

1. **Pages and the tree.** Two scopes, one table; depth ten; fractional order; moves with the subtree, across scopes; soft delete in groups, restore by the root, the 30-day purge; visibility equal to the scope's (questions 4 to 7).
2. **Content and projections.** The stored state the source of truth (ADR 0005 §6.4); the projections stored and the HTML rendered at use (departure 1); one schema module and its revision; validation on store (question 8).
3. **Encryption and search.** Encrypted state, projections and versions, bytes as base64 text through the manifest (question 9); the ADR 0008 amendment chosen (question 10).
4. **Versions.** Content JSON per version (departure 2 from ADR 0005 §6.9); when made, how long kept; restore as a forward change; compare over Markdown (questions 11 to 13).
5. **Comments.** Two parents on `Comment`, anchors as relative positions, one level of replies, resolved; plain text with tokens (questions 18 and 19).
6. **Mentions and embeds.** Items by id under visibility, the refs read, "Mentioned in pages", the item's page link; people recorded on store by claimed client ids (questions 16 and 17).
7. **The collaboration server.** A service from the worker image, one instance without the Redis extension (departure 3 from ADR 0005 §6.1's "several instances share documents through the Redis extension", deferred), its two listeners, the token, the `access` notice now, server-side writes through the private port, the caps' values (ADR 0005 open question 10's "values set at H4"), presence inside the editor (questions 20 to 26).
8. **Keys.** The `pages` domain and the data migration (question 2).
9. **Notifications and export** (questions 27 and 28).
10. **Agents.** Never connected; read projections; propose; applied through the server-side write path.

- *Consequences*: page content is not queryable in place, so everything reads projections that lag by up to ten seconds; a schema change is a transform and a rebuild; one collaboration instance is a single point of failure for editing (reading the page row and comments still works; the editor shows "reconnecting"); the memory budget grows (question 20).

## Open questions for the owner (undecided)

Each question stands alone. The recommended option is first and marked; each option carries its main trade-off. **Question N is decision 337 + N.** Grouped for batches of four.

**Words, keys and scope**

1. **What are the new things called, and where are the rules recorded?** (decision 338)
   - A (recommended). "Page", "Pages" in the sidebar and "Workspace pages" for the workspace's tree; `PageContent` confirmed; "Page version" (`PageVersion`, UI "Versions", "Save version"); "Page watcher"; "Item mention" (`PageItemMention`; "Mentioned in pages"); "Comment anchor", "Resolved", "Reply"; "Slash menu" (UI "Insert"); read tools `list_pages`/`get_page`; a new ADR 0015 "Documents and collaboration", with ADR 0005 amended where 4.1 departs. Every word avoids an existing ban; one ADR holds the page rules.
   - B. As A, but `PageSnapshot` for a version, matching ADR 0006's reserved `CanvasSnapshot`. Symmetric with the canvas; "Snapshot" is banned for the transition record and projections, and people say "version".
   - C. As A, with no new ADR: the rules go into ADR 0005 as amendments. One fewer document; ADR 0005 grows from a sync decision into the pages design.

2. **What are the permission keys?** (decision 339)
   - A (recommended). Rename the unused `docs` domain to `pages` with `view`, `create`, `edit`, `comment`, `delete`; Owners, Admins and Members hold all, Viewers `view`, Guests nothing until 8.4; stored custom roles' `docs` grants rewritten by a data migration. The key speaks the page's word; Viewers read pages and write nothing, as on items.
   - B. As A, and Viewers also hold `pages.comment`. Readers can discuss a page; Viewers comment on pages but not on items.
   - C. Keep the `docs` key name. No data migration; a banned word in a customer-facing key (ADR 0006 rule 2).

3. **Do work-item descriptions and comments become rich text in 4.1?** (decision 340; decision 127 said rich text waits for 4.1)
   - A (recommended). No: 4.1 is pages; descriptions and comments stay plain text with `<@userId>` tokens and key links, and page comments use the same grammar. A later decision moves descriptions to the page editor (without collaboration) if wanted. Smallest blast radius: the search seam, mentions, intake accept, templates, repeats, notifications and exports all read descriptions as plain text today.
   - B. Descriptions become rich text (the page editor without collaboration, stored as encrypted ProseMirror JSON, `If-Match` kept) in a seventh pull request; comments stay plain. Richer items; touches every description reader and the 2.7d mention path.
   - C. Descriptions and comments both become rich text. One text model everywhere; the largest change, and comments lose their simple token grammar.

4. **What shape does the tree take?** (decision 341)
   - A (recommended). One tree per project and one for the workspace, nested at most ten levels, ordered by hand; a page moves with its subtree within its tree and across trees (project to workspace, workspace to project, project to project). Deep enough for any wiki; moving a section between projects works.
   - B. As A with no depth limit. No arbitrary cap; the breadcrumb and the recursive reads need a bound anyway.
   - C. As A, but no moves across trees. Simpler moves; reorganising means copy and delete, losing comments and versions.

**The tree and its pages**

5. **Can a page be narrower than its tree?** (decision 342)
   - A (recommended). No: a project page is readable by whoever reads the project, a workspace page by every `pages.view` holder; per-page restriction waits for 8.4's grants. One visibility rule, already enforced everywhere.
   - B. A page may be marked private to its creator (a personal draft). Common in wiki tools; a second visibility rule in every page read, search and refs answer.
   - C. Per-page member lists. Fine-grained; a sharing model built ahead of 8.4.

6. **Where does a page's title live?** (decision 343)
   - A (recommended). A plaintext row field (at most 200), renamed by a versioned write, shown in the tree, breadcrumb, notifications and search without opening the content. Cheap reads, plain search; two people renaming at once get a 409 rather than a merge.
   - B. The first heading of the Yjs document, projected to the row on store. Collaborative title edits; the title lags by the store debounce and every title read depends on the collaboration server's projection.

7. **What happens on delete, and is there an archive?** (decision 344)
   - A (recommended). Delete soft-deletes the page and its subtree as one group (undo toast), restore through the group's root, a nightly purge after 30 days; no page archive (an archived project makes its pages read-only). The work items' rules, already understood.
   - B. As A, plus "Archive" for a page (read-only, hidden from the tree, kept). Old pages can be kept out of the way; a third state to read everywhere.
   - C. Hard delete behind the undo toast only. Simplest; a mistaken delete after five seconds is unrecoverable.

8. **Which projections are stored?** (decision 345)
   - A (recommended). The Yjs state (source of truth) plus encrypted `contentJson` and `plainText`, and the mention and item-mention rows; sanitised HTML rendered at each export or email from `contentJson` (a departure from ADR 0005 §6.4). One fewer encrypted copy; the sanitiser's current rules apply at the point of use.
   - B. As ADR 0005 §6.4 says: also a stored, sanitised HTML projection. No rendering at export; a stored copy that must be rebuilt when the sanitiser changes.
   - C. The state only; projections computed on demand by the collaboration server. Nothing derived is stored; every read of content (agents, export, diff, search) goes through the collaboration server.

**Content, encryption and search**

9. **How is the binary Yjs state encrypted?** (decision 346)
   - A (recommended). Base64 text in a `String` column, encrypted by the existing manifest path; the rotation sweeps re-wrap it unchanged. No change to security-critical code; about 1.8 times the raw size.
   - B. Teach the encryption extension, both rotation sweeps and the manifest guard a `Bytes` path. Smaller rows; new code in the most sensitive module.
   - C. Encrypt in the collaboration server's repository, outside the manifest. Flexible; a second encryption path the guards cannot see, against CLAUDE.md's manifest rule.

10. **Are pages searched, and how?** (decision 347; an ADR 0008 amendment)
    - A (recommended). Titles, bodies and page comments, through a `PageSearchVector` table of plaintext stemmed words on the decision-245 pattern, bounded like decision 250. Pages are found like items; **the searchable words of every page and page comment become readable in the database, its dumps and off-host backups**, as decision 124 accepted for descriptions and comments.
    - B. Titles only. Nothing new readable; a page's body is never found from the palette.
    - C. Titles, and bodies by keyed word tokens (ADR 0008's never-built option A). No readable words; a second search mechanism, whole words only, no stemming.
    - D. Nothing. No exposure; pages cannot be searched at all.

11. **What does a version hold?** (decision 348)
    - A (recommended). The page's content JSON at that moment, encrypted (a departure from ADR 0005 §6.9's "encoded snapshots"). Viewing, comparing and restoring read it directly; it carries no Yjs history (none is usable with garbage collection on).
    - B. The full encoded Yjs state, encrypted. Closest to ADR 0005's words; every view or diff decodes a state first.
    - C. Yjs snapshots over a document with garbage collection off. Tiny versions and character-level history; the document grows for ever and every load replays it.

12. **When are versions made, and how long are they kept?** (decision 349)
    - A (recommended). Automatically when editing goes quiet for 10 minutes and at most hourly while it continues, on "Save version" (named), and before every restore; automatic ones thinned to all for 7 days, one a day for 90 days, then one a week; saved ones kept for the page's life, until 8.3's retention table says otherwise. Enough history to recover a week of work; storage bounded.
    - B. Keep every automatic version. Nothing ever thinned; storage grows with every editing session.
    - C. Only saved versions and before-restore copies. Least storage; nothing to go back to unless someone remembered to save.

**Editor**

13. **How are versions compared?** (decision 350)
    - A (recommended). A block-level line diff of the two versions' Markdown, with jsdiff (BSD-3-Clause) in inflect's copied `VersionDiff`. Small, already proven in inflect; formatting-only changes show as changed lines.
    - B. A structural, inline diff through `prosemirror-changeset` (MIT, inside `@tiptap/pm`). Changes shown in place in the rendered page; more code to write and test.
    - C. No compare in 4.1; view and restore only. Least work; a reviewer cannot see what changed.

14. **Which blocks does the editor offer?** (decision 351)
    - A (recommended). Paragraphs, headings 1 to 3, bullet and numbered lists, quote, plain code block, divider, table, links, person and work-item mentions, work-item embeds, page links; a slash menu over them; no images until 4.4, no external embeds, no callouts or toggles. Covers specs and meeting notes; every block is in the sanitiser's allowlist.
    - B. As A, plus toggles (details), callouts and a table of contents (all MIT now). Richer pages; more nodes to project, sanitise, export and transform later.
    - C. As A without tables. Smallest schema; tables are a common need.

15. **May a page hold untracked to-dos?** (decision 352)
    - A (recommended). No checkbox lists; "Create work item" turns a line or selection into a real work item and leaves its chip. Principle 3 holds: tracked work is a work item.
    - B. Checkbox lists as formatting, never tracked. Familiar; a second kind of to-do beside work items.
    - C. Both. Choice for the writer; the ambiguity principle 3 exists to avoid.

16. **How do work items appear in pages, and pages on items?** (decision 353)
    - A (recommended). An inline chip and a block embed, each storing the id only and rendered through a refs read that answers "No access" for anything the reader cannot see; "Mentioned in pages" on the item from a stored projection; "Link a page" on the item as a `WorkItemLink` of type `PAGE`. Both directions navigable, always current, never leaking.
    - B. As A without "Mentioned in pages". No projection rows; an item never shows the pages that discuss it.
    - C. As A without the item's page link. One mechanism fewer; an item cannot point at its spec unless the spec mentions it.

**Mentions and comments**

17. **How are people mentioned in page bodies, and who is the author?** (decision 354)
    - A (recommended). A mention node with the person's id, recorded on store as a `Mention` row with a page parent, attributed to the person whose Yjs client id inserted it (client ids claimed per connection, a claim on another person's id refused); notifies and makes the person a watcher, as 2.7d does. Decision 129 holds inside a CRDT.
    - B. A separate `PageMention` model. No change to `Mention`; two models for one concept.
    - C. No person mentions in bodies, only in page comments. No attribution machinery; people cannot be called into a page's text.

18. **What shape do page comments take on `Comment`?** (decision 355)
    - A (recommended). `workItemId` nullable, `pageId` added, exactly one by CHECK; an optional anchor (two Yjs relative positions; the comment survives its text's deletion, marked as such); one level of replies; resolved and reopened on root comments. Inline review as people expect, on the existing table.
    - B. A separate `PageComment` model. Leaves the work-item comment code untouched; contradicts the prompt, ADR 0005 §6.10 and ADR 0006's Comment row, which would need amending.
    - C. As A without anchors (comments on the whole page only). Simpler; no "comment on selection".

19. **What text format do page comments use?** (decision 356)
    - A (recommended). Decision 127's plain text with `<@userId>` tokens, as item comments. One comment grammar, one sanitiser profile.
    - B. Rich text (the editor, without collaboration). Formatting in comments; a second comment format and its own sanitiser path.

**Collaboration and deployment**

20. **Where does the collaboration server run, and where does its memory come from?** (decision 357)
    - A (recommended). A new `collab` service from the worker image, 384 MB, and the stack's ceiling raised from 4 GB to 4.5 GB on the shared VM (the compose file says about 11 GB is free beside Agrent and Playerz). Own process as ADR 0005 §6.1 requires; nothing else loses memory.
    - B. A new service at 384 MB inside the 4 GB, taken from the app (1,024 to 768) and the worker (768 to 640). No change to the ceiling; less headroom for requests and jobs.
    - C. Inside the worker process. No new container; a long job stalls typing, and a worker restart drops every editor.

21. **How do browsers reach it?** (decision 358)
    - A (recommended). The same origin, `wss://islestone.cloud/collab/…`, routed by Caddy straight to the service before the app; an explicit `wss://` origin in `connect-src`. No new name or certificate; the token and the server's own checks replace the edge middleware.
    - B. A subdomain, `collab.islestone.cloud`. Clean separation; DNS, a certificate and a cross-origin rule to maintain.
    - C. Through the Next server (a custom server with WebSocket upgrades). One entry point; ADR 0005 §6.1 chose not to rely on it, and the standalone server would change.

22. **One instance, or several from the start?** (decision 359)
    - A (recommended). One instance, documents in its memory, no `@hocuspocus/extension-redis`. Matches decision 50; avoids the extension's dependency `@sesamecare-oss/redlock` 1.4.0, whose `package.json` says `UNLICENSED` though it ships an MIT `LICENSE.md`.
    - B. Several instances through the Redis extension, with an ADR 0007 exemption for redlock 1.4.0 pinned to its MIT file. Ready to scale; an exemption, a second ioredis copy, and page updates in flight through Redis.

23. **How does losing access reach an open connection in 4.1?** (decision 360)
    - A (recommended). Content-free `access` and `page` notices published after commit on a per-workspace Redis channel, through ADR 0005 §4's one guarded publish function, which 4.3 then extends; the token refresh stays the backstop. Disconnection is immediate (H4); 4.3 inherits the channel.
    - B. The 60-second token refresh only. Nothing of 4.3 built early; a removed member keeps editing for up to a minute.
    - C. The app calls the collaboration server's private port for each revocation. Immediate; a second mechanism beside the channel 4.3 builds anyway.

24. **How does the app change page content on the server (restore now, proposals later)?** (decision 361)
    - A (recommended). An HMAC-signed call to the collaboration server's private port, applied through a direct connection as the acting person. One write seam (ADR 0005 §6.6); live editors see it at once; a 503 when the server is down.
    - B. A queued job the collaboration process consumes. Durable and retried; a restore is not immediate.
    - C. The app writes the stored state itself when no session is open, else asks the server. Works while the server is down; two write paths, against §6.6.

25. **What are the caps and rate limits?** (decision 362; H4 sets the final values)
    - A (recommended). A page state at most 4 MB; a message at most 1 MB; per connection 60 messages a second (bursts 120) and 4 MB a minute; awareness 2 KB, 20 a second; 10 connections per person per workspace, 300 per workspace; 30 upgrades a minute per IP; ten levels deep; 500 automatic versions per page. Generous for writing, bounded for abuse, sized for one instance.
    - B. Half of each. Safer for one small container; long pages and busy workshops hit them.
    - C. Twice each. Room for large pages; one workspace can take more of the one instance.

26. **How much presence ships in 4.1?** (decision 363)
    - A (recommended). Carets and selections with names inside the editor (the awareness collaboration needs, identity checked server-side); "who is here" on pages, items and canvases in 4.3. Collaboration feels live; 4.3 keeps its scope.
    - B. No carets until 4.3. Smaller 4.1; editors collide blind.
    - C. All page presence now, including the "who is here" row. More of 4.3 early; a second presence surface to align later.

**Notifications, export, sources and delivery**

27. **Who is notified about pages?** (decision 364)
    - A (recommended). Page watchers (creator, commenters and mentioned people automatically; anyone may watch or stop); `PAGE_MENTIONED` (immediate email allowed) and `PAGE_COMMENTED` (in-app and digest); no notification for content edits; never text.     - C. Write the editor fresh, copying nothing. No provenance rows; repeats inflect's tested link hardening and accessibility work.

30. **How is 4.1 split into pull requests?** (decision 367)

    - C. Three: tree with server and editor; mentions, embeds and comments; versions, export and search. Fastest to track; the first is about 6,000 lines in one review.
