## Summary

- **Most of the architecture is already decided.** ADR 0005 (Accepted, 2026-11-19) fixed it: a page's stored Yjs state is the source of truth for its body (§6.4); the collaboration server is its own Node process (§6.1) and the only writer of that state and its projections (§6.6); every connection carries a signed, 60-second collaboration token and is re-checked on every refresh (§6.2); references to work items store the id and nothing else (§6.3); content from a client is untrusted (§6.7); state and snapshots are encrypted under the workspace key (§6.8); page comments are `Comment` rows anchored by a Yjs relative position (§6.10); one audit entry per person per page per 10 minutes (§6.11); agents never connect (§6.12). ADR 0006 already reserves `Page`, `PageContent` and "Projection", and bans "Doc, Document, Wiki, Note, Article" for a page. This map builds on all of it and asked only what was still open.
- **Seven things to build.** (1) A page tree per project and one for the workspace, ordered by fractional index, moved, soft-deleted in groups, restored and purged like work items. (2) The editor: Tiptap 3 (MIT) with a schema module shared by browser and server, a slash menu written in-house on `@tiptap/suggestion` (MIT), the core blocks plus toggles, callouts and a table of contents (decision 351), people and work-item mentions, work-item embeds, page links. (3) The collaboration server: Hocuspocus 4 (MIT) as a new `collab` service from the worker image, its token, its re-checks, its store path (encryption, projections, audit), its caps, and a route through Caddy. (4) Comments on pages on the existing `Comment` table: anchored, with one level of replies and a resolved state, in rich text (decision 356). (5) Versions: saved and automatic, viewed, compared and restored as a forward change. (6) Search over page titles, bodies and comments through a `PageSearchVector` table (decision 347, an ADR 0008 amendment). (7) **Rich text in work items** (decision 340): item descriptions and item comments move from plain text with `<@userId>` tokens to the editor's item-text format (no collaboration), stored as encrypted ProseMirror JSON beside an encrypted plain-text projection, with every existing description and comment converted by a job.
- **Three tensions, settled.** Pages are encrypted at rest, and searching their words stores a readable derivative, as ADR 0008 did for descriptions and comments: accepted (decision 347). The stack's six long-running services already use exactly its 4 GB ceiling (`tests/unit/deploy/compose-prod.test.ts`): the ceiling rises to 4.5 GB for a 384 MB collaboration server (decision 357). The `Comment` table is welded to work items (a NOT NULL `workItemId`, a three-column unique key the answer and mention keys point at, the search seam): it takes a second parent, with the ripple (decision 355).
- **Decision 340 is the largest change in 4.1, and it changes code that is built.** Six of the seven pull requests add new things beside the work items; 4.1g rewrites how every work-item description and comment is stored, validated, sanitised, rendered, searched and mentioned, and converts every one ever written. The text is encrypted, so Postgres cannot convert it: a job reads each row through the decrypting client and writes it back, workspace by workspace, while the previous image may still be running. Every reader of a description or comment changes with it (the search seam, mentions, intake accept, templates, project templates, repeats, field sets, answers, the detail, the comments panel, the Activity, the create dialog, the API's shapes, the scale seed, a dozen guards). Its risks are named in "Rich text in work items (4.1g; decision 340)", "Risks".
- **What is taken.** From inflect-compliance: its Tiptap editor (`src/components/ui/RichTextEditor.tsx`, 462 lines: the StarterKit configuration, the hardened link, the placeholder, the accessible editor surface, the toolbar, the lazy-load posture), its 16 `richtext` copy keys and its rendered test, copied and adapted; its version diff (`src/components/ui/VersionDiff.tsx`, 284 lines, over jsdiff), copied and adapted. inflect has no Yjs, Hocuspocus, slash-menu, mention or comment-anchor code (ADR 0005, "What inflect-compliance has built"; its `package.json` lines 138 to 142 hold only five Tiptap packages). Everything else is written fresh. No inspiration-only project (Docmost, AppFlowy, Outline, Plane) was read.
- **Licences.** Every package taken is MIT, apart from `diff` (BSD-3-Clause), both on the allowlist; decision 351 adds `@tiptap/extension-details` and `@tiptap/extension-table-of-contents` (MIT), and the callout is Islestone's own node. Tiptap's paid "Pro" extensions (snapshots, snapshot compare, comments, AI, document export and import) are not on the public registry (a 404 for `@tiptap-pro/*`, 2026-11-27) and are not used: comments, versions and export are built in-house, as roadmap §2.3 says. The licence gate gains no deny-list entry for them (decision 366). One trap: `@hocuspocus/extension-redis` 4.8.0 and 4.9.0 depend on `@sesamecare-oss/redlock` 1.4.0, whose `package.json` declares `UNLICENSED` while its tarball ships an MIT `LICENSE.md`; the licence gate refuses `UNLICENSED`. One collaboration server needs no Redis extension (decision 359).

"Doc" is a banned word for a page, and a permission key is customer-facing (ADR 0006 rule 2), so the domain becomes `pages` with `comment` and `delete` added (decision 339).

## What makes the prompt harder than it reads

- **"On the existing comment model."** `Comment.workItemId` is NOT NULL; `Comment` carries `@@unique([id, workItemId, tenantId])` because `WorkItem.answerCommentId` and `Mention.commentId` point at it through that triple; `SearchVector.workItemId` is NOT NULL; and every comment read is by work item. A comment on a page needs a second, mutually exclusive parent, a second unique triple, second keys from `Mention`, and a search row of its own. ADR 0002's sketch already says "roadmap 4.1 adds pageId; a CHECK then requires exactly one parent" (ADR 0002 §12); the cost is in the ripple.
- **A CRDT has no author per write.** Decision 129 records a mention only for "a person's own write". The collaboration server sees merged binary updates from several connections, not form submits. Attributing a mention to the person who typed it needs the Yjs client id of the inserting update mapped to the connection that sent it, and a refusal of updates that claim another connection's client id (below).
- **"Checks … on every connection"** is the easy half. H4 wants a person who loses access disconnected while connected, and ADR 0005 §4 puts the `access` notice on 4.3's Redis channel. 4.1 needs some of 4.3's channel now (decision 360).
- **Binary state, encrypted, searchable.** The encryption extension handles strings only (`encryptValue`, `encryption-middleware.ts` lines 250 to 253), so Yjs bytes must become text or the extension must learn bytes (decision 346). Searching what is encrypted repeats ADR 0008's trade-off (decision 347).
- **History in a garbage-collected CRDT.** A Yjs document with garbage collection on cannot be rewound. A "version" is therefore a stored copy, and a restore is a new change applied on top of the live document, never a rewind (decision 348).
- **The memory budget is spent.** Postgres 1,536 MB, PgBouncer 128, Redis 512, the app 1,024, the worker 768, Watchtower 128: 4,096 MB, the ceiling the compose test holds.
- **Sanitising a CRDT.** The server never receives HTML from a client; it receives Yjs structures any client can forge, including a link mark with a `javascript:` URL or an element the schema does not know. Sanitisation happens when projections are built and again at export, and the browser's schema must refuse a dangerous URL when it renders another client's content.
- **Restarts drop every socket.** Watchtower replaces containers on each release. The client reconnects and Yjs resends what was not acknowledged; the server must flush pending stores on shutdown inside the grace period.
- **Rich text in items is a migration of encrypted text** (decision 340). Every description and comment is ciphertext under its workspace's key, so no SQL migration can read or rewrite it; the conversion is a job through the decrypting client, bounded per page, idempotent, and safe while the previous image (which writes plain text) is still running during Watchtower's roll. The `<@userId>` token grammar, `MentionTextarea`, `MentionText` and every place that reads a description as a string move with it.
- **The words.** The sub-phase is called "Documents", but "Document" and "Doc" are banned for a page in UI text and identifiers, "Space" is banned for workspace and project, "History" and "Thread" are banned in every schema identifier (the schema guard enforces both strictly), and "Draft" is a proposal's word. Hocuspocus's own API says "document"; that stays inside the adapter (ADR 0006 rule 5).

## The model (4.1a)

### Page and the tree (decisions 341 to 344)

```prisma
model Page {
  id              String    @id @default(cuid())
  tenantId        String
  projectId       String?   // NULL: a workspace page
  parentId        String?   // NULL: a top-level page of its tree
  sortKey         String    // COLLATE "C" in the migration (ADR 0002 §5)
  title           String    // plaintext, sanitizePlainText, at most 200 (decision 343)
  version         Int       @default(1)  // the row's title and placement, not the body
  createdByUserId String
  contentUpdatedAt DateTime?            // set by the store path
  deletedAt       DateTime?
  deletedByUserId String?
  deletionId      String?
  createdAt       DateTime  @default(now())
  updatedAt       DateTime  @updatedAt

  @@unique([id, tenantId])
  @@unique([id, projectId, tenantId])   // target for comments and mentions that must match a page
  @@index([tenantId, projectId, parentId, sortKey])
  @@index([tenantId, deletionId])
}
```

- **Two kinds of tree, one table** (decision 341). A project's tree (`projectId` set) and the workspace's (`projectId` NULL). The tree read is children of one parent in one scope, in `sortKey` order, through two partial indexes written in SQL (`… WHERE "deletedAt" IS NULL AND "projectId" IS NOT NULL` leading `tenantId, projectId, parentId, sortKey`, and the workspace twin), with a catalogue test; Prisma cannot declare either.
- **Same scope, always.** A page's parent is in its own scope: the usecase checks it under the tree lock and a trigger refuses a row whose parent's `projectId` differs (a composite key cannot carry a nullable scope column). The parent key is `(parentId, tenantId)` → `Page(id, tenantId)`, `DEFERRABLE INITIALLY DEFERRED` like the work-item parent link, so a subtree move is one transaction.
- **Depth at most ten** (decision 341), counted by a depth-capped, path-guarded recursive query (the pattern of `WorkItemRepository.ancestry`); a move into its own subtree is `PAGE_WOULD_CYCLE`, past the cap `PAGE_TOO_DEEP`. Every write that changes `parentId` or `projectId`, every delete and restore and every purge page takes `lockPageTree(tenantId)` FIRST (a transaction advisory lock, `page-tree:<tenantId>`), then the page rows in id order (the multi-row rule of decision 173).
- **Waiting a turn.** Tree writes that take `lockPageTree` wait their workspace's turn in the process first, through the one queue implementation (`write-queue.ts`, the pattern of `inWorkItemGraphQueue`, decision 254), so a burst of moves does not hold PgBouncer's connections while it waits.
- **Rows that name a member** (`PageWatcher`, page `Mention` rows) follow CLAUDE.md's "A row that names a member": the people are read `FOR KEY SHARE` through `MembershipRepository.lockActiveUserIds` after the page, a removed person named on purpose is a 400 and one a write brings along is skipped.
- **Order** is `sortKey` from `keyBetween` ("after X, before Y", computed by the server), compared with `<`; the rebalance job learns pages (below). A `sortKey` write does not bump `version`.
- **Moves.** Within a scope: a new parent and a place. Across scopes (a project to the workspace, the workspace to a project, one project to another; decision 341): the page and its live subtree move together, each row's `projectId` rewritten in one transaction; comments, versions and mentions follow the page id. Moving into an archived or deleted project is refused (`PROJECT_ARCHIVED`, 404).
- **Visibility** (decision 342). A project page is readable exactly when its project is visible (`visibleProjects`, so today every role but Guest) and live; a workspace page by every holder of `pages.view`. An archived project's pages are readable and read-only (writes 409 `PROJECT_ARCHIVED`, connections read-only). No page is narrower than its scope in 4.1: private pages and per-page sharing wait for 8.4's grants.
- **Title** (decision 343). A row field, plaintext like a work item's title: it is shown in the tree, the breadcrumb, notifications and search results, none of which should open the document. Renaming is a versioned write (`If-Match` required, 428 without it, 409 `VERSION_CONFLICT` with the current row), audited `PAGE_RENAMED` with the old and new title (titles are plaintext and already audited this way for work items). The editor shows the title as a separate field above the body.
- **Delete, restore, purge** (decision 344). Delete soft-deletes the page and its live subtree under one `deletionId` (`PAGE_DELETED`), closes every open connection to those pages, and goes through the undo toast; restore brings the group back through its root only (`DELETED_WITH_PARENT`), under a live parent (`PARENT_DELETED`) in a live scope; a restored row whose `sortKey` collides is re-placed (`planRestoredSortKeys`). The nightly `page-purge` hard-deletes groups deleted more than `PAGE_PURGE_DAYS` (30) ago; content, versions, comments, mentions, watchers and search rows cascade. Deleting a project hides its pages with it, and its purge cascades them. No archive for pages (an archived project archives its pages' writes).
- **Creating a page** writes the row and an empty `PageContent` row in one transaction (`PAGE_CREATED`); the first store fills it. A create names a scope, an optional parent and a place, and a title (default "Untitled").

### Page content: the state and its projections (decision 345)

```prisma
model PageContent {
  pageId        String   @id
  tenantId      String
  state         String?  // the encoded Yjs state, base64, then encrypted (manifest) (decision 346)
  contentJson   String?  // the ProseMirror JSON projection, schema-validated, encrypted (manifest)
  plainText     String?  // the text projection, encrypted (manifest)
  schemaRevision Int     // PAGE_SCHEMA_REVISION the projections were built with
  stateBytes    Int      // the decoded state's size, for the cap and the dashboards of H4
  updatedAt     DateTime @updatedAt
  // (pageId, tenantId) → Page ON DELETE CASCADE
}
```

- **The stored Yjs state is the source of truth** (ADR 0005 §6.4, decided). Written only by the collaboration server's store path (§6.6); the guard ADR 0005 §8 asks for lists that one writer.
- **The projections written on each store** (decision 345): `contentJson` (what agents, export, the version diff and the print view read), `plainText` (for search, decision 347, and for 6.5), and the `PageItemMention` and `Mention` rows (4.1c). **A departure from ADR 0005 §6.4 (decision 345):** sanitised HTML is not stored; it is rendered from `contentJson` with `@tiptap/static-renderer` and passed through `sanitizeRichTextHtml` at each export or email, so there is one fewer encrypted copy and the sanitiser's current allowlist always applies (H4's "sanitised on the server before any export or email" holds at the point of use).
- **Validation.** Projections are built by decoding the state through `@tiptap/y-tiptap` into a ProseMirror document over the shared schema (`src/lib/pages/schema.ts`, below); nodes, marks and attributes the schema does not know are dropped and counted in the store's log line (never their content); a link mark whose URL fails the sanitiser's schemes (`http`, `https`, `mailto`, `tel`) is dropped. Whether `y-tiptap`'s converter throws or skips on an unknown element is verified in 4.1b; either way the store records the drop and never stores an unvalidated projection.
- **Schema changes.** `PAGE_SCHEMA_REVISION` (beside the schema) is bumped by any change to the node set; the `page-projection-rebuild` job re-projects rows at an older revision, and a node rename ships a tested transform of stored states (ADR 0005, "Consequences").

### Encryption (decision 346)

- **State, `contentJson`, `plainText` and every `PageVersion.contentJson` are in the encryption manifest** (ADR 0005 §6.8 and open question 6, decided). Titles are plaintext (above). Comment bodies stay encrypted as today, and their rich text (`Comment.bodyJson`) and, from 4.1g, the descriptions' (`WorkItem.descriptionJson`, `WorkItemTemplate.descriptionJson`) join the manifest (decision 340).
- **Bytes as text** (decision 346): the encoded state is base64-encoded and stored in a `String` column, so the existing extension encrypts it unchanged and the key-rotation sweeps (`key-rotation`, `tenant-dek-rotation`) re-wrap it like any manifest field. The cost is size (base64 of the ciphertext of base64: about 1.8 times the raw state) and one large value per page for the sweeps to page through. Teaching the extension a `Bytes` path touches the encryption middleware, both sweeps and the manifest guard, which scans `String` columns only.
- **Write-once rows admit the re-wrap.** `PageVersion` is write-once by trigger; the trigger admits the sweeps' rewrite of `contentJson` from ciphertext to `v2:` ciphertext with every other column unchanged (CLAUDE.md, "Key rotation (1.5b)"), as the review rows' trigger does.
- **In flight.** The state crosses the WebSocket as Yjs updates under TLS from the browser to Caddy, and in clear on the private Docker network from Caddy to the collaboration server, as every API request does today. With one collaboration server no update crosses Redis (decision 359).

### Search (decision 347; an ADR 0008 amendment)

ADR 0008 excluded pages until an amendment ("Pages' plain-text projection … needs its own amendment to this ADR before it is built"). **Decided: A** (decision 347), knowing that the searchable words of every page body and page comment become readable in the database, its dumps and its off-host backups, as decision 124 accepted for descriptions and comments; ADR 0008 is amended. The options as put, with what each stores:

| | What is searched | What becomes readable outside the application | Cost |
|---|---|---|---|
| **A (decided)** | Page titles; page bodies; page comments | Titles (already plaintext); the stemmed words of every page body and page comment, in every dump and off-host backup, as for descriptions and comments (decision 124) | A `PageSearchVector` table (`tenantId`, `pageId`, nullable `commentId`, `lexemes`, configuration, revision, `updatedAt`), written in the store's transaction from `plainText` and by the page-comment usecases, through one seam; two new search functions (`search_page_titles`, `search_page_contents`) on the decision-245 pattern with page visibility inside, bounded like decision 250; the palette's "Pages" group; the rebuild learns pages |
| B | Page titles only | Nothing new (titles are plaintext) | An expression index and one search function; bodies are found only by opening pages |
| C | Titles; bodies by keyed word tokens (ADR 0008's option A, never built) | Nothing readable; token frequencies | A second search mechanism beside `islestone_bg_en`: whole words, no stemming, no phrases |
| D | Nothing | Nothing | Pages cannot be found from the palette |

A separate `PageSearchVector`, rather than widening `SearchVector` to two parents, keeps the pinned, plan-checked item functions (`search_item_contents` and its hashes) untouched. A page found in search opens at the top; snippets are built from the decrypted `plainText` under the same visibility, never stored (ADR 0008's rule). A page comment's vector is written from its rich text's plain-text projection (decision 356), as an item comment's is from 4.1g (decision 340, "Rich text in work items"). The 6.5 embeddings over pages need a further amendment.

### Versions (decisions 348 to 350; 4.1e)

```prisma
model PageVersion {
  id            String   @id @default(cuid())
  tenantId      String
  pageId        String
  number        Int                       // per page, from 1; @@unique([pageId, number])
  origin        PageVersionOrigin         // AUTOMATIC, SAVED, BEFORE_RESTORE
  name          String?                   // a saved version's name, plaintext, at most 120
  contentJson   String                    // encrypted (manifest)
  schemaRevision Int
  createdByUserId String?                 // the saver or restorer; NULL for AUTOMATIC
  contributorIds String[]                 // who edited since the previous version
  createdAt     DateTime @default(now())
}
```

- **What a version holds** (decision 348): the page's `contentJson` at that moment, not a Yjs state. Viewing, comparing and restoring all need the ProseMirror document; a state with garbage collection on records no history that a person could use. **This departs from ADR 0005 §6.9's "full encoded snapshots"**, which the amendment records.
- **When one is made** (decision 349): automatically when an editing session on the page goes quiet (no store for 10 minutes, the audit window of ADR 0005 §6.11) and at most once an hour while editing continues; when a person chooses "Save version" with an optional name; and before every restore (`BEFORE_RESTORE`). Identical content makes no automatic version.
- **How long** (decision 349): saved and before-restore versions are kept for the page's life; automatic ones are thinned by `page-version-compaction`: every one for 7 days, then the last of each day for 90 days, then the last of each week. 8.3's retention table may later set limits; until then nothing else deletes a version.
- **Restore** is a forward change: the server records a `BEFORE_RESTORE` version, then replaces the live document's content with the version's through the direct connection (decision 361), so live editors see it at once and the next store keeps it. Audited `PAGE_VERSION_RESTORED`. The version list and each version's content are read under `pages.view`; save and restore take `pages.edit`.
- **Compare** (decision 350): a block-level diff of two versions' Markdown projections (the same serializer as export) with jsdiff, in the copied `VersionDiff`; "Compare with current" diffs against the latest store.

## The editor (4.1b, 4.1c)

### One schema, browser and server

- `src/lib/pages/schema.ts` (client-safe, no React) exports the extension list and `PAGE_SCHEMA_REVISION`. The editor adds the React-only pieces (node views, popups) on top; the collaboration server builds its ProseMirror schema from the same list (`getSchema`), so a node the browser can write is a node the server can project, and nothing else is. It also exports the **item-text** node set, the subset descriptions and comments use (decisions 340 and 356; "Rich text in work items" below), and `sanitizeRichTextDocument` validates against it.
- The editor is loaded with `next/dynamic({ ssr: false })` behind an error boundary (inflect's posture), at `src/components/pages/editor/`; it is never given `content`: the Collaboration extension binds it to the provider's `Y.Doc`, and `immediatelyRender: false`.
- The link extension is configured with Islestone's schemes through `isAllowedUri` (http, https, mailto, tel: the sanitiser's set), so a link another client wrote with another scheme is neither rendered nor followed.

### Blocks and the slash menu (decisions 351 and 352)

- **Blocks** (decision 351, option B, a departure from the recommended A): paragraphs; headings 1 to 3; bullet and numbered lists; quote; code block (plain, no highlighting); divider; table (`@tiptap/extension-table`); hard break; marks bold, italic, strike, inline code, link; **toggles** (`@tiptap/extension-details`: a summary line and folding content), **callouts** and a **table of contents** (`@tiptap/extension-table-of-contents`). Islestone's nodes: person mention, work-item mention, work-item embed, page link, callout. Not in 4.1: images and files (4.4 adds them with uploads), external embeds (`frame-src` is not opened), mathematics, emoji.
- **The three added blocks, as decided.** Each is a node in the shared schema module, so the collaboration server projects it, validates it and counts what it drops like every other node, and `PAGE_SCHEMA_REVISION` starts with them in it.
  - *Toggle*: Tiptap's `details`, `detailsSummary` and `detailsContent`; whether a toggle is open is the reader's own view state, never stored in the document (so one person folding a section does not fold it for everyone).
  - *Callout*: Islestone's own `callout` node (no callout extension is among the registry's MIT packages the map read), block content inside, one attribute `tone` from a closed set (`info`, `success`, `warning`, `danger`); an unknown tone is dropped to `info` on projection, an unknown attribute dropped.
  - *Table of contents*: a node with no content of its own; its list is computed from the page's headings each time it is shown or exported, never stored as text, so it never goes stale and holds nothing a projection must search. Headings carry the stable ids `@tiptap/extension-unique-id` gives them, as the extension needs.
  - *Export, print and the sanitiser.* The Markdown serializer writes a toggle as its summary in bold followed by its content, a callout as a quote led by its tone's label, and a table of contents as a list of the headings; the print view renders a toggle open as plain blocks with the summary as a bold paragraph, a callout as a `blockquote` led by its label, and the table of contents as links to the heading ids `sanitizeRichTextHtml` already allows (`h1` to `h6` may carry an `id`). So **the sanitiser's tag and attribute allowlists are not widened** (no `details`, `summary`, `aside` or `class`): a widening would be a security change of its own, and the blocks do not need one.
  - *Cost, named.* Three more nodes to project, validate, export, diff and, at any later schema change, transform in stored states; the version diff shows a toggle or callout as its serialized lines. Item text does not take them (below).
- **The slash menu**, in-house on `@tiptap/suggestion`: `/` at a line start or after a space opens a filtered list of the blocks above plus "Work item" (search and embed), "Mention work item", "Link to page", "Mention person" and "Create work item" (decision 352). Keyboard: arrows, Enter, Escape, by the editor's own key handling (no window listener; `useKeyboardShortcut` stays for the shell's shortcuts). Every label is a `pages.editor.slash.*` key.
- **To-dos and principle 3** (decision 352): no checkbox list block. "Create work item" turns the current line or selection into a new work item in a chosen project (the normal create dialog, prefilled with the text as the title, through `useWorkItemMutations`) and replaces the text with its chip; an untracked to-do would be a second kind of tracked work.

### Work-item mentions and embeds (decision 353; 4.1c)

- **Stored as the id only** (ADR 0005 §6.3, decided): `workItemMention { id }` inline, `workItemEmbed { id }` as a block. Typing a known key (`ISL-123`, decision 131's grammar) and a space turns it into a chip; the slash menu's "Work item" searches through `/api/t/:slug/search`.
- **Rendered under visibility.** `GET /api/t/:slug/work-items/refs?ids=` (`work_items.view`, at most 100 ids, one statement over `WorkItem` with `deletedAt` and `projectVisibilityWhere`) answers each id with the chip's fields (key, title, state and its category, assignee id, due date, review mark) or `{ id, access: 'none' }`, the same for a missing, deleted or invisible item (a reader learns nothing from the difference). The chip shows "No access" for those. The read registers with `work-item-cache.ts`, so an item written in this tab updates its chips; other tabs refresh on focus until 4.3's change notices.
- **"Mentioned in pages"** (decision 353): on each store the server writes `PageItemMention(tenantId, pageId, workItemId, firstSeenAt)` for the ids the page names, removing the ones it dropped; the item detail lists the pages the caller can read that mention it (`GET /work-items/:id/pages`, `work_items.view`, the page visibility applied, at most 50). Nothing is notified when an item is mentioned in a page.
- **Linking a page from an item** (decision 353): "Link a page" on the item's Links panel writes a `WorkItemLink` with type `PAGE` and the page id as its location, rendered as the page's current title, or "No access", under page visibility; ADR 0006's Link row already names pages.

### Person mentions (decision 354; 4.1c)

- **In page bodies**: `personMention { id }`, chosen with `@` from `GET /users/assignable` (2.7d's picker, as a Tiptap suggestion). A chip shows the person's current name; the node never stores the name.
- **Recorded on store, as the person who typed it** (decision 129). The collaboration server keeps, per document, the Yjs client ids each connection has used: a client id is claimed by the first connection whose update carries it, and an update carrying a client id another person claimed is refused and its connection closed (so nobody can write as someone else). On store, each mention node new since the last store is attributed to the person whose client id inserted it; `recordMentionsInTx` is generalised to a page source and records a `Mention` row (`pageId` set, `commentId` NULL) for each new person who is an ACTIVE member with `pages.view` and may read the page (`mentionableAmong`'s rules); the rest render as plain text with no chip and notify nobody, as an unrecorded token did in 2.7d. Mention nodes removed since the last store delete their rows.
- **Effects** as in 2.7d: the mentioned person becomes a page watcher, gets a `PAGE_MENTIONED` bell and, by preference, an immediate email naming who and which page and linking to it, never the text (decision 130). Audited `PAGE_MENTIONED` with ids.
- **In page comments**: mention nodes in the comment's rich text (decision 356, following decision 340), recorded by the comment usecases' `recordMentionsInTx` path from the document's nodes as a person's own write, with the `Mention` row carrying `pageId` and `commentId`. Decision 127's `<@userId>` tokens are not used for pages at all.
- **The model change**: `Mention.workItemId` becomes nullable, `Mention.pageId` is added, a CHECK requires exactly one; the comment key gains a twin `(commentId, pageId, tenantId)` → `Comment(id, pageId, tenantId)` beside the existing `(commentId, workItemId, tenantId)` (each enforced only when all its columns are set, Postgres's MATCH SIMPLE, which the CHECKs make exact).

### Comments (decisions 355 and 356; 4.1d)

- **On the `Comment` table** (ADR 0005 §6.10, ADR 0006's Comment row and the prompt; decision 355 asks the shape). `workItemId` becomes nullable; `pageId` is added with `(pageId, tenantId)` → `Page ON DELETE CASCADE`; a CHECK requires exactly one; `@@unique([id, pageId, tenantId])` beside the existing triple; `@@index([tenantId, pageId, createdAt])`. Every existing read is by `workItemId`, so page comments never appear on an item; the answer key still requires a comment of the same item, so a page comment can never be an answer.
- **Anchors**: `anchorFrom` and `anchorTo`, the two Yjs relative positions (base64), both or neither (CHECK); NULL is a comment on the whole page. They hold Yjs ids and clocks, not text: classified in the encryption guard's `NOT_SENSITIVE` with that reason. The anchored text itself is not stored; the panel shows the live text at the anchor. The highlight is a decoration drawn from comment rows, never a mark in the document, so commenting writes nothing to the document, a reader who may comment but not edit can comment, and a comment's text never enters the Yjs state (§6.10).
- **When the anchored text is deleted** the comment stays, listed as "The text this comment was on was removed", and can be resolved or deleted like any other.
- **Replies**: `parentCommentId` → `(parentCommentId, pageId, tenantId)` → `Comment(id, pageId, tenantId)`, so a reply is on the same page; one level only (a trigger refuses a reply to a reply); page comments only (CHECK). **Resolved**: `resolvedAt` and `resolvedByUserId` on a root comment only (CHECK), set and cleared by anyone who may comment on the page (`PAGE_COMMENT_RESOLVED`, `_REOPENED`); resolved conversations fold away in the panel.
- **Text** (decision 356, which follows decision 340 and was not asked separately): **rich text, in the same format as item comments**: a document of the item-text nodes (below), validated and sanitised by `sanitizeRichTextDocument`, stored encrypted in `Comment.bodyJson` with its plain-text projection in `Comment.body` (encrypted, as today), written from the comments panel's editor (no collaboration: a comment is a form write with its own author, not a CRDT). Edited by its author only and deleted by its author or an admin (`comment.policies.ts`, decision 53, unchanged); deleting a root deletes its replies in the same transaction. Page comments are rich from their first row in 4.1d, so `Comment.bodyJson`, the item-text schema, its validator and sanitiser and the static renderer arrive in 4.1d; 4.1g moves item comments and descriptions onto them. A CHECK requires `bodyJson` on a page comment.
- **Usecases**: `addPageComment`, `editPageComment`, `deletePageComment`, `resolvePageComment` beside the item ones, sharing the sanitiser, the policy, `recordMentionsInTx` and the page search seam (decision 347). The write-seam guards for mentions and search learn the new writers.

## Collaboration (4.1b)

### The collaboration server (decisions 357 and 359)

- **A new service, `collab`** (decision 357): `scripts/collab.ts` bundled by `scripts/build-worker.mjs` into `dist/collab.mjs` inside the existing worker image, started with its own command through `wait-for-migrations.mjs`, named `islestone-collab`, on `islestone_internal` only, watched by Watchtower with the `depends-on` label, `mem_limit` 384m and a stated heap (`--max-old-space-size=256`), `cpus` 0.5. The worker image already carries Prisma, the pruned production tree and the migration head; no third image. The worker import-graph guard gains `scripts/collab.ts` as a root (no NextAuth, no `next/headers`).
- **One instance** (decision 359), like the one app container (decision 50): documents live in its memory, so no `@hocuspocus/extension-redis` and no `UNLICENSED` exemption. A second instance needs that extension (or a sticky route per document) and is a later decision with its own measurement.
- **Two listeners**: the public WebSocket port that Caddy routes (below) and a private HTTP port on `islestone_internal` for the app's server-side writes (decision 361) and the healthcheck. Caddy never routes the private port.
- **Shutdown**: on SIGTERM the server stops accepting upgrades, stores every loaded document with pending changes, then closes connections, inside a budget below Docker's grace period (the pattern of `shutdown-budget.ts`); clients reconnect to the new container and resend what was not acknowledged.

### Authentication: the collaboration token

- `POST /api/t/:slug/pages/:pageId/collaboration-token` (`requirePermission('pages.view')`, through `getTenantCtx`, so the workspace MFA gate applies) mints `v1.<tenantId>.<pageId>.<userId>.<userSessionId>.<sessionVersion>.<access>.<issuedAtMs>.<nonce>.<mac>`, with `mac` an HMAC-SHA256 under `deriveSubkey('islestone-collaboration-token-v1')` and one spelling of the MAC (the H2f lesson in `form-token.ts`); `access` is `write` when the caller holds `pages.edit` and the page's scope is writable, else `read`; it lives 60 seconds (ADR 0005 §6.2). A route that mints for a page the caller cannot read answers 404.
- **`onAuthenticate`** verifies the MAC, the age, that the document name (`<tenantId>/page/<pageId>`) equals the token's, and the `Origin` header (equal to `NEXT_PUBLIC_APP_URL`'s origin, checked at upgrade in `onUpgrade`); then, through `runInTenantContext` as the workspace's system user, re-reads: the `UserSession` row live (not revoked, not expired, its `sessionVersion` current), the membership ACTIVE with `pages.view` (and `pages.edit` for `write`), the page live in a live, visible scope. A `read` connection is read-only (Hocuspocus does not apply its updates). Any failure closes the connection with a generic reason.
- **Refresh**: the provider fetches a new token every 45 seconds and sends it over the open connection (`onTokenSync`); each refresh re-runs every check and may downgrade `write` to `read`. A connection whose token is not refreshed within 60 seconds is closed. So a revocation takes effect within a minute even if its notice is lost (ADR 0005 §6.2).

### Staying authorised: losing access (decision 360)

- **The `access` notice now** (decision 360). The usecases that take access away publish, after their commit, a content-free notice on a per-workspace Redis channel (`ChangeNotice` `{ kind: 'access'; userId }` and, new, `{ kind: 'page'; op: 'delete' | 'move' | 'scope'; pageId }`), through one publish function guarded by a strict Zod schema (ADR 0005 §4); the collaboration server subscribes and closes, or downgrades, the affected connections at once. The publishers: member removal, role or custom-role change, session revocation and "revoke all", page delete and move, project archive (downgrade to read-only), delete and restore. 4.3 builds the SSE stream and every other notice kind on the same function and channel.
- H4's test: each of those acts closes or downgrades an open connection within the stated time.

### Persistence: the store path

- `onLoadDocument` reads `PageContent.state` (decrypted by the extension), decodes it into the document, and refuses a page whose decoded state exceeds the cap (decision 362).
- `onStoreDocument` (debounced 2 seconds, at most 10, the defaults) runs one transaction under the workspace's context as its system user: the new state, the projections, `contentUpdatedAt`, the mention and item-mention rows, (decision 347) the search rows, and an automatic version when due. A store with an unchanged state vector writes nothing.
- **Audit** (ADR 0005 §6.11, decided): one `PAGE_EDITED` entry per contributing person per page per 10 minutes, written as that person (`logEvent` with a context resolved for them at store time by `resolveMemberContext`; a contributor who no longer resolves is named by id in the system user's entry, never as the actor), saying who edited, never what. The window lives in the server's memory; a restart writes at most one extra entry.
- **Single write seam** (ADR 0005 §6.6 and §8): only the store path writes `PageContent` and the projections; a guard lists it, and the purge's cascade delete is the only other change to those rows.

### Server-side writes (decision 361)

A restore now, and from 6.2 an approved proposal, an import or a template, change page content on the server. Decided (decision 361): the app calls the collaboration server's private port (`POST /internal/pages/:pageId/apply`, a JSON body naming the change, signed with an HMAC under `deriveSubkey('islestone-collab-internal-v1')` and a timestamp, refused when older than 30 seconds); the server opens a direct connection (`openDirectConnection`), applies the change as the acting person, and stores. Live editors see it at once and the next store keeps it. When the server is down the app answers 503 and changes nothing. The app never writes `PageContent` itself.

### Untrusted content (ADR 0005 §6.7)

- Every update's size and rate are checked in `beforeHandleMessage`; `websocketOptions.maxPayload` bounds a frame before authentication.
- The decoded state's size is checked on store; a document past the cap stops accepting updates (its connections are closed with a reason the editor shows: "This page is too large; changes after this point were not saved").
- Projections validate against the schema and drop what it does not know; export and email sanitise again.
- Awareness state is checked in `beforeHandleAwareness`: its user id must be the connection's, its size bounded; names are fetched through the API from that id, never taken from a client.
- Client ids are claimed per person (above).

### Caps and rate limits (decision 362; H4 sets the final values)

The values (decision 362; H4 may tighten them): a decoded page state of at most 4 MB; one WebSocket message at most 1 MB; per connection at most 60 messages a second (bursts to 120) and 4 MB of updates a minute; awareness states at most 2 KB, 20 a second; per person at most 10 connections per workspace; per workspace at most 300 connections; per IP at most 30 upgrades a minute; a page at most ten levels deep; at most 500 automatic versions kept per page after compaction. Over a connection cap the upgrade is refused (HTTP 429 before the socket opens); over a message cap the connection is closed. The limits are counted in the server's memory (one instance, decision 50's reasoning), and every refusal is a metric with the workspace id never an attribute.

### Presence (decision 363)

Decided (decision 363): 4.1 ships what collaboration needs inside the editor (each person's caret and selection, labelled with their current name, through `@tiptap/extension-collaboration-caret` and Yjs awareness, throttled as ADR 0005 §5 says); 4.3 ships presence elsewhere ("who is here" on pages, items and canvases, R1's presence-only rooms).

### The route through the edge (decision 358)

- **The same origin** (decision 358). `wss://islestone.cloud/collab/…`: a `handle /collab/*` block in `deploy/caddy/islestone.caddy` routes WebSocket upgrades to `islestone-collab:<port>` (and answers 404 to anything that is not an upgrade), before the app's `reverse_proxy`, with the same `X-Forwarded-For` rule; Caddy's `request_body` limit does not apply to WebSocket frames, so the server's own caps are the limit. The Next middleware never sees these requests: the token, the Origin check and the per-IP upgrade limit replace the edge's checks, and `/collab` needs no `MACHINE_CALLER_PREFIXES` entry because it never reaches the app.
- **CSP**: `connect-src` gains the explicit `wss://<app host>` from `NEXT_PUBLIC_APP_URL` (today it holds `'self'`, `blob:` and `https:`, with `ws:` only in development, `csp.ts` lines 168 to 174), so no browser depends on how it reads `'self'` for WebSocket schemes.
- **Local and CI**: `docker-compose.yml` and the Playwright web server start the collaboration server beside the app; the client reads its URL from a new `NEXT_PUBLIC_COLLAB_URL` (in `src/env-client.ts`, `.env.example`, the compose file and `deploy/.env.prod.example` together).

## Rich text in work items (4.1g; decision 340)

**Decided: C, a departure from the recommended A** (decision 340, 2026-11-27). Work-item descriptions and work-item comments become rich text in 4.1, in the editor's item-text format and without collaboration; page comments use the same format from their first row (decision 356). This **supersedes decision 127's "plain text until 4.1"** (its plain text and its `<@userId>` token grammar); decisions 128 to 131 stand unchanged: a mention notifies and adds a watcher, machine-made text never mentions, a notification never carries the text, and a key typed in text links at display time. The recommendation was A because this change reaches built code across the product; the owner chose one text model for items and pages. What follows is the design under the decision. Where decision 340 named no choice, the map proposed one; the owner decided those six on 2026-11-27 as decisions 368 to 373 ("Decisions under decision 340" at the end of this part), five as proposed and one, the API's plain strings (decision 372), as a departure; and decision 374 keeps 2.7d's tokens in a person's plain-string write.

### The format

- **One schema module, two node sets.** `src/lib/pages/schema.ts` exports the page extensions and the **item-text** extensions, a subset: paragraphs, headings 1 to 3, bullet and numbered lists, quote, plain code block, divider, hard break, the marks (bold, italic, strike, inline code, link) and person mentions (`personMention { id }`). Not in item text: tables, toggles, callouts, a table of contents, work-item chips and embeds, and page links. A description or a comment is a field of a record, read in a detail and a panel, not a document: the blocks that make a page a page stay on pages. Keys typed in item text stay text and link at display time (decision 131 unchanged), so no item text stores another item's id.
- **Stored form.** The document is canonical ProseMirror JSON of the validated item-text nodes, in a new encrypted column: `WorkItem.descriptionJson`, `Comment.bodyJson`, `WorkItemTemplate.descriptionJson`. The existing columns keep their names and become the **plain-text projection** of the document, still encrypted and written only with it in the same statement: `WorkItem.description`, `Comment.body`, `WorkItemTemplate.description`. Keeping the old column as the projection means search, snippets, 6.2's read tools and the previous image during the roll all read valid plain text, and a migration never renames an encrypted column under Watchtower (migrations go forward; add, then remove in a later release). The projection is the text of every text node, blocks separated by a blank line and hard breaks by a newline; a mention projects as its legacy token `<@userId>`, which `searchableText` already strips, so no mention becomes a lexeme and the projection of a converted document equals its old text.
- **Optimistic concurrency is unchanged** (ADR 0002 §9, ADR 0005 §6.13): a description is still a row field, edited with `If-Match` required (428 without it) and a 409 with the current row; a comment edit is still its author's. Rich text changes the field's format, not its concurrency: descriptions do not move to Yjs.

### Validation and sanitisation

- **`sanitizeRichTextDocument`** (new, in `@/lib/security/sanitize`, beside the HTML and plain-text profiles) is the server's one door for item text: it parses the document against the item-text node set and **refuses** (400 `RICH_TEXT_INVALID`, naming the path) any node, mark or attribute the set does not know, rather than dropping it as the collaboration server's projection does (a request is a form write a person can correct; a CRDT update is not); runs every text node through `sanitizePlainText`; passes every link through `sanitizeUrlText` and the schemes `http`, `https`, `mailto`, `tel`; refuses an agent mention node until 6.3; and caps depth (16), nodes (10,000), mentions (`MAX_MENTIONS_PER_TEXT`) and the serialised size (the description's 100,000 characters, counted on the JSON) before encryption. The projection is computed from the sanitised document, never taken from the client.
- **Rendering** is the static renderer to React elements over the same node set (`RichText`, client-safe), never `dangerouslySetInnerHTML`; a node the renderer does not know renders nothing. HTML exists only for an export, rendered with `@tiptap/static-renderer` and passed through `sanitizeRichTextHtml`.
- `tests/guards/sanitize-rich-text-coverage.test.ts` learns the JSON columns: each encrypted rich-text column names the sanitiser that guards it.

### Mentions

- **Mention nodes replace tokens** in descriptions and comments, item and page alike: `personMention { id }`, chosen with `@` in the editor through a Tiptap suggestion over `GET /users/assignable` (2.7d's endpoint and rules). `mentionIdsOf(document)` in `src/app-layer/domain/mention.ts` (pure, client-safe) reads the ids of a document write. The token grammar (`parseMentionIds`) stays for two readers: a person's plain-string write (decision 374, below) and the converter that reads old text.
- **The rows stay the authority.** `recordMentionsInTx` reads the ids from the document and records exactly as 2.7d does: a person's own write only (`writesAsPerson`), new people only, each an ACTIVE member with `work_items.view` whose role sees the project (`mentionableAmong`), an edit recording and notifying only the people it adds and removing the rows of the nodes it drops. A mention node whose source has no row (a repeat copy, a template, a person dropped as not mentionable) renders as plain text with no chip and notifies nobody, as an unrecorded token did. Intake accept, templates, repeat copies, API keys, agents, the system user and the conversion job record nothing (decision 129). A person's own plain-string write keeps 2.7d's behaviour (decision 374): each valid `<@userId>` token becomes a mention node, recorded (`Mention` rows) and notified as today, through the same grammar (`parseMentionIds`) and `recordMentionsInTx`; machine paths (intake accept, templates, repeats, API keys, agents, the system user) record nothing, and the one-time conversion of stored text (decision 370) still turns a token into a node only where an existing `Mention` row backs it.
- **Effects are 2.7d's, unchanged**: the newly mentioned become watchers, `WORK_ITEM_MENTIONED` audited with ids, `emitMentionBells` after the commit, the immediate email by preference, never the text (decision 130).
- `MentionTextarea` and `MentionText` are replaced by the editor in its item-text mode and `RichText`; `segmentText` and the textarea picker's `mentionQueryAt` / `insertMention` retire with them.

### Converting what exists

- **A job, never a SQL migration.** Every description, comment and item-template description is ciphertext, so Postgres cannot read it. `rich-text-conversion` (on demand for one workspace through an admin route under `admin.manage`, audited; and nightly at 03:50 UTC until a workspace has nothing left, then a no-op) walks every live workspace as its system user, a keyset walk by id in pages of 500 per kind, each page reading only its own rows (the lesson of issue #79): the items of a page locked in id order (`lockForWrite`), their comments after them, then each row decrypted, converted, and written with a conditional update on the ciphertext it read (the rotation sweeps' pattern, so a row a person changed in between is left for the next run). Deleted comments and soft-deleted items are converted too, so a restore needs nothing.
- **The converter** (`src/lib/pages/convert-plain-text.ts`, pure, property-tested) interprets nothing but line structure: the text is sanitised again with `sanitizePlainText`; a blank line separates paragraphs; a single newline is a hard break; `*`, `#`, `_` and backticks stay what they were (old text was never Markdown, and reading it as Markdown would change what people wrote). A `<@userId>` token becomes a mention node **only where its source has a `Mention` row for that person**, because the rows were the authority; any other token stays the literal characters a reader saw. A key stays text. Properties: the projection of the converted document equals the old text after the converter's whitespace normalisation (runs of blank lines collapsed, line ends trimmed); converting twice changes nothing; the document always validates. So the job writes the document beside the old text and rewrites the old column only where that normalisation changed its whitespace, never its words.
- **What the conversion is not.** It bumps no `version`, writes no `editedAt`, records no mention row, rings no bell, sends no email and writes no audit entry per row: one counts-only `RICH_TEXT_CONVERTED` per workspace and run. It is not an edit: the marked answer's lock (decision 113) is a usecase rule for people, and the trigger `comment_answer_not_deleted` watches `deletedAt` only, so a marked comment is converted like any other. A key rotation running at the same time re-wraps whichever ciphertext it reads; each writes conditionally on what it read, so neither overwrites the other.
- **The search seam.** Each converted description and comment calls `SearchVectorRepository.replaceForSource` in its transaction with `{ keepTime: true }`, so a vector's `updatedAt` (decision 250's "recent") still says when a person last wrote the text, not when it was converted; the write-seam guard lists the job as a writer.
- **The roll.** Watchtower replaces the app while the previous image may still write a description as plain text into the old column. The new image treats a row whose stored text, normalised, is not the projection of its document as written by the previous image, reads it from the text and converts it again on its next write or the next run; so no description is shown from a stale document. From the release after 4.1g, every write path writes both columns and the check stays as a guard.
- **No way back once people format.** Until a row is edited in the editor its document is a lossless function of its old text; after that, the plain-text projection keeps the words and loses the formatting. Reverting 4.1g is therefore a forward fix, never a rollback of data.

### Every reader, as decided

- **Search** (ADR 0008 amended). `searchableText` takes the projection; mention nodes never become lexemes; `SEARCH_VECTOR_REVISION` goes from 1 to 2, so the nightly `search-index-rebuild` re-vectorises every description and comment from its projection (at most 100,000 writes of each kind a run, so a large workspace takes more than one night, during which its older vectors still find the same words), keeping each vector's time. Snippets are built from the decrypted projection. The search functions, their bodies and their pinned hashes do not change: they read lexemes.
- **Encryption.** `descriptionJson` and `bodyJson` (and the template's) join the encryption manifest; the rotation sweeps re-wrap them; a description now costs two ciphertexts, the document and its projection, roughly doubling its stored size.
- **Notifications and email.** Unchanged in what they carry: no bell, email or digest ever holds description or comment text (decision 130), so nothing renders rich text into a message; the mention and comment emails name who, which item and a link.
- **The work-item views.** The detail's description shows `RichText`; "Edit" loads the editor in its item-text mode (no collaboration, the toolbar, the `@` picker, a slash menu over the item-text blocks only) and saves with `If-Match`; the comments panel renders each comment with `RichText`, and the composer and an edit load the same editor; the create dialog's description, the intake accept dialog's description and the item-templates manager's description are the same editor. The editor's chunk (about 200 KB gzipped by inflect's estimate) loads on demand (`next/dynamic`, when a person starts writing), never with the list, the board, My Work or the detail's first paint; the detail sheet opened from a list shows rendered text first. The Activity renders comments with `RichText`.
- **The API's shapes.** A create and an update carry `description` as a document (`RichTextDocumentSchema`, built from the item-text node set, strict), and a comment's add and edit carry `body` as one; responses carry the document in the same field. **A plain string is accepted for good** (decision 372, a departure from the map's proposal to refuse it after one release): a `description` or `body` sent as a string is converted by the converter's line rule (decision 370: paragraphs and hard breaks, never Markdown) into a document and stored as that person's own write; it is never deprecated or refused. A person's own plain-string write keeps 2.7d's behaviour (decision 374): each valid `<@userId>` token becomes a mention node, recorded (`Mention` rows) and notified as today, through the same grammar (`parseMentionIds`) and `recordMentionsInTx`; machine paths (intake accept, templates, repeats, API keys, agents, the system user) record nothing, and the one-time conversion of stored text (decision 370) still turns a token into a node only where an existing `Mention` row backs it. 5.2's API keys publish both shapes, the string and the document. The list's rows never carried a description and still do not.
- **Answers (2.4b-c).** The marked answer is a comment, so its body is rich text: `PinnedAnswer` renders it with `RichText`, its `answer.mentions` from the rows; marking, clearing, the lock (409 `ANSWER_LOCKED`) and the composite key are unchanged.
- **Field sets.** A description is "present" when its document holds text or a mention; an empty document is empty for `FIELD_SET_UNMET`.
- **Templates, intake and repeats.** An item template's description and a project template's starter items' descriptions feed descriptions through `templateToCreateInput`, so they are stored in the same format (`WorkItemTemplate.descriptionJson`; a project template's content `version` 2 holds documents, and a version 1 document is read through the converter). An intake request's body stays plain text in intake (an outsider's text; ADR 0008 keeps it out of search) and becomes the new item's document through the converter at accept, with the form-field lines as paragraphs and no mention recorded. A repeat copies its source's document.
- **Export.** There is no work-item export today. Any later reader that exports descriptions or comments (5.2's API, 6.2's read tools, a workspace export) reads the document or its projection; HTML is rendered with the static renderer and passed through `sanitizeRichTextHtml`, and Markdown is written by the pages' serializer (`src/lib/pages/markdown.ts`), so H4's "sanitised on the server before any export" holds for item text too. Time entries' descriptions are their own plain text and unchanged.
- **Agents.** 6.2's read tools read the projection; a proposal that changes a description carries a document validated by `sanitizeRichTextDocument` like a request.
- **Imports and chat (later).** 5.4's replies by email and 5.5's importers bring outside text into comments and descriptions: each converts through the converter (or an importer's own mapping to the item-text nodes), never storing HTML or Markdown.
- **The seed and performance.** The scale seed writes documents and their projections, encrypted for real, and the 10k and 100k shapes keep their sizes; no new list query (the detail read gains a column); the conversion job's pages are plan-checked; the detail's statements per request do not change; the `item-detail` latency is re-measured with documents.

### Risks, named honestly

1. **Every description and comment ever written is rewritten by a job.** A converter bug reaches every workspace. Mitigations: the old text stays as the projection and the job changes at most its whitespace, conversion is idempotent and conditional, and a wrong document can be rebuilt from the text until a person edits it. After that, the text keeps words only (above).
2. **A rolling deploy writes both formats.** The previous image writes plain text for the minutes of the roll; the stale-document check covers it, but it is a rule every future write path must keep (a guard holds the two columns written together).
3. **More built code changes than in the six page pull requests together**: the search seam and its guard, mentions and their guard, intake accept, templates, project templates and their content version, repeats, field sets, answers, the detail, the comments panel, the Activity, the create dialog, the intake accept dialog, the templates manager, the API schemas, the permission-matrix bodies, the seed and several guards. 4.1g is the largest pull request of 4.1 by touched files.
4. **The editor's weight reaches the work-item views.** If its chunk loaded with the detail or the create dialog, the H2b budgets for the detail would regress; it loads on demand, and the rendered text uses the static renderer only.
5. **A larger attack surface on the most-read records.** Item text now carries links and structured documents from every member; the server's refusal of unknown nodes, the scheme list and the render-to-React rule are what stop a stored payload, and each has a test (a forged document with a `javascript:` link, an unknown node, an oversized or over-deep document, an agent mention).
6. **Storage roughly doubles for descriptions and comments** (two ciphertexts each), and the key-rotation sweeps have twice the values to page through.
7. **Search rebuilds everything once.** The revision bump re-vectorises every description and comment, over several nights in a large workspace; search stays correct meanwhile (old vectors, same words), and decision 250's order is kept by `keepTime`.
8. **Two mention paths live side by side.** Documents carry mention nodes, and a person's plain-string write still carries `<@userId>` tokens read by `parseMentionIds` (decision 374), so both must record, refuse and notify the same way, held by one test over both shapes; the converter reads tokens in stored text too, but only where a row backs them.
9. **Formatting is one-way.** People will format descriptions; a later decision to go back to plain text would lose it.
10. **Accessibility moves onto the busiest screen.** The editor's toolbar, keyboard and labels on the detail and in the comments panel need the H2e-style pass the board had; the copied editor brings inflect's accessible surface (`role="textbox"`, `aria-multiline`, labelled buttons), and its rendered test comes with it.

### Decisions under decision 340 (decisions 368 to 374)

The map proposed six choices that follow from decision 340; the owner decided them on 2026-11-27 (relayed), five as proposed and one as a departure, and then decided a consequence the map had inferred, against the inference (decision 374).

1. **Blocks** (decision 368, as proposed). Item text is a subset of the page schema: no tables, toggles, callouts, table of contents, work-item chips, embeds or page links; work-item keys in item text stay display-time links (decision 131).
2. **Storage** (decision 369, as proposed). The existing column (`WorkItem.description`, `Comment.body`, `WorkItemTemplate.description`) becomes the encrypted plain-text copy, and the rich document goes in a new encrypted column beside it (`descriptionJson`, `bodyJson`).
3. **Conversion** (decision 370, as proposed). Old text is converted by line breaks only (paragraphs and hard breaks), never read as Markdown; in stored text an unrecorded token stays literal text.
4. **Templates** (decision 371, as proposed). Item templates and project templates' starter items store descriptions in the same rich format; intake requests stay plain text until accepted.
5. **The API's plain strings** (decision 372, **a departure from the map's proposal**, which was to accept a string for one release and then refuse it). A plain-string description or comment is **accepted for good**, converted by line breaks (decision 370), and never deprecated or refused ("The API's shapes").
7. **Tokens in a person's plain string** (decision 374, **against the map's inference** that such a token stays literal text). A person's own plain-string write keeps 2.7d's behaviour (decision 374): each valid `<@userId>` token becomes a mention node, recorded (`Mention` rows) and notified as today, through the same grammar (`parseMentionIds`) and `recordMentionsInTx`; machine paths (intake accept, templates, repeats, API keys, agents, the system user) record nothing, and the one-time conversion of stored text (decision 370) still turns a token into a node only where an existing `Mention` row backs it.
6. **The conversion's audit** (decision 373, as proposed). The conversion bumps no version and writes no audit entry per row: one counts-only `RICH_TEXT_CONVERTED` entry per workspace and run; no notification and no mention row.

## Keys and who sees what (decisions 339 and 342)

- **The `pages` domain** (decision 339) replaces the unused `docs`: `pages.view`, `pages.create`, `pages.edit` (body, title, move within what the caller may write, versions), `pages.comment`, `pages.delete` (delete and restore). OWNER and ADMIN hold all; MEMBER holds all; VIEWER holds `view`; GUEST nothing until 8.4 (decision 204). ## H4 and 4.1

Tests 4.1 ships for H4's lines (the canvas and upload lines are 4.2's and 4.4's):

- **Losing access disconnects**: a removed member, a narrowed role (losing `pages.edit` downgrades to read-only; losing `pages.view` closes), a revoked session and "revoke all", a deleted page, a page moved out of reach, an archived project (read-only) and a deleted one: each closes or downgrades an open connection within the stated time, by notice and, with the notice dropped, by the token refresh.
- **Tokens**: expired, another workspace's page, another page, a tampered or re-spelled MAC, a wrong `Origin`, a token whose session was revoked after minting: each refused. A read-only connection's updates are never applied.
- **Two tenants**: the server never loads a document whose name's workspace differs from the token's; every new table has its two-tenant test in `ISOLATION_TESTED`.
- **Caps per tenant**: an oversized frame, an oversized document, a message flood, a connection flood from one workspace that leaves another's connections working.
- **Sanitisation**: a forged update with a `javascript:` link, an unknown element, an attribute the schema does not know: none reaches a projection, an export or the browser's rendering; exported Markdown and the print view's HTML pass the sanitiser.
- **Convergence**: two clients editing one page converge; a restore during a live session survives the next store.
- **Attribution**: an update claiming another person's client id is refused; a mention typed by A is recorded as A's.
- **Item text** (4.1g, decision 340; the H4 sanitisation line applied to descriptions and comments): a forged document with a `javascript:` link, an unknown node, mark or attribute, an over-deep or oversized document and an agent mention are refused with 400 `RICH_TEXT_INVALID`; nothing stored renders through anything but `RichText`; an exported or printed description passes the sanitiser.

## Rules no decision names (4.1a, as built)

Built on `wt/p41map` after the decisions; each is a choice the decisions and the body above leave open, recorded here and in [`docs/pages.md`](../../pages.md).

1. **`PageContent` has its own `id`**, with `pageId` unique, where the sketch made `pageId` the key: the key-rotation sweeps (`key-rotation`, `tenant-dek-rotation`) page every manifest table by `id`. `schemaRevision` defaults to 0 ("no projection built yet") and `stateBytes` to 0, so a create writes the row empty. `app_user` holds no DELETE on it: the row goes with its page's cascade.
2. **The same-tree rule is a deferred constraint trigger** (`page_same_scope`), checked at commit on every insert and every change of `parentId` or `projectId`: the row's parent is in its tree, and so is every child of it. A move rewrites a subtree row by row, so a row-level check before commit would refuse every cross-tree move.
3. **A move carries the subtree's deleted rows too**, where the body says "its live subtree": every row stays in its parent's tree (rule 2), and a restore later lands in the tree its parent is in. They stay deleted.
4. **Creates and reorders take the page-tree lock too**, besides the writes the body names: the placement (`keyBetween` over the live siblings) and the depth check read the tree. Every tree write waits its workspace's turn first (`inPageTreeQueue`, one at a time); a rename takes neither (one versioned row).
5. **Title search is a route of its own in 4.1a, not the palette**: `GET /pages/search` (`pages.view`), read by the move dialog's parent search. The palette's search route has a statements budget of 6 that only goes down, and its Pages group arrives whole, with bodies and comments, in 4.1f. Like the item search, it leaves an archived project's pages out, though they are readable.
6. **`search_page_titles`** takes the visibility input like the item functions and keeps a page to the workspace's tree or a live, unarchived project in that input; the caller asks `pages.view` first. Its spec joined `tests/helpers/search-definer.ts` (a `Page` table, its `deletedAt`, the page-tree predicate), its body hash is pinned, and `app_search_definer` gained column SELECT on five `Page` columns.
7. **The Deleted list takes `pages.delete`**, the key that restores, as the work items' Deleted view takes `work_items.delete`; it lists each group's root with the group's size, newest first, at most 500.
8. **A tree read answers 200 children at a time** with an `after` cursor (the last page's id) and each child's live subpages counted, so the tree knows when to offer "Expand".
9. **A move's `If-Match` is optional** (a rename's is required, decision 343): a move changes no text, and the tree lock orders concurrent moves.
10. **A restored root whose kept key a live sibling holds comes back right after that sibling** (`keyBetween` with the next live key). Only the root can collide: nothing can be created or moved under a deleted page.
11. **Bounds**: a delete or a move carries at most 2,000 pages (409 `PAGE_TREE_TOO_LARGE`); the purge deletes whole groups only, at most ten a transaction; the rebalance one sibling group a transaction, at most 500 groups a workspace a run, at 03:55 UTC; `page-purge` runs at the body's 02:50 UTC, beside `intake-purge`.
12. **The data migration's audit goes through the audit outbox**: a migration cannot compute the chain's hash, so it queues one counts-only `CUSTOM_ROLES_DOMAIN_RENAMED` (`category: 'custom'`, `rolesRewritten`) per workspace with rewritten roles, and `audit-outbox-flush` appends it within five minutes. A `docs` key that is not an object is dropped; a role already holding `pages` keeps it.
13. **Page joined the plan checks' guarded tables**, and the scale seed holds pages (about 1,100 at 10k: one per ten items in each project's tree, ten per project in the workspace's, up to five deep, about 3 % of leaves deleted). Every page budget is an estimate: nothing was measured when 4.1a landed (no disk to seed on the development machine). No latency scenario yet: `page-open` and `page-tree` come with 4.1b's `page-sync`.
14. **A page's address is `/t/<slug>/pages/<id>`** whatever its tree, so a move keeps it; the project's Pages are `/projects/<KEY>/pages`, reached by a "Pages" link in the project page's header (the project page has no tab bar; the milestones link is the same).
15. **The Pages sidebar entry is built and held back** by a constant (`PAGES_IN_SIDEBAR = false` in `nav-config.ts`), so 4.1b turns it on in one line; `/pages` is classified a main page and in `NAV_PATHS`, reachable by its address meanwhile.
16. **The body area says "This page has no content yet."** until 4.1b's editor.
17. **`createdByUserId` is an actor stamp with no key**, as on goals: a page outlives its creator's membership.
18. **Nothing was copied in 4.1a**: decision 366's rows (the editor, its copy and test, the version diff) arrive with 4.1b and 4.1e, which use them, so no `PROVENANCE.md` row is owed yet.

4. **What shape does the tree take?** (decision 341)
   - A (recommended). One tree per project and one for the workspace, nested at most ten levels, ordered by hand; a page moves with its subtree within its tree and across trees (project to workspace, workspace to project, project to project). Deep enough for any wiki; moving a section between projects works.
   - B. As A with no depth limit. No arbitrary cap; the breadcrumb and the recursive reads need a bound anyway.
   - C. As A, but no moves across trees. Simpler moves; reorganising means copy and delete, losing comments and versions.
   - **Decided:** A, one tree per project and one for the workspace, ten levels, moves with the subtree within and across trees (decision 341, 2026-11-27).

**The tree and its pages**

5. **Can a page be narrower than its tree?** (decision 342)
   - A (recommended). No: a project page is readable by whoever reads the project, a workspace page by every `pages.view` holder; per-page restriction waits for 8.4's grants. One visibility rule, already enforced everywhere.
   - B. A page may be marked private to its creator (a personal draft). Common in wiki tools; a second visibility rule in every page read, search and refs answer.
   - C. Per-page member lists. Fine-grained; a sharing model built ahead of 8.4.
   - **Decided:** A, no page narrower than its tree; per-page restriction waits for 8.4 (decision 342, 2026-11-27).

6. **Where does a page's title live?** (decision 343)
   - A (recommended). A plaintext row field (at most 200), renamed by a versioned write, shown in the tree, breadcrumb, notifications and search without opening the content. Cheap reads, plain search; two people renaming at once get a 409 rather than a merge.
   - B. The first heading of the Yjs document, projected to the row on store. Collaborative title edits; the title lags by the store debounce and every title read depends on the collaboration server's projection.
   - **Decided:** A, a plaintext row field of at most 200, renamed by a versioned write (decision 343, 2026-11-27).

7. **What happens on delete, and is there an archive?** (decision 344)
   - A (recommended). Delete soft-deletes the page and its subtree as one group (undo toast), restore through the group's root, a nightly purge after 30 days; no page archive (an archived project makes its pages read-only). The work items' rules, already understood.
   - B. As A, plus "Archive" for a page (read-only, hidden from the tree, kept). Old pages can be kept out of the way; a third state to read everywhere.
   - C. Hard delete behind the undo toast only. Simplest; a mistaken delete after five seconds is unrecoverable.
   - **Decided:** A, a subtree soft delete in one group through the undo toast, restore by the root, the 30-day purge, no page archive (decision 344, 2026-11-27).

8. **Which projections are stored?** (decision 345)
   - A (recommended). The Yjs state (source of truth) plus encrypted `contentJson` and `plainText`, and the mention and item-mention rows; sanitised HTML rendered at each export or email from `contentJson` (a departure from ADR 0005 §6.4). One fewer encrypted copy; the sanitiser's current rules apply at the point of use.
   - B. As ADR 0005 §6.4 says: also a stored, sanitised HTML projection. No rendering at export; a stored copy that must be rebuilt when the sanitiser changes.
   - C. The state only; projections computed on demand by the collaboration server. Nothing derived is stored; every read of content (agents, export, diff, search) goes through the collaboration server.
   - **Decided:** A, the Yjs state plus encrypted `contentJson` and `plainText` and the mention rows; HTML rendered at use, a departure from ADR 0005 §6.4 recorded there (decision 345, 2026-11-27).

**Content, encryption and search**

9. **How is the binary Yjs state encrypted?** (decision 346)
   - A (recommended). Base64 text in a `String` column, encrypted by the existing manifest path; the rotation sweeps re-wrap it unchanged. No change to security-critical code; about 1.8 times the raw size.
   - B. Teach the encryption extension, both rotation sweeps and the manifest guard a `Bytes` path. Smaller rows; new code in the most sensitive module.
   - C. Encrypt in the collaboration server's repository, outside the manifest. Flexible; a second encryption path the guards cannot see, against CLAUDE.md's manifest rule.
   - **Decided:** A, base64 text in a `String` column through the existing manifest path (decision 346, 2026-11-27).

10. **Are pages searched, and how?** (decision 347; an ADR 0008 amendment)
    - A (recommended). Titles, bodies and page comments, through a `PageSearchVector` table of plaintext stemmed words on the decision-245 pattern, bounded like decision 250. Pages are found like items; **the searchable words of every page and page comment become readable in the database, its dumps and off-host backups**, as decision 124 accepted for descriptions and comments.
    - B. Titles only. Nothing new readable; a page's body is never found from the palette.
    - C. Titles, and bodies by keyed word tokens (ADR 0008's never-built option A). No readable words; a second search mechanism, whole words only, no stemming.
    - D. Nothing. No exposure; pages cannot be searched at all.
    - **Decided:** A, titles, bodies and page comments through `PageSearchVector`, knowing that the searchable words of every page and page comment are readable in the database, its dumps and its off-host backups. Applied: ADR 0008 amended (decision 347, 2026-11-27).

11. **What does a version hold?** (decision 348)
    - A (recommended). The page's content JSON at that moment, encrypted (a departure from ADR 0005 §6.9's "encoded snapshots"). Viewing, comparing and restoring read it directly; it carries no Yjs history (none is usable with garbage collection on).
    - B. The full encoded Yjs state, encrypted. Closest to ADR 0005's words; every view or diff decodes a state first.
    - C. Yjs snapshots over a document with garbage collection off. Tiny versions and character-level history; the document grows for ever and every load replays it.
    - **Decided:** A, the content JSON per version, encrypted, a departure from ADR 0005 §6.9 recorded there (decision 348, 2026-11-27).

12. **When are versions made, and how long are they kept?** (decision 349)
    - A (recommended). Automatically when editing goes quiet for 10 minutes and at most hourly while it continues, on "Save version" (named), and before every restore; automatic ones thinned to all for 7 days, one a day for 90 days, then one a week; saved ones kept for the page's life, until 8.3's retention table says otherwise. Enough history to recover a week of work; storage bounded.
    - B. Keep every automatic version. Nothing ever thinned; storage grows with every editing session.
    - C. Only saved versions and before-restore copies. Least storage; nothing to go back to unless someone remembered to save.
    - **Decided:** A, automatic versions on a quiet 10 minutes and at most hourly, saved and before-restore versions, automatic ones thinned to all for 7 days, daily to 90 and weekly after (decision 349, 2026-11-27).

**Editor**

13. **How are versions compared?** (decision 350)
    - A (recommended). A block-level line diff of the two versions' Markdown, with jsdiff (BSD-3-Clause) in inflect's copied `VersionDiff`. Small, already proven in inflect; formatting-only changes show as changed lines.
    - B. A structural, inline diff through `prosemirror-changeset` (MIT, inside `@tiptap/pm`). Changes shown in place in the rendered page; more code to write and test.
    - C. No compare in 4.1; view and restore only. Least work; a reviewer cannot see what changed.
    - **Decided:** A, a block-level line diff of the Markdown with jsdiff in inflect's copied `VersionDiff` (decision 350, 2026-11-27).

14. **Which blocks does the editor offer?** (decision 351)
    - A (recommended). Paragraphs, headings 1 to 3, bullet and numbered lists, quote, plain code block, divider, table, links, person and work-item mentions, work-item embeds, page links; a slash menu over them; no images until 4.4, no external embeds, no callouts or toggles. Covers specs and meeting notes; every block is in the sanitiser's allowlist.
    - B. As A, plus toggles (details), callouts and a table of contents (all MIT now). Richer pages; more nodes to project, sanitise, export and transform later.
    - C. As A without tables. Smallest schema; tables are a common need.
    - **Decided:** **B, the core blocks plus toggles, callouts and a table of contents, a departure from the recommendation** (decision 351, 2026-11-27). Applied: "Blocks and the slash menu" and "The three added blocks" (`@tiptap/extension-details` and `-table-of-contents`, MIT, pinned in 4.1b; the callout Islestone's own node with a closed `tone`; a toggle's open state never stored; the table of contents computed, never stored; export and print written without widening the sanitiser's allowlists), the packages table, the vocabulary's three rows, and 4.1b's and 4.1e's sizes. Item text does not take them (decision 368).

15. **May a page hold untracked to-dos?** (decision 352)
    - A (recommended). No checkbox lists; "Create work item" turns a line or selection into a real work item and leaves its chip. Principle 3 holds: tracked work is a work item.
    - B. Checkbox lists as formatting, never tracked. Familiar; a second kind of to-do beside work items.
    - C. Both. Choice for the writer; the ambiguity principle 3 exists to avoid.
    - **Decided:** A, no checkbox lists; "Create work item" turns a line into a work item and leaves its chip (decision 352, 2026-11-27).

16. **How do work items appear in pages, and pages on items?** (decision 353)
    - A (recommended). An inline chip and a block embed, each storing the id only and rendered through a refs read that answers "No access" for anything the reader cannot see; "Mentioned in pages" on the item from a stored projection; "Link a page" on the item as a `WorkItemLink` of type `PAGE`. Both directions navigable, always current, never leaking.
    - B. As A without "Mentioned in pages". No projection rows; an item never shows the pages that discuss it.
    - C. As A without the item's page link. One mechanism fewer; an item cannot point at its spec unless the spec mentions it.
    - **Decided:** A, chips and embeds by id through the refs read, "Mentioned in pages" and "Link a page" (decision 353, 2026-11-27).

**Mentions and comments**

17. **How are people mentioned in page bodies, and who is the author?** (decision 354)
    - A (recommended). A mention node with the person's id, recorded on store as a `Mention` row with a page parent, attributed to the person whose Yjs client id inserted it (client ids claimed per connection, a claim on another person's id refused); notifies and makes the person a watcher, as 2.7d does. Decision 129 holds inside a CRDT.
    - B. A separate `PageMention` model. No change to `Mention`; two models for one concept.
    - C. No person mentions in bodies, only in page comments. No attribution machinery; people cannot be called into a page's text.
    - **Decided:** A, a mention node recorded on store as a `Mention` row with a page parent, attributed by claimed client ids (decision 354, 2026-11-27).

18. **What shape do page comments take on `Comment`?** (decision 355)
    - A (recommended). `workItemId` nullable, `pageId` added, exactly one by CHECK; an optional anchor (two Yjs relative positions; the comment survives its text's deletion, marked as such); one level of replies; resolved and reopened on root comments. Inline review as people expect, on the existing table.
    - B. A separate `PageComment` model. Leaves the work-item comment code untouched; contradicts the prompt, ADR 0005 §6.10 and ADR 0006's Comment row, which would need amending.
    - C. As A without anchors (comments on the whole page only). Simpler; no "comment on selection".
    - **Decided:** A, `workItemId` nullable and `pageId` added with exactly one by CHECK, optional anchors, one level of replies, resolved and reopened (decision 355, 2026-11-27).

19. **What text format do page comments use?** (decision 356)
    - A (recommended). Decision 127's plain text with `<@userId>` tokens, as item comments. One comment grammar, one sanitiser profile.
    - B. Rich text (the editor, without collaboration). Formatting in comments; a second comment format and its own sanitiser path.
    - **Decided:** **Rich text, in the same format as item comments; not asked separately, it follows decision 340** (decision 356, 2026-11-27). Option A (decision 127's plain text with tokens) assumed item comments stayed plain; with decision 340 one comment grammar means rich text for both. Applied: "Comments", "Text"; page comments use the item-text node set, `Comment.bodyJson` and mention nodes from their first row in 4.1d.

**Collaboration and deployment**

20. **Where does the collaboration server run, and where does its memory come from?** (decision 357)
    - A (recommended). A new `collab` service from the worker image, 384 MB, and the stack's ceiling raised from 4 GB to 4.5 GB on the shared VM (the compose file says about 11 GB is free beside Agrent and Playerz). Own process as ADR 0005 §6.1 requires; nothing else loses memory.
    - B. A new service at 384 MB inside the 4 GB, taken from the app (1,024 to 768) and the worker (768 to 640). No change to the ceiling; less headroom for requests and jobs.
    - C. Inside the worker process. No new container; a long job stalls typing, and a worker restart drops every editor.
    - **Decided:** A, a `collab` service from the worker image at 384 MB, the stack's ceiling raised from 4 GB to 4.5 GB on the shared VM (decision 357, 2026-11-27).

21. **How do browsers reach it?** (decision 358)
    - A (recommended). The same origin, `wss://islestone.cloud/collab/…`, routed by Caddy straight to the service before the app; an explicit `wss://` origin in `connect-src`. No new name or certificate; the token and the server's own checks replace the edge middleware.
    - B. A subdomain, `collab.islestone.cloud`. Clean separation; DNS, a certificate and a cross-origin rule to maintain.
    - C. Through the Next server (a custom server with WebSocket upgrades). One entry point; ADR 0005 §6.1 chose not to rely on it, and the standalone server would change.
    - **Decided:** A, the same origin, `wss://islestone.cloud/collab/…` through Caddy, an explicit `wss://` origin in `connect-src` (decision 358, 2026-11-27).

22. **One instance, or several from the start?** (decision 359)
    - A (recommended). One instance, documents in its memory, no `@hocuspocus/extension-redis`. Matches decision 50; avoids the extension's dependency `@sesamecare-oss/redlock` 1.4.0, whose `package.json` says `UNLICENSED` though it ships an MIT `LICENSE.md`.
    - B. Several instances through the Redis extension, with an ADR 0007 exemption for redlock 1.4.0 pinned to its MIT file. Ready to scale; an exemption, a second ioredis copy, and page updates in flight through Redis.
    - **Decided:** A, one instance, no `@hocuspocus/extension-redis`, so no `UNLICENSED` exemption (decision 359, 2026-11-27).

23. **How does losing access reach an open connection in 4.1?** (decision 360)
    - A (recommended). Content-free `access` and `page` notices published after commit on a per-workspace Redis channel, through ADR 0005 §4's one guarded publish function, which 4.3 then extends; the token refresh stays the backstop. Disconnection is immediate (H4); 4.3 inherits the channel.
    - B. The 60-second token refresh only. Nothing of 4.3 built early; a removed member keeps editing for up to a minute.
    - C. The app calls the collaboration server's private port for each revocation. Immediate; a second mechanism beside the channel 4.3 builds anyway.
    - **Decided:** A, content-free `access` and `page` notices on a per-workspace Redis channel through ADR 0005 §4's guarded publish function; the token refresh the backstop (decision 360, 2026-11-27).

24. **How does the app change page content on the server (restore now, proposals later)?** (decision 361)
    - A (recommended). An HMAC-signed call to the collaboration server's private port, applied through a direct connection as the acting person. One write seam (ADR 0005 §6.6); live editors see it at once; a 503 when the server is down.
    - B. A queued job the collaboration process consumes. Durable and retried; a restore is not immediate.
    - C. The app writes the stored state itself when no session is open, else asks the server. Works while the server is down; two write paths, against §6.6.
    - **Decided:** A, an HMAC-signed call to the private port applied through a direct connection as the acting person; a 503 when the server is down (decision 361, 2026-11-27).

25. **What are the caps and rate limits?** (decision 362; H4 sets the final values)
    - A (recommended). A page state at most 4 MB; a message at most 1 MB; per connection 60 messages a second (bursts 120) and 4 MB a minute; awareness 2 KB, 20 a second; 10 connections per person per workspace, 300 per workspace; 30 upgrades a minute per IP; ten levels deep; 500 automatic versions per page. Generous for writing, bounded for abuse, sized for one instance.
    - B. Half of each. Safer for one small container; long pages and busy workshops hit them.
    - C. Twice each. Room for large pages; one workspace can take more of the one instance.
    - **Decided:** A, the values as written; H4 sets the final values (decision 362, 2026-11-27).

    - B. No carets until 4.3. Smaller 4.1; editors collide blind.
    - C. All page presence now, including the "who is here" row. More of 4.3 early; a second presence surface to align later.
    - **Decided:** A, carets and selections with names inside the editor; "who is here" in 4.3 (decision 363, 2026-11-27).
