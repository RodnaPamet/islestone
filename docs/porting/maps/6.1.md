**What the funnel stub does not do: feed the circuit breaker.** At the source the breaker's rate signals are fed only from `src/lib/mcp/authorize.ts` (`openBreakerGate` L1074, `recordAuthorizedCall` L1300, which calls `observeToolCall` and `evaluateWindow`). **Order relative to 6.2.** The 6.2 map (`6.2.md` "Ordering" step 2) recommends landing 6.2a's funnel library before 6.1's engine-tools change. If that happens, `funnel.ts` is a re-export file from its first commit and the stub bodies above are never written. Either order works; the interface is the contract.

## Prisma models and migrations

Islestone starts with a fresh migration history, so no source migration is replayed. Write **one migration** (for example `<ts>_agent_engine`) after 1.3's base migration and 1.5's audit and encryption migrations. Put the models (and `AiDecisionLog`) in a new `prisma/schema/agent.prisma` and the enums in Islestone's `enums.prisma` (one file per rule, as 1.3 sets it up). Replaying is the wrong tool because the source history is about 30 incremental ALTERs, backfills and `NOT VALID` rewrites (for example `20260913000000_tenant_fks_composite_batch2`). Their rolling-deploy hedges have no meaning on an empty database: nullable columns "because added to a populated table", and text columns plus CHECK where an enum would do.

### Known traps

- **The funnel is the engine's authority.** Until 6.2 lands, `funnel.ts` has an empty registry. Every Tool Runner run settles `EMPTY_CATALOGUE`, and a static definition with a READ or PROPOSE step fails at its first tool call. That is the safe direction, but it means 6.1 delivers no usable agent run in production, and no route starts a profile run (S). The static driver relies on the funnel for its tool-boundary kill-switch and guard checks; the Tool Runner checks the kill switch itself before every model call. Recommend landing 6.2a immediately after 6.1, or before it (6.2's recommendation).
- **The proposal seam answers "none" and must not outlive 6.1.** Each stub's empty answer is true only while no proposal can exist. The day 6.2 registers a propose tool, every seam body must be the real read in the same change; otherwise the breaker never counts a quarantined proposal, compaction drops queued proposals from the run-state block, and a run awaiting a person is stamped "no human review". Put the six functions in one file so 6.2 cannot miss one, and give 6.2 a test per function.
- **"Make both drivers pass it."** The source has no conformance adapter for the static driver: it takes no model turns, so the run scenarios do not apply to it. Only the Tool Runner (run half, `tests/unit/agentic/tool-runner-driver.test.ts`) and Flue (`tests/flue/…`, cut) have adapters. Islestone either writes a static adapter that declares a variance for each model-turn scenario, each naming an owner decision (`checkVariances` refuses one without), or records in an ADR that the run half binds reasoning engines only. Both engines can pass the admission half (the admission adapter registers its own `tool-runner` definition). Recommend the ADR note.
- **`Agent` before 6.3.** Runs, cards, kills, breakers and profiles all FK the agent, and the admission scenario reads its standing. So 6.1 lands a minimal `Agent`, and 6.3 extends it (delegate, sessions, checkout, budgets, transfer, retirement triggers, invocation depth). The alternative is plain `agentId` strings with no FK until 6.3. The owner should pick one before the migration. Either way, no 6.1 code creates an agent: tests seed them.
- **Hard-coded paths and lists.**
  - `SKILLS_DIR` is `process.cwd()`-relative (`skills/index.ts` L132), so tests must run from the repository root, and the production image must contain `src/lib/agentic/skills/corpus` (I). Without it every Tool Runner start fails with ENOENT, which is what source #4301 was.
