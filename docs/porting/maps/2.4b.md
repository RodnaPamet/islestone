## Summary

- **Nothing is copied.** inflect-compliance's `Task` has a second person column (`reviewerUserId`, `prisma/schema/tasks.prisma` line 31) and an "awaiting review" list filter, and a free-text `resolution` (line 26). Neither is taken: a reviewer is 2.8's concern, and the answer here is a pointer to a comment, not a text column. Everything is written fresh.
- **(1) Waiting on** is one nullable column, `WorkItem.waitingOnUserId`, a member under the same composite FK and RESTRICT rule as the assignee, cleared by every move into Done or Cancelled (one effect in `stateTransitionEffects` and a CHECK that makes forgetting it impossible), recorded in `WorkItemTransition` so 3.6 can count time waiting. A single-field versioned write, a filter, a column and a lane. It never makes anyone accountable.
- **(2) Field sets** are rows, `WorkItemTypeField` (one per type and field: required, optional or hidden). Built-in fields' rules belong to the type workspace-wide; custom fields' rules belong to the type within one project, because custom fields belong to a project (ADR 0002 §7). One pure, client-safe module evaluates them, for the usecases and for every form. Enforcement touches every create path, not only the create route: template sub-items, project template starter items, repeat copies and intake accept all go through it.
- **(3) Questions**: `WorkItem.answerCommentId` points at one live comment of the same item. Marking it is a person's act (`work_items.edit`, never an API key or agent), moves the item to a Done state in the same versioned write, and notifies watchers. The answer is itself a field-set field (shown or hidden, hidden by default), so "Question" needs no type identity: it is a type row with a field set, made by a Settings preset, plus an item template.
- **Size.** About 5,500 lines of source and 4,000 of tests, so three pull requests in the prompt's order (open question 20).
- **The roadmap's open questions** (words, where a field set lives and what it does to old items, who else sets waiting-on, the answer and decision 53, which Done state, seeding Question) are refined below, with eleven new ones the code raised.

## Vocabulary (ADR 0006)

Rule 1: each concept gets a row before its first model or label. Proposed words (open questions 1–3):

| Concept | Model | UI | Note |
|---|---|---|---|
| Waiting on | `WorkItem.waitingOnUserId` | Waiting on; "Waiting on me" (2.7) | Not Owner, Responsible, Assignee (banned or taken). "Awaiting" stays the agent session's (`AWAITING_INPUT`, ADR 0003 §5). |
| Field set | No model: a type's `WorkItemTypeField` rows; enum `FieldRequirement` (`REQUIRED`, `OPTIONAL`, `HIDDEN`) | Fields (a type's tab); Required, Optional, Hidden | Like "Workflow", which is a team's `WorkflowState` rows. Not "Field layout" ("Layout" is a view's), not Property or Attribute (banned for custom fields), not "Form" (an intake form). |
| Answer | `WorkItem.answerCommentId` | Answer; "Mark as answer", "Clear answer" | Not "Accepted answer" (Accept is intake's verb and a banned synonym of Approve), not "Reply" as a model (banned for comments). |
| Question | No model: a work item type a workspace makes (user data, like Feature) | Question | ADR 0006's Form field row already reserves the word for this type. |

**A trap in the guard.** `tests/guards/schema-vocabulary.test.ts` reads every ban from the table, and an unqualified ban that names no concept becomes a schema-wide strict ban. So the new rows qualify every ban that could collide: banning "Awaiting" bare would refuse 6.3's `AWAITING_INPUT`, and banning "Requirement" bare would refuse `FieldRequirement`. The drafts below are written that way.

## Part 1 — Waiting on

### Model and migration (`2026112x120000_waiting_on`)

- `WorkItem.waitingOnUserId String?`, composite FK `(tenantId, waitingOnUserId)` → `TenantMembership(tenantId, userId)`, `ON DELETE RESTRICT`, exactly as `assigneeId` (ADR 0003 §1).
- **CHECK `WorkItem_waiting_on_open_only`**: `"stateCategory" NOT IN ('DONE','CANCELLED') OR "waitingOnUserId" IS NULL`. The rule "cleared when the item closes" is then unrepresentable to forget: a path that moves an item into a closed state without clearing it fails instead of leaving a stale name.
- Index `@@index([tenantId, waitingOnUserId, stateCategory, dueDate])`, the twin of the assignee's: it backs the filter, the lane counts and 2.7's "waiting on me" section, and satisfies the FK-index guard (Layer B).
- `WorkItemTransition.waitingOnUserId String?` (NULL in older rows), and the trigger function and `work_item_transition_update` replaced with the column in the row, in `UPDATE OF` and in the `WHEN` clause, as 2.5b did for the milestone. 3.6 then reads time waiting from recorded changes, never from the current value (decision 76 as written into 3.6). Open question 8.
- No RLS change: no new table. `db:check-schema-drift` and the catalogue test (`tests/integration/…-sql-constructs`) cover the CHECK and the trigger.

### Usecases, routes and keys

- `setWorkItemWaitingOn(ctx, id, { userId | null }, expectedVersion?)` in `work-item.ts`, the shape of `assignWorkItem`: `loadWritableItem`, refuse a closed item (409 `ITEM_CLOSED`, the CHECK is the backstop), `assertActiveMember` (the assignee's rule; open question 4), `WorkItemRepository.updateVersioned` (the version increases; `If-Match` optional, a single-field change, ADR 0002 §9), audit inside, bells after the commit.

- `createWorkItemInTx` takes `waitingOnUserId` (a Question needs it at create); refused when the create's state is closed. `CreateWorkItemInput`, its Zod schema and `overridesOf` gain it.
- **Every move into a closed state clears it**, through one place: `stateTransitionEffects` returns `waitingOnUserId: null` for a move into `DONE` or `CANCELLED`. Its callers today: `setWorkItemState`, `bulkSetWorkItemState`, `moveWorkItemOnBoard`, marking a duplicate (`work-item-relations.ts`), the state delete's bulk move (`workflow-state.ts` → `TeamRepository.moveItemsToState`, whose `effects` parameter is typed to two timestamps and must widen), and the create path. A reopen does not restore it.
- `removeTenantMember` clears it before the membership goes, with the version increased and one audited `WORK_ITEMS_WAITING_ON_CLEARED_ON_MEMBER_REMOVAL`, as `unassignAll` does. A deactivated member stays named and shows as inactive, like an assignee.
- Who else sets it (decision 106): a repeat copy takes its source's value (an open source's, while that person is an active member; otherwise none, named in the copy's `skipped`); 2.8's review steps will set it; templates and intake accept do not (intake accept gains it with field sets, 2.4b-b). **From 6.3 it may name the delegate's agent session**: 6.3 adds a nullable session reference beside `waitingOnUserId` with a CHECK that at most one of the two is set, and widens the closed-item CHECK to both. No session column now, because there is nothing to reference; the member column keeps its name and data.

## Part 2 — Field sets

### Model and migration (`2026112x130000_field_sets`)

```prisma
enum FieldRequirement { REQUIRED OPTIONAL HIDDEN }

/// One field's rule in a work item type's field set (ADR 0002 §1a).
model WorkItemTypeField {
  id            String           @id @default(cuid())
  tenantId      String
  typeId        String
  /// NULL for a built-in field's rule (workspace-wide); the project for a custom field's.
  projectId     String?
  /// One of CONFIGURABLE_BUILT_IN_FIELDS; a CHECK lists them.
  builtInField  String?
  customFieldId String?
  requirement   FieldRequirement
  createdAt     DateTime         @default(now())
  updatedAt     DateTime         @updatedAt
  // FKs: (typeId, tenantId) → WorkItemType CASCADE; (projectId, tenantId) → Project CASCADE;
  //      (customFieldId, projectId, tenantId) → CustomField(id, projectId, tenantId) CASCADE.
  @@index([tenantId, typeId])
  @@index([tenantId, projectId, typeId])
  @@index([tenantId, customFieldId])
}
```

- CHECKs: exactly one of `builtInField` and `customFieldId`; `builtInField` → `projectId IS NULL`, `customFieldId` → `projectId IS NOT NULL` (under open question 9's option A); `builtInField` in the configurable list; the answer never `REQUIRED`.
- Partial uniques: `(tenantId, typeId, builtInField) WHERE builtInField IS NOT NULL`; `(tenantId, typeId, customFieldId) WHERE customFieldId IS NOT NULL`.
- `CustomField` gains `@@unique([id, projectId, tenantId])` as the FK's target (today it has `(id, type, projectId, tenantId)` only).
- `builtInField` is text with a CHECK, not an enum: 3.4 (estimate) and 2.8 will add fields, and an enum value is a migration of its own and a two-deploy read hazard (ADR 0002 §3).
- RLS (`tenant_isolation`, `tenant_isolation_insert`, `superuser_bypass`, FORCE), its own `GRANT … TO app_user`, a two-tenant test in `ISOLATION_TESTED`.
- **No row means optional**, except the answer, which is hidden without a row (part 3). So no backfill, and every existing workspace behaves exactly as today.

### The pure module

`src/lib/work-items/field-sets.ts`, client-safe, the one home of the rules (like `compileIntakeRequestSchema` for forms):

- `CONFIGURABLE_BUILT_IN_FIELDS` (open question 11): description, assignee, waiting on, priority (required means not None), labels (at least one), start date, due date, cycle, milestone, answer (shown or hidden only). Title, type, project and state are always required and never configurable.
- `resolveFieldSet(rows, typeId, projectId)` → requirement per field; `fieldSetGaps(set, values, { open })` → the required fields left empty; `hiddenFieldsNamed(set, patch)`. The usecases, the server pages and the forms all call these with the server's rows; no component restates a rule.

- `listFieldSet(ctx, typeId, projectId?)`, `setFieldRequirement(ctx, { typeId, builtInField | customFieldId, projectId?, requirement })` (an upsert; `OPTIONAL` with no other meaning deletes the row), in a new `field-set.ts`.

Open question 13.
- **Enforcement, server side, in every path that writes an item's fields:**
  - `createWorkItemInTx`: after the template projection, `fieldSetGaps` over the plan; a gap is 400 `FIELD_SET_UNMET` naming the fields; a hidden field named by the request is 400 `FIELD_HIDDEN` (open question 12), and one a template brings is skipped and named in `templateSkipped`.

  - Machine-made items (`insertTemplateItemInTx` sub-items and starter items, repeat copies) follow open question 12's answer. Today a refusal inside `runRecurrenceRule` is caught as `failed` and retried every night without holding the rule, so the recommended path adds `RecurrenceHold.FIELD_SET_UNMET` (its own migration).
  - **Intake accept** (`AcceptIntakeInput`) carries only type, state, priority, assignee, labels, cycle, title and description: it gains due date, start date, milestone and waiting on, or a type that requires one of them could never be accepted.
  - 6.2 checks proposals against the same function at propose time and approval (decision 77); nothing to build now beyond keeping the function pure.
- Project templates: `ProjectTemplateContentSchema` gains the project's custom-field rules (matched by type name and field name, misses in `fromTemplate.skipped`), `contentVersion` 2; old content reads as having none. Item templates are checked at use, not at save (open question 12).

## What makes the prompt harder than it reads

1. **"Cleared when the item closes" has six writers.** State changes happen in `setWorkItemState`, the bulk state write, the board move, marking a duplicate, deleting a state (a bulk `updateMany` into any category, through `moveItemsToState`, whose `effects` type admits only two timestamps) and the create path. Hence the effect in one function plus a CHECK.
2. **A Question requires waiting on, and closing clears it.** "Required" must mean "required while open", or every close of a question is refused.
3. **Types have no identity.** A type is a renamable, archivable row with a unique name; nothing in code may key on the name "Question". Making the answer a field-set field (hidden unless shown) avoids a type flag.
4. **Item templates belong to a project** (decision 71), so "a Question item template" has no single home, and it names a per-workspace type id.
5. **Custom fields belong to a project and types to the workspace**, so one table carries two scopes; `CustomField` needs a new unique for the FK; project templates must carry the custom-field rules (content version 2).
6. **Create paths that cannot fill a required field**: template sub-items and starter items (title only), repeat copies (a refusal today is a silent nightly retry, not a hold), intake accept (no due date, milestone or waiting on in its input), the sub-item quick add.
7. **The answer pointer needs a target the schema lacks** (`Comment` has no `(id, workItemId, tenantId)` unique), and a soft delete is an `UPDATE` no FK sees.
8. **Nobody may be watching a question.** The create path adds no watcher, so the asker is not notified of the answer unless the design says so.
9. **3.6 needs waiting-on history from the day the column exists**, so the transition record must gain it in part 1, and the burn-up must stay exact with rows that change nothing it reads.
10. **Two lists of filter keys.** The saved-view `FilterKey` is a regex separate from `WORK_ITEM_FILTER_KEYS`; both change, with `MOVABLE_LANES` and the lane value.
11. **The vocabulary guard turns unqualified bans into schema-wide bans**, so the new rows' "words not to use" must be qualified where they could collide.

## ADR amendments (applied 2026-11-20)

### ADR 0002 §1, replaced

> ### 1. One table, configurable types
>
> Every kind of work is a row in `WorkItem`. Its kind is a `WorkItemType` row that each workspace configures (name, icon, colour, sort key, archived). A type carries one behaviour, its field set (below); otherwise any type may parent any type, and every type uses its team's workflow. A workspace seeds default types at creation (ADR 0006, open question 6).
>
> Why rows, not an enum: types are customer data, and an enum change is a migration and a two-deploy rollout.
>
> **Field sets** (roadmap 2.4b, owner decision 77). For each type, a field set says which fields are required, optional or hidden. It is the type's `WorkItemTypeField` rows; a field with no row is optional, except the answer (§15), which is hidden.
>
> - The configurable built-in fields are description, assignee, waiting on (§14), priority, labels, start date, due date, cycle, milestone and the answer (shown or hidden only). Title, type, project and state are always required.
> - A built-in field's rule belongs to the type across the workspace. A custom field's rule belongs to the type within the field's project (§7).
> - The usecases enforce it. A create, or a write to an open item, that leaves a required field empty is refused, naming the fields; a write that sets a hidden field is refused. A closed item is never refused for a missing field. A type change is checked against the new type's whole set. A new or tightened rule does not rewrite existing items.
> - Every form reads the rules from the server and evaluates them with the same function the usecases use. Agent proposals are checked against them when made and when approved (roadmap 6.2).
> - Types carry no other behaviour: per-type workflows, parent rules or review steps would each be a new decision.

### ADR 0002 §7, appended

> - A project's custom field may be required, optional or hidden for each work item type, in that project only (§1, field sets). The rule goes with the field, the type or the project. An archived field is never required.

### ADR 0002 §9, the optional-`If-Match` bullet

> - Optional for single-field changes: state, assignee, waiting on, delegate, priority, labels, cycle, milestone, the answer, one custom field. …

### ADR 0002 §10, added bullets

> - `(tenantId, waitingOnUserId)` → `TenantMembership(tenantId, userId)`: only a member can be waited on; RESTRICT, cleared by member removal as the assignee is.
> - `(answerCommentId, id, tenantId)` → `Comment(id, workItemId, tenantId)`: an answer is a comment of the same item.

### ADR 0002, new §14 and §15 (after §13, so nothing renumbers)

> ### 14. Waiting on
>
> - `WorkItem.waitingOnUserId` names at most one member who must act next (roadmap 2.4b, owner decision 76). It never makes anyone accountable: the assignee stays the one accountable person (ADR 0003 §1), and nothing routes reminders, delegation or proposals by it until a later sub-phase says so.
> - It is set by a person (roadmap 2.8's review steps will set it too; a repeat copy takes its source's). From roadmap 6.3 it may name the delegate's agent session instead of a member (owner decision 106): 6.3 adds a nullable session reference with a CHECK that at most one of the two is set. It is cleared by every move into `DONE` or `CANCELLED`: `stateTransitionEffects` returns the clear, and a CHECK refuses a closed item that names one. A reopen does not restore it.
> - Each change is recorded in `WorkItemTransition`, so time waiting is counted from recorded changes (roadmap 3.6).
>
> ### 15. Marked answer
>
> - `WorkItem.answerCommentId` points at one live comment of the same item (roadmap 2.4b, owner decision 78). A person who may edit the item marks it, never an API key or an agent; marking moves an open item to a `DONE` state of its team in the same versioned write. Clearing it leaves the state as it is.
> - It is offered only where the item's field set shows the answer. While a comment is the marked answer, deleting and editing it are refused until the answer is cleared; an admin moderates by clearing, then deleting (owner decision 113).

### ADR 0002 §13, added lines

> - `(tenantId, waitingOnUserId, stateCategory, dueDate)`: the waiting-on filter, lanes and My Work's "waiting on me" (2.7).
> - `(tenantId, answerCommentId)`: the answer FK.

**Words (roadmap question 1)**

1. **Waiting on.** A. "Waiting on" (`waitingOnUserId`). *Recommended*: reads as a sentence on every surface ("Waiting on Ana", "Waiting on me"). B. "Next to act" (`nextActorUserId`): precise, stiffer in a list column. C. "Whose turn" (`turnUserId`): friendly, odd as a filter label.

    **Answered 2026-11-20: A (decision 101).**
3. **Answer.** A. "Answer" (`answerCommentId`), action "Mark as answer". *Recommended*: shortest, no clash. B. "Marked answer" as the noun: unambiguous, longer on every label.
    **Answered 2026-11-20: A (decision 102).**

**Waiting on**

4. **Who may be waited on.** A. Any active member, the assignee's rule (Viewers included); guests from 8.4 when they can see the project. *Recommended*: consistent with assignment; a Viewer can be asked to look. B. Only members who hold `work_items.comment`: everyone named can reply in the item, but Viewers, often the people asked, cannot be named.
    **Answered 2026-11-20: A (decision 103).**
5. **Which key sets it.** A. `work_items.edit`, as cycle and milestone. *Recommended*: Members and above; matches the other single-field routes. B. `work_items.assign`: it names a person, as assignment does; same roles today, differs for custom roles. C. As A, plus the person named may hand it back (to the assignee or nobody) under `work_items.comment`: useful for guests in 8.4; can wait for 8.4.
    **Answered 2026-11-20: A (decision 104).**
6. **Does the person named hear about it?** A. One in-app bell when someone else names them (a new notification type, its own preference), no email and no reminders until 2.7. *Recommended*: otherwise the field is invisible to them until 2.7's section; the prompt's "nothing routes notifications by it" reads as reminders and digests. B. Nothing but the watcher fan-out, as the prompt's wording literally says: least scope, but people are waited on without knowing. C. A bell and they become a watcher: they then hear everything after, which may be noise.
    **Answered 2026-11-20: A (decision 105).**
7. **Who or what else sets it** (roadmap question 3). A. A person only in 2.4b; 2.8's review steps set it; per-state defaults wait for 5.1's automation; repeat copies take the source's value only while the source is open (a closed source's is cleared); an agent session is never named, and from 6.3 a session awaiting input reads as waiting on the assignee, derived, no column. *Recommended*: no rules engine before 5.1, one person column. B. Per-state defaults a team configures now (none, assignee, creator): handy hand-offs, but a second workflow-like setting before 2.8. C. Allow naming the delegate's agent session from 6.3 (a second nullable column, exactly one set): direct, but an agent becomes a party to wait on, close to the accountability line.
    **Answered 2026-11-20: C (decision 106).** In 2.4b people set it by hand, review steps set it in 2.8 and a repeat copy takes its source's value; from 6.3 it may name the delegate's agent session (a nullable session reference beside `waitingOnUserId`, at most one of the two set). ADR 0003 §1 is unchanged.
8. **Record its changes in the transition table now.** A. Yes: `WorkItemTransition` gains `waitingOnUserId` and the trigger fires on it. *Recommended*: 3.6 needs history from day one, one writer. B. A separate trigger-written table: keeps transitions to planning fields, adds a second record. C. Defer to 3.6: no cost now, but every change between 2.4b and 3.6 is lost.
    **Answered 2026-11-20: A (decision 107).**

**Field sets (roadmap question 2)**

9. **Where a field set lives** (roadmap question 2). A. Built-in fields per type, workspace-wide; custom fields per type within their project. *Recommended*: matches ADR 0002 §7 without workspace-wide fields. B. Everything per project and type: most flexible, but every project re-configures "Question" and the preset must run per project. C. Built-in fields only, per type; custom fields wait for workspace-wide fields: simplest, but a project cannot require its own fields.
    **Answered 2026-11-20: A (decision 108).**
10. **What a new rule does to existing items** (roadmap question 2, second half). A. Nothing is rewritten; a create, and a write that empties a required field of an open item, are refused; a type change is checked in full; other writes to a non-conforming item pass, and its detail lists the gaps. *Recommended*: rules bite from now on without freezing old work. B. Any write to a non-conforming open item is refused until it is filled: strict, but blocks bulk moves, the rollover's neighbours and quick state changes. C. Rules apply to new items only: least friction, but an edit can then empty a required field.
    **Answered 2026-11-20: A (decision 109).**
11. **Which built-in fields are configurable.** A. Description, assignee, waiting on, priority (required = not None), labels (at least one), start date, due date, cycle, milestone, answer (shown or hidden). *Recommended*: everything a person fills; title, type, project, state stay fixed. B. Description, assignee, waiting on, start and due dates only: smaller first step; priority, labels, cycle and milestone wait.
    **Answered 2026-11-20: A (decision 110).**
12. **Hidden fields and machine-made items.** A. Hidden means not offered and refused when a write sets it (a template's value is skipped and named); template sub-items, starter items and repeat copies are checked like any create, and a refused repeat holds with a new reason (`FIELD_SET_UNMET`). *Recommended*: one rule for every caller, as H2 asks, and the hold makes the failure visible. B. Hidden is a form concern only and machine-made items are exempt, their gaps shown on the item: nothing ever stops a job, but the API and the forms disagree. C. As A, but machine-made items are exempt from "required" only: repeats never hold, at the cost of items that break their type.
    **Answered 2026-11-20: A (decision 111).**
13. **Who manages field sets.** A. Built-in rules under `admin.manage` (as types, decision 52); custom-field rules under `projects.edit` (as field definitions, decision 58). *Recommended*: each rule sits with what it constrains. B. All under `admin.manage`: one gate, but members who define a project's fields cannot require them. C. A new key: precise, but changes the permission set and every custom role.
    **Answered 2026-11-20: A (decision 112).**

**Questions and the answer (roadmap question 4)**

14. **The answer and decision 53** (roadmap question 4). A. While a comment is the marked answer, deleting and editing it are refused (409, "clear the answer first"); an admin moderates by clearing then deleting. *Recommended*: the record of an answer cannot change silently; moderation stays possible in two steps. B. Delete clears the mark (audited, watchers told), the item stays Done; edit is allowed and shown "edited after it was marked": one step, but the answer can change or vanish under a closed question. C. Delete refused, edit allowed with the marker: keeps typo fixes, but the text can still change.
    **Answered 2026-11-20: A (decision 113).**
15. **Which Done state** (roadmap question 4). A. The first live Done state in the team's order, with a chooser in the mark dialog when there are several. *Recommended*: no setting, and the person can pick. B. A per-team "answered" state setting: exact, but one more Settings control. C. Always the first Done state, no chooser: simplest, wrong for teams with "Done" and "Released".
    **Answered 2026-11-20: A (decision 114).**
16. **Marking and clearing on a closed item.** A. Marking on a Done or Cancelled item sets the pointer only and leaves the state; clearing never reopens. *Recommended*: marking never surprises a closed item. B. Marking moves a Cancelled item to Done, clearing reopens to the default state: symmetric, but clearing a typo reopens work.
    **Answered 2026-11-20: A (decision 115).**
17. **Seeding Question and its template** (roadmap question 4). A. Not seeded: Settings → Work item types offers "Add the Question type" (type, field set: due date and waiting on required, answer shown), and each project's templates manager offers "Add a Question template" (due in 5 days). *Recommended*: keeps ADR 0006's Feature, Bug, Chore seed, works for existing workspaces, gives the per-project template a home. B. Seed Question for new workspaces with the others, its template into each new project, and the preset for existing ones: works out of the box, a fourth type everyone meets. C. Seed everywhere, including existing workspaces and projects, by a data migration: uniform, but writes into customers' configuration and clashes with a type they named Question.
    **Answered 2026-11-20: A (decision 116).**
18. **Who hears that a question was answered.** A. Watchers, and the item's creator becomes a watcher when they create an item whose type shows the answer. *Recommended*: the asker always hears, without changing the create path for other types. B. Watchers only, as the prompt says: nothing new, but the asker often is not watching. C. Watchers, creator and assignee, notified directly without watching: reaches everyone, adds a recipient rule outside watching.
    **Answered 2026-11-20: A (decision 117).**
19. **Is the answer limited to types that show it.** A. Yes: the answer is a field-set field, hidden unless shown. *Recommended*: no type identity in code, any workspace can make another question-like type. B. A flag on `WorkItemType` ("takes an answer"): explicit, but a second type behaviour beside field sets. C. Any item may have an answer: simplest, but every item's comments grow a "Mark as answer" action.
    **Answered 2026-11-20: A (decision 118).**

20. **How many pull requests.** A. Three, in the prompt's order (a waiting on, b field sets, c questions). *Recommended*: each usable alone; b may split server from forms. B. Two (a+b, then c): fewer reviews, one very large pull request. C. One.
