The roadmap's gate, verbatim:

> **Hardening H2.**
> - Performance: seeded tenants at 10,000 and 100,000 items; list, board and search stay under an agreed response budget; no query in a loop; every list query has a backing index (port the index and query-shape guardrails).
> - Concurrency tests for reordering, key allocation and bulk updates under parallel writers.
> - A permission matrix test: every role against every work-item route, including guests limited to their projects, and the review-step routes once 2.8 lands.
> - A required field (2.4b) is refused by the usecase for an API caller that skips the form; an earlier review round (2.8) is never rewritten by a later one.
> - Drag and drop passes keyboard and screen-reader checks.
> - Public forms and email intake fuzzed for injection, oversized bodies and floods.
> - End-to-end tests run in isolated tenants; no shared mutable state between tests.

## Summary

- **Half of H2 is already in the tree, and none of it is the hard half.** The index and query-shape guardrails were ported in 2.2 (`schema-index-coverage.test.ts`, layers A, B, C and C-completeness; `query-shape-guardrails.test.ts`, D1 and D2 with a zero budget). Every signed-in E2E spec already runs in its own registered workspace (`tests/e2e/fixtures.ts`). The permission matrix has a behavioural seed (`work-items-api.test.ts`: OWNER, MEMBER, VIEWER and GUEST over the work routes) and a static half (`tenant-crud-authz-coverage.test.ts`). Field sets are refused in the usecases (`field-sets.test.ts`). The board's keyboard path is rendered-tested and E2E-tested. What is missing is everything that needs **data at scale, real parallelism, or hostile input**: no seed tooling, no latency measurement, no plan check on raw SQL, concurrency tested only in pairs or tens, no ADMIN or custom role in the matrix, no route-level field-set table, no browser-level accessibility check, no fuzzing, and no guard that E2E stays isolated.
- **Static guardrails are not runtime proof.** Layer C pins named composite indexes, and C-completeness ties every `findMany` to one; neither sees `$queryRaw` (search, the trigram and full-text reads, the field sort), neither sees what the planner actually does on a skewed 100k table, and D1 sees a read in a loop only lexically. H2 adds the runtime half: `EXPLAIN` assertions on a seeded database, and statements-per-request counted from `pg_stat_statements`.
- **One finding already, from reading the code.** The bulk usecases read their items without a row lock (`WorkItemRepository.listByIds`: no `FOR UPDATE`, no `orderBy`) and then update them one by one in that unordered order. Two overlapping bulk calls can deadlock (`40P01`), and the audit entry's "from" state can be stale against a concurrent single edit. The concurrency suite (part 2) is designed to expose it; the fix is decision 173 (question 8): lock in id order, then plan.
- **2.8 adds two things the gate names.** The review-step routes join the matrix's population automatically (it is read from git); "an earlier round is never rewritten" gets a model-based sequence test on top of 2.8a's trigger tests. Both land after 2.8a merges; the gate closes after 2.8c (open question 14).
- **Proposed split: seven pull requests** (part 9), H2a to H2g, most of them independent of each other and of 2.8.

## 1. Performance

### 1.1 The seed (proposed; open questions 5 and 6)

`scripts/seed-scale/` (TypeScript, run with `tsx`), deterministic from a seed string, idempotent per workspace slug. Two shapes:

| Shape | Workspace | Projects | Items | Other rows |
|---|---|---|---|---|
| `10k` | 1 team of 5, 40 members | 10 × 1,000 | 10,000 | 3 comments/item (≈30k), 1.5 labels/item, 0.3 BLOCKS edges/item, 5 custom fields per project (60 % filled), 1 cycle per team per fortnight for a year, 3 milestones per project, ≈20 % sub-items, 70 % with a description |
| `100k` | 5 teams, 200 members | 19 × 4,200 and one of 20,000 (skew) | 100,000 | the same ratios (≈300k comments) |

Plus, in both, a **second workspace of the same size** so tenant selectivity is realistic for the planner and RLS (`tenantId`-leading indexes only prove themselves when other tenants' rows exist). The state distribution is skewed as real backlogs are (≈45 % Done, 10 % Cancelled, 25 % Backlog, 12 % Unstarted, 8 % Started); due dates spread over ±180 days around the run date; assignees Zipf-distributed, so My Work has heavy and light users.

How it writes (open question 6, recommendation A, the hybrid):

- **Through the real usecases:** the workspace, members, teams, states, projects, types, labels, custom fields, cycles, milestones, and a 1 % sample of items with comments (so the sampled items carry real audit entries, mentions and search vectors written by the seam, and the Activity feed has something to read).
- **In bulk for the rest,** as the database superuser in batches of 5,000 (`INSERT … SELECT FROM unnest(…)`): numbers claimed from `ProjectKeySequence` in the same statement batch; `sortKey` from `fractional-index.ts` in Node; **descriptions and comment bodies encrypted in Node with the workspace's DEK through the real field-encryption function** (a plaintext row would make every detail read fail closed); `SearchVector` rows computed in SQL with `to_tsvector('islestone_bg_en', …)` over the same `searchableText` the seam uses; `WorkItemTransition` rows written by its trigger as the inserts happen; audit entries for the bulk rows are not written (the 1 % sample carries them; part 1.5 says what that leaves unmeasured).
- **Text is generated, Bulgarian and English mixed**, from a small word list committed with the seeder (no corpus download), so the `islestone_bg_en` configuration is exercised on both scripts.
- **A dump, cached.** After seeding, `pg_dump -Fc`; cached in GitHub Actions under a key of `hashFiles('prisma/migrations/**', 'scripts/seed-scale/**', 'deploy/postgres/**')`; a run restores it with `pg_restore -j 4`. A migration change invalidates the cache and the next run reseeds.
- **Verified on every run:** row counts per table, `verifyAuditChain` for both workspaces, a decrypt of 100 random descriptions, and `rls-coverage`'s two-tenant read through `runInTenantContext`. A seeder that wrote the wrong thing fails before anything is measured.

### 1.2 Plan checks (deterministic; block every pull request at 10k)

`tests/perf/plans.test.ts` (a Jest project `perf`, not run by `npm test`; it needs the seeded database). Pattern from inflect's `tests/integration/task-tenant-index-plan.test.ts` (seed a skew, `ANALYZE`, ask the planner), pattern only, written fresh:

- For each **named query** (the list in each sort the API offers, the board column read, My Work's six sections, the cycle and milestone pages' counts, the search usecase's raw reads, the list's `q`, the custom-field sort, the reminder and digest scans, the purge sweep), run the real repository method inside a transaction with `SET LOCAL auto_explain`-style capture, or call `EXPLAIN (FORMAT JSON)` on the SQL the method produces through a query hook, and assert: **no `Seq Scan` on `WorkItem`, `Comment`, `SearchVector`, `WorkItemTransition` or `AuditLog`**, and the index named in Layer C (or the search index named in `search.test.ts`) is used.
- **Buffers bound.** `EXPLAIN (ANALYZE, BUFFERS)` shared hits plus reads under a per-query ceiling at 100k (for a first page: under 2,000 buffers), so a plan that uses the index but walks most of it is caught.
- The query list is a registry, `PLAN_CHECKED_QUERIES`, with a C-completeness-style forcing test: every repository method that reads `WorkItem`, `Comment` or `SearchVector` is either in it or carries a reason. A new list query cannot avoid the check.

### 1.3 Statements per request (deterministic; blocks every pull request)

The runtime twin of D1. The perf job starts Postgres with `shared_preload_libraries=pg_stat_statements` (a flag `scripts/ci-postgres.sh` gains; the official image ships the module); the harness resets `pg_stat_statements` before each scenario, runs it N times, and divides the statement count by N. Budgets: list 8, board column 8, search 10, detail 12, My Work section 8, create 25 (audit, automation stub, search seam, mentions, watchers). A request whose count grows with the page size or the item count is a loop the lexical guard missed. Reported per scenario in the job summary.

### 1.4 Latency budgets (proposed; open questions 1 to 3)

Measured **on a reference machine** (open question 1, recommendation A): the GitHub-hosted `ubuntu-24.04` runner (4 vCPU, 16 GB), Islestone's Postgres image through PgBouncer in transaction mode as `scripts/ci-postgres.sh --pgbouncer` starts them, Redis, and the standalone build (`npm run start`) with `RATE_LIMIT_ENABLED=0`. The harness signs in as a member with a typical load (≈300 open assigned items at 100k), warms each scenario with 20 requests, then takes **200 sequential samples** (p50 and p95, server time observed from the client on the same machine), and a separate **10-client concurrent pass** reported for throughput, not budgeted.

| Scenario (what the page sends) | 10k p50 / p95 | 100k p50 / p95 |
|---|---|---|
| **List**, first page of 50, one project, manual order | 80 / 200 ms | 100 / 250 ms |
| List, workspace-wide (Work items page), two filters, sort by due date | 120 / 300 ms | 180 / 450 ms |
| List sorted by a custom field (`listByCustomField`) | 150 / 350 ms | 250 / 600 ms |
| List with `q` (trigram title, stemmed title and content vectors) | 150 / 350 ms | 250 / 600 ms |
| **Board**, one column (50 cards, by state), in the 20k project at 100k | 80 / 200 ms | 100 / 250 ms |
| Board, whole first load (view config plus every column, as the page fires them in parallel), wall clock | 250 / 500 ms | 300 / 700 ms |
| **Search**, command palette (`/search?q=`, titles, keys, projects and content, limit 20) | 100 / 250 ms | 200 / 500 ms |
| **Detail**, `GET` the item | 50 / 120 ms | 50 / 120 ms |
| Detail, what the sheet loads in parallel (item, comments, activity, sub-items, custom fields), wall clock | 150 / 350 ms | 150 / 350 ms |
| My Work, six sections in parallel, wall clock | 300 / 600 ms | 400 / 800 ms |
| Writes (reported, budget at both sizes): create, edit, move, reorder | p95 400 ms | p95 400 ms |
| Bulk state change of 100 items | p95 2,000 ms | p95 2,000 ms |

Two rules beside the numbers: **detail must not depend on workspace size** (100k p95 within 1.2× of 10k p95, so a read that scales with the workspace is caught even when it is under budget), and **a 100k list first page within 1.5× of the 10k one** (keyset pagination should make it nearly flat).

Browser timings, **reported only** (they are noisy on a shared runner): Playwright on the seeded 100k workspace, 20 runs each, from navigation to the first row (list), to every column's first card (board), and from click to the sheet's title (detail); proposed targets 1.3 s, 2.0 s and 0.6 s at p95.

### 1.5 What the seed leaves unmeasured

Activity reads audit entries per item, and the bulk rows have none; the 1 % sample measures the Activity read on items that have history, but the `AuditLog` table is smaller than a real 100k workspace's. The perf report says so. If the owner wants the audit table at scale (open question 6, option B), the seeder appends entries through `appendAuditEntry` in batches: the chain lock serialises them per workspace (roughly 400k entries, measured before committing to it).

### 1.6 The harness (open question 4)

Recommendation A: an in-house harness, `scripts/perf/run.mjs` (plain Node, `undici` already in the tree, `perf_hooks.createHistogram` for percentiles, no new dependency). It signs in through the credentials flow, replays the scenarios above, writes `perf-summary.json` and a Markdown table to the job summary, and **refuses a run that measured nothing**: a scenario with fewer than its sample count of 2xx responses, an empty histogram, or a missing summary fails the job whatever the latency (inflect's `scripts/k6-summary-gate.mjs` header records a month of green nightly runs in which 99.7 % of list requests were signed out; that lesson is taken as a rule, pattern only). The budgets live in `scripts/perf/budgets.json`, one owner, with the reasoning in `docs/performance.md` (new).

inflect's k6 scenarios (`tests/load/*.js`, BUSL-1.1, copyable) are not proposed: k6 itself is AGPL-3.0, a Go binary installed in CI (not shipped, so not a licence-gate matter), and its scenarios are compliance routes that would be rewritten anyway. Its `docs/slos.md` (read p95 < 500 ms, write p95 < 1,000 ms) is the pattern for stating budgets per class.

### 1.7 How it runs in CI

- **`ci.yml`, new job `Performance (10k)`**, on every pull request, `needs: build` (reuses the build artifact as E2E does): restore or build the 10k dump, run the plan checks (1.2) and the statements-per-request budgets (1.3), **blocking**; run the latency scenarios at 10k and post the table, **not blocking** on latency (open question 3). About 6 minutes with a warm cache, 9 cold. This is also what keeps the seeder from rotting.
- **`.github/workflows/perf.yml`, new**: `schedule` (nightly, `cron: '41 2 * * *'`, off the hour and away from DAST's 03:17), `workflow_dispatch` (input `scale: 10k | 100k`), and `push` to `main` only for the job summary. Restores or builds the 100k dump, runs everything at 100k, **blocking on the latency budgets with a 25 % tolerance and one automatic re-run of a failing scenario**; a red night opens or updates one GitHub issue (inflect's `integration-stress.yml` header: a suite that turns red only after the merge went unnoticed for 32 hours and about 20 merges). Uploads `perf-summary.json` (90 days) so trends can be read.
- `actions/cache` is on a major tag (`actions/*`); any other action is pinned by SHA (`workflow-action-pinning.test.ts`).

### As built (H2a, decisions 166, 168, 170 to 172)

### As built (H2b, decisions 166 to 169)

Writes run after every read, the browser and the concurrent pass, so their rows and the vacuum they cause never sit under a read's figures.

The seed and the server share one throwaway `DATA_ENCRYPTION_KEY` (the dumps' cache keys carry `k1` for it).
- **Measured** (the development machine, not the reference runner; `docs/performance.md` has every figure): at 10k every scenario within its budget but the palette search's p50 (101 against 100, within the tolerance); at 100k every scenario within budget but the list's `q` and the palette search (p95 0.85 to 1.2 s against 600 and 500 ms; every matching vector is ranked): **finding F3**, recorded as a known finding at 100k. Owner decision 250 (2026-11-26) decides it: content search ranks only a bounded candidate set, at most about 2,000 matches walked most recently updated first, then ranked; titles and keys are still searched fully, and the interface says it is showing recent matches. The fix is its own pull request; F3 stays a known finding until it lands. The ratio rules held (the detail 1.1× to 1.2×, a project's first page 0.92× to 1.01×). The browser timings met their targets but the timeline's. The timeline read is within 3.1's latency budget at both sizes, but its answer is 3.2 to 3.9 MB (467 to 545 KB gzipped) against 1.5 MB and 250 KB, and its first bars take 2.1 to 2.7 s p95 in the browser against 2.0 s: issue #73, H3's, reported. The 100k buffer budgets are about twice the measured buffers, never below the 10k budget, the goal, initiative and progress reads of 3.2a and 3.2b included; every plan rule held at 100k.
- **F3, fixed** (decision 250, issue #89): content search ranks the caller's 2,000 most recently written live, visible matches, walked on `SearchVector_search_recent` in a large workspace (migration `20261217120000_search_recent_candidates`; `docs/search.md`, "The bound on content matches"); at 100k the list's `q` and the palette search now take 159 and 164 ms p95 on the development machine, and the markers are gone from `budgets.json`.

## 2. Concurrency (part 2)

`tests/integration/concurrency/*.test.ts`, in the integration project, DB-gated, each test ending with invariant checks over the table, never only over the returned values. Writers are real usecases in separate transactions (`Promise.allSettled` of N calls; the pool and `TENANT_TX_TIMEOUT_MS` from `src/lib/db/concurrency-limits.ts` are the stated limits). Each test runs its scenario several rounds with fresh rows (as `work-item-graph.test.ts` already does for cycles). A larger, slower variant (`STRESS_SCALE=4`, inflect's `tests/stress/` shape, pattern only) runs in the nightly perf workflow.

| Scenario | Writers | Invariants checked afterwards |
|---|---|---|
| **Key allocation** under a burst in one project | N creates (10 now; the burst the owner states, open question 9), plus creates in a second project interleaved | numbers contiguous from the sequence's previous value, unique, `lastValue` equals the highest number; failed creates (a random 20 % with a bad state) used no number; no transaction timed out below the stated burst |

| **Bulk** state, two overlapping calls in opposite id order | 2 × 100 items, half shared | both complete or one is refused with a typed 409; **never a `40P01` deadlock to the caller**; each item's audit "from" state equals its state before that transition (read from `WorkItemTransition`) |

**Expected defect.** The bulk usecases (`bulkSetWorkItemState`, `bulkAssignWorkItems`, `bulkSetWorkItemDueDate`, `bulkDeleteWorkItems` in `src/app-layer/usecases/work-item.ts`) read with `WorkItemRepository.listByIds` (no lock, no order) and update per item in the order the read returned. The opposite-order test should reproduce a deadlock or a stale audit "from" state. **Decided fix (decision 173, question 8, A):** one repository method `lockForWrite(ids)` (`SELECT … FOR UPDATE … ORDER BY id`) at the start of every bulk usecase and every multi-row write, then plan from the locked rows. **Decided burst (decision 174, question 9, A):** 25 simultaneous creates in one project.

### As built (H2c, decisions 173 and 174)

- **The lock.** `WorkItemRepository.lockForWrite(ids)` (`SELECT "id" … ORDER BY "id" FOR UPDATE`, one statement), with three predicate twins: `lockItemsOfPerson` (a member's removal: assigned, waiting on, person values, pending reviewer rows), `lockInState` (a state's delete) and `lockPurgeBatch` (a purge batch and the rows still pointing at it). Every multi-row repository write takes the brand `LockedWorkItemIds` (`src/app-layer/repositories/work-item-locks.ts`): `bulkUpdate`, `bumpVersion`, `softDelete`, `restoreDeletion`, `unassignAll`, `clearWaitingOnAll`, `moveCycle`, `clearCycleIncludingDeleted`, `clearMilestoneIncludingDeleted`, `moveRow`, `hardDelete`, `rewriteSortKey` and `TeamRepository.moveItemsToState`; the unused `stampStartedAt` went, and a single item's version bump is `bumpVersionOf`. Callers that lock first: the four bulk verbs, a delete's subtree, restore, a move to another project, a member's removal, a state's delete, cycle and milestone deletes, the rollover, a label's delete, the review engine's withdraw-and-settle, the purge and the rebalance.
- **The guard** is `tests/guards/work-item-multi-row-lock.test.ts`: every `WorkItem` write in `src/` is in a branded function or a listed single-row writer; no cast to the brand outside its module; no single-row writer in a loop; every lock method orders by id `FOR UPDATE` in one statement. Out of its reach, and said so in it: the key rotations' interpolated-table sweeps (one row per statement, in id order already) and a single-row writer reached through a helper called in a loop.
- **A second finding: the placement order.** A board drop that changed the state wrote the item, then locked the project's sequence row; a reorder locked the sequence row, then wrote the item. Dropping and reordering the same item at once deadlocked (shown by `reorder.test.ts` before the fix). A drop or a re-parent with a position now takes the sequence row first.
- **A third: the burst was a pool problem.** 25 simultaneous creates in one project: 24 failed before the fix, though a create alone took 30 to 70 ms. Each waiter held a pooled connection inside its transaction while it waited on the sequence row, and the head of the queue needed another for its audit append (`logEvent` appends on its own connection); none was free until the waiters expired. A longer transaction limit would not have helped, so decision 174's "raise the limit or shorten the locked section" was met by shortening what a waiter holds: `createWorkItem` waits its turn per project in the process before opening a transaction (`inProjectSequenceQueue`). `TENANT_TX_TIMEOUT_MS` is unchanged; `WORK_ITEM_CREATE_BURST_PER_PROJECT = 25` is stated in `concurrency-limits.ts`. Creates inside another usecase's transaction (intake accept, starter items, repeats) do not queue.
- **The suite** is `tests/integration/concurrency/` (`key-allocation`, `reorder`, `bulk-lock-order`), invariants read from the tables. Shown failing before the fix: the 25-create burst, drops racing reorders (40P01), a bulk change racing a move of the subtree it touches (40P01), a bulk state change's stale audit "from" (an item changed while the bulk change waited), and a bulk assign against the member's removal (the removal refused by the assignee FK, its write's snapshot missing the rows the assign committed). It passed under full CPU load on the 4-CPU session machine. The map's other rows (moves across keys, a rebalance racing reorders, waiting on against close, answer against delete, recipient lists against removal, cycle overlap, `STRESS_SCALE` in the nightly) are not built in H2c; the overlap and close rows already have tests in their own suites.

## 6. Fuzzing public forms and email intake (part 6; open question 13)

Three layers, all on code that exists (`src/lib/intake/`):

**Property fuzzing (fast-check, Jest node project).** Each property states what must hold for any input, not one example:

| Target | Properties |
|---|---|
| `public/capped-body.ts` | any body of length ≤ cap is read whole; any longer body is refused with the typed error before more than cap + one chunk is buffered; a lying `Content-Length` (shorter or longer than the body) changes nothing; chunk boundaries anywhere; invalid UTF-8 refused, never thrown as an untyped error |
| `form-definition.ts` (`compileIntakeRequestSchema`) | for random form definitions and random answers: parsing never throws outside Zod; accepted output has only the form's keys (never `__proto__`, `constructor`, `prototype`), every string within its declared limit, every choice among the form's options; a definition beyond its limits is refused when saved |
| `public/form-token.ts` | a token with any single byte changed never verifies; a token of another form, version or workspace never verifies; an expired or too-young one never verifies |
| `pow.ts` | a wrong nonce never verifies; verification time is bounded for any input length |
| `email/mime.ts`, `rfc2047.ts`, `text.ts`, `content.ts` | for messages mutated from a seed corpus (Gmail, Outlook, Apple Mail, nested multipart, `message/rfc822`, 1,000 parts, unknown charsets, bad base64 padding, folded 100 KB headers, NUL bytes, bidi controls): never throws untyped; terminates in under 50 ms per message at the size cap (a ReDoS shows as a timeout); output text length bounded; no markup re-forms after stripping (`<scr<script>ipt>`); attachment count capped |
| `email/auth-results.ts` | `VERIFIED` only with the trusted `authserv-id` and a DMARC pass or aligned DKIM pass, for any header order, case, comments and duplicates; a forged header from any other server never verifies |
| `email/address.ts` | the reply-address parser accepts only the configured domain and token alphabet, for any case and any surrounding text; never a match on a look-alike domain or a Unicode homoglyph |
| `email/svix.ts` | any change to body, id, timestamp or signature refuses; any timestamp outside five minutes refuses |

On pull requests each property runs at its default size (100 runs, a few seconds); the **nightly perf workflow re-runs them with `FC_NUM_RUNS=20000`** and prints the seed of any failure so it can be replayed. A failing seed found nightly becomes an example test in the same pull request as the fix.

**Route fuzzing (integration).** Through the real handlers and usecases:

- **Injection.** Script, SVG and event-handler payloads, `javascript:` URLs, SQL-looking strings, Unicode bidi and zero-width characters, and CR/LF sequences in the requester's name and address and in the email subject: stored sanitised (`sanitizePlainText`), rendered as text on the Intake page (an E2E step asserts the payload shows literally and **no CSP violation report arrives**), and **no CR or LF reaches an outbox email's header fields** (the confirmation and the acknowledgement name the requester).
- **Oversized.** Bodies at cap − 1, cap and cap + 1 bytes; chunked with no `Content-Length`; a `Content-Encoding: gzip` body (refused or read as bytes, never inflated); JSON nested 10,000 deep; an answers object with 10,000 keys; a 1 MB email with 2,000 parts. Each is the typed 413 or 400, and memory stays bounded (the handler never buffers past the cap).
- **Floods.** 200 concurrent valid submissions to one form: exactly the daily cap is accepted (the caps are counted under the form's row lock); per-IP limits answer 429 with `Retry-After` (the suite sets `RATE_LIMIT_ENABLED=1`, because under `NODE_ENV=test` the limiter is otherwise bypassed); a spoofed `X-Forwarded-For` from the client does not mint a new budget (the app trusts the first entry, which Caddy sets from the connection: `tests/unit/deploy/caddy-snippet.test.ts` holds that half); 100 concurrent Resend webhooks with the same `svix-id` make one `IntakeInboundEmail` row; the per-address and per-sender throttles hold under concurrency; a blocked sender's flood stores nothing.

**DAST.** The nightly ZAP baseline (`dast.yml`) is passive; adding `/f/<publicId>` and the two public POST routes to its scope is cheap and is proposed for H2f, still report-only until its dated marker (2026-12-03).

Not proposed: a coverage-guided fuzzer (Jazzer.js, Apache-2.0) on the MIME parser. It finds deeper parser bugs than property tests do, at the cost of a native dependency and a separate harness (question 13, option B).

## 7. End-to-end isolation (part 7; open question 15)

The audit, as of `e60fac3`:

- **Isolated by fixture:** 15 of the 19 specs import `{ test } from './fixtures'` (`isolatedTenant`, `authedPage`: a fresh workspace per `test()`); `invite-flow.spec.ts` records that it was collapsed from four serial tests. No spec uses `test.describe.serial`, a module-level `let`, or `storageState` files across tests (the two `storageState` reads in `app-shell.spec.ts` copy the same test's own session).
- **Not isolated by construction, today correct by convention:**
  - nothing stops a new spec from signing in without the fixture, or from sharing a `let` across tests;
  - **server-side shared state**: the rate-limit counters are per process and keyed by IP (every spec is `127.0.0.1`), but the E2E server's `AUTH_TEST_MODE=1` bypasses every tier, the public intake limits included (`isRateLimitBypassed`, `src/lib/security/rate-limit-middleware.ts`), so no budget is shared; the cost is that no E2E spec sees a limit, which unit and integration tests cover. The server enqueues into the one Redis (emails, jobs) and no worker runs, so nothing a spec enqueues reaches another; a spec that one day starts the worker must key what it asserts by its own workspace;
  - **"today"**: cycles, repeats, due-soon and reminders read the date in `NOTIFICATIONS_TZ`; a run that crosses midnight there can split one spec across two days;
  - **CI retries** (`retries: 1`) turn an order-dependent failure into a pass on the second try.

Proposed:

### As built (H2g, decision 180)

Each detector is proved on a planted repository. `BASELINE` is empty: no existing spec broke a rule.
- **The clock seam** is `todayClock(timeZone, now?)` in `src/lib/clock.ts`, the one helper: off the E2E server it returns `now` (`new Date()`); with `NEXT_TEST_MODE=1` and a valid `E2E_TODAY` it returns noon of that date in the zone, so `todayInTz`, `dayKeyInTz`, `todayIn` and `classifyDueWindow` all land on it in every zone (tested from UTC-12 to UTC+14 across a year of daylight-saving changes). Every request-time "today" goes through it: cycles (status and the burn-up's last day), milestones (late), repeats (next date), due soon and the list's `due` filters, the due bell after a write, intake's daily key, review steps' due days, item and project templates' dates, goal progress, the roadmap, the calendar's and the timeline's `asOf`. `tests/guards/today-clock-seam.test.ts` refuses a fresh clock read (`new Date()`, `Date.now()`) as a date helper's instant anywhere in `src/`, and a reader of `E2E_TODAY` outside the schema, the seam and the startup refusal. `E2E_TODAY` is refused in production unless `NEXT_TEST_MODE=1` by `src/env.ts` and by `checkProductionTestClock` in the startup refusals; the production compose file may not set it.
- **The day.** `playwright.config.ts` pins `E2E_TODAY` on its first load in the runner (so every worker and the server share it) to the run's first day in `NOTIFICATIONS_TZ`, unless the caller set one; the specs build dates from `e2eToday()`, `e2eDay(n)` and `plannedDay(n)` (`tests/e2e/e2e-utils.ts`), which replaced five specs' own clock reads.

Pull requests keep `retries: 1`.
- **Rules no decision names.** (1) The fixed day is the run's first day, not a constant: the server's stored times (`createdAt`, a transition's time) stay real, so a constant far from the real date would put an item finished now outside a cycle that starts "today". (2) Only "today" is fixed, never the instant: stored times and the browser's own clock are untouched (no spec reads the browser's date). (3) The nightly jobs keep the `now` their runner gives them; no worker runs on the E2E server. (4) A red isolation night opens its own issue, as the performance run's does. (5) "Each spec file alone" keeps the config's workers (two on CI): alone means no other file's tests, not one worker.

## Finding F1, decided (decision 245, 2026-11-21)

H2a's finding F1, reported and not fixed on its branch (`wt/h2a`, `docs/performance.md`, "Findings"): under row-level security, a full-text (`@@`), `ILIKE` or trigram (`%`) condition cannot be an index condition, because those operators are not `LEAKPROOF`, so the planner applies the policy first and every search reads the whole workspace's GIN entries. The owner decided the fix:

- **Scoped `SECURITY DEFINER` search functions**, one per search read (titles and keys, project names, descriptions and comments), so the planner may use the tenant-leading GIN indexes inside them.
- **Owned by a non-login role**, not by `app_user` and not by a superuser that can log in.
- **The tenant comes from `app.tenant_id`**, read inside the function, never a parameter (a call without it set matches no row, as the policies do).
- **Each function filters `tenantId`, `deletedAt` and project visibility itself**, in its own `WHERE`, as the repository predicates do today (the item's and a comment's `deletedAt`, `projectVisibilitySql`'s rule).
- **It returns ids only**; the caller reads the rows under RLS as before, so no text leaves the function.
- **A guard pins each function's body**, so a change to what a definer function reads is a reviewed diff.
- **RLS stays on every table**: nothing is disabled, bypassed or relaxed for search.

## Open questions for the owner

Each question stands alone. The recommended option is first and marked; each option carries its main trade-off.

**Performance**

1. **Where are the response budgets measured?**
   - A (recommended). On a stated reference machine: GitHub's standard Linux runner (4 CPUs, 16 GB) running the production Postgres image, PgBouncer and the built app. Repeatable and free; it is not production hardware, so a pass says the code is fast enough, not that the production VM is.
   - B. On the production VM, out of hours, against a seeded workspace. Real hardware, but it is shared with Agrent and Playerz, needs an operator, and puts synthetic data in the production database.
   - C. Both: CI as the gate, plus a weekly report from production request timings. Best picture, but production has no metric shipping yet, so this waits for it.
   - **Decided:** A, the reference machine (decision 166, 2026-11-20).

2. **What are the budgets?**
   - A (recommended). The table in part 1.4 of the map: at 100,000 items, p95 250 ms for a list's first page, 700 ms for a whole board load, 500 ms for search, 350 ms for an item's detail (and the detail no slower at 100,000 than at 10,000), with p50 targets beside each. Ambitious enough to catch a missing index, loose enough for a CI runner.
   - B. One number for every read: p95 under 300 ms at 100,000 items. Simple to state, but a whole board (several parallel reads) or a full-text search cannot honestly meet it.
   - C. Budgets only at 10,000 items; 100,000 measured and reported, never enforced. Fewer red nights, but the gate's 100,000 tenant would prove nothing.
   - **Decided:** A, the per-surface table in part 1.4 (decision 167, 2026-11-20).

3. **What happens when a budget is missed?**
   - A (recommended). Deterministic checks (query plans use their indexes, statements per request, "the run measured something") block every pull request at 10,000 items; latency budgets block only the nightly 100,000 run, with 25 % tolerance and one automatic re-run, and a red night opens an issue. Catches regressions without flaky pull requests.
   - B. Everything report-only until a dated deadline (as the H1 security scans are), then blocking. Gentler start, but a regression can merge in the meantime.
   - C. Latency budgets also block pull requests. Strictest, but shared runners are noisy enough to fail good pull requests.
   - **Decided:** A: deterministic checks block pull requests at 10,000; latency blocks the nightly 100,000 run with 25 % tolerance and one re-run, and a red night opens an issue (decision 168, 2026-11-20).

4. **What drives the load?**
   - A (recommended). A small in-house Node script using libraries already installed; no new tool. Exactly the measurements needed, and it refuses a run that measured nothing.
   - B. Port inflect-compliance's k6 scenarios. Proven scripts, but k6 is an AGPL-3.0 binary to install in CI and the scenarios are compliance routes that must be rewritten anyway.
   - C. autocannon (MIT, npm). A familiar tool, one more dev dependency, and weaker at multi-step scenarios such as signing in first.
   - **Decided:** A, an in-house Node script (decision 169, 2026-11-20).

5. **What do the seeded workspaces look like?**
   - A (recommended). 10,000 items in 10 projects, and 100,000 in 20 projects with one large project of 20,000; realistic ratios of comments, labels, dependencies, custom-field values and sub-items; a second workspace of the same size beside each, so the database sees other tenants' rows as in production.
   - B. 100,000 spread evenly over 100 projects. Easier queries; misses the large-project case where lists and boards hurt most.
   - C. As A, plus a 1,000,000-item stretch run on demand. Shows the next ceiling; the seed takes much longer and needs a bigger runner.
   - **Decided:** A, realistic seeds with a 20,000-item project and a sibling workspace (decision 170, 2026-11-20).

6. **How is the seed written?**
   - A (recommended). Configuration and a 1 % sample of items through the real application code; the rest in bulk SQL, with descriptions and comments encrypted by the real encryption code and search vectors computed by the database; saved as a cached database dump. Minutes to build; the audit trail is only sampled, which the report says.
   - B. Everything through the application code, audit entries included. Most realistic; tens of minutes to hours at 100,000 because the audit chain is written one entry at a time per workspace.
   - C. Pure SQL with plain-text descriptions. Fastest, but every item read would fail, because the app refuses to show text it cannot decrypt.
   - **Decided:** A: 1 % through the application code, the rest bulk SQL with real encryption and database-computed vectors, cached as a dump (decision 171, 2026-11-20).

7. **Should H2 also fix what the measurements find, or only report it?**
   - A (recommended). Fix in the same series: a missing index, a query in a loop or a slow plan found by H2a or H2b is fixed in a follow-up pull request before the gate closes. The gate means "fast enough", not "measured".
   - B. Report in issues and close the gate once the tooling exists. Faster to close, but the phase ends with known slow paths.
   - **Decided:** A, fix what H2 finds before the gate closes (decision 172, 2026-11-20).

**Concurrency**

8. **Bulk updates read items without locking them and update them in no fixed order, so two overlapping bulk changes can deadlock and the audit trail can record a stale "from" state. What should change?**
   - A (recommended). Every bulk change, and every other write that touches several items, first locks its items in id order, then plans from the locked rows. Removes the deadlock and the stale read; slightly longer lock hold on 100 items.
   - B. Keep the code; retry once on a deadlock in the API layer. Smaller change, but the stale audit "from" state remains.
   - C. Both A and the retry. Belt and braces; the retry hides any future ordering mistake.
   - **Decided:** A, lock items in id order before any multi-item write; this fixes issue #65 (decision 173, 2026-11-20). Built in H2c (part 2, "As built").

9. **How large a burst of simultaneous creates in one project must succeed?** Keys are numbered without gaps, so creates in one project wait for each other; today ten are tested, and twenty on a busy CI runner timed out (issue #32).
   - A (recommended). State 25 simultaneous creates in one project as supported, test it, and raise the transaction time limit or shorten the locked section until it passes. Covers imports and automations at human scale.
   - B. Keep ten as the stated limit. No change; a large paste or an automation can hit timeouts.
   - C. Allow gaps in item numbers to remove the wait. Scales freely, but changes ADR 0002 ("a failed create uses no number").
   - **Decided:** A, 25 simultaneous creates in one project, supported and tested (decision 174, 2026-11-20). Built in H2c.

**Permissions**

10. **Which roles does the permission matrix cover?**
    - A (recommended). Every tenant API route against Owner, Admin, Member, Viewer and Guest, plus two custom roles (one that narrows Member, one that widens Viewer), from a hand-written expected table that every new route must join. Covers the custom-role paths the product sells.
    - B. The five built-in roles only. Smaller; custom roles stay tested only in their own suites.
    - C. As A, plus every page (server-rendered routes) per role. Most complete; doubles the size, and pages already refuse through the same server context.
    - **Decided:** A, five roles and two custom roles from a hand-written table (decision 175, 2026-11-20).

11. **Guests: the gate says "guests limited to their projects", but until roadmap 8.4 a guest sees no project at all. What does H2 test?**
    - A (recommended). That a guest sees nothing and can do nothing, today; every guest cell is tagged so a check fails when 8.4 arrives until those cells are rewritten. Tests the rule that exists and forces the later one.
    - B. Leave guests out of H2 and test them in 8.4. Less work now; nothing stops 8.4 from forgetting.
    - **Decided:** A, a guest sees nothing now; guest cells tagged to fail when 8.4 arrives (decision 176, 2026-11-20).

**Accessibility**

12. **How is drag and drop checked for screen readers?**
    - A (recommended). Automated browser checks (accessibility rules in a real browser with `@axe-core/playwright`, a dev-only MPL-2.0 package used unmodified; snapshots of what the accessibility tree exposes at each step; focus after a move) plus a scripted manual pass with NVDA and VoiceOver once per hardening gate, recorded in the docs. Only a person can confirm what a reader actually speaks.
    - B. Automated checks only. Cheaper; misses wording and timing problems a reader user would hit.
    - C. An external accessibility audit. The strongest evidence; costs money and time and is better spent before general availability (9.2).
    - **Decided:** A, automated browser checks (`@axe-core/playwright`, dev-only) plus a scripted NVDA and VoiceOver pass per gate (decision 177, 2026-11-20).

**Fuzzing**

13. **How deep does fuzzing go?**
    - A (recommended). Property-based fuzzing of every intake parser and schema in the normal test run, a long run (20,000 cases each) nightly, plus route-level injection, oversize and flood tests, and the public form pages added to the nightly passive security scan. No new tools.
    - B. As A, plus a coverage-guided fuzzer (Jazzer.js, Apache-2.0) on the email parser nightly. Finds deeper parser bugs; adds a native dependency and a separate harness.
    - C. Property tests on pull requests only, no nightly long run. Least cost; rare inputs are found later.
    - **Decided:** A: property fuzzing in the normal run, a 20,000-case nightly run, route-level injection, oversize and flood tests, the public form pages in the nightly passive scan (decision 178, 2026-11-20).

**End-to-end tests and the gate**

14. **When does H2 close relative to 2.8 (reviews)?**
    - A (recommended). Merge H2's parts as they are ready; close the gate only when the review-route rows and the "earlier round is never rewritten" test are in, after 2.8c. Nothing waits on 2.8 except what must.
    - B. Start H2 only after all of 2.8 has merged. One clean sequence, but performance and concurrency work waits for weeks.
    - C. Close H2 without the review parts and move them to H3. Faster close; the roadmap's wording for H2 is not met.
    - **Decided:** A, merge parts as ready; close the gate after 2.8c (decision 179, 2026-11-20).

15. **End-to-end isolation: what is enforced?**
    - A (recommended). A guard against tests sharing state through variables (ported from inflect-compliance), a guard that signed-in specs use the per-test workspace, a fixed "today" for the test server, and a nightly run with every test repeated twice, no retries and four workers. Pull requests keep one retry.
    - B. The two guards only. Stops new violations; the date dependence stays, so a run across midnight can still split a test.
    - C. As A, and remove the retry on pull requests too. Order dependence surfaces at once, but so does every flaky browser step.
    - **Decided:** A: two guards, a fixed "today", and a nightly double run with no retries (decision 180, 2026-11-20).

16. **How is H2 delivered?**
    - A (recommended). Seven pull requests (seed and plans; budgets and the nightly; concurrency; permission matrix and required fields; board accessibility; intake fuzzing; E2E isolation), then one small pull request for the 2.8 parts. Each reviewable alone; most can run in parallel.
    - B. Three larger pull requests (performance; correctness: concurrency, permissions, fields; interface: accessibility, fuzzing, E2E). Fewer reviews, each much larger.
    - **Decided:** A, seven pull requests plus one for the 2.8 parts (decision 181, 2026-11-20).
