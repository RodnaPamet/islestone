## Summary

- **What moves.** The automation engine's mechanism:
  - the in-process bus on `globalThis`, with tenant and actor stamped from `RequestContext`;
  - the BullMQ dispatcher with insert-to-claim idempotency (`(tenantId, idempotencyKey)` unique, P2002 is a silent skip), the `PENDING → RUNNING` claim and the settle that only lands on a `RUNNING` row, so a cancel stands;
  - the DSL v2 filter evaluator, the rule chain with an else branch and its cycle guard, the execution watchdog (`sla-monitor`) and the date-relative `SCHEDULE` sweep;
  - the action executor's safety rules: actions run as the rule author's real membership, re-read every time; webhooks go through `safeFetch` with reserved headers stripped; the signing key sits in an encrypted column and never leaves the server;
  - rule readiness (a rule cannot be enabled while incomplete), dry run, re-trigger with an audit row, cancel, the live monitor, analytics, templates;
  - the form-based rule builder (`RuleBuilderModal`), the rule detail sheet, the rules, monitor and analytics tabs, and the step inspector (`AutomationInspectorPanel`).
- **What is cut.**
  - Every compliance event: 24 of the 27 catalogue names (Risk, control testing, Evidence, Control, Policy, Vendor, Onboarding and the emitter-less Issue pair; see "Event catalogue" below).
  - Compliance actions and targets: `UPDATE_STATUS` on Risk and Control, `CREATE_TASK`'s Control link and severity, `SCHEDULE` targets Evidence, ControlException and ControlTestPlan.
  - `INVOKE_SUBFLOW`, which is keyed on tldraw canvas group nodes.
  - `INVOKE_AGENT`, which moves to 6.3 as `START_AGENT_RUN`.
  - The scheduled control-check runner (`jobs/automation-runner.ts`), the auditor evidence pack, risk-based rule suggestions, the compliance onboarding wizard, the automation-bias metrics, the web-events switch and the legacy `secretRef` migration.
  - The process-canvas module switch (`usecases/process-canvas-module.ts`). At source it hides every automation surface: `processes/layout.tsx` L46–L54 calls `notFound()` and `SidebarNav.tsx` L198–L202 hides the nav item. In Islestone, Automations is a permission-gated area with its own nav entry and palette command.
- **The canvas is not a dependency.** The source's visual editor is an `AUTOMATION` mode of the tldraw process canvas, with a sync bridge between canvas nodes and rules. Roadmap section 6 lets Phase 4 (and 4.2, the canvas) run beside Phase 3, and requires only Phase 2 before Phase 5. So 5.1 builds its graph builder on React Flow (`@xyflow/react`, MIT; roadmap section 2.3's library table and sub-phase 5.1) as a projection of the rules. The canvas bridge (about 1,575 lines) stays behind. Details are under "Canvas coupling".
- **What is new.**
  - A project-management event catalogue (work items, comments, cycles, intake, integrations, schedule) and its emitters in the Phase 2 usecases.
  - Actions: `CREATE_WORK_ITEM`, `SET_FIELD`, `ASSIGN`, `ADD_COMMENT`.
  - A per-chain automation depth carried on `RequestContext` and stamped on events by the bus. It generalises the source's `__agentInvokeDepth` and `__subflowDepth` and closes the A → B → A loop the source could only refuse by event name.
  - The React Flow builder.
  - Two gaps the source has: an audit row when an operator cancels an execution, and server-side sanitising of the free text inside `actionConfigJson` (the source sanitises only `name` and `description`).
- **One deviation from the roadmap prompt.** Roadmap 5.1's prompt lists "start an agent run" among the actions. This map defers it to 6.3, because it needs the agent engine (Phase 6). See open decision 7.
- **Size.**
  - In scope at source: about 9,600 lines (14 engine modules 2,571, 4 jobs 1,052, 4 usecases 1,061, schemas, data and labels 684, 9 routes 339, 10 UI files 3,890).
  - Carried after edits: about 7,800.
  - Cut, not ported: about 4,700 lines.
  - New non-test code: about 2,000 lines (builder about 1,000, catalogue and contracts about 600, loop guard and emitters about 250, executor arms about 300). One fresh migration of about 160 lines.
- **Blocker before any COPY row.** As in the 2.1–2.2 map: ADR 0001 D1 is unsigned and `CLAUDE.md` ("Provenance and licences") forbids copying until it is. The task says the owner has authorised copying. Record that in ADR 0001 and amend `CLAUDE.md` before step 1 of "Ordering and risks". Every row below also needs a `PROVENANCE.md` entry.

### Canvas coupling

At source, the "visual rule editor" is the tldraw process canvas in `ProcessCanvasMode.AUTOMATION` (`enums.prisma` L1612–L1616). Five node kinds (`trigger`, `condition`, `action`, `agent`, `slaGate`; `components/processes/node-taxonomy.ts` L84–L118 and L347–L460) map onto rules:

- `services/canvas-rule-sync.ts` (443) creates a DRAFT stub rule for each new `action` or `agent` node on map save. It writes `ProcessNode.dataJson.ruleId` back, wires `chain-delay`, `condition-pass` and `condition-fail` edges to `nextRuleId` and `elseRuleId`, and hydrates nodes with the rule's status and count on load. It is called from `usecases/process-map.ts` L14–L17, L53–L54, L143 and L174–L175.
- `services/canvas-subflow-membership.ts` (189) writes `AutomationRule.subFlowGroupId` from canvas group nesting. That key is what `INVOKE_SUBFLOW` targets.
- `lib/processes/canvas-rule-wiring.ts` (125) decides which rule a feeding node (trigger, condition, SLA) configures.
- `components/processes/ProcessInspector.tsx` (753) L95–L103 and L236–L290 mounts `AutomationInspectorPanel` for an automation node.
- `canvas-rule-status.tsx` (81), `canvas-execution-overlay.tsx` (311), `canvas-sync-status.tsx` (36), `canvas-mode-context.tsx` (33), `run-mode-context.tsx` (34), `switch-canvas-mode.ts` (56) and `services/governance-graph-builder.ts` (200) are display and mode plumbing around it.

**Recommendation: no canvas bridge in 5.1.** The Islestone builder is a React Flow graph projected from the rules: trigger node, condition node, action node, then `nextRuleId` and `elseRuleId` edges. Positions come from dagre, so there is no geometry table and no second source of truth to sync. The source's invariant becomes trivially true: logic lives only on `AutomationRule`.

Carried as patterns:

- `RULE_OWNING_KINDS` / `FEEDING_KINDS` (`canvas-rule-wiring.ts` L30, L56) become the node kinds of the projection.
- The inspector's rule ("feeding steps edit their rule's single fields here; forms open the rule builder"; `AutomationInspectorPanel.tsx` L1–L31) is kept.
- Readiness reasons come from the server.

If the owner later wants hand-arranged layouts, add an `AutomationFlowLayout` table (positions only) keyed by rule id. It must never hold logic.

**Known traps**

1. **Catalogue and union change together.** The compile-time check in `event-contracts.ts` (L199–L207) fails `tsc` on a catalogue entry without a contract, and `EVENT_LABELS` is `Record<AutomationEventName, …>`, so it fails too. Land events, contracts and labels in one commit.
2. **The dispatchers bypass RLS.** They use the `prisma` singleton with explicit `tenantId` filters. That works only because the role is not `app_user`, so `superuser_bypass` applies (`automation-event-dispatch.ts` L132–L143 and L175–L298, `rule-chain-dispatch.ts` L49–L171, `schedule-trigger-sweep.ts` L157). Islestone's preamble wants RLS to bind. Wrap the single-tenant dispatchers in 1.3's `runInTenantJobContext` (source label `'automation'`, which is not a KEK-bypass source) around the reads and writes only, never around the action. `executeAction` opens its own tenant context through the usecases, and a held transaction around a webhook pins a PgBouncer connection. The cross-tenant SCHEDULE and watchdog reads use `runWithoutRls({ reason })`.
3. **Loops.** Routing actions through usecases makes them emit (the source's own note, L421–L446). With four new item-writing actions, a two-rule ping-pong is easy to configure and every hop has a fresh `stableKey`. Ship the depth limit in the same change as the first item-writing arm, and test the A → B → A case against a real database.
4. **The 2.2 stub's shape.** 2.2's map (2.1-2.2.md L366) defines the stub as `emitAutomationEvent(ctx, e: { event; entityType: 'WorkItem'; entityId: string; actorUserId: string; stableKey: string; data })` with two data types. Two directions matter.
   - **Metadata widens, and must.** 5.1's `EmitAutomationEvent` takes `actorUserId: string | null` and `stableKey?: string`, as the source's `AutomationEventMetadata` has them (`event-contracts.ts` L28–L35). System emitters have no actor: the 2.5 cycle job, the schedule sweep, the watchdog. Widening a parameter type keeps every 2.2 call site compiling, so the stub's required `string` fields are compatible.
   - **Data types must not narrow.** A 2.2 call site passes an object literal, so dropping a stub field is an excess-property error there. Keep the stub's types as the first two members of the new union with every field (`title` included, until risk 6 is decided), and add fields only as optional. If `title` goes, remove it from 2.2's two call sites in the same commit.
5. **Barrel cycle.** `action-executor` → `usecases/work-item` → `automation/index` → `automation-bus`. This is safe only while the barrel never exports `action-executor` or `jobs/*`. Remove the `bus-bootstrap` re-export (manifest), so usecases do not load BullMQ through the barrel.
6. **Free text in payloads.** `WEBHOOK` posts `data` verbatim, the history API returns `triggerPayloadJson` with only a key-name scrub (`automation-executions.ts` L27), and rule filters can only test fields that are present. Keep `title` and `body` out of contracts, or decide explicitly that `title` is allowed and put it through the scrub. The source event carried `title`, and so does the 2.2 stub's `WorkItemCreatedData`, so dropping it touches 2.2's call sites (risk 4).
7. **Hard-coded enum lists.** `ACTION_CONFIG_BY_TYPE`, the executor switch, `buildActionLabels` (`AutomationInspectorPanel.tsx` L85–L94), `automation-filter-defs.ts` L36–L58, the builder's `ActionType` and its option list all spell the action enum out. The vocabulary guard checks them against the Prisma enum; keep it.
8. **Generated types.** `z.nativeEnum(AutomationActionType)` and the route's enum imports need `prisma generate` after every enum change; run it before typecheck in CI. When 6.3 adds `START_AGENT_RUN`, the schema map and the executor switch fail to compile until handled. That is intended.
9. **undici pairing.** `safeFetch` must use undici's own `fetch` with undici's `Agent` (`webhook-safety.ts` L23–L27 and L277–L286). Global `fetch` with an npm `Agent` broke every webhook on undici 8. It is 1.5's file, but 5.1's webhook test is the first to exercise it end to end.
10. **Mixed client and server imports.** `event-labels.ts` and `rule-filter-defs.ts` are client-bundled. They must import `automation/events.ts` only, never the barrel (which reaches observability and BullMQ). The bundle-size budget and client-env guard from H1 will catch a slip.
11. **`createdByUserId` required.** It removes the firing-actor fallback. A rule whose author left fails with a named reason on every firing, and nothing reassigns it. Add a "rule author left" signal (a watchdog finding or a notification to admins), or the rule fails silently from the user's point of view.
12. **Webhook delivery is one attempt.** 8-second timeout, no retry, no delivery log. 5.2 builds signed delivery with retries and replay. Either route `WEBHOOK` through it when 5.2 lands, or say in 5.1's docs that automation webhooks are best-effort. Event delivery itself is best-effort too: an enqueue failure is logged and swallowed (`bus-bootstrap.ts` L62–L79), and there is no outbox.
13. **H5 items not in the source:** per-tenant execution budgets, and flood tests. Plan them for the hardening series.
14. **Project deletion against a RESTRICT FK.** Without the archive and purge steps (Prisma section), 2.1's purge fails on the first project that has a rule. Land them with the migration that adds `projectId`.
15. **Test imports from the barrel.** Four tests import `toDispatchPayload` or `installAutomationBusDispatcher` from `@/app-layer/automation` (index row). Removing the barrel re-export without switching them fails `tsc` at step 3.
