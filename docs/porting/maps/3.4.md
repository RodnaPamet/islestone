## Summary

- **Four parts, each its own model, all written fresh.** Estimates on work items, in a unit each team chooses (decision 257); time entries a person records on a work item, by hand or with a timer (decisions 260 to 264); a weekly timesheet per person that is submitted and approved, which freezes its entries (decisions 268 to 270); and billable rates in a cascade of project, member and workspace, with history, one currency per workspace and amounts frozen at approval (decisions 271 to 274).
- **Nothing ports from inflect-compliance**: it has no time entries, timers, estimates, timesheets or rates. Three of its patterns are taken as patterns only: money as integer minor units with an ISO 4217 code under a CHECK (`AgentSpendingAuthority`), separation of duties that also covers authorship (its policy approval), and, as a lesson not followed, a workspace "currency symbol" that names no currency. From Kaneo (MIT, already adopted), **pattern only**: a timer is an entry with no end, and the duration is derived on the server. The AGPL trackers (Kimai, solidtime, Traggo) were **not read**.
- **Estimates** (`WorkItem.estimatePoints`, `WorkItem.estimateMinutes`, `Team.estimateUnit`; decision 257): off until a team chooses Points or Hours; the team's current unit decides which one is shown and counted. `estimate` becomes a configurable built-in field of the field sets; templates and repeats carry it (decision 258); the transition trigger records it, so the cycle burn-up gains a Points or Hours switch (decision 259, the 2.5a promise). The timeline and progress are unchanged.
- **A time entry is not a work item and not an activity.** `TimeEntry`: one person, one work item (decision 260), one date, a number of minutes, billable or not, an optional description (encrypted). A running timer is the person's one entry with no minutes yet (decision 262), counting at most 12 hours (decision 263). Stored to the minute, never rounded (decision 264).
- **Timesheets** (`Timesheet`, decision 268): off by default; when an Owner or Admin turns on "Timesheets need approval", a person submits their Monday-to-Sunday week, anyone holding `time.approve` other than themselves approves or returns it (decision 269), and a database trigger refuses any change to the entries of a submitted or approved week (decision 270).
- **Rates** (`BillableRate`, decisions 272 to 274): a project's rate, else the member's, else the workspace's, each with an effective date; an entry's amount is its minutes times the rate in force on its date, rounded per entry to the currency's minor unit; approval freezes each entry's rate; only holders of `time.rates` (Owners and Admins) see money.
- **A new `time` permission domain** (decision 265): `time.view`, `time.track`, `time.approve`, `time.rates`. Members record and see time; Viewers see it; Guests nothing (decision 204). Only a signed-in person records, submits or approves time: never an API key, agent or job (decision 278, ADR 0003).
- **Pages**: a "Time" sidebar entry with My time (the week grid and the timer), Timesheets (approvals) and Time totals (the sums, and an export as CSV or Excel; decision 275, the owner's choice C); a Time panel on the item's detail; the running timer in the top chrome. "Report" is banned (ADR 0006's View row), so no page is called one.
- **Four pull requests** (decision 279): 3.4a estimates, 3.4b time entries and timers, 3.4c timesheets and approval, 3.4d rates, totals and export (CSV and Excel). About 8,500 lines of source and 7,100 of tests.

## Estimates (3.4a)

### The model (decision 257)

```prisma
enum EstimateUnit { POINTS HOURS }

model Team {
  // … as today
  /// Roadmap 3.4a: NULL means the team does not estimate.
  estimateUnit EstimateUnit?
}

model WorkItem {
  // … as today
  /// A whole number of points, 0 to 100 (CHECK); counted when its team estimates in points.
  estimatePoints  Int?
  /// Minutes, 0 to 60,000 (1,000 hours; CHECK); counted when its team estimates in hours.
  estimateMinutes Int?
}
```

- **Two typed columns, not one number with a unit.** Points and minutes never mix in a sum, a CHECK bounds each, and a team that changes its unit loses nothing: the other column is kept, hidden and not counted, and switching back restores it (decision 257). An item moved to a team with another unit keeps its value the same way. Both may be set at once only by such a history; a write sets only the column of the item's team's current unit (400 `ESTIMATE_UNIT` otherwise, 409 `ESTIMATES_OFF` for a team that does not estimate).
- **Hours are stored as minutes** and entered as "2h 30m", "2.5h" or "150m"; one parser in `src/lib/work-items/estimate.ts` (client-safe, property-tested), used by every form and the API's input schema.
- **No index** for 3.4: nothing filters or sorts by an estimate yet (neither is offered; see "The views"), and the burn-up reads transitions. A later sort adds its index with its plan check.
- **The transition trigger records both** (`WorkItemTransition.estimatePoints`, `.estimateMinutes`), and both join its `UPDATE OF` list and `WHEN` clause, in the migration that adds them, as `20261128120100_waiting_on` did for `waitingOnUserId`: the 2.5 map's rule ("a column a later sub-phase wants counted joins the trigger's `UPDATE OF` list in its migration"). Rows written before carry NULL. `READ_ONLY_TABLES` is unchanged.
- **A team's unit** is changed under `admin.manage` through the team route (`PATCH /teams/:teamId { estimateUnit }`), audited `TEAM_UPDATED` naming the field; Settings → Teams gains the control. Changing it moves no value.
- **No automatic conversion of custom fields.** A project that made a NUMBER custom field called "Points" in 2.4 keeps it; nothing copies it into the estimate (a one-off copy tool is not built).

### Writes

- `PUT /work-items/:id/estimate { value: number | null }` (`work_items.edit`), the value in the team's unit (points, or minutes): a single-field versioned write (`updateVersioned`, `If-Match` optional), as `PUT /work-items/:id/cycle`; audited `WORK_ITEM_ESTIMATE_CHANGED` with the unit and both values (numbers, not text); then the watcher fan-out (`emitWatcherActivity`, kind `estimate`).
- A create (`createWorkItemInTx`, `insertTemplateItemInTx`) takes `estimate` in the same unit.
- **Field sets**: `estimate` joins `CONFIGURABLE_BUILT_IN_FIELDS`, and the CHECK `WorkItemTypeField_built_in_known` widens in its own migration, as `20261215120200_field_set_goal` did. A rule on a team that does not estimate is ignored (it cannot be met), as an archived field's rule is. Every create and the estimate write ask the field set (`assertFieldWrite`; 400 `FIELD_SET_UNMET` / `FIELD_HIDDEN`), and `tests/integration/field-set-routes.test.ts` gains the route.
- **Copies** (decision 258): `TemplateItemSource`, `TemplateOverrides` and `TemplateProjection` gain `estimatePoints` and `estimateMinutes`; `WorkItemTemplate` gains both columns (the item-templates manager's form shows the one its project's team uses); a project template's starter items carry an estimate in `ProjectTemplateContentSchema` (`version` stays 1, the field optional); a repeat copies its source's. A copy into a team that does not estimate, or estimates in the other unit, skips it and names it in `templateSkipped` (`estimate:unit`), never silently.
- **Agents** may later propose an estimate like any field (6.2; 7.1's plan proposals name "estimates"); approval runs this write as the person. Nothing in 3.4 writes an estimate but a person.

### The burn-up (decision 259)

- `TransitionFact` gains `estimatePoints` and `estimateMinutes`; `burnUp` gains a `measure: 'items' | 'points' | 'hours'` input, and each point gains `unestimated` (in-scope items with no estimate in the counted unit). Points and hours are summed from each item's picture at the end of the day, so an estimate changed mid-cycle shows as scope change on the day it changed. Pure, property-tested as today (the items measure is byte-identical to today's output).
- `GET /cycles/:id/burn-up?measure=points|hours` (`cycles.view`); the measure the team's unit allows, else 400 `MEASURE_UNAVAILABLE`. The cycle page's chart gains "Items / Points" (or "Hours") and the summary line "34 points, 6 items not estimated". The table under the chart shows the same numbers.
- **Unchanged**: milestone, initiative and goal progress count items (decision 212; `docs/goals.md` names weighting as a later decision); the timeline's durations come from dates (decision 185), and an hours estimate is not a duration; the calendar, the roadmap and calendar sync carry no estimate.

### The views

- Detail (page and sheet): an "Estimate" property under the dates, shown where the item's team estimates and the field set does not hide it; a number input for points, the duration parser for hours.
- List: an `estimate` column (gear, hidden by default; "5 pts", "2h 30m", blank for none or another unit). No sort, filter or lane in 3.4 (`LIST_SORTS`, `WORK_ITEM_FILTER_KEYS`, `BUILT_IN_LANES` unchanged): a sort across teams with different units has no meaning, and none was asked.
- Board card: a small estimate badge. Create dialog and intake accept dialog: the field, through the field set.
- Copy `workItems.estimate.*`, `settings.teams.estimateUnit*`, `cycles.burnUp.measure*`.

## Time entries and timers (3.4b)

### The model

```prisma
enum TimeEntrySource { MANUAL TIMER }

model TimeEntry {
  id              String          @id @default(cuid())
  tenantId        String
  /// The person whose time it is. FK → User (no cascade: users are not deleted before 8.3).
  userId          String
  /// FK (workItemId, tenantId) → WorkItem, ON DELETE SET NULL ("workItemId") in SQL: a purged item leaves the entry (decision 261).
  workItemId      String?
  /// The project the time was recorded in; FK (projectId, tenantId) → Project. Not moved with the item (decision 261).
  projectId       String
  /// The day the time counts on, date-only (never passed through a zone after it is set).
  workDate        DateTime        @db.Date
  /// 1 to 1,440 (CHECK). NULL only while the timer is on.
  minutes         Int?
  /// When the timer started; set for TIMER entries only (CHECK).
  timerStartedAt  DateTime?
  source          TimeEntrySource
  billable        Boolean
  /// ENCRYPTED (manifest), sanitised, at most 2,000 characters (CHECK on the plaintext in the usecase).
  description     String?
  /// Set when the week is approved, cleared when it is reopened (decision 273); both or neither (CHECK).
  frozenRateMinor Int?
  frozenRateLevel BillableRateLevel?
  /// Optimistic concurrency for edits (If-Match).
  version         Int             @default(1)
  /// Who wrote it: always the person whose time it is (decision 267; a CHECK holds it equal to userId).
  createdByUserId String
  createdAt       DateTime        @default(now())
  updatedAt       DateTime        @updatedAt

  @@unique([id, tenantId])
  @@index([tenantId, userId, workDate])
  @@index([tenantId, workItemId, workDate])
  @@index([tenantId, projectId, workDate])
}
// In the migration: the partial unique ("tenantId", "userId") WHERE "minutes" IS NULL
// (one timer per person per workspace, decision 262); CHECKs: minutes 1..1440 or NULL,
// (minutes IS NULL) implies source = 'TIMER' AND timerStartedAt IS NOT NULL,
// frozen columns both or neither; the trigger time_entry_week_frozen (3.4c).
```

- **Every entry is on one work item** (decision 260, principle 3). The item must be live, in a live, unarchived project the person can see (`visibleProjects`); closed items are allowed (decision 261). `projectId` is the item's project when the entry is written, and stays when the item moves: the time was spent for that project (decision 261). A purge clears `workItemId` and keeps the entry; the item reads "Deleted item".
- **No FK to the membership**: removing a member must not lose an approved week. `removeTenantMember` stops the member's timer (records it) in its transaction; their entries and weeks stay. The FK to `User` restricts, which is moot until 8.3, whose user deletion must handle time entries (recorded for 8.3 in `docs/time-tracking.md`).
- **Tenant-table rules**: `tenantId`, the three tenant-leading indexes, the four RLS policies with FORCE, `GRANT SELECT, INSERT, UPDATE, DELETE … TO app_user` in the creating migration, a two-tenant test in `ISOLATION_TESTED`, Layer B and C of `schema-index-coverage`, a catalogue test for the partial unique and the CHECKs. `TimeEntry` joins the plan checks' `GUARDED_TABLES` (see "Performance").
- **Not search-indexed** (ADR 0008: a new source is an amendment), **not in the Activity** (the item's Time panel shows entries; Activity stays changes and comments), **no automation event** (5.1's stub), **no watcher fan-out**.

## Timesheets and approval (3.4c)

### The model (decisions 268 to 270)

```prisma
enum TimesheetStatus { SUBMITTED APPROVED RETURNED WITHDRAWN }

model Timesheet {
  id                String          @id @default(cuid())
  tenantId          String
  userId            String          // the person whose week it is; FK → User
  weekStart         DateTime        @db.Date   // a Monday (CHECK extract(isodow) = 1)
  status            TimesheetStatus
  submittedAt       DateTime
  decidedAt         DateTime?
  decidedByUserId   String?         // an actor stamp, no FK; never the week's own person (CHECK)
  returnExplanation String?         // ENCRYPTED (manifest), sanitised; required with RETURNED (CHECK)
  version           Int             @default(1)
  createdAt         DateTime        @default(now())
  updatedAt         DateTime        @updatedAt
  @@unique([tenantId, userId, weekStart])
  @@unique([id, tenantId])
  @@index([tenantId, status, weekStart])
}

model TenantTimeSettings {           // one row per workspace; no row = defaults
  tenantId                String   @id
  approvalRequired        Boolean  @default(false)
  /// ISO 4217, three upper-case letters (CHECK); NULL until set (decision 273).
  currency                String?
  /// The recipient list notified of submitted weeks (2.7e); ON DELETE SET NULL ("approvalRecipientListId").
  approvalRecipientListId String?
  version                 Int      @default(1)
  updatedAt               DateTime @updatedAt
}
```

- **No row means not submitted.** A week the person never submitted has no row; status words are decision 256's (Submit, Approve, Return; `WITHDRAWN` when the person takes it back).
- **A week is Monday to Sunday by each entry's `workDate`** (decision 268): date-only arithmetic, so no zone enters the week once the date is set. `weekStart` is that Monday.
- **The freeze** (decision 270): the trigger `time_entry_week_frozen` (`BEFORE INSERT OR UPDATE OR DELETE ON "TimeEntry"`, `SECURITY INVOKER`) reads the timesheet of the entry's person and week (old and new week for an update) `FOR SHARE` and raises `TIMESHEET_FROZEN:` when its status is `SUBMITTED` or `APPROVED`. It admits exactly three writes: approval's stamp of `frozenRateMinor` / `frozenRateLevel` (and reopening's clear) with every other column unchanged; the key rotations' re-wrap of `description` (ciphertext to `v2:` ciphertext with every other column unchanged, the rule recorded for write-once triggers on encrypted columns); and the purge's `SET NULL` of `workItemId`, which fires user triggers as an ordinary update. A catalogue test reads the trigger; a behaviour test drives every writer against it.
- **Tenant-table rules** for both tables as for `TimeEntry`; `app_user` holds no DELETE on `Timesheet` (a decision is history) and none on `TenantTimeSettings`.

## Rates, totals and export (3.4d)

### The model (decisions 271 to 274)

```prisma
enum BillableRateLevel { WORKSPACE PROJECT MEMBER }

model BillableRate {
  id              String            @id @default(cuid())
  tenantId        String
  level           BillableRateLevel
  projectId       String?           // set for PROJECT; FK (projectId, tenantId) → Project, cascade
  userId          String?           // set for MEMBER; no FK to the membership (history outlives it)
  /// Minor units of the workspace's currency per hour, 0 to 2,000,000,000; NULL = "no rate at this level from this date".
  hourlyRateMinor Int?
  effectiveFrom   DateTime          @db.Date
  createdByUserId String
  createdAt       DateTime          @default(now())
  @@index([tenantId, level, projectId, userId, effectiveFrom])
}
// In the migration: CHECK level ↔ columns (WORKSPACE: neither; PROJECT: projectId only;
// MEMBER: userId only); UNIQUE NULLS NOT DISTINCT ("tenantId", "level", "projectId", "userId", "effectiveFrom").

model Project {
  // … as today
  /// New entries on this project are billable unless the person unticks it (decision 271).
  timeBillableByDefault Boolean @default(false)
}
```

- **The cascade** (decision 272): for an entry, the rate in force on its `workDate` at the PROJECT level for its project, else at the MEMBER level for its person, else at the WORKSPACE level; a NULL row at a level means "none at this level from this date" and falls through. No rate anywhere: the entry has no amount and Time totals say "No rate" for it. One pure function, `resolveRate` in `src/app-layer/domain/billable-rate.ts`, property-tested against a day-by-day reference; every reader calls it.
- **Amounts**: a billable entry's amount is `round_half_up(minutes × hourlyRateMinor / 60)` in minor units, rounded per entry, so a total is the sum of its lines; a non-billable entry has none. Computed on read from the rate history, or from the frozen rate once its week is approved (decision 273). Never stored as an amount.
- **Rate rows** are written by one usecase (`billable-rate.ts`, `time.rates`): `PUT /billable-rates/workspace`, `PUT /projects/:id/billable-rates`, `PUT /members/:userId/billable-rates` replace the rows for a date or add one; a row for a date may be deleted until that date has passed; audited `BILLABLE_RATE_SET` / `_REMOVED` (level, scope, date, amount: rates are not personal free text). Approved weeks are untouched by any rate change, because their rates are frozen.
- **Currency** (decision 273): one ISO 4217 code per workspace in `TenantTimeSettings`, required before the first rate; formatted with `Intl.NumberFormat` (its minor-unit digits, so JPY shows no decimals); changing it is refused while any rate row exists (409 `CURRENCY_IN_USE`).
- **Rates are plaintext integers**, protected by the key, not by encryption: totals are summed in SQL, and the manifest guard covers free text, which these are not. `encryption-manifest-coverage.test.ts` classifies them.

### Time totals

- `GET /time-totals?from&to&groupBy=project|person|item|week&projectId&userId&billable` (`time.view`; amounts only for `time.rates`): the window at most 366 days (400 `TIME_RANGE`), live entries in projects the caller can see, grouped in one aggregate over `TimeEntry` (minutes, billable minutes, entry count per group), at most 2,000 groups read one past (422 `TIME_TOTALS_TOO_LARGE` with the count, never cut); for a rates holder, amounts from one more read of the rate rows in the window and the frozen rates, computed per entry in the usecase (`timeAmounts`, pure), so the read touches each entry once. Not audited.
- **The page**: filters (dates, project, person, billable), group-by, a `DataTable` of the groups with hours, billable hours and (rates holders) amount, the total line, and Export with two choices, "CSV" and "Excel".
- **Export** (decision 275, **the owner's choice C over the recommended A: CSV and Excel**): `GET /time-totals/export?format=csv|xlsx&…` returns the entries in the filter as `text/csv` or as an Excel workbook (`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, one sheet, "Time entries"): date, person, project key, item key and title, hours to two decimals, minutes, billable, and for rates holders rate and amount; description only for the person's own entries or with `time.approve`. Both formats carry the same rows and columns, built once by one pure function (`timeExportRows`) and written by two small writers; at most 50,000 rows (422 `TIME_EXPORT_TOO_LARGE`). In the CSV every cell that starts with `=`, `+`, `-`, `@`, tab or carriage return is prefixed with `'`; in the workbook every text cell is written as a string cell (never a formula, which the writer cannot produce from a string) and numbers and dates as typed cells, and the same prefix is applied to text cells too, so a workbook saved back as CSV stays safe. Audited `TIME_EXPORTED` (`data_lifecycle`, `exported`; the format, the filter and the row count, never content). In the mutation tier's budget, since it decrypts.
- **The spreadsheet writer** (decided with 275; added in 3.4d, not before): **`write-excel-file` 4.1.1** (MIT, published 2026-06-08), whose one runtime dependency is **`fflate`** (MIT; 0.8.3 resolves under its `^0.8.2`), used on the server through its `write-excel-file/node` entry. Both licences are on the gate's allowlist; the scratch install of 2026-11-26 found no other package in the tree. **ExcelJS was checked first and not chosen**: `exceljs` 4.4.0 (its latest, MIT) brings about 190 packages, and four of them fail `npm run licence:check`: `buffers` 0.1.1 declares no licence, `chainsaw` 0.1.0 declares `MIT/X11` (not an SPDX id), and `pako` 1.0.11 declares `(MIT AND Zlib)` with Zlib off the allowlist; each would need an ADR 0007 exemption, and its `unzipper`, `archiver` and `jszip` chain is far more code than writing one sheet needs. 3.4d pins `write-excel-file` exactly (`.npmrc`'s `save-exact`), confirms `fflate`'s pinned version in the lockfile, runs `npm run licence:check`, adds no `NOTICE` line (MIT asks for none beyond the installed licence files) and a `PROVENANCE.md` row only if code is copied (none is planned).
- **Settings → Time tracking** (`settings/time-tracking`, a `SUBPAGES` entry): "Timesheets need approval", who is notified (a recipient list), the currency, the workspace rate and its history (`time.rates`); a project's rates and billable default on Settings → Projects and the project page (`time.rates`); a member's rate on Settings → Time tracking's Members tab. Removing a future rate goes through the undo toast (`SITE_CONTRACTS`).

## H3 and 3.4

## Rules no decision names (3.4a, as built)

Built on `wt/p34map` after the decisions; each is a choice the decisions and the body above leave open, recorded here and in [`docs/work-items.md`](../../work-items.md), "Estimates (3.4a)".

1. **The write's body.** `PUT /work-items/:id/estimate` takes `{ value, unit? }`: the value in the team's current unit, and the unit it was typed in. `unit` is optional for an API caller and always sent by the browser, so a value typed under one unit is never written under another after the team changed it (400 `ESTIMATE_UNIT`). A create names the column itself (`estimatePoints` or `estimateMinutes`, as a template does), not a unit-less `estimate`; both at once is 400 `ESTIMATE_UNIT`. A value out of range or not whole is 400 `ESTIMATE_RANGE` (the schema bounds the request to 60,000 first; points above 100 reach the usecase).
2. **Off means off, clearing included.** A team that does not estimate refuses every estimate write, `null` too (409 `ESTIMATES_OFF`): a clear would have to choose a column the team does not count.
3. **A rule the team cannot meet is HIDDEN, not OPTIONAL.** `resolveFieldSet` takes the project's team's unit (`estimateUnit`); `null` makes the estimate HIDDEN whatever its rule, so a form offers nothing and a value is refused, while the usecases answer `ESTIMATES_OFF` before the field set is asked. Left out (the timeline's and the calendar's date rules), the rule stands. `loadFieldSets` reads the unit when its caller has not (`TeamRepository.estimateUnitOfProject`): one more statement on a create and on `PATCH /work-items/:id`, not measured on the seed (the statements budget for a create is 32).
4. **Templates hold one estimate.** An item template's estimate is checked against its project's team's unit at save (`ESTIMATES_OFF`, `ESTIMATE_UNIT`) and saving one clears the other column, so a template never carries a hidden value.
5. **What a copy takes.** `templateToCreateInput` keeps the source's value in the column of the target team's current unit; a source whose only value is in the other column, or a team that does not estimate (or a use context that names no unit), is skipped as `estimate:unit`. A hidden value beside the counted one (an item that switched units) is not the source's estimate: it is not copied and not named. "Save as template" carries each item's counted estimate only; a project template's item templates keep theirs only in the new team's unit, else `estimate:unit` in `fromTemplate.skipped`.
6. **The watcher fan-out** uses the existing `updated` kind with the detail "estimate 5 points", as the goal write does; the map's `estimate` kind would have needed a new notification wording for one field. The Activity phrase is "changed the estimate".
7. **The team's unit is edited in the team's Edit dialog.** Settings → Teams' "Rename" became "Edit" (name and Points / Hours / Off, with a sentence that a change keeps every estimate); a new team may be given a unit in its create dialog, sent as a second `PATCH` after the create (`CreateTeamSchema` stays name-only). An unchanged save writes and audits nothing (a rename used to audit even an unchanged name).
8. **The burn-up's answer** carries `measure` and `measures`; the items measure's points keep 2.5a's shape exactly (no `unestimated` key), so 2.5a's output is byte-identical. The cycle page keeps the previous measure's chart while another loads, labelled by its own `measure`.
9. **The board card's badge** reads "5 pts" or "2h 30m" with a screen-reader prefix "Estimate"; the list's `estimate` column joins the column gear's choices, hidden by default.

## Rules no decision names (3.4b, as built)

Built on `wt/p34b` (stacked on `wt/p34map`) after the decisions; each is a choice the decisions and the body above leave open, recorded here and in [`docs/time-tracking.md`](../../time-tracking.md).

1. **Two route keys, the rest in the usecase.** A week is read under `time.track`; another member's week also asks `time.approve`, refused past the route's key with an audited 403 `TIME_APPROVE_REQUIRED` (a route takes one literal key, and a custom role may hold `time.approve` without `time.track`: until 3.4c's Timesheets give an approver a route of their own, such a role reads no week). An item's time is read under `work_items.view`; the usecase asks `time.view` or `time.track` and refuses neither with an audited 403 `TIME_VIEW_REQUIRED`.
2. **The granular key decides** (`time.policies.ts`), as `work_items.comment` does: a custom role built on VIEWER that grants `time.track` records time, one built on MEMBER without `time.view` sees only its own entries; with no granular layer the coarse tier stands in (`canRead`, `canWrite`, `canAdmin`).
3. **"A person" is the health rule's** (`recordsTimeAsPerson`, as `setsHealthAsPerson`): no API key or agent, no job context and never the workspace's system user; the refusal is audited `AUTHZ_DENIED` with `NOT_A_PERSON`, as health's is. `assertActingAsPerson` alone would admit a job.
4. **Another person's entry is a 404**, not a 403, on change and delete: it is not the caller's to change, and its existence is not theirs to learn by id.
5. **A running timer is not an entry.** It cannot be changed (409 `TIMER_ON`), it is deleted to discard it, it counts in no total, and it is left out of an item's entries and totals (others do not see who is working right now); one's own week lists it, its cell marked "Timer on".
6. **A full day refuses the stop, the start that would stop it, and nothing else.** Stopping a timer whose minutes would take the day past 24 hours is 409 `DAY_FULL` with the minutes left (the person states fewer or discards it); so is a start that would record the timer it replaces. Member removal never fails on it: the removed member's timer records what its day still holds, or is discarded. A start replacing a timer stops it by the same rules, under 30 seconds discarded.
7. **Two locks, in one order.** The person's timer lock (`time-timer:<workspace>:<person>`) first for the timer's acts, then the week locks in date order; the partial unique remains the backstop. The map's week lock key is used as written.
8. **Re-picking an entry's item moves its project.** Decision 261 keeps an entry's project when its item moves; when the person picks another item for the entry, the time was recorded on that item, so `projectId` becomes the new item's project (`TIME_ENTRY_UPDATED` names both fields).
9. **An entry whose item is gone may be deleted, not changed** (409 `ITEM_DELETED` for a purged item; a soft-deleted item or an archived project refuses as for adding time, 404 or 409 `PROJECT_ARCHIVED`).
10. **No date limit.** An entry may be dated in the future or long ago; only 3.4c's frozen weeks will refuse a date.
11. **Bounds.** A week read reads at most 1,000 entries and refuses more (422 `TIME_WEEK_TOO_LARGE`, never cut); an item's entries are paged 50 at a time, newest first by date then id (`ITEM_TIME_ORDER`).
12. **Billable is unticked by default** until 3.4d adds the project's default (decision 271).
13. **A deleted project that time was recorded in is held from the purge**, items and all, while its time entries remain (`purgeableProjectIds`): decisions 261 and 277 keep the entries with their project for the workspace's life, `TimeEntry.projectId` is NOT NULL, and the work-item purge (`WORK_ITEM_PURGE_DAYS`) would otherwise refuse or cascade. An item purged on its own still leaves its entries, which read "Deleted item". An owner question (`docs/HANDOFF.md`). **Decided (281, 2026-11-27):** the lasting rule is a project tombstone: the purge removes the project's items and content but keeps a minimal project row (key, name, deleted) so its time entries keep their project; the hold is the interim until that is built (issue to follow).
14. **The pages' choices.** The Time entry sits in the sidebar's first section, after Inbox (My time is the person's own); My time opens on the week of today in `NOTIFICATIONS_TZ` through the clock seam, and a new entry's date defaults to the browser's today; "Add row" is "Add time" with the item picker (a row appears with its first entry, no empty rows are kept); the top chrome's timer shows at md and up, as the chrome does, and counts on the server's clock (`serverNow`); a timer is started from the palette only on the item whose Time panel is open.
15. **Labels for what the reader cannot see.** In the week, an entry whose item was purged or soft-deleted, or whose project was deleted, reads "Deleted item"; "Item you cannot see" is kept for a caller whose visibility is granted (a guest after 8.4).
16. **Measured, not the map's numbers.** The scale seed writes about 29,000 entries per 10k workspace (a writer whose day is full hands the entry to another; the map said about 30,000). Statements per request: the week 5 and an item's time 6 (the map proposed 4 and 3 without the tenant binding and Prisma's relation reads), adding time 12; the 100k buffer budgets are extrapolated (issue #93).

## Open questions for the owner (all decided, 2026-11-26)

Each question stands alone. The recommended option is first and marked; each option carries its main trade-off. Each carries its decision, numbered 254 + its question.

**Words**

1. **What are the new things called, and where are the rules recorded?**
   - A (recommended). "Time entry" (`TimeEntry`), "Timer" (a time entry being timed), "Time spent", "Estimate" (`Team.estimateUnit`, `WorkItem.estimatePoints` / `estimateMinutes`), "Timesheet" (`Timesheet`), "Billable", "Billable rate" (`BillableRate`), "Time tracking settings"; a sidebar entry "Time" with "My time", "Timesheets" and "Time totals"; the verb "Add time". A new ADR 0012 records the rules, with ADR 0006 rows and an ADR 0002 section. Avoids every banned word ("Log", "Report", "Lock", "Mode", "Story").
   - B. The same words, no new ADR: the rules go in ADR 0002 and `docs/time-tracking.md`. One fewer document; money rules (cascade, rounding, freezing) sit in the work-item ADR.
   - C. "Worklog"-style naming ("Log time", "Time log"), as Jira does. Familiar to Jira users; needs an ADR 0006 amendment, since "Log" is banned for activity and transitions.
   - **Decided:** A, the names as proposed and a new ADR 0012 (decision 255, 2026-11-26). Applied: ADR 0012 (Accepted), ADR 0006 "Time words of sub-phase 3.4", ADR 0002 §12 and §18, ADR 0003 §4.

2. **What are a timesheet's verbs?** "Approve" is the proposal's verb today, and reviews chose "Sign off" to avoid it.
   - A (recommended). Submit, Approve, Return (statuses Submitted, Approved, Returned). The words every timesheet product uses; ADR 0006 records that "Approve" now names both a proposal's and a timesheet's decision, told apart by their object.
   - B. Send for approval, Approve, Return. Echoes reviews' "Send for review"; the same "Approve" overlap.
   - C. Submit, Sign off, Return, reusing review steps' words. No overlap with proposals; "Signed off" then means two things, a review outcome and a timesheet decision.
   - **Decided:** A, Submit, Approve, Return (decision 256, 2026-11-26); ADR 0006 records that "Approve" names a proposal's decision and a timesheet's, told apart by their object.

**Estimates**

3. **How do teams estimate?**
   - A (recommended). Each team chooses Points, Hours or no estimates (none by default); points are whole numbers from 0 to 100, hours are entered as "2h 30m" and stored as minutes. Changing a team's unit keeps the other kind of value stored but hidden and uncounted, so switching back restores it. Nothing is lost; a team cannot mix units.
   - B. As A, but changing the unit clears every estimate of the team's items, after a confirmation that counts them. Simpler data; a mistaken switch destroys estimates.
   - C. One unit for the whole workspace. Simplest; ignores the roadmap's "per team".
   - D. Points and hours side by side on every item. Most flexible; two numbers to keep current and two burn-ups to read.
   - **Decided:** A, Points, Hours or none per team; the other kind kept, hidden and uncounted (decision 257, 2026-11-26).

4. **What copies an estimate?**
   - A (recommended). Item templates, project templates' starter items and repeats carry it; a copy into a team that does not estimate, or uses the other unit, skips it and says so. A moved item keeps its value, hidden if its new team uses another unit. Matches how every other field is copied.
   - B. Only repeats copy it; templates carry none. Smaller; a template for routine work cannot preset its usual size.
   - C. Nothing copies it. Every copy starts unestimated; repeated work must be re-estimated by hand.
   - **Decided:** A, templates, starter items and repeats carry it, a skip named; a move keeps it (decision 258, 2026-11-26).

5. **What do estimates change?**
   - A (recommended). The cycle burn-up gains a "Points" (or "Hours") switch beside "Items" for a team that estimates, from the recorded changes (the transition trigger watches the estimate), with unestimated items counted and named. Milestone, initiative and goal progress keep counting items, and the timeline keeps using dates. Delivers 2.5a's promise and nothing riskier.
   - B. The burn-up and all progress (milestones, initiatives, goals) weighted by estimate. Progress closer to effort; mixed units across teams make a goal's progress ambiguous.
   - C. Nothing in 3.4: estimates are shown only; points in the burn-up wait for 3.6. Smallest; the burn-up stays items a while longer.
   - D. As A, and an undated item with an hours estimate gets that duration on the timeline. Fills timelines; contradicts decision 185 (one working day) and mixes effort with elapsed time.
   - **Decided:** A, the cycle burn-up's Points or Hours switch from transitions; progress and the timeline unchanged (decision 259, 2026-11-26).

**Time entries and timers**

6. **What can time be recorded against?**
   - A (recommended). Always one work item. Keeps principle 3 (tracked work is a work item); a project that wants a bucket for meetings makes an item for it.
   - B. A work item, or a project directly. Fits "general project time" without a placeholder item; two kinds of entry in every total and rule.
   - C. A work item, a project, or nothing (workspace time, such as training). Most flexible; time that belongs to no project has no rate below the workspace's and no approver's context.
   - **Decided:** A, always one work item (decision 260, 2026-11-26).

7. **What about closed, archived, deleted and moved items?**
   - A (recommended). Time may be recorded on open and closed items, not on deleted items or in archived projects. A moved item's entries stay with the project they were recorded in. A purged item's entries are kept, shown as "Deleted item". People often record time after closing; approved weeks never change underneath.
   - B. As A, but a moved item's unapproved entries move with it to its new project (approved ones stay). Totals follow the item; a move silently changes a project's hours and amounts.
   - C. Refused on closed items too: reopen to record time. Tidier records; tedious, and late time goes unrecorded.
   - **Decided:** A, open and closed items, not deleted items or archived projects; entries stay with their project; a purged item's entries kept (decision 261, 2026-11-26).

8. **How many timers can a person have on?**
   - A (recommended). One per person per workspace, kept on the server so every tab and device shows it; starting another stops the first and records it. Prevents double counting; a person working in two workspaces can have one in each.
   - B. One per person across all workspaces. Stricter; needs a check across workspaces, outside row-level security.
   - C. Several at once. Covers parallel work; easy to double count.
   - **Decided:** A, one timer per person per workspace, on the server (decision 262, 2026-11-26).

9. **What happens to a forgotten timer, and which day does a timer count on?**
   - A (recommended). A timer counts at most 12 hours, then stops counting; no job is needed, and on Stop the person may lower the time. The time counts on the day it started, in the person's own time zone, and a week cannot be submitted while one of its timers is on. Bounds a forgotten timer's damage without a background job.
   - B. A job stops any timer at 12 hours, records 12 hours and notifies the person. The timer really stops; the record says 12 hours until fixed.
   - C. No limit, and a timer crossing midnight splits into one entry per day. Precise; one forgotten timer makes days of entries.
   - **Decided:** A, a timer counts at most 12 hours, on the day it started in the person's zone; no week submitted while one of its timers is on (decision 263, 2026-11-26).

10. **Is time rounded?**
    - A (recommended). No: stored to the minute, as entered or as timed (a timer's seconds to the nearest minute, at least one). The record says what happened; billing rules can come later.
    - B. A workspace increment (5, 6, 10 or 15 minutes), applied when a timer stops or an entry is saved, rounded up. What many agencies bill; the stored record is no longer what happened.
    - C. Stored exactly, and the increment applied only to billable amounts in totals and the export. Exact record and billing rounding; two numbers for one entry.
    - **Decided:** A, stored to the minute, never rounded (decision 264, 2026-11-26).

**Who**

11. **Who may record time, and under which keys?**
    - A (recommended). A new `time` domain: `time.view`, `time.track`, `time.approve`, `time.rates`. Owners and Admins hold all four, Members view and track, Viewers view, Guests nothing (decision 204). Custom roles can grant each; nothing rides on `work_items.edit`.
    - B. Recording time rides on `work_items.edit`, approval and rates on `admin.manage`. No new domain; a custom role cannot let someone track time without editing items, or approve weeks without workspace administration.
    - C. As A, and Viewers also track their own time. Fits outside consultants added as Viewers; Viewers would write for the first time (decision 60 lets them save only personal views).
    - **Decided:** A, a new `time` domain: `view`, `track`, `approve`, `rates` (decision 265, 2026-11-26).

12. **Who sees other people's time?**
    - A (recommended). Everyone holding `time.view` sees who recorded how much time on items they can see, with descriptions; a person's whole week only an approver; money only rate holders. Teams see where effort went, without a view of each person's week.
    - B. Each person sees only their own entries and each item's total; approvers see everything. More private; less useful to a team planning its work.
    - C. Only their own; no totals for others except approvers and admins. Most private; an item's time spent is invisible to its own team.
    - **Decided:** A, `time.view` sees who recorded how much on visible items; a whole week only an approver; money only rate holders (decision 266, 2026-11-26).

13. **May someone record time for someone else?**
    - A (recommended). No: a person records only their own time; an approver returns a week to have it fixed. Every entry is its person's own statement.
    - B. Holders of `time.approve` may add or change another member's entries while the week is not approved, recorded with who wrote them; that approver then cannot approve the week, and the member is notified. Helps with contractors and corrections; a manager can put words in someone's timesheet.
    - C. Any member who can edit an item may record time on it for anyone. Easiest for team leads; no clear authorship.
    - **Decided:** A, nobody records time for someone else (decision 267, 2026-11-26).

**Timesheets**

14. **Are timesheets approved, and what is a week?**
    - A (recommended). Off by default: an Owner or Admin turns on "Timesheets need approval" in Settings → Time tracking. A week is Monday to Sunday, by each entry's date, as the product's date pickers already start weeks. Teams that only track time are not made to submit; one week for everyone.
    - B. Always on, Monday to Sunday. Matches the roadmap's wording literally; every workspace must submit weekly to keep records tidy.
    - C. Off by default, with the week's first day chosen per workspace. Fits Sunday-start countries; a week that differs from the date pickers', and a change of start day reshapes past weeks.
    - **Decided:** A, off by default, Monday to Sunday (decision 268, 2026-11-26).

15. **Who approves, and what is approved?**
    - A (recommended). Anyone holding `time.approve` (Owners and Admins, or a custom role) approves a member's whole week, never their own; the people of a recipient list chosen in the settings are notified, or every holder when none is. One decision per week; reuses recipient lists.
    - B. Per project: each project's approvers approve that project's lines, and a week is approved when every project's are. Fits agencies billing clients per project; needs project approvers, a concept that does not exist.
    - C. A named approver per member ("approves for"). Mirrors a reporting line; a new person-to-person relation to maintain.
    - **Decided:** A, any holder of `time.approve`, a whole week, never their own; a recipient list notified (decision 269, 2026-11-26).

16. **What can change once a week is submitted or approved?**
    - A (recommended). Submitting freezes the week's entries; the person can take it back until it is decided; Return reopens it with an explanation; an approved week stays frozen unless an approver reopens it, with an explanation, audited and notified. A database trigger holds the freeze. Approved weeks are dependable; mistakes can still be fixed openly.
    - B. Approved is final: corrections are new entries in the current week. Simplest audit story; corrections land in the wrong week.
    - C. Submitting freezes nothing; only approval does. Fewer steps; an approver can approve a week that changed after they read it.
    - **Decided:** A, submitting freezes; take back, return and reopen with an explanation; a trigger holds the freeze (decision 270, 2026-11-26).

**Money**

17. **Is an entry billable?**
    - A (recommended). Each project says whether its new entries are billable by default (off unless set); the person can change it on each entry while the week is open; non-billable entries carry no amount. Covers billable clients and internal projects alike.
    - B. Every entry is billable unless the person unticks it. Never under-bills; internal work shows amounts until people remember to untick.
    - C. Decided by the project only, never per entry. Consistent; no way to mark one hour of goodwill.
    - **Decided:** A, a per-project billable default, changeable per entry while the week is open (decision 271, 2026-11-26).

18. **How does the rate cascade work?**
    - A (recommended). As the roadmap lists it: the project's rate, else the member's, else the workspace's; no rate anywhere means no amount ("No rate"). Three levels, simple to explain; one project rate applies to everyone on it.
    - B. A member-on-a-project rate first, then project, member, workspace. Covers "Ana bills 120 on this client, 100 elsewhere"; a fourth level to manage.
    - C. The member's rate first, then the project's, then the workspace's. Rates follow people (seniority); a client's fixed project rate cannot override them.
    - **Decided:** A, project, then member, then workspace; no rate is "No rate" (decision 272, 2026-11-26).

19. **How do rates change over time, and in what currency?**
    - A (recommended). Every rate has an effective date and a history; an entry takes the rate in force on its date; approving a week freezes each entry's rate, so later changes never alter it. One currency per workspace (ISO code, chosen before the first rate, not changeable while rates exist), amounts in minor units, rounded per entry. Correct past amounts without stored totals; invoices stay stable once approved.
    - B. Only the current rate; changing it changes every unapproved entry's amount; approval freezes. Simpler; a rate rise on the 15th reprices the start of the month.
    - C. As A, with a currency per project. Fits agencies with foreign clients; totals across projects need conversion, which Islestone would not do.
    - **Decided:** A, effective dates and history, rates frozen at approval, one ISO currency per workspace, per-entry rounding in minor units (decision 273, 2026-11-26).

20. **Who sees rates and amounts?**
    - A (recommended). Only holders of `time.rates` (Owners and Admins by default) see and set rates and amounts; Members see hours and billable flags, never money, their own included. Keeps pay-adjacent numbers private.
    - B. Members also see the amounts of their own entries. Transparent to the person; reveals their rate.
    - C. Everyone who sees time sees amounts. Simplest; exposes every member's rate to the team.
    - **Decided:** A, only `time.rates` holders see rates and amounts (decision 274, 2026-11-26).

21. **Is there an export?**
    - A (recommended). A CSV of the entries behind Time totals' filter, at most 50,000 rows, amounts only for rate holders, protected against spreadsheet formulas, audited. What invoicing and payroll need now.
    - B. No export until the public API (5.2). Smaller 3.4; finance copies numbers by hand meanwhile.
    - C. CSV and Excel. Nicer for finance; a spreadsheet writer dependency and its licence check.
    - **Decided:** **C, CSV and Excel, a departure from the recommendation** (decision 275, 2026-11-26): the export offers both formats with the same rows, limits, formula protection and audit as A; the Excel workbook needs a spreadsheet writer, added in 3.4d: `write-excel-file` 4.1.1 with `fflate` (both MIT), because ExcelJS 4.4.0's tree fails the licence gate ("Rates, totals and export" above).

**Around it**

22. **Which notifications and reminders?**
    - A (recommended). A bell to whoever approves when a week is submitted; to the person a bell and an immediate email when it is returned, and a bell when approved; and a Monday reminder to people who recorded time last week and have not submitted it, while approval is on. All under the person's preferences. People learn of decisions; weeks get submitted.
    - B. The same, without the weekly reminder. Fewer notifications; weeks go unsubmitted.
    - C. None: the Timesheets page and the week's status line only. Quietest; returned weeks go unnoticed.
    - **Decided:** A, the submitted, returned (with immediate email) and approved notifications and the Monday reminder (decision 276, 2026-11-26).

23. **How long is time kept, and how is an entry deleted?**
    - A (recommended). For the workspace's life (8.3's retention settings may change that later); an entry deleted by its person (only while its week is open) is removed, and the audit trail keeps that it existed, with its date and minutes. Simple and complete.
    - B. Entries older than a workspace-chosen number of years are purged nightly. Data minimisation; billing disputes and audits may need older records.
    - C. Deleted entries are soft-deleted and restorable for 30 days, like work items. Recoverable; a third deletion lifecycle to maintain, beside the undo toast that already guards a slip.
    - **Decided:** A, kept for the workspace's life; an entry deleted only while its week is open, the audit keeping its date and minutes (decision 277, 2026-11-26).

24. **May agents or API keys record time?**
    - A (recommended). No: only a signed-in person records, changes, submits or approves time, never an API key, an agent or a job (ADR 0003: an agent is never a person). An agent may propose an estimate like any field from 6.2; 6.3's agent sessions keep their own durations, never as time entries. Time stays a person's own statement.
    - B. Agents may propose time entries for a person to approve (from 6.2). Could draft a week from activity; a person's record of their work, written by a machine.
    - C. API keys may write time from 5.2 (for imports from other trackers); agents never. Opens migrations from other tools; a key acts as its creator, so entries could be written in someone else's name.
    - **Decided:** A, only a signed-in person records, changes, submits or approves time; an agent may propose an estimate from 6.2 (decision 278, 2026-11-26).

25. **How is 3.4 delivered?**
    - A (recommended). Four pull requests: 3.4a estimates, 3.4b time entries and timers, 3.4c timesheets and approval, 3.4d rates, totals and export. Each reviewable alone; estimates ship first and unblock the burn-up.
    - B. Three: estimates; time entries and timers; timesheets, rates and totals together. Fewer reviews; the last one mixes the freeze with money rules.
    - C. Two: estimates, then all of time tracking. Fastest to track; about 6,500 lines in one review.
    - **Decided:** A, four pull requests: 3.4a, 3.4b, 3.4c, 3.4d (decision 279, 2026-11-26).
