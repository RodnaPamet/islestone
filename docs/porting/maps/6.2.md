## Summary

- **What moves.** The MCP funnel, which is the whole value of the subsystem: `buildMcpInvocation` (principal ∧ credential, resolved once per request), `authorizeToolCall` (kill switch → audience → credential liveness → breaker → tool-manifest pin → deny-by-default exposure → autonomy ceiling → policy card → capability → resource scope → `assertPermission` → `assertCan*`, one `AUTHZ_DENIED` row per refusal), the read and propose registries with their deny-by-default loadable-set snapshot, per-domain redaction, the RFC 8693 token exchange (`POST /api/mcp/token`, signed audience-scoped `ifxt_` tokens, stateless), the two-budget rate limit (`MCP_IP_CEILING_LIMIT` 600/min/IP before auth, `MCP_PER_KEY_LIMIT` 60/min per verified key after it, charged before the invocation is built), tool-definition pinning (`McpToolManifestPin`, ASI04), and `local/require-mcp-tool-authorization`. The proposal queue: `createAgentProposal` (schema-validate → sanitise → output guard → QUARANTINED or PENDING), approve / approve-with-edits / reject / bulk reject with four-eyes tiering, write-once `requiredApprovals`, the base-digest stale check, expiry and retrospective sampling, its review page and quarantine view.
- **Every tool module is compliance except the mechanism.** 15 read tools and 5 propose tools ship in the source; **none is kept as is**. `list_tasks` and `get_tenant_context` are the only generic-shaped ones and both are rewritten against 2.2 usecases. Islestone writes 7–13 read tools and 4–6 propose tools (projects, work items, comments, cycles, search, docs, analytics; work-item create/update, comment, relation, plan, schedule change), staged by the sub-phase that owns each usecase.
- **What is cut.** The Entra grant and service-principal endpoints (642 lines), the outbound MCP clients (`lib/mcp/client/**`, `wire-transport.ts`, `tools/external-tools.ts`: 2,391 lines), pipelock receipts, the harness, recertification, audit-workpaper, framework, risk, control, evidence, finding and knowledge tools, the compliance resources, dashboard redaction rules, workpaper-dissent rules, the agent risk-tier/assessment terms, oversight switches for AUDITOR, external-write and process-map proposal kinds, and `/agents/compose`.
- **The source does not use the MCP SDK.** `protocol.ts` hand-rolls JSON-RPC for revisions `2025-06-18` and `2024-11-05` and supports batches. The 2026-07-28 revision (per-request `_meta` envelope, `server/discover`, no `ping`, no batches with a modern element, `resultType`, cache hints, in-band `input_required` instead of server→client requests) is served by replacing `dispatchMcp` with `createMcpHandler` from `@modelcontextprotocol/server@2.4.0` (Apache-2.0) over a per-request low-level `Server`. The auth, budget and funnel stay in front of it unchanged (section "SDK v2 and the 2026-07-28 revision").
- **Three ordering traps, all outside the roadmap's stated dependencies.** (1) 6.1's engine-neutral tool core imports this funnel (`engine-tools/offer-tools.ts`, `run-guarded-tool.ts`), so the funnel library has to land before 6.1's engine-tools step. (2) MCP authenticates only with `TenantApiKey`, which 1.4 deferred to 5.2, and Phase 6 does not depend on Phase 5 (roadmap §6; the first release is 0–2 + 6.1–6.4 + 7.1), so the API-key slice must be pulled forward. (3) The `Agent` model arrives in 6.3, so the agent-keyed funnel terms ship as same-path stubs that answer "no governed agent".
- **Database.** Four tenant tables in one fresh migration (`Proposal`, `ProposalApproval`, `ProposalSampleAudit`, `McpToolManifestPin`) with RLS, CHECKs and six trigger functions re-written from nine source migrations; three columns on `TenantApiKey` and one on `TenantSecuritySettings`; two `NotificationType` values. `AgentProposal` is renamed `Proposal`, `SuggestionItemStatus` becomes `ProposalStatus`, `kind` becomes checked text (ADR 0003 §8, ADR 0006 rule 8).
- **Size.** About 17,800 source lines are read for the manifest; about 12,500 land after cuts (≈4,900 `lib/mcp`, ≈3,300 `lib/agentic`, ≈3,000 usecases and jobs, ≈2,800 UI and routes), plus ≈1,200 new lines of PM tools, stubs and the SDK adapter. About 60 test files (≈19,000 lines) come with it, most COPY+EDIT with new PM fixtures; about 250 are left behind or belong to 6.1/6.3/later.
- **Gate before any copy.** Islestone's `CLAUDE.md` and `PROVENANCE.md` still say "pattern only, copy nothing" until ADR 0001 records the BUSL grant. Every row below needs a `PROVENANCE.md` entry in its PR.

### Traps

- **Phase ordering hides two prerequisites.** Roadmap §6 says Phase 6 needs Phase 2 and 2.7; the MCP surface also needs API keys (5.2, not a stated dependency, and skipped by the first-release cut) and its funnel is imported by 6.1's tool core. Both are called out above; neither is optional.
- **Fail-closed defaults bite small workspaces.** With no `Agent` model, `resolveApprovalRequirement` classifies every MCP proposal as `UNREGISTERED_MACHINE_PRINCIPAL` → `SECOND_APPROVER` → two distinct approvers. A one-person workspace cannot approve an MCP proposal until 6.3 binds keys to agents (whose card can say `SINGLE_APPROVER`, ADR 0003 §8's default). Decide before 6.2c ships whether that is acceptable or whether an integration key's proposals take one approver; do not silently loosen the term.
- **Stubs must not widen.** The registration-gate stub answers `no_binding`, which is the source's own "register switched off" path: authority is still principal ∧ key scopes, writes are still proposals, the audience and liveness checks still run. The breaker stub is the one fail-open term; say so in its header and close it in H6. Never stub `assertPermission`, the audience check or credential liveness.
- **`McpServer.registerTool` validates before the gate.** Using the high-level SDK API would put argument validation ahead of `authorizeToolCall`, breaking the source rule that a refusal is decided on raw arguments (the policy card's data rung reads them) and that nothing runs before the gate. Use `Server.setRequestHandler`.
- **`tools/list` is per invocation.** Never register tools statically in the factory and never mark list results `public` in the 2026-07-28 cache hints; a shared cache would serve one principal's catalogue to another.
- **Batch semantics change.** The source's per-message charging and its 60-message batch cap exist because it accepted batches. Refusing arrays changes behaviour; delete the batch tests rather than porting them, and record it in the implementation note.
- **Hard-coded lists that must move together.** `MCP_READ_TOOL_NAMES`/`MCP_PROPOSE_TOOL_NAMES` (pinned equal to the registries by `mcp-tools-use-shared-authz`), `MCP_TOOL_KEY_SCOPE` (pinned to each `resourceScope`; the scope must exist in 5.2's `VALID_SCOPES`), `MCP_TOOL_CORPUS` (6.1's provenance table; completeness test), `PROPOSAL_KINDS` and the proposal field list (`proposal-labels.ts`, closed and tested), `APPROVE_PERMISSION` (`proposal-approve-permission.ts`), `proposal-refusal-keys.ts`, `PROPOSE_RESULT_FIELDS`, the route-permission rules, `MACHINE_CALLER_PREFIXES`, the read-suite guardrail's expected-tool list. A new tool or kind touches all of them in one PR.
- **One-way strings.** `SIGNING_PURPOSE` and the token prefix can change freely only before production tokens exist (tokens live ≤ 15 minutes, so the risk is small); `SEED_PURPOSE_PREFIX` for sampling and the `deriveSubkey` material are one-way once a sample is drawn (1.5.md's `DERIVED_SUBKEY_KEY` rotation rule applies). `TOOL_PROVENANCE_BUILTIN` and every tool description are hashed into `McpToolManifestPin`: changing a description after launch re-pins (BASELINE) for new tenants and refuses for tenants that pinned the old text until re-approved (`context-tools.ts` says so in its comment). Write the final descriptions before the first deploy.
- **Generated types.** `tool-data-scope.ts` and `policy-card.ts` import `AgentDataAccessScope` from `@prisma/client`; `proposal-guard-state.ts` imports `AgentGuardVerdict` via 6.1's guard. Run `prisma generate` with those enums present before `tsc`, or the funnel's typecheck fails on an import, not on logic.
- **Circular imports that already exist and must be preserved, not "fixed".** `auth.ts` ↔ `authorize.ts` (`enforceMcpCapability`/`denyToolCall`), `registry.ts` ↔ `authorize.ts` (type), `mount-gated-tools.ts` → `authorize.ts`, `tool-visibility.ts` → `authorize.ts` (type), `tool-definitions.ts` → both registries; `loadable-tools.ts` and `tool-catalogue.ts` are deliberate leaves and must stay import-free (`tool-catalogue` is read client-side; `loadable-tools` must never import `authorize`).
- **Client bundle.** `ProposalDiffPanel` and the client page import `proposal-diff-status.ts`, `proposal-labels.ts`, `proposal-refusal-keys.ts` only; `proposal-diff.ts` uses `crypto` and must stay server-side (#3726). Islestone's 1.1 guard only checks env reachability; bring the node-builtins guard with it.
- **Env.** No new secrets: token signing derives from 1.5's key hierarchy. `MCP_SERVER_ENABLED` is the only new variable; `PIPELOCK_STRICT_MODE` is not ported. Remember `.env.example` and the client/server env split (no MCP module is client-reachable except `tool-catalogue.ts`, which imports nothing).
- **Edge.** `/api/mcp` must be a `MACHINE_CALLER_PREFIXES` entry (no cookie), and the edge must never decide whether a key is real; the handler does. An exchanged token must stay refused on `/api/t/**` (`getTenantCtx` recognises only the API-key prefix), or a token minted for one MCP tool becomes a REST credential.
- **Naming.** ADR 0006 reserves "workflow" for team states and "session" for agent sessions; the source's `WorkflowRun`, `proposedBySessionRef` and "MCP session" wording must be translated in comments and identifiers, and `PROVENANCE.md` records each rename.
