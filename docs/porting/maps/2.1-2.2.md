## Summary

- **What moves.** The task engine's behaviour, renamed to the ADR 0006 vocabulary. That covers: the per-scope key counter, the pure transition check with discriminated errors and display-name refusals, create/list/get/update/delete/restore, assign, the four bulk verbs, comments, watchers and their bell fan-out, the assignment email and bell, the due-date reminder (shared helper plus daily job), the activity feed read from the audit trail, the side-effect ordering, and the tenant-scoping fixes: unlink scoped to the owning item, child writes check the parent is in the tenant, members must be ACTIVE.
- **Side-effect order is not one order.** The state-change path (`setTaskStatus` and `bulkSetTaskStatus` through `applyTaskStatusPostWrite` / `afterTaskStatusCommit`, task.ts 973–1020) runs audit inside the transaction, then COMMIT, then automation, cache bump and watchers. `createTask` differs: `logEvent`, `emitAutomationEvent` and the assignment-email enqueue all run **inside** the transaction (task.ts 433–461, inside `runInTenantContext` opened at 387), and the due bell (469), the assignment bell (474) and the cache bump (476) run after it. `updateTask` and `assignTask` audit inside and run their bells after. The port keeps each path's order as it is and the tests pin each separately (see `work-item.ts` edits).
- **Second source.** Kaneo (MIT) is named by roadmap 2.1 for subtasks, dependencies and labels. It contributes ideas, not code: it models a sub-task as a relation row (`relationType: 'subtask'`) and has no cycle refusal, so ADR 0002's `parentId` and locked cycle check stand. What it does contribute is a project-access model (`workspace_member_access.projectAccess` + `workspace_member_project`) that informs the guest seam below. Record it in `PROVENANCE.md` as pattern only.
- **What is cut.** Everything compliance-shaped:
  - `controlId`, `findingId`, `Evidence.taskId`, `remediatedVulnerabilities`, `templateTaskId`, `retentionUntil`;
  - the `TaskType`/`TaskSeverity`/`TaskSource`/`TaskPhase`/`TaskLinkEntityType` enums;
  - polymorphic `TaskLink` targets, the type-relevance gate, source reconciliation (`task-source-reconcile.ts`), SLA by severity;
  - the four-eyes reviewer (`reviewerUserId`, `IN_REVIEW`, reviewer eligibility, `TASK_REVIEW_REQUESTED`);
  - the mandatory `resolution` text, checklists in JSON, `metadataJson`, the evidence tab/routes, `listTasksByControl`, the legacy `/api/tasks` route and the `Issue*` aliases.
- **What is missing and must be written fresh for 2.1:** `Team`; `Project` (with key prefix and prefix history); `ProjectKeySequence` (per project, not per tenant); `WorkItemType` rows; `WorkflowState` rows per team in five categories; fractional `sortKey`; sub-items through `parentId`; `WorkItemRelation` (BLOCKS/RELATES/DUPLICATES) with cycle refusal under an advisory lock, plus a property test; `Label`/`WorkItemLabel`; `WorkItemLink` (URL/PR/commit/page/canvas).
- **What is missing for 2.2:**
  - the `version` column with `If-Match` and 409;
  - subtree soft delete with `deletionId`, and a purge job (ADR 0002 §8);
  - comment edit/delete;
  - explicit `deletedAt` and project-visibility filtering at every read and write site (no extension; the full list is under "Explicit predicates");
  - moves (reorder, re-parent, change project, change team) per ADR 0002 §2 and §10, and routes for move, key lookup and sub-item listing;
  - a project-visibility seam that keeps guests to their projects (H2), failing closed until 8.4 adds project grants;
  - audit rows and audited refusals for watcher add/remove, which the source writes neither of.
- **Cross-map ownership.** 1.6's map ports `notifications/assignment.ts`, `watcher.ts`, `inserted-ids.ts`, `notification-bus.ts` and the `WORK_ITEM_ASSIGNED` / `WORK_ITEM_WATCH_UPDATE` enum values, and defers `task-due.ts`, the due job and `NOTIFICATIONS_TZ` to 2.7. This map's scope names the due job and `task-due.ts`, so it keeps them in 2.2; whichever lands first owns them, and 1.6's 2.7 deferral then lapses. 1.3's map sends `query-shape-guardrails` to 2.2, and keeps `soft-delete.ts` out of 1.3 ("belongs to 2.1"); this map does not port the extension at all.
- **Size.**
  - In scope at source: about 6,140 lines (16 modules plus 19 routes).
  - Carried forward after edits: about 3,900 lines.
  - Cut: about 2,800 lines.
  - New non-test code for the missing 2.1/2.2 pieces: roughly 3,600 lines (with moves, the visibility seam and the purge job). Fresh migration SQL: about 650 lines.
- **Licence record.** ADR 0001 is Accepted (owner decisions, 2026-11-18). D1 allows copying from inflect-compliance, and every copied file gets a `PROVENANCE.md` row (source path, commit, BUSL-1.1, changes). The copy rule adds no per-file header, and `NOTICE` takes no inflect-compliance entry. D2 makes Islestone BUSL-1.1 itself, and `package.json` says `BUSL-1.1`. ## Prisma models and migrations

**Write a fresh migration.** Islestone starts with an empty migration history (no `prisma/` exists). The source's task tables were built by about 20 migrations, through a type unification (`20260310191803_unified_task_model`), an enum rename pinned with `@@map`, a control-task stack removal and a composite-FK retrofit. Replaying them would import compliance columns only to drop them, and every one names a model Islestone does not have. One migration `prisma/migrations/<ts>_work_core/migration.sql` creates 2.1's tables; 2.2's additions (`version`, `deletionId`, `Comment.editedAt`/`deletedAt`, notification enum values) can be a second migration, or folded into the first if 2.1 and 2.2 merge before any deploy.

**Models (2.1).** The field lists are ADR 0002 §12; this map adds what the port needs.

- `Team`: `id`, `tenantId`, `name`, `createdAt`, `updatedAt`, `deletedAt?`. `@@unique([id, tenantId])`, `@@unique([tenantId, name])`.
- `Project`: `id`, `tenantId`, `teamId`, `name`, `keyPrefix`, `version`, `archivedAt?`, `deletedAt?`, `deletedByUserId?`. `@@unique([id, tenantId])`, `@@unique([id, teamId, tenantId])`, `@@index([tenantId, teamId])`. No `initiativeId` until 3.2.
- `ProjectKeyPrefix`: `@@id([tenantId, prefix])`, `@@index([tenantId, projectId])`, `retiredAt?`.
- `ProjectKeySequence`: `projectId @id`, `tenantId`, `lastValue`, `@@index([tenantId])`. FK `(projectId, tenantId) → Project(id, tenantId)`.
- `WorkItemType`: `name`, `icon?`, `color?`, `position` (fractional, `COLLATE "C"`), `archivedAt?` (ADR 0002 §1 lists name, icon, colour, position, archived; the §12 sketch omits icon and colour). `@@unique([tenantId, name])`, `@@unique([id, tenantId])`.
- `WorkflowState`:
  - `teamId`, `name`, `category WorkflowStateCategory`, `position`, `isDefault`, `archivedAt?`;
  - `@@unique([tenantId, teamId, name])`, `@@unique([id, teamId, category, tenantId])`, `@@index([tenantId, teamId, position])`;
  - partial unique `(tenantId, teamId) WHERE "isDefault"` in SQL.
- `WorkItem`: the ADR 0002 sketch minus `cycleId`, `milestoneId` (2.5), `delegateAgentId` (6.3) and `estimate` (optional; keep if 3.x wants it).
  - Columns: `teamId`, `projectId`, `number`, `typeId`, `title`, `description?` (encrypted), `stateId`, `stateCategory`, `priority`, `assigneeId?`, `creatorId`, `parentId?`, `sortKey`, `startDate?`/`dueDate?` (`@db.Date`), `startedAt?`/`completedAt?`/`cancelledAt?`, `version`, `createdAt`, `updatedAt`, `deletedAt?`, `deletedByUserId?`, `deletionId?`.
  - Uniques: `@@unique([tenantId, projectId, number])`, `@@unique([id, tenantId])`, `@@unique([id, projectId, tenantId])`.
  - Indexes, ADR §13 rows whose columns exist in 2.1:
    - `[tenantId, projectId, sortKey, id]`
    - `[tenantId, projectId, stateId, sortKey]`
    - `[tenantId, teamId, stateCategory, sortKey]`
    - `[tenantId, assigneeId, stateCategory, dueDate]`
    - `[tenantId, parentId, sortKey]`
    - `[tenantId, creatorId, createdAt]`
    - `[tenantId, projectId, updatedAt, id]`
    - `[tenantId, stateCategory, dueDate]`
    - `[tenantId, typeId]`
    - `[deletedAt]`, the one non-tenant-leading index, for the purge sweep.
  - **Foreign-key indexes ADR 0002 §13 requires** ("every foreign-key column is indexed, alone or as the second column after `tenantId`") that the list indexes above do not provide:
    - `[tenantId, stateId]`: `stateId` is only third in `[tenantId, projectId, stateId, sortKey]`, and deleting or merging a workflow state must find its items by state across projects (and the `RESTRICT` FK check scans by it);
    - `[tenantId, deletedByUserId]`, if `deletedByUserId` is a foreign key to `User`. Alternative: keep it a plain column with no FK (it is an actor stamp, like an audit row's user id) and record that choice in the schema comment; then no index is needed.
  - `teamId`, `projectId`, `assigneeId`, `creatorId`, `parentId` and `typeId` are already second after `tenantId` in a list index above.
- `WorkItemKeyAlias`: `@@id([tenantId, projectId, number])`, `@@index([tenantId, workItemId])`.
- `WorkItemRelation`:
  - `type WorkItemRelationType`, `fromId`, `toId`, `createdByUserId`;
  - **column order differs from the ADR 0002 §12 sketch**, which declares `@@unique([tenantId, type, fromId, toId])` and `@@index([tenantId, type, toId])`. There `fromId` and `toId` sit third, behind `type`, so neither FK is indexed under §13's own rule, and the `ON DELETE CASCADE` from `WorkItem` (and the purge) would scan. Use `@@unique([tenantId, fromId, type, toId])` and `@@index([tenantId, toId, type])`: the same uniqueness, the same "blocked by" read (`toId` + `type`), and both FKs second after `tenantId`. The sketch is marked "illustrative, not final", so this is a refinement within the ADR, but name it in the 2.1 PR;
  - `@@index([tenantId, createdByUserId])`.
- `Label`: `teamId?`, `name`, `color?`, `deletionStartedAt?` (Kaneo's "being deleted" rule). `@@unique([id, tenantId])`, `@@index([tenantId, teamId])`.
- `WorkItemLabel`: `@@id([workItemId, labelId])`, `@@index([tenantId, labelId, workItemId])`.
- `Comment`: `workItemId`, `authorUserId`, `body` (encrypted, sanitised), `editedAt?`, `deletedAt?`, `createdAt`. `@@index([tenantId, workItemId, createdAt])`, `@@index([tenantId, authorUserId])`.
- `WorkItemWatcher`: `@@id([workItemId, userId])`, `@@index([tenantId, userId])`, plus `@@index([tenantId, workItemId])` for the fan-out read.
- `WorkItemLink`: `kind String`, `target String`, `title?`, `createdByUserId`, `createdAt`. `@@index([tenantId, workItemId])`, `@@index([tenantId, createdByUserId])`.
- No `FK_INDEX_EXEMPT` entries: §13 leaves no room for one. The source exempts the equivalent actor columns (`Task.createdByUserId`, `TaskComment.createdByUserId`, `TaskWatcher.userId`; `schema-index-coverage.test.ts` 180–183); Islestone indexes them instead.

**`ON DELETE` behaviour.** `WorkItem(projectId, teamId, tenantId) → Project` is `CASCADE` (only the purge job hard-deletes a project, and it deletes the items in batches first); `WorkItem → WorkflowState` and `WorkItem → WorkItemType` are `RESTRICT` (ADR 0002 §3); children of `WorkItem` (`WorkItemRelation` both ends, `WorkItemLabel`, `Comment`, `WorkItemWatcher`, `WorkItemLink`, `WorkItemKeyAlias`) are `CASCADE`; the parent link is `ON DELETE NO ACTION` with `DEFERRABLE INITIALLY DEFERRED` (Postgres refuses to defer a `RESTRICT` check, so it must be `NO ACTION`; the purge deletes a whole subtree in one transaction, which the deferred check allows); `WorkItem.assigneeId → TenantMembership` is `RESTRICT` (ADR 0003 §1).

**Enums.** `WorkflowStateCategory`, `WorkItemPriority`, `WorkItemRelationType`, all in `enums.prisma` with no `@@map`. 1.6's `NotificationType` gains `WORK_ITEM_DUE`, `WORK_ITEM_ASSIGNED`, `WORK_ITEM_WATCH_UPDATE`; `EmailNotificationType` gains `WORK_ITEM_ASSIGNED`.

**Composite FKs.** Every child references `(xId, tenantId) → Parent(id, tenantId)`. **Known traps:**

1. **Licence and process.** See the licence record in the summary. Islestone is BUSL-1.1 itself (ADR 0001 D2), so a copied file is under the same licence as its new home; what remains is the `PROVENANCE.md` row per copied file (source path, commit `5528464f…`, licence, changes) and the Kaneo row moved to Adopted (pattern only). Copied files carry no header line: ADR 0001's copy rule keeps the notices the copied material already carries and adds none (the source files carry no per-file header).
2. **Hard deletes in disguise, and reads that silently see deleted rows.** `deleteTask` calls `db.task.delete` (task.ts line 746) and `bulkDeleteTask` calls `db.task.deleteMany` (line 694). Both are soft deletes only because `src/lib/soft-delete.ts` rewrites them for models in `SOFT_DELETE_MODELS`. Ported without that extension, they become **hard deletes**, cascading comments, links and watchers. Write explicit `updateMany` soft deletes. Add a test that a delete leaves the row with `deletedAt` set. The same extension also filters every `Task` read (`findFirst`, `findMany`, `count`, `groupBy`, …), so without it every read site that does not say `deletedAt: null` returns deleted items: `getById`'s top-level read (561), the metrics (761–765), `listByIds` before the bulk writes (806), `assertTaskInTenant` (task.ts 147, which gates comment, watcher and link writes), and the watcher fan-out (1549). "Explicit predicates" lists every site; the repository test asserts each. Add a guard that `WorkItem` is never added to an extension model list, so the two mechanisms never stack.
3. **Nested soft-delete reads.** Prisma relation reads and `_count` ignore `deletedAt` (source `TaskRepository.ts` 597–605, #5305). Every nested read of sub-items, relations and comments filters `deletedAt: null` explicitly.
4. **Encrypted text leaking into the audit log.** `updateTask` logs `metadata: patch` (task.ts line 613), which carries the plaintext `description` into an audit row that streams to a SIEM in the source. ADR 0002 §11 requires "changed, not its text". Log field names only.
5. **Cursor shape.** The source cursor is `(createdAt, id)` desc; the list orders by `sortKey`. Reusing `buildCursorWhere` with a `sortKey` orderBy silently skips or repeats rows across pages.
6. **Date-only due dates.** `daysUntilDue` passes `dueAt` through `Intl` in `NOTIFICATIONS_TZ`. A `@db.Date` reads back as UTC midnight, which in any zone west of UTC formats as the *previous* day. That shifts every window by one and breaks the "overdue" filter. Compute the due day from the UTC date parts; convert only "now" to the zone.
7. **Job and RLS.** The source job reads every tenant through the global client (owner role, `superuser_bypass`) and writes `Notification` rows with no tenant context. No RLS applies and there is no auto-audit (source `docs/implementation-notes/2026-08-21-job-rls-tenant-context.md`). In Islestone, loop tenants and scan each inside the tenant context, or the job reads zero rows when the worker connects as `app_user`. The per-tenant loop also lets `[tenantId, stateCategory, dueDate]` serve the scan; the source's system-wide predicate has no `tenantId`. The scan is paged (`take: 500`, keyset on `(dueDate, id)`) with one write and one read-back per page, not per item (manifest row). The purge job is the one place a cross-tenant read is right (the `[deletedAt]` index), and it does that read only under `runWithoutRls` with a logged reason, then deletes inside each tenant's context.
8. **Relation direction.** `BLOCKED_BY` in the source is stored on the blocked side. Importers (5.5) and any copied test fixtures must invert it to `BLOCKS from=blocker`.
9. **Hard-coded model lists** that must change in the same PR as the models:
   - `SOFT_DELETE_MODELS` (`src/lib/soft-delete.ts`) and `SOFT_DELETE_TARGETS` (`src/lib/security/classification.ts` 243);
   - `ENCRYPTED_FIELDS` (`encrypted-fields.ts` 292–296);
   - `TENANT_SCOPED_MODELS` (1.3's `rls-middleware.ts`), which the RLS coverage test reads;
   - `RESET_TABLES` (`tests/helpers/db.ts` 1120);
   - `RICH_TEXT_COVERAGE`, `LIST_QUERY_INDEXES`, `LIST_MODELS_TENANT_INDEX_SUFFICIENT`, the forward-lock list, the `schema-index-coverage` parser self-tests (source 1226–1243 name `Task` and `TaskLink` and expect more than 80 models);
   - `tenant-crud-authz-coverage`'s route spec table and `list-filter-enum-cast`'s expected-sites list;
   - the retention inventory;
   - `route-permissions.ts` rules;
   - `CacheableEntity` (`list-cache.ts` 70) and `AggregationEntity`/`AGGREGATIONS['tasks-metrics']` (`aggregation-registry.ts` 35, 88–92), if the cache is ever ported;
   - `AssignmentNotificationKind`;
   - `NotificationType`/`EmailNotificationType`;
   - `JobPayloadMap`/retry options in `jobs/types.ts`;
   - `restore-validators.ts`, if anyone ports it.
10. **Editing another sub-phase's schema file.** Prisma needs both sides of every relation, so 2.1 must add relation fields to `Tenant`, `User` and `TenantMembership` in 1.3's `auth.prisma`. Use named relations from the start (`"WorkItemAssignee"`, `"WorkItemCreator"`, `"CommentAuthor"`) to avoid ambiguity errors.
11. **SQL Prisma cannot express.** Collation, DEFERRABLE, CHECKs, partial uniques. `prisma migrate dev` will not reproduce them and may propose dropping a partial index it does not know. Gate with a fresh-DB drift check and an expected-residue file, as the source does, plus catalogue tests.
12. **Enum values and rollouts.** Adding `WORK_ITEM_*` to 1.6's `NotificationType` after 1.6 has shipped is an `ALTER TYPE … ADD VALUE`. Before launch it is harmless. After any production deploy it is the two-deploy change ADR 0002 §3 describes: readers first, writer second. Prefer 1.6 reserving the values.
13. **Composite FKs need composite uniques on the target.** Prisma refuses a relation whose `references` is not unique. Declare `@@unique([id, teamId, tenantId])` on Project and `@@unique([id, teamId, category, tenantId])` on WorkflowState before the WorkItem relations. Moving an item between teams must write `teamId`, `stateId` and `stateCategory` in one UPDATE.
14. **Lock order.** Take `lockWorkItemGraph` FIRST in the transaction, before any row read or lock, or a relation write and a re-parent can deadlock. Large imports must batch graph writes, because the lock serialises the workspace.
15. **Generated-type churn.** Any Phase 1 port that quietly kept a `Task` reference stops compiling once `TaskStatus` and friends are gone: a copied `deadline-monitor.ts`, the dashboard repository, `work-tools.ts`. Grep the Islestone tree for `Task`/`task.` before step 1. ADR 0006's banned-identifier rule should land with this sub-phase.
16. **Circular imports.**
    - `task.ts` re-exports from `task-checklist.ts`, which imports `TaskRepository`; that cycle goes with the checklist.
    - Keep the due helper in `notifications/`, never `jobs/`: the usecase and the job both import it, and a usecase importing `jobs/` drags the job graph into the request path (source rationale in `task-due.ts` lines 11–17).
    - The automation stub must not import `jobs/`.
    - `domain/workflow-state.ts` must stay free of `@/lib/errors/types`, which imports `@/env`, so a client component can import it (Islestone's `client-env-boundary` guard).
17. **`errors/types` pulls `@/env`.** Any script or seeder that imports a usecase validates the whole server env (source `task-checklist.ts` 39–44). Keep seeders on repositories plus pure modules.
18. **`ctx.tenantSlug` optional.** Every bell helper returns early when `ctx.tenantSlug` is unset: `if (!ctx.tenantSlug) return` in `emitTaskDueNotification`, `emitTaskAssignedNotifications` and `emitTaskWatcherActivityBatch`. A context builder that omits it silences all notifications with no error. Assert it in the two-tenant test.
19. **Scale.** The source live list reads up to 5,000 rows uncursored. H2 seeds 100,000 items per tenant. Cursor-only from day one, and the Deleted view keeps its cap.
20. **Key search.** The source `q` matches `key contains`, a stored string. Islestone stores a number. Parse `ISL-123` (current prefix, prefix history, alias) for an exact hit, and keep title search separate; full-text is 2.7.
21. **Branding.** The email template's "Inflect Compliance" sign-off (`templates.ts` 44, 55, 95, 106: text and HTML of both the single and the digest mail), its "View Tasks" button (54, 105) and every `/tasks` link must not survive. A page or mail carrying the parent product's name is both a vocabulary breach and a brand problem. (The same sign-off recurs at 139, 149, 182 and 193 in builders this map does not take.)
22. **Optimistic concurrency.** The source `update`/`setStatus`/`assign` repositories read and then `update({ where: { id } })`, which is last-writer-wins. The version check must be the WHERE of one `updateMany`, with `count === 0` re-read to tell a 404 from a 409. A read-then-update leaves a race. `sortKey` writes do not bump `version` (ADR 0002 §5).
23. **Vocabulary leaks in prose.** Comments, refusal messages and audit `details` strings in the copied files say "task" and name TP-2, SOC 2, auditors, controls and findings throughout. ADR 0006 rule 4 ("prose follows code") makes each one a defect. The manifest rows name the lines found (list-filter.ts, list-backfill-cap.ts, the job, `watcher.ts`, `assignment.ts`, the policies, `TaskRepository.ts` 43 and 49–50, `schemas/index.ts`, the route comments); sweep every copied file again before review, with a grep for `task|Task|control|risk|asset|vendor|finding|audit|SOC|NIS2|TP-` over the copied set.
24. **Tests in a directory no project runs.** Islestone's Jest matches only `tests/unit`, `tests/guards` and `tests/rendered` (plus `tests/integration` once 1.3 adds it). A source `tests/guardrails/*.test.ts` copied to the same path is silently never run. Use the destinations in "Tests to bring".
25. **Copied guards that pass by checking nothing.** A guard whose population comes from `fs.readdirSync` over a path that does not exist yet in Islestone (or whose skip list misses a new directory) passes with zero files. Every guard this map brings takes `gitFiles()` and has a planted failing fixture.
26. **Type-only imports.** Islestone lint has `consistent-type-imports` at error. Source files import types as values in places (`task.policies.ts` line 1 `import { RequestContext }`, `db-context.ts` line 1 per 1.3's map). Each becomes `import type` on the way in.
27. **A deferrable FK cannot be `RESTRICT`.** Postgres only defers `NO ACTION` checks. The parent link must be `NO ACTION DEFERRABLE INITIALLY DEFERRED`; Prisma's `onDelete: Restrict` would silently make the subtree move fail mid-transaction.
28. **Watchers and other "personal" writes are still mutations.** The source treats watch/unwatch as a subscription and audits nothing; the route admits on the view key and refuses inside the usecase, so a refusal leaves no `AUTHZ_DENIED` row. The roadmap 4 preamble ("every mutation … audited with `logEvent`") and the route split in the manifest close both.
29. **Project visibility is a predicate, not a check.** A guest test that only calls `GET /work-items/:id` passes while the list, metrics, activity, relations and sub-item reads still leak. The H2 matrix test must call every route, and the repository test asserts the visibility fragment on every `WorkItem` read (source warning: `task.policies.ts` 70–77).
30. **Cross-map ownership drift.** 1.6 brings `assignment.ts`, `watcher.ts` and their unit tests, and defers the due reminders to 2.7; 1.3 defers `query-shape-guardrails` to 2.2. Before copying a file named here, check whether the owning sub-phase already copied it, and edit rather than overwrite.
