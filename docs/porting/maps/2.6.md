## Summary

- **Nothing large is copied.** inflect-compliance has no intake, no form builder and no inbound email. What it has, and what 2.6 takes, is the discipline of its two anonymous surfaces: the Trust Center's gated-document request (`src/lib/trust-center/gated.ts`, `src/app/api/trust/[slug]/access-request/route.ts`) and the external vendor-assessment respondent (`src/app-layer/usecases/vendor-assessment-response.ts`, `src/app/api/vendor-assessment/**`): a missing or disabled target answers exactly like an unknown one; the response is uniform so the endpoint is no oracle; a rule the page shows is enforced on the server, never trusted from the body; a visitor-supplied email is never proof of anything; the anonymous context holds no authority rather than a forged one; free-text answers are sanitised per answer type; and the edge rate-limits each anonymous path, under its own bucket, before the public-path allowlist lets it through (inflect `src/middleware.ts` blocks 0–0d, `docs/rate-limiting.md` "Anonymous edge surfaces"). Its react-hook-form usage (`useForm` + `zodResolver` with a schema built from the server's bounds, `src/app/t/[tenantSlug]/(app)/incidents/NewIncidentModal.tsx`) is the client pattern. All pattern only; the code is written fresh.
- **An intake request is its own table, not a work item** (recommended; open question 1). ADR 0006 already names `IntakeRequest` and says accepting one makes a work item. Keeping requests out of `WorkItem` means spam never takes a key number (numbers are never reused), no list, board, search, burn-up, transition, notification, automation or agent read has to learn to exclude them, and outsiders' personal data and untrusted text stay out of the work table. Principle 3 is about tracked work; a request is not yet tracked work. Accept creates the work item and marks the request in one transaction.
- **Intake belongs to a project.** Each project may turn intake on. A request always names a project (the key comes from the project), and a triager may move it to another project before deciding. One page per project and one workspace-wide page list requests; both are called **Intake** (open question 7).
- **Three channels, in three pull requests** (open question 13): (a) **internal forms** for signed-in people, with the model, the Intake page and all four triage actions; (b) **public forms** at an unguessable link, anonymous, rate-limited and bot-checked (open questions 2 and 4); (c) **inbound email**, one address per project, after the owner chooses how mail reaches Islestone (open question 3, which is a sub-processor decision).
- **Forms** are built in Settings → Intake from a closed set of field kinds (short text, long text, select, multi-select, date, number, URL, checkbox), each optionally mapped to one of the project's custom fields. The form definition is a validated, versioned JSON document; one client-safe function compiles it into the Zod schema that both react-hook-form (in the browser) and the route (on the server) use, so they cannot disagree.
- **Triage** (open question 6): **accept** (creates the item in a backlog or unstarted state, fields prefilled and editable), **decline** with a reason (spam is a reason, and can block the sender), **merge** into an existing work item or another pending request, **snooze** until a date (a daily job wakes it). Decided requests are purged after a retention window (recommended 90 days, spam 7).
- **The requester** sees an on-screen confirmation. Email updates go only to an address the requester confirmed by a link, or to an email sender whose domain authentication passed; they never repeat the text the requester typed (open question 5).
- **Permissions** (open question 8): a new `intake` domain (`view`, `triage`, `manage`) is recommended, because a request holds an outsider's personal data and triage is a gate, not an edit. Accepting also needs `work_items.create` in the target project.
- **Size.** About 7,000 lines of source and 4,000 of tests across the three pull requests; more than the roadmap's M.

What the migrations add beyond Prisma's DDL, each with a catalogue test:

- CHECKs: an `ACCEPTED` row has `workItemId` set at the moment of the decision (a column-scoped `SET NULL` later, when the item is purged, is allowed: the CHECK reads `status <> 'ACCEPTED' OR decidedAt IS NOT NULL`); a `MERGED` row has exactly one of `mergedIntoWorkItemId`, `mergedIntoRequestId`; `mergedIntoRequestId <> id`; `SNOOZED` has `snoozedUntil`; `DECLINED` has `declineReason`; `INTERNAL_FORM` has `requesterUserId`; `PUBLIC_FORM` has `formId` at insert; `dailyCap` between 1 and 5000.
- A merge target may not itself be merged (no chains), held in the usecase under a row lock on the target, as ADR 0002 §6 holds duplicates.
- `app_user` gets SELECT, INSERT, UPDATE on every new table, and DELETE on `IntakeRequest`, `IntakeFollowUp`, `IntakeResponder`, `IntakeBlockedSender` (the purge and the settings need it); `IntakeForm` is archived, never deleted.
- Every table: `tenantId`, a tenant-leading index, the four RLS policies, its grant, and a two-tenant test in `ISOLATION_TESTED`. The two global uniques (`IntakeForm.publicId`, `ProjectIntake.emailToken`) are the only lookups made before a tenant is known (see "Tenant resolution").

**Encryption** (open question 12): `body`, `answersJson`, `declineNote`, `internalNote` and `IntakeFollowUp.body` go in the manifest (`src/lib/security/encrypted-fields.ts`, workspace DEK) and are sanitised (`tests/guards/sanitize-rich-text-coverage.test.ts` classifies them). `requesterName` and `requesterEmail` go in `PII_FIELD_MAP` with `hash: 'requesterEmailHash'`, and `IntakeRequest` joins `PII_TENANT_SCOPED_MODELS` so the master-key rotation reaches it (`tests/guards/pii-rotation-coverage.test.ts`). `title` stays plaintext (it is shown in lists and becomes a work item title, which is plaintext under ADR 0002 S1). `definitionJson` is not encrypted: it is the workspace's own published text, shown to anyone with the link.

## Tenant resolution and the public surface

### Routes outside the workspace path

A public form must not carry the workspace slug or the project key, and the edge's membership gate (`/t/<slug>/**`) must not apply to it. So:

| Path | What | Edge |
|---|---|---|
| `/f/<publicId>` | The public form page (server-rendered) | `PUBLIC_PATH_PREFIXES` gains `/f/`; the edge rate-limits GET at `intakeform:<publicId>` (IP + form) before the allowlist returns, as inflect does for `/trust/<slug>` |
| `/f/confirm/<token>` | The requester's "confirm my address" page: a button that POSTs, never a GET that confirms (mail scanners follow GET links) | Same prefix and limit (`intakeconfirm`) |
| `POST /api/intake/forms/<publicId>` | The public submit | `MACHINE_CALLER_PREFIXES` gains `/api/intake/forms`, with a contract in `tests/guards/machine-caller-paths-self-authenticate.test.ts`: POST's gate is `acceptPublicIntakeRequest(` (signed form token, bot check, size cap, handler limits); no other method is exported |
| `POST /api/intake/confirm` | The confirmation POST | Same, contract `confirmRequesterAddress(` |
| `POST /api/intake/email/<provider>` | 2.6c: the inbound email webhook | `MACHINE_CALLER_PREFIXES` gains `/api/intake/email`, contract: the provider signature verifier |
| `/api/t/<slug>/intake/**`, `/api/t/<slug>/projects/<id>/intake/**` | Everything signed in: internal submit, triage, forms, settings | The ordinary tenant gate, read tier, `requirePermission` |

The machine-caller list is path-scoped, not method-scoped, so each public route file exports POST only, and its contract names that one method (a GET added later fails the guard).

### Tenant resolution without disclosure

`resolvePublicIntakeForm(publicId)` reads one narrow row (`id`, `tenantId`, `projectId`, `access`, `publishedAt`, `archivedAt`, `definitionJson`, `definitionVersion`, `dailyCap`, the project's archived and deleted flags, the workspace's deleted flag) through `runWithoutRls({ reason: 'public-intake-resolve' })`, a new `RlsBypassReason` added after review, logged like every bypass. Everything after that runs in `runInTenantContext` for the resolved workspace. It returns null, and the route answers one identical 404 (same body, same headers, no timing branch worth measuring: the lookup is one indexed read either way), for: an unknown id, `access = MEMBERS`, an unpublished or archived form, an archived or deleted project, a project with intake off, a soft-deleted workspace, and a deployment with public forms switched off (open question 2). The email webhook resolves its address the same way under the existing `webhook-ingest` reason.

The public page renders only the form's own published text (its name, intro, fields and confirmation text). It never shows the workspace name, the project name or key, or any member, unless the form's author typed them into the form. The page is outside the app shell and loads only the `intake.publicForm.*` messages into the client provider, not the whole catalogue. A guard in the style of inflect's trust-center coverage holds that the public modules (`src/lib/intake/public/**`, the `/f/` pages and the two public routes) import no repository or usecase beyond the resolver and the one accept function.

Public forms never read the browser's session: a signed-in member who opens a public link is treated as anyone else, so no session crosses into a workspace the link resolves to.

### Bot defence, caps and request hygiene

Layered, all in-house (recommended; open question 4):

1. **Signed form token.** The page embeds a token: `HMAC(deriveSubkey('intake-form-token'), publicId | definitionVersion | issuedAt | nonce)`. The submit refuses a token older than 24 hours or younger than 3 seconds (a person does not finish a form in under three seconds), and spends its nonce once in Redis (`SET NX` with a 24-hour expiry), so a captured token cannot be replayed.
2. **A hidden trap field** a person never sees or fills (labelled for screen readers as "leave empty", `tabindex=-1`, `autocomplete=off`). A filled trap answers the same success screen and stores nothing.
3. **A small proof-of-work** the browser solves while the person types (an HMAC-signed challenge in the page, a SHA-256 puzzle of about a second on a phone), written in-house; no script from another host, so the Content-Security-Policy is unchanged.
4. **Rate limits.** Edge: `intakeform:<publicId>`, IP + form, every method, the read tier's 120/min. Handler (`withApiErrorHandling` with its own preset `INTAKE_PUBLIC_SUBMIT_LIMIT`): 5 per minute and 30 per hour per IP and form. Per form per day: `dailyCap` (default 200), counted from `IntakeRequest` rows in the database through `[tenantId, formId, createdAt]`, because production runs `RATE_LIMIT_MODE=memory` (decision 50) and a deploy resets the in-memory counters. Per workspace per day: 2,000 public requests across forms. Past a cap the form answers 429 with a person-readable "This form is not taking requests right now".
5. **Size caps.** The JSON body is refused above 64 KB (413, read through a capped reader, not `req.json()`, because `req.json()` has already allocated the whole body when its length could be checked); title 200 characters, body 10,000, each answer 2,000, at most 30 fields, at most 20 values in a multi-select.
6. **Cross-site posting.** The submit requires `Content-Type: application/json` (a cross-origin `fetch` with it needs a CORS preflight, which `src/lib/security/cors.ts` refuses for an unlisted origin) and refuses `Sec-Fetch-Site: cross-site` when the header is present (the `admin-session-guard` check). There is no session to ride, so classic CSRF does not apply; the check stops other sites from spending the form's budget. The internal submit and every triage route are ordinary session routes.
7. **Content.** Every text value goes through `sanitizePlainText` before it is stored (encrypted values too). A title with control or bidirectional-override characters has them removed. Text is never rendered as HTML anywhere: the Intake page renders it as React text.
8. **Embedding.** `frame-ancestors 'none'` stays: a public form is a link, not an embed (open question 2).

### What the requester sees and is told

Recommended (open question 5): after sending, an on-screen confirmation with a short reference (the request id's last eight characters) and the form's confirmation text. If the form asks for an email and the requester ticks "Email me about this request", Islestone sends **one** email asking them to confirm the address; updates are sent only after they press the button on the confirmation page, and at most one confirmation email per address per form per day. After confirmation: "accepted", "declined" (with the reason and note the triager chose to send) and "being handled together with an existing request" (merged). Snoozing sends nothing. No email repeats the title or body the requester typed (otherwise anyone could make the workspace's sender deliver their text to a stranger); emails name the form and the reference only. Emails go through `enqueueEmail` (an outbox row inside the deciding transaction), from the workspace's sender, with `appLink`-free text (an outsider cannot open the app), and the outbox dedupe key carries `hashForLookup` of the address. No status page in 2.6.

## Inbound email (2.6c)

Built after open question 3 is answered. The design below is provider-neutral; only the adapter changes.

- **Address format.** `<token>@in.islestone.cloud`: a 12-character random token from an unambiguous alphabet, one per project, shown in Settings → Intake with a copy button and a "Generate a new address" action (the old one stops working; audited). A subdomain keeps the apex domain's mail, if it ever has any, untouched. The token, not the workspace slug or project key, so an address cannot be guessed from a key in a URL. Replies use `<token>+r<replyToken>@in.islestone.cloud`, a per-request token, so a requester's reply lands on its request without trusting `In-Reply-To` headers.
- **Receiving.** Recommended (open question 3, A): a hosted inbound service posts each received email to `POST /api/intake/email/<provider>` as a signed web request. The handler verifies the provider's signature over the raw body and a timestamp (refused outside a five-minute window), refuses a body over 2 MB (413), dedupes on the provider's event id and on `sha256(Message-ID)` (a repeat answers 200 and writes nothing, so a provider retry never makes a second request), resolves the address token, and parses and stores in the same request; an unknown or disabled address answers 200 and stores nothing (the provider learns nothing it did not already know; the sender learns nothing at all).
- **Sender authentication.** The service's verdict (or Islestone's own check, if the receiver is self-hosted) on SPF, DKIM and DMARC alignment becomes `senderCheck`. `FAIL` is treated as spam: stored as `DECLINED`/`SPAM` without a notice, visible under the Spam filter for the retention window. `NONE` is stored as pending but never acknowledged by email. An email from an address matching a member's `emailHash` with `PASS` is attributed to that member (`requesterUserId`); otherwise the requester is external.
- **Parsing.** Prefer the `text/plain` part; otherwise turn HTML into text (block tags to newlines) and `sanitizePlainText`. Strip quoted history (lines after "On … wrote:" and `>`-quoted blocks; heuristic, tested on fixtures from the common clients). Subject → title (decoded, CR and LF removed, 200 characters), text → body (10,000). Attachments are counted in `attachmentsDropped` and never stored until 4.4 brings scanned storage.
- **Spam and abuse.** Per address: 30 emails per hour and 300 per day; per sender hash per address: 10 per hour; past the limit, emails are counted and dropped. Blocked senders (by address hash, per project or workspace) are dropped. Auto-replies and bounces (`Auto-Submitted`, `Precedence: bulk/auto_reply`, a null return path) are dropped and never answered, which also prevents a loop with another system's auto-responder.
- **Threading.** A reply to a pending or snoozed request adds an `IntakeFollowUp` and wakes a snoozed request. A reply to a decided request is dropped (one "this request is closed" answer per request at most, only to an authenticated sender). Email replies on work items are 5.4's ("reply-to-comment by email"), not 2.6's.
- **Personal data.** The sender's address and display name are personal data, encrypted in place by the PII extension with a lookup hash; no log line carries them (decision 34's rule, reused). The raw email is never stored.
- **Environment and deploy** (option A): `INTAKE_EMAIL_DOMAIN` (`in.islestone.cloud`), `INTAKE_EMAIL_PROVIDER` (the adapter name, or unset for off), `INTAKE_EMAIL_SIGNING_KEY` (a secret, required in production when the provider is set, refused twice like the other secrets), in `src/env.ts`, `.env.example`, `deploy/.env.prod.example` and the `app` service of `deploy/docker-compose.prod.yml` together (`tests/unit/deploy/compose-prod.test.ts`). An MX record for `in.islestone.cloud` pointing at the provider is an operator step in `docs/deployment.md`. Caddy already accepts the path (10 MB body limit). Option B (self-hosted receiver) instead needs a new service publishing port 25 on the shared VM, a firewall rule an operator adds, its own certificate and MX at the VM: a change to the delivery rules ("nothing publishes a port"), listed under the question.

## Triage

The Intake page (per project, and workspace-wide over the projects the person may triage) lists requests by status: New (pending), Snoozed, Spam, Decided. Every write is versioned (`If-Match`; 409 `VERSION_CONFLICT` with the current row), claims the request with a conditional `updateMany` on its status and version, and is audited.

| Action | What it does | Writes |
|---|---|---|
| **Accept** | Creates a work item in the request's project, or another the person may create items in, in the team's default state or a chosen Backlog or Unstarted state; title and body prefilled and editable; type, priority, assignee, labels and cycle optional; answers mapped to the project's custom fields fill them, the rest are appended to the description as "Field: value" lines. An internal requester becomes a watcher. | One transaction: claim the request, create the item through the create path (below), set `ACCEPTED`, `workItemId`, `decidedAt/By`, audit `INTAKE_REQUEST_ACCEPTED` and the item's `WORK_ITEM_CREATED` (with `intakeRequestId` and `channel` in its metadata), enqueue the requester's notice; after the commit, the create path's bells and the internal requester's bell. |
| **Decline** | Reason (Not planned, Out of scope, Spam, Other), an optional note to the requester, an optional internal note; "Spam" sends nothing and offers "Block this sender". | Claim, `DECLINED`, audit (reason code only), enqueue the notice unless spam. |
| **Merge** | Into a live work item the person can see (picked by key or title, the list query's `q`), or into another pending request in the same project. The merged request's text stays on its own record; the target shows "N requests merged" with links. A request merged into a request follows it: when the target is accepted, the merged requesters are told too. | Claim, `MERGED` with exactly one target, audit on both sides (`INTAKE_REQUEST_MERGED` on the request, and an entry the work item's Activity shows), enqueue the notice. |
| **Snooze** | Until a date: Tomorrow, Next week, or a picked date (date-only). | Claim, `SNOOZED`, `snoozedUntil`, `snoozedBy`, audit. |
| **Move** | To another project with intake on, where the person may triage. | Versioned update, audit. |
| **Reopen** | A declined, merged or snoozed request back to pending, while it is retained; refused for an accepted one (the item exists). | Versioned update, audit. |

Rules:

- **Accept reuses the create path.** `createWorkItem`'s body moves into an in-transaction function (`createWorkItemInTx(db, ctx, input)` returning the row and its after-commit effects), which `createWorkItem` and the accept usecase both call, so key claiming, the fractional order, custom-field validation, 2.4b's field sets when they land, audit, the automation event and the assignment email stay in one place, in their order (`tests/unit/usecases/work-item-sequence-order.test.ts` gains the accept path).
- **Two accepts of one request make one item:** the claim is the `WHERE status IN ('PENDING','SNOOZED') AND version = $v` of one `updateMany`, inside the transaction, before the item is created; the loser gets 409.
- **Merge into a work item never uses `WorkItemRelation`** (a request is not a work item); the link is the request's `mergedIntoWorkItemId`, and the item's side lists its merged requests through the index.
- **Decline and merge are sent from inside the undo toast** (the destructive-action convention, `tests/guards/undo-toast-coverage.test.ts` gains the sites), and Reopen covers a change of mind after the window.
- **Agents never triage** (principle 2, ADR 0003): 7.2 proposes duplicates, a project, labels and questions as proposals; accept, decline and merge stay a person's acts. Request text is untrusted input from outside the workspace: any later agent read of it goes through the injection guard as untrusted content (6.1, 7.2).

## Audit, automation and notifications

- **Audit** (`logEvent`, transaction client, structured `detailsJson`): `INTAKE_REQUEST_RECEIVED` (actor: the member, or the system user with `channel`), `_ACCEPTED`, `_DECLINED` (reason code), `_MERGED`, `_SNOOZED`, `_WOKEN`, `_MOVED`, `_REOPENED`, `_REQUESTER_CONFIRMED`, `INTAKE_REQUESTS_PURGED` (counts); `INTAKE_FORM_CREATED`, `_UPDATED`, `_PUBLISHED`, `_UNPUBLISHED`, `_ARCHIVED`; `PROJECT_INTAKE_UPDATED`; `INTAKE_ADDRESS_ROTATED`; `INTAKE_SENDER_BLOCKED`, `_UNBLOCKED`. Entries name ids, the channel and reason codes; never a title, body, answer, note, name or address, not even hashed.

- **Bells** (two new `NotificationType` values, each with a writer in `src/app-layer/notifications/` that asks `isInAppTypeEnabled` and dedupes): `INTAKE_REQUEST_RECEIVED` to the project's responders (one per request; open question 11), `INTAKE_REQUEST_WOKEN` to the person who snoozed it. - **Email** (new `EmailNotificationType` values and templates): `INTAKE_CONFIRM_ADDRESS`, `INTAKE_ACCEPTED`, `INTAKE_DECLINED`, `INTAKE_MERGED`, and in 2.6c `INTAKE_RECEIVED_ACK` for authenticated email senders. ## Ordering and risks

- **Three pull requests**, each usable alone (open question 13): **2.6a** the model, permission keys, ADR rows, internal forms, the builder, the Intake page with all triage actions, both jobs and the two new enum values (no writer of the values ships before the deploy that adds them is live); **2.6b** public forms (the public page and routes, bot defence, edge and handler limits, the requester's confirmation and notices, the abuse tests); **2.6c** inbound email, after open question 3.
- **New enum values on existing enums** (`NotificationType`, `EmailNotificationType`): a running container whose Prisma client predates a value fails any read that meets it (ADR 0002 §3, "Adding a category later is a two-deploy change"), and Watchtower updates the app and the worker separately. So every new value is added in 2.6a's migration (its own migration file), and a value is first written by a later release: the two bell types from 2.6a's follow-up commit once the migration is live (or from 2.6b if the owner prefers the strict two-deploy form), the outsider email types from 2.6b, the email acknowledgement from 2.6c.
- **`createWorkItem` refactor.** Moving its body into an in-transaction function touches the busiest usecase; the sequence-order test and the existing integration suite hold it, and the refactor is its own commit.
- **Public forms widen the attack surface** of a product with no anonymous write today. The deployment switch (open question 2) keeps them off in production until H2's abuse tests pass and the operator opens it, as public sign-up is (decision 7).
- **Inbound email** brings either a new sub-processor or a port on a shared VM (open question 3); it is last so the rest does not wait for that choice.
- **Duplicates before 7.2.** Without search (2.7) and embeddings (7.2), merge relies on the person finding the target by key or title.
- **Retention** is a purge job before 8.3's retention settings exist; 8.3 makes the windows a workspace setting if the owner wants that.

## Open questions for the owner

Each question says what is being decided, the options, and the recommendation. "Recommended" is what the map applies if the owner accepts all.

1. **Is an incoming request a work item from the start, or a separate record until someone accepts it?**
   - A. **A separate record** (an "intake request") until it is accepted; accepting creates the work item. Spam and rejected requests never take an item number, never appear in lists, boards, search, charts or notifications, and outsiders' personal details stay out of the work table. The vocabulary ADR already names this record. *Recommended.*
   - B. A work item in a special "intake" status from the moment it arrives (Linear's and Plane's way). One table, but every list, board, chart, search, notification, automation and agent must learn to leave those items out; spam uses up item numbers, which are never reused; it needs a sixth status category, which is a two-step change to the work-item ADR.
   - C. Both: a work item row plus an intake record beside it. The costs of B with the bookkeeping of A.

2. **Do anonymous public forms ship now, or only forms for signed-in people?**
   - A. **Both in 2.6, public forms as the second pull request.** A public form works only after an admin publishes it, at a long random link that reveals nothing about the workspace; and a deployment switch keeps public forms off in production until the operator turns them on (as public sign-up is, decision 7). A form is a link to share, not something embedded in another website. *Recommended.*
   - B. Only forms for signed-in people in 2.6; public forms later (for example with sharing in 8.4).
   - C. Both, public forms available without the deployment switch.
   - Also: should forms be embeddable inside a customer's own website? Recommended: not in 2.6 (it needs a change to the page security policy and more abuse controls).

3. **How does email reach Islestone, and may a new outside company handle it?** Each project gets an address such as `k7m2q9xh4tpb@in.islestone.cloud` (random, so it cannot be guessed; a new one can be generated at any time). Whichever way mail arrives, the emails contain the senders' names and addresses and whatever they wrote.
   - A. **A hosted email-receiving service** receives the mail and forwards each email to Islestone as a signed web request. Simple and robust, includes spam filtering; that company sees every email, so it is a **sub-processor** (recorded in the register 6.x and 8.6 call for, with a data-processing agreement). Prefer the same company that sends Islestone's mail, if it can also receive with signed requests and process in the EU, so no additional company sees data; otherwise choose one (for example Mailgun with its EU region, Amazon SES in an EU region, or Postmark; whether each signs its inbound requests must be checked before choosing). *Recommended.*
   - B. **Islestone runs its own mail receiver** on its server. No outside company, but it opens the email port on the shared server (with Agrent and Playerz), needs its own certificate and spam handling, and is the first Islestone service to listen on a port of its own, which changes a delivery rule.
   - C. **Islestone reads one mailbox** it owns at an email host (for example a Google Workspace or Microsoft 365 mailbox, with a "+project" address per project) every minute. The email host is the sub-processor; a minute's delay; the connection is not a web request, so it needs its own outbound safety checks.
   - D. **Each workspace connects its own mailbox**, and Islestone reads it. No sub-processor (it is the customer's own provider), but each customer must set it up, and Islestone stores their mailbox password or token.
   - E. **No email intake in 2.6**; revisit with chat and email in 5.4.
   - Also: an email from an address that matches a member, with the sender's domain authentication passing, is shown as coming from that member. Recommended: yes.

4. **How are robots kept off public forms, and is an outside "captcha" service acceptable?**
   - A. **Islestone's own checks, no outside service:** a hidden field robots fill and people never see, a signed timestamp that refuses forms filled in under three seconds or reused, a small puzzle the browser solves invisibly in about a second, limits per visitor and per form, and a daily cap per form. Nothing for a person to click, and no visitor data leaves Islestone. *Recommended.*
   - B. **An outside challenge** (Cloudflare Turnstile, hCaptcha or Google reCAPTCHA). Stronger against determined attackers, but the provider sees each visitor's address and browser (a sub-processor), and the page security policy must allow its script.
   - C. A now, with B as a per-workspace option added later if abuse appears.

5. **What does the person who sent a request see and get told?**
   - A. **A confirmation on screen with a short reference, always.** Email updates only if they ask for them and confirm their address by pressing a button on a page we email them (at most one such email per address per form per day). After that: accepted, declined (with the reason and note the triager chooses to send), or "handled together with an existing request". Snoozing sends nothing. Emails never repeat the text they typed, so nobody can use a form to make the workspace email a stranger. People who emailed in (2.6c) get an acknowledgement only when their domain's authentication passes. *Recommended.*
   - B. On-screen confirmation only; no emails to outsiders in 2.6.
   - C. An immediate email to whatever address was typed, without confirmation. Not recommended: anyone could make the workspace send mail to a stranger.
   - Also: a page where the requester can check their request's status. Recommended: not in 2.6.

6. **How do snooze and decline work, and how long are decided requests kept?**
   - Snooze: A. **until a date** (Tomorrow, Next week, or a chosen date); the request comes back at 08:00 that day, marked as woken, and the person who snoozed it gets a notification; a follow-up email from the requester brings it back early. *Recommended.* B. Until a date and time. C. Indefinitely, until someone brings it back.
   - Decline: A. **a reason** (Not planned, Out of scope, Spam, Other), an optional note for the requester and an optional internal note; "Spam" sends nothing, hides the request under a Spam filter and offers "Block this sender"; a declined or merged request can be reopened while it is kept. *Recommended.* B. Decline with a free-text reason only.
   - Merge: A. **into an existing work item or into another pending request**; when that request is accepted, everyone merged into it is told. *Recommended.* B. Into work items only.
   - Keeping: A. **Decided requests (accepted, declined, merged) are deleted 90 days after the decision, spam after 7 days**; the work item an accepted request became is kept as usual, and the audit log keeps only ids. *Recommended.* B. Keep every request until the workspace is deleted. C. A setting per workspace (8.3 brings retention settings; the 90 days applies until then).

7. **What is the triage page called, so it is not confused with the notification Inbox?**
   - A. **"Intake"** for the page and the sidebar entry, "Request" for one entry, "Triage" only as a verb; the 2.7 notification list stays "Inbox". This is what the vocabulary ADR already says. *Recommended.*
   - B. "Triage" for the page (needs an ADR amendment: the ADR bans it as a noun).
   - C. "Requests".

8. **Who may triage, and who may build forms?**
   - A. **New permissions, `intake.view`, `intake.triage` and `intake.manage`.** Owners, Admins and Members read and triage requests; Viewers and Guests do not (requests hold outsiders' personal details). Only Owners and Admins turn intake on, build and publish forms, and manage the email address, because a public form speaks for the workspace on the internet. Accepting also needs permission to create work items in the target project. Custom roles can grant any of the three. Anyone who can see a project may send a request through its internal forms. *Recommended.*
   - B. **No new permissions:** triage under "create work items" (Members), forms under "edit projects" (Members can then publish public forms) or under workspace administration.
   - C. A as recommended, but Members may also build internal (signed-in only) forms; publishing a public form stays admin-only.

9. **Where are forms built?**
   - A. **Settings → Intake** (admins), per project: intake on or off, who is notified, the forms, the email address, blocked senders. *Recommended* (Settings is already where admins configure projects, decision 55).
   - B. A tab on each project's page, for whoever holds the permission.

10. **May we add these words to the vocabulary ADR (0006)?** "Intake form" (shown as "Form"), "Form field" (not "Question", which 2.4b plans as a work item type), "Requester" (the person a request came from; not "Reporter" or "Submitter"), "Intake email address", "Follow-up" (a later email on a request), "Decline reason", "Blocked sender", and the channels "Form", "Public form" and "Email". Also a note in ADR 0002 that an intake request is not a work item. *Recommended:* yes to all.

11. **Who is notified inside the workspace when a request arrives?**
    - A. **A list of people per project**, set in Settings → Intake (by default whoever turned intake on), who get a notification for each new request; everyone who may triage sees a count beside "Intake" in the sidebar. From 2.7 the list can be a distribution group. *Recommended.*
    - B. Everyone who may triage the project (noisy in a large workspace).
    - C. Nobody; the count in the sidebar only.

12. **What is encrypted?**
    - A. **The request's text, the form answers, follow-up emails and both notes** under the workspace's key; **the requester's name and email** as personal data, matched by a one-way hash; **the title in plain text**, like a work item's title (it is shown in lists and becomes the item's title). *Recommended.*
    - B. A, and the title encrypted too (it may hold personal details from outside; it would then have to be decrypted for every list, and becomes plaintext anyway once accepted).

13. **One pull request or several?**
    - A. **Three, in order:** 2.6a the intake model, internal forms, the form builder, the Intake page with accept, decline, merge and snooze, and the two jobs; 2.6b public forms with their protections; 2.6c inbound email once question 3 is answered. *Recommended.*
    - B. Two: forms (internal and public), then email.
    - C. One.
