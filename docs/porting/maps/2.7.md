## Summary

- **Six parts, five of them independent.** (1) My Work's "waiting on me" section and the waiting-on due reminder; (2) search over titles and keys (S1, no ADR needed) with the palette switched on; (3) search over encrypted descriptions and comments, under ADR 0008 (Accepted: a plaintext full-text index with Bulgarian and English stemming); (4) the Inbox page, per-member preferences and digests; (5) mentions; (6) recipient lists (the roadmap's "distribution groups"; decision 138). Six pull requests (decision 144).
- **What is copied from inflect-compliance.** The search usecase's shape and its pure ranking module (`src/app-layer/usecases/search.ts`, `src/lib/search/rank.ts`) and the route (`src/app/api/t/[tenantSlug]/search/route.ts`); Islestone already took `src/lib/search/types.ts` and the palette hook in 1.7. inflect's search is substring matching over plaintext titles (its own S1): no `tsvector`, no index, nothing over encrypted text. `UserNotificationPreference` (`prisma/schema/automation.prisma` lines 116–128, enum `NotificationDelivery` `IMMEDIATE | DAILY_DIGEST | DISABLED`) is a model nothing in inflect reads or writes; its shape is a starting point, not a port. inflect has **no** inbox page (only the bell, already ported in 1.7), **no** mention handling and **no** distribution lists. Its digest templates (`digest-templates.ts`) are compliance digests; the mechanism Islestone needs (`dispatchDigest`, `enqueueEmail`) is already ported.
- **What inflect-compliance decided that Islestone can reuse as a precedent, not code.** Its knowledge store (`docs/ai-architecture/weaviate.md`, owner decisions D-L4-2 "vectors only, chunk text encrypted" and D-L4-7 "lexical arm: a keyed blind-token index", 2026-11-11/12) chose keyed tokens (this map's recommendation, S3) for lexical search over encrypted text and recommended against a plaintext `tsvector` ("it is the text, tokenised"). D-L4-7 is decided but not built there, so there is no code to copy. Islestone's owner chose the plaintext index instead (decision 124).
- **The hard part is search.** Titles are plaintext and get a real Postgres full-text index; descriptions and comment bodies are encrypted, and Postgres cannot index ciphertext. Decided (124, 126): a plaintext `tsvector` per description and comment, stemmed by a custom Bulgarian and English configuration, written by the usecases in the same transaction as the text, with a rebuild job. The Bulgarian dictionary needs Islestone's own Postgres image. ADR 0008 is Accepted.
- **Size.** About 7,500 lines of source and 6,000 of tests across the six pull requests.

## Part 2 — Search over titles and keys (S1, no ADR needed)

### What exists

`WorkItemFilters.q` already filters the list by `title ILIKE '%q%'` or an exact key (`keyHitFor`), and `FilterToolbar`'s search box in the filter popover sends it (`WorkItemsView`, `MyWorkView`). There is no index behind it, and no `/search` route.

### Migration (`202612xx120000_search_titles`)

- `CREATE EXTENSION IF NOT EXISTS pg_trgm; CREATE EXTENSION IF NOT EXISTS btree_gin;` (contrib, in the pgvector image; migrations run as the superuser; `btree_gist` set the precedent in 2.5a).
- `CREATE INDEX "WorkItem_title_trgm" ON "WorkItem" USING gin ("tenantId", "title" gin_trgm_ops) WHERE "deletedAt" IS NULL;` — tenant-leading (btree_gin lets a GIN index lead with a scalar), serving the existing substring semantics of `q`.
- `CREATE INDEX "WorkItem_title_fts" ON "WorkItem" USING gin ("tenantId", to_tsvector('simple', "title")) WHERE "deletedAt" IS NULL;` — for ranked word matches in the palette. `'simple'` in 2.7b because the Bulgarian dictionary arrives with its Postgres image in 2.7f; 2.7f replaces this index with an `islestone_bg_en` one (decision 126, ADR 0008 D2).
- `Project` gets the same pair on `name`.
- Prisma cannot declare these; they live in the migration with a catalogue test (`tests/integration/search-sql-constructs.test.ts`), as 2.1's partial uniques do. Risk: confirm `npm run db:check-schema-drift` ignores expression GIN indexes as it ignores the partial uniques; if not, a residue group with its reason.

### Usecase and route

- `src/app-layer/usecases/search.ts`, copied from inflect's and cut to Islestone's two hit types (`workItem`, `project`; `SearchHitType` already says so): one `runInTenantReadContext`, `visibleProjects(ctx)` passed to each query, `deletedAt: null`, archived projects excluded, per-type cap `DEFAULT_PER_TYPE_LIMIT`, a key hit ranked first. Raw SQL only in `WorkItemRepository.searchTitles` / `ProjectRepository.searchNames` (`ts_rank` over the expression, then trigram similarity), bounded.
- `src/lib/search/rank.ts`, copied from inflect (pure; type baselines cut to two). Unit tests copied and edited.
- `GET /api/t/<slug>/search?q=&limit=`: `requirePermission('work_items.view', …)` and a `route-permissions.ts` rule; the query is never logged; read tier at the edge applies. Guest (no projects until 8.4) gets empty hits.
- `ENTITY_SEARCH_AVAILABLE = true`; the palette's entity rows, headings (`commandPalette.entity*`) and the hook's unit tests flip with it.

### Tests

## Part 3 — Search over encrypted descriptions and comments (ADR 0008)

Decided (decisions 124 to 126): a plaintext `tsvector` full-text index (ADR 0008 D1, option C), Bulgarian and English stemming through one custom configuration (D2), no key (D3, moot). ADR 0008 is the authority; this part is the build plan for 2.7f. The owner chose it knowing that the searchable words of descriptions and comments are readable in Postgres, its dumps and the off-host backups.

### The Bulgarian dictionary and the Postgres image (decision 126)

- **Dictionary.** The open-source Hunspell `bg_BG` dictionary (the LibreOffice dictionaries' `bg_BG`, from the bgoffice project). 2.7f reads its licence at the commit it takes, pins that commit and the files' sha256, and adds a `PROVENANCE.md` row and the `NOTICE` text its licence asks for. If the licence is not one ADR 0007 admits, 2.7f stops and asks the owner. The files are converted to UTF-8 and installed as `bulgarian.dict` / `bulgarian.affix` in `$SHAREDIR/tsearch_data`.
- **Image.** `deploy/postgres/Dockerfile` (or `docker/postgres/`), `FROM pgvector/pgvector:0.8.7-pg17-trixie` by digest, copying the pinned files; built and published by the release workflow beside the app images (`ghcr.io/rodnapamet/islestone-postgres`), scanned by Trivy. Used by `deploy/docker-compose.prod.yml`, the local `docker-compose.yml`, CI's `Integration` and `DAST` services (built in the job, or pulled by digest) and the restore drill (`deploy/backup.sh`, `RESTORE_DRILL=1`). `tests/unit/deploy/compose-prod.test.ts` and `tests/guards/deploy-compose-files.test.ts` gain the image; `docs/deployment.md` says how to roll the database container onto it (a restart, no dump and restore: the data directory is unchanged).
- **Configuration** (migration `202612xx120000_search_configuration`): `CREATE TEXT SEARCH DICTIONARY bulgarian_hunspell (TEMPLATE = ispell, DictFile = bulgarian, AffFile = bulgarian)`; `CREATE TEXT SEARCH CONFIGURATION islestone_bg_en (COPY = pg_catalog.english)`; `ALTER MAPPING FOR word, hword, hword_part WITH bulgarian_hunspell, simple`; Latin token types stay on `english_stem`. The migration then runs a fixture list of Bulgarian inflections and English words through `to_tsvector('islestone_bg_en', …)` and raises if any does not stem to its expected lexeme.
- **Fail closed.** A missing dictionary fails that migration (and every later one), so `migrate` exits and both images wait at `wait-for-migrations`. `src/instrumentation-node.ts` and `scripts/worker.ts` run the same fixtures at startup and refuse to start in production on a miss; `/api/readyz` gains a closed error string `search_configuration`. No code names another configuration (a guard: every `to_tsvector` / `websearch_to_tsquery` in `src/` and `prisma/migrations/` names `islestone_bg_en`, except the title index migration of 2.7b, which 2.7f replaces).
- **Costs to measure in 2.7f:** the per-backend memory of the loaded dictionary against the database's `mem_limit` and PgBouncer's pool; whether Postgres's `ispell` template reads the chosen affix file (2.7f stops and reports if it cannot).

### Model and migration (`202612xx120100_search_vectors`)

```prisma
/// The full-text search vector of one encrypted text: a work item's
/// description (commentId NULL) or one live comment's body. PLAINTEXT
/// stemmed words with positions, by ADR 0008 D1 (decision 124).
model SearchVector {
  id         String   @id @default(cuid())
  tenantId   String
  workItemId String
  /// NULL for the description row.
  commentId  String?
  lexemes    Unsupported("tsvector")
  /// The text-search configuration the vector was built with.
  configName String
  /// The build's revision; the rebuild job rewrites older rows.
  revision   Int
  updatedAt  DateTime @updatedAt
  @@index([tenantId, workItemId])
}
```

- One row per source: a partial unique each way (`(tenantId, workItemId) WHERE commentId IS NULL`; `(tenantId, commentId) WHERE commentId IS NOT NULL`), in the migration. FKs: `(workItemId, tenantId)` → `WorkItem`, `(commentId, tenantId)` → `Comment` and `tenantId` → `Tenant`, each `ON DELETE CASCADE`, so the 30-day purge, a comment's hard delete and a workspace's purge take the vectors with the text.
- `CREATE INDEX … USING gin ("tenantId", "lexemes")` (btree_gin), in the migration.
- RLS: `tenant_isolation`, `tenant_isolation_insert`, `superuser_bypass`, FORCE; `GRANT SELECT, INSERT, UPDATE, DELETE … TO app_user`; a two-tenant test in `ISOLATION_TESTED` (`tests/integration/search-vector-isolation.test.ts`).
- **The encryption-manifest guard** scans `String` columns only, so it gains a second population: every `Unsupported("tsvector")` column must sit in a new `PLAINTEXT_DERIVATIVES` map (`SearchVector.lexemes`: "plaintext stemmed words of `WorkItem.description` and `Comment.body`, ADR 0008 D1, decision 124"), apart from `NOT_SENSITIVE`, with a no-stale test. `docs/encryption.md` says the same.
- Whether `npm run db:check-schema-drift` reproduces an `Unsupported` column and the expression and GIN indexes cleanly is checked in 2.7b; a residue group, with its reason, if not.

### Write path: one seam

- `SearchVectorRepository.replaceForSource(db, ctx, source, plaintext)` is the only writer and the only module with SQL against the table (`to_tsvector('islestone_bg_en', $1)`, the sanitised plaintext as a bind parameter, capped before vectorising). It is called **in the transaction that writes the text**, by: `createWorkItemInTx` (so intake accept, repeat copies, template starter items and sub-items inherit it), `insertTemplateItemInTx`, `updateWorkItem` (description), `addComment`, `editComment`; `deleteComment` deletes the row; an empty description deletes the description row. A guard lists those call sites against every write of `description` or `Comment.body`, so a new write path that forgets it fails CI.
- Mention tokens (part 5) are stripped before vectorising.
- Field sets (2.4b-b): a hidden description is still indexed when present (hidden governs forms, not storage).
- The plaintext is never logged; `docs/deployment.md` records `log_statement = none` and `log_parameter_max_length_on_error = 0`.

### Rebuild and backfill job

`search-index-rebuild` (scheduled nightly, 02:40 in `NOTIFICATIONS_TZ`; `SCHEDULED_JOBS` entry, `executorRegistry`): per live workspace, inside its context, pages of 500 sources missing a row or at an older `revision`, decrypts through the normal client, writes the rows. It is the backfill on first deploy (until it finishes, the palette and the filter say "Descriptions and comments are still being indexed" from a per-workspace count) and the rebuild after a configuration, dictionary or normaliser change (a revision bump, never a data migration). On-demand variant for one workspace (`admin.manage`, `POST …/admin/search-index/rebuild`, audited).

### Query path

- `SearchVectorRepository.matchItems(db, ctx, visible, query, cap)`: one raw query, `lexemes @@ websearch_to_tsquery('islestone_bg_en', $1)` under the tenant, joined to `WorkItem` for `deletedAt` and `projectVisibilityWhere` (`tests/unit/repositories/work-item-repository-predicates.test.ts` gains it), ranked with `ts_rank`, capped at 1,000 ids.
- The list filter `q` becomes: title substring (trigram) OR key hit OR title full-text match OR `id IN matchItems(...)`. Its order stays the list's sort.
- The palette's usecase adds description and comment matches below title matches; a hit says where it matched ("in the description", "in a comment"). Snippets: the top five hits' matched source is decrypted and a sanitised 120-character window shown, read under the same visibility; nothing is stored.
- 2.7f's migration replaces 2.7b's title and project-name expression indexes (built with `simple`) by `islestone_bg_en` ones, so titles, bodies and queries stem alike.

### Interactions

Intake requests are not work items (decision 85) and are never indexed; their body becomes a description only on accept, through `createWorkItemInTx`. Template text and project-template content are never indexed (decision 124). Pages (4.1) and embeddings (6.5) each need an amendment to ADR 0008.

- **The workspace is the ceiling.** `TenantNotificationSettings.mutedInAppTypes` and `enabled` (email) still win; a member's preference only narrows. - **Defaults per type** (a table in `src/app-layer/notifications/preference-defaults.ts`, exhaustive over `NotificationType`, client-safe copy of the labels): in-app on for every type; email IMMEDIATE for assigned, mentioned and waiting on; DAILY for due and watcher updates; OFF for intake (open question 9). - **The digest.** `notification-digest` at 08:10 in `NOTIFICATIONS_TZ` (after the due bells at 08:00): per live workspace (the liveness census in `cross-tenant-recipient-liveness.test.ts` gains it), per ACTIVE member with any DAILY type: their unarchived, unread bell rows of DAILY types created in the last window, plus their due items (assigned or, by part 1, waiting on), as one `NOTIFICATION_DIGEST` email through `enqueueEmail` (dedupe per address and day). This wires 1.6's unused `DUE_DIGEST` path or retires it (open question 10). An email never carries a description or comment text (they are encrypted at rest; the bell row's `body` is generated copy).

## Part 5 — Mentions

### Format (open question 4)

Comments and descriptions are plain text today (`sanitizePlainText`), rendered as text; rich text (Tiptap, MIT) arrives with 4.1 pages. Recommended: keep plain text and store a mention as a token, `<@userId>`, chosen in a picker (`@` in the textarea opens the assignable-members picker, `GET /users/assignable`). `sanitizePlainText` keeps the token as typed; the renderer turns it into a chip showing the person's current name.

### Model and migration (`202612xx150000_mentions`)

- `Mention` (`id`, `tenantId`, `workItemId`, `commentId String?`, `mentionedUserId`, `mentionedById`, `createdAt`), FKs to the item and the comment cascade, `(tenantId, mentionedUserId)` FK to `TenantMembership` cascade (a removed member's mentions go, and render as plain text); partial uniques per source and person; index `(tenantId, mentionedUserId, createdAt)`. RLS, grants, two-tenant test.
- `NotificationType.WORK_ITEM_MENTIONED` and `EmailNotificationType.WORK_ITEM_MENTIONED`, each in its own migration.

### Rules

- **The `Mention` rows are the authority, not the text.** The renderer shows a chip only for a token that has a row for that source; any other `<@…>` renders as literal text. So a token typed by an intake requester (decision 85: the body becomes the description on accept), copied by a template or a repeat, or pasted from elsewhere names nobody and notifies nobody.
- **Parsing** is a pure, property-tested function (`src/app-layer/domain/mention.ts`) run by `addComment`, `editComment` and `updateWorkItem` on the sanitised body, inside the write transaction: it keeps tokens naming ACTIVE members who can see the item's project (`visibleProjects` for their role; a GUEST none until 8.4), writes the rows for the new set, and returns the newly added people. An edit notifies only people not mentioned before; removing a mention deletes the row and notifies nobody.
- **Machine-made text never mentions** (open question 6): `createWorkItemInTx` called by intake accept, a repeat copy or a template writes no `Mention` rows from the projected description. A person's later edit can.
- **Notification**: after the commit, `WORK_ITEM_MENTIONED` to each new person, never the author, through a writer in `src/app-layer/notifications/mention.ts` (preference and ceiling checked); email IMMEDIATE by default. The bell and the email say who mentioned them on which item and link to it; they never carry the comment or description text (open question 7).

## What makes the prompt harder than it reads

1. **"Full-text search over comments" contradicts "comments are encrypted"**; Postgres cannot index ciphertext, and a `tsvector` is the words in plaintext (in every backup). ADR 0008 accepts that cost for descriptions and comments (decision 124). Two search pull requests: titles in 2.7b, bodies in 2.7f with the Bulgarian dictionary's image.
2. **Vectors need the plaintext, which only the usecase holds.** The database never sees it (encryption is in the Prisma extension), so vectors cannot come from a trigger or a generated column, and a backfill cannot be a migration: it is a job.
9. **Postgres has no Bulgarian stemmer** (decision 126): the Hunspell dictionary must be in every Postgres the code meets (production, CI, local, the restore drill), with its licence pinned, and a missing one must stop migrations and startup rather than silently index Bulgarian unstemmed.
3. **Eight writers of a description or comment** (create, template item, template sub-item, starter item, repeat copy, intake accept, update, comment add/edit) must all write a search vector; most go through `createWorkItemInTx`, and a guard pins the rest.
4. **Mentions in plain text can be forged** by anyone who can type, including an outsider on a public form; rendering from stored rows rather than from the text closes that.
5. **The bell row's text is plaintext** (`Notification.body`, classified not sensitive), so a mention or digest that quoted a comment would copy encrypted text into a plaintext column and an email.
6. **Preferences are per member, the mute is per workspace**, and both must be read once per batch inside writers that run in other people's transactions.
7. **Lists are named by five later sub-phases** with send-time re-checks; one resolver, or each will re-implement visibility and liveness differently.
8. **The vocabulary guard** again: the new rows' bans must be qualified.

## Open questions for the owner

All twenty-one answered on 2026-11-20 (decisions 124 to 144, question *n* is decision 123 + *n*): recommendation A for every question except 1 (C: a plaintext `tsvector`, the owner confirming that its words are readable in the database, its dumps and the off-host backups), 2 (moot), 3 (Bulgarian and English stemming, an answer not among the options: the Bulgarian Hunspell dictionary for Cyrillic words and `english_stem` for Latin ones, in one custom configuration in Islestone's own Postgres image, failing closed) and 20 (A, with "Search token" replaced by "Search vector").

Each gives the options with the recommendation first and a one-line trade-off. Questions 14–17 are the roadmap's own; 1 is the search ADR; the rest are new.

**Search**

1. **How encrypted descriptions and comments are searched (ADR 0008 D1).** A. S3, keyed word tokens. *Recommended*: whole-word search with no readable words in the database; no prefixes or typos on bodies. B. S3 plus prefix tokens: as-you-type on bodies; about 4× the rows and more frequency signal. C. S2, a plaintext `tsvector`: best search, but the words sit readable in every dump and backup. D. S1 only: comments stay unsearchable, contrary to the prompt. **Decided (124): C**, the plaintext `tsvector`, the owner confirming that the searchable words of descriptions and comments will be readable in Postgres, its dumps and the off-host backups (ADR 0008 D1).
2. **The token key (ADR 0008 D3).** A. Per workspace, from the deployment subkey (`deriveSubkey`) and the workspace id. *Recommended*: survives both key rotations untouched. B. From the workspace DEK: a DEK rotation re-keys tokens too; the DEK sweep must rebuild the index. **Decided (125): moot**, because no tokens are stored.
3. **Language handling.** A. Language-neutral: lower case, accents folded, no stemming, Postgres `'simple'` for titles. *Recommended*: predictable for any language; "running" does not find "run". B. English stemming on both sides: better recall for English, wrong for other languages. C. A per-workspace language setting: right for each workspace, one more setting and a rebuild on change. **Decided (126), revised by the owner: Bulgarian and English stemming**, one custom configuration `islestone_bg_en`: the Bulgarian Hunspell dictionary (`bg_BG`) for Cyrillic words, `english_stem` for Latin ones, installed in Islestone's own Postgres image, failing closed (ADR 0008 D2; 2.7f).

**Mentions**

4. **Text format.** A. Plain text with a `<@userId>` token chosen from a picker, rendered as a chip; rich text with 4.1. *Recommended*: smallest change, no new editor or sanitiser profile. B. Adopt Tiptap for comments and descriptions now, mentions as nodes, stored as sanitised HTML: richer, but pulls 4.1's editor forward and changes every stored body. C. Markdown with `@` handles: familiar, but a renderer and a second sanitiser to secure.
5. **What a mention does.** A. Notifies and adds the person as a watcher. *Recommended*: they hear the replies, as in most trackers. B. Notifies only: less noise, but the person misses the answer to what they were asked.
6. **Machine-made text.** A. Mentions notify only on a person's own write; intake accept, templates and repeat copies record none. *Recommended*: no surprise notifications from a nightly job or an outsider's text. B. Template and repeat text mentions too (as its owner): useful for "@reviewer" in a recurring item; mails people every cycle.
7. **What a mention notification shows.** A. Who mentioned you on which item, with a link; never the text. *Recommended*: encrypted text never lands in plaintext bell rows or email. B. A snippet in the bell, with `Notification.body` added to the encryption manifest: more useful, and every bell read decrypts. C. A snippet in bell and email: most useful; copies encrypted text out by email.
8. **Work-item references in text.** A. A key such as `ISL-123` renders as a link at display time; nothing stored. *Recommended*: cheap, always current. B. Store references as backlinks shown on the target item: richer; the same projection 4.1 needs for pages, so better built once there. C. Nothing in 2.7.

**Inbox, preferences and digests**

9. **Preference granularity.** A. Per type: in-app on/off and email off, immediate or daily; immediate offered only for assigned, mentioned and waiting on. *Recommended*: covers "email me mentions, digest the rest" without a template per type. B. One email choice for everything plus per-type in-app mutes: simplest page, coarse. C. Per type and per project: precise, a large grid and a slower writer path.
10. **The digest.** A. One daily email at 08:10 in `NOTIFICATIONS_TZ` with the day's DAILY notifications and due items, replacing 1.6's separate `DUE_DIGEST`. *Recommended*: one email a day, one dispatcher. B. Keep the due digest and add a notification digest: two emails some days. C. Daily or weekly per member: more choice, two schedules.
11. **Inbox actions.** A. Read/unread and Done (archive), shown as tabs Unread, All, Done. *Recommended*: the familiar inbox model, small. B. As A plus snooze until a date: useful; needs a wake job and another state. C. Read/unread only: smallest; the list never empties.
12. **Retention.** A. Done rows purged after 90 days, read rows after 180, unread kept. *Recommended*: bounded table, nothing unseen lost. B. Keep everything until the workspace is deleted: simplest; the table grows without bound. C. Purge everything after 90 days: smallest table; unread items can vanish.
13. **Admin notification settings page.** A. Settings → Notifications in 2.7c over the existing API (email on/off, sender, BCC, muted types). *Recommended*: members' preferences show a ceiling, so admins need to see and set it. B. Keep it API-only: less work; admins cannot see what their mute does.

**Waiting on (roadmap)**

14. **Due reminders to the person an item waits on** (decision 76 left it open). A. Yes: the same windows and type, worded "waiting on you", also for unassigned items. *Recommended*: whoever must act next hears the deadline; one preference governs both. B. No, assignee only: fewer bells; the person who holds the item up is not told. C. Only on the due day and when overdue: less noise, later warning. D. Yes, under a separate type so it can be muted alone: most control, one more row in the preferences grid.

**Recipient lists (roadmap decision 79)**

15. **The word.** A. "Recipient list" (`RecipientList`). *Recommended*: says what it is for, collides with nothing. B. "Distribution list": familiar from email, but it is the audited product's own term. C. "Audience": short, reads as marketing and odd in "add an audience to watchers".
16. **Copy or follow when added to an item's watchers.** A. Copy: the list's members at that moment become ordinary watchers, each free to stop watching. *Recommended*: no new watcher model; later features that name a list as recipients resolve it at send time anyway. B. Follow: the item watches the list as it changes; needs a list-watch table and a per-item opt-out, and a person cannot simply stop watching. C. Copy now, offer follow later if asked.
17. **Who manages lists.** A. Workspace lists under `admin.manage`, project lists under `projects.edit`. *Recommended*: mirrors decisions 58 and 112; Members manage their projects' lists. B. A new key `notifications.manage_lists` (a new domain): finer for custom roles, one more key everywhere. C. Anyone with `projects.view` creates lists; only the creator or an admin changes them: most open, lists multiply.
18. **Archive or delete.** A. Archive and restore only; no delete (as intake forms). *Recommended*: 2.8, 4.5, 5.1, 7.4 and 7.6 will point at lists, and an archived list keeps their history readable. B. Delete while unreferenced, archive otherwise: tidier list, a reference check per later feature.
19. **Intake's notify list** (decision 95's "may"). A. A project's intake may name one recipient list in addition to its member rows, resolved at send time for `intake.view` holders. *Recommended*: decision 95 as written, nothing removed. B. Replace the member rows with a list: one mechanism, but a migration of 2.6's data. C. Leave intake alone in 2.7.

**Vocabulary and delivery**

20. **ADR 0006 rows.** A. Accept the five rows drafted above (Recipient list, Mention, Notification preference, Digest, Search token) and "Done" as the Inbox's archive verb. *Recommended*: each concept has one word before its model. B. Accept with changes the owner names. **Decided (143): A**, with "Search token" replaced by "Search vector" (`SearchVector`) to fit the plaintext index.
21. **How many pull requests.** A. Six, in the order above, 2.7f after ADR 0008 is signed. *Recommended*: each usable alone; titles search ships without waiting for the ADR. B. Four (a+b, c+d, e, f): fewer reviews, two large pull requests. C. Three (a+b+f, c+d, e): search in one; blocks on the ADR.
