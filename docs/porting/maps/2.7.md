## Part 2 — Search over titles and keys (S1, no ADR needed)

### What exists

`WorkItemFilters.q` already filters the list by `title ILIKE '%q%'` or an exact key (`keyHitFor`), and `FilterToolbar`'s search box in the filter popover sends it (`WorkItemsView`, `MyWorkView`). There is no index behind it, and no `/search` route.

### Migration (`2026113x120000_search_titles`)

- `CREATE EXTENSION IF NOT EXISTS pg_trgm; CREATE EXTENSION IF NOT EXISTS btree_gin;` (contrib, in the pgvector image; migrations run as the superuser; `btree_gist` set the precedent in 2.5a).
- `CREATE INDEX "WorkItem_title_trgm" ON "WorkItem" USING gin ("tenantId", "title" gin_trgm_ops) WHERE "deletedAt" IS NULL;` — tenant-leading (btree_gin lets a GIN index lead with a scalar), serving the existing substring semantics of `q`.

- `Project` gets the same pair on `name`.
- Prisma cannot declare these; they live in the migration with a catalogue test (`tests/integration/search-sql-constructs.test.ts`), as 2.1's partial uniques do. Risk: confirm `npm run db:check-schema-drift` ignores expression GIN indexes as it ignores the partial uniques; if not, a residue group with its reason.

### Usecase and route

## Part 3 — Search over encrypted descriptions and comments (ADR 0008)

Built only after the owner decides ADR 0008 (open question 1). Written here for the recommendation, S3.

### Model and migration (`2026113x130000_search_tokens`)

```prisma
/// Keyed hashes of the normalised words of one encrypted text: a work item's
/// description (commentId NULL) or one comment's body. Never the words.
model SearchToken {
  tenantId          String
  workItemId        String
  /// NULL for the description row.
  commentId         String?
  /// Distinct tokens of the source, each HMAC-SHA256 under the workspace's
  /// search key, truncated to 16 bytes, hex. A set: no order, no counts.
  tokens            String[]
  /// The tokeniser's revision; the reconcile job rebuilds older rows.
  tokenizerRevision Int
  id                String   @id @default(cuid())
  updatedAt         DateTime @updatedAt
  @@index([tenantId, workItemId])
}
```

- One row per source: a partial unique each way (`(tenantId, workItemId) WHERE commentId IS NULL`; `(tenantId, commentId) WHERE commentId IS NOT NULL`), in the migration; `id` is the Prisma key. FKs: `(workItemId, tenantId)` → `WorkItem` and `(commentId, tenantId)` → `Comment`, both `ON DELETE CASCADE`, so the 30-day purge and a workspace purge take the tokens with the text.
- `CREATE INDEX … USING gin ("tenantId", "tokens")` (btree_gin), in the migration.
- RLS: `tenant_isolation`, `tenant_isolation_insert`, `superuser_bypass`, FORCE; `GRANT SELECT, INSERT, UPDATE, DELETE … TO app_user`; a two-tenant test in `ISOLATION_TESTED` (`tests/integration/search-token-isolation.test.ts`).
- Encryption manifest guard: `tokens` classified as derived, not free text.

### The tokeniser (pure, `src/lib/search/tokenize.ts`, server-only)

NFKC, lower case, accents folded (NFKD minus combining marks), split on Unicode non-letters/digits, drop tokens shorter than 2 and a short stop list (the, and, of …: the highest-frequency anchors for frequency analysis), dedupe, cap 2,000 tokens per source. The query goes through the same function. Mention tokens (part 5) are stripped first. `TOKENIZER_REVISION = 1`; property tests (idempotent, order-free, query ⊆ document when words match).

### The key (ADR 0008 D3, open question 2)

Recommended: `searchKey(tenantId) = HMAC(deriveSubkey('islestone-search-token-v1'), tenantId)`. Per workspace (equal words in two workspaces give unrelated tokens), outside the database, and stable across both rotations: `DERIVED_SUBKEY_KEY` is pinned during a master-key rotation, and a tenant DEK rotation does not touch it. The alternative derives it from the tenant DEK, so a DEK rotation re-keys the tokens too, at the cost of a rebuild in the `tenant-dek-rotation` sweep.

### Write path: one seam

- `SearchTokenRepository.replaceForSource(db, ctx, source, plaintext)` is the only writer (a guard like the transition record's: no other file names `searchToken` writes). It is called with the plaintext **in the transaction that writes it**, by: `createWorkItemInTx` (so intake accept, repeat copies, template starter items and sub-items inherit it), `insertTemplateItemInTx`, `updateWorkItem` (description), `addComment`, `editComment`; `deleteComment` deletes the row (soft-deleted comments are not searchable). A guard lists those call sites against every write of `description` or `Comment.body`, so a new write path that forgets it fails CI.
- Field sets (2.4b-b): a hidden description is still tokenised when present (hidden governs forms, not storage).

### Reconcile and backfill job

`search-index-reconcile` (scheduled nightly, 02:40 in `NOTIFICATIONS_TZ`; `SCHEDULED_JOBS` entry, `executorRegistry`): per live workspace, inside its context, pages of 500 sources missing a row or with an older `tokenizerRevision`, decrypts through the normal client, writes the rows. It is also the backfill on first deploy (until it finishes, the palette and the filter say "Descriptions and comments are still being indexed" from a per-workspace count). On-demand variant for one workspace (`admin.manage`, `POST …/admin/search-index/rebuild`, audited) for a revision bump or a key change.

### Query path

- `SearchTokenRepository.matchItems(db, ctx, visible, tokens, cap)`: one raw query, `tokens && $1` under the tenant, grouped by `workItemId`, `HAVING` every query token matched across the item's description and live comments; joined to `WorkItem` for `deletedAt` and `projectVisibilityWhere` (`tests/unit/repositories/work-item-repository-predicates.test.ts` gains it); capped at 1,000 ids.
- The list filter `q` becomes: title substring (trigram) OR key hit OR `id IN matchItems(...)`. Its order stays the list's sort.
- The palette's usecase adds description and comment matches below title matches; a hit says where it matched ("in the description", "in a comment"). Snippets: the top five hits' matched source is decrypted and a sanitised 120-character window shown, read under the same visibility; nothing is stored.
- Ranking is coarse (matched-token count, title match, recency); prefixes and typos work on titles only (trigram), whole words on bodies (open question 1, option B adds prefixes).

### Interactions

Intake requests are not work items (decision 85) and are not searched; their body becomes a description only on accept, through `createWorkItemInTx`. Pages (4.1) will tokenise their plain-text projection (ADR 0005 §6.4) under the same ADR. 6.5's embeddings are a separate decision (S2 by nature); ADR 0008 says so.

### Rules

- **The workspace is the ceiling.** `TenantNotificationSettings.mutedInAppTypes` and `enabled` (email) still win; a member's preference only narrows. One function, `deliveryFor(db, tenantId, userIds, type)` in `settings.ts`, read once per batch (no N+1), replaces `isInAppTypeEnabled` inside every writer, and `enqueueEmail` callers ask it for the email channel.
- **Defaults per type** (a table in `src/app-layer/notifications/preference-defaults.ts`, exhaustive over `NotificationType`, client-safe copy of the labels): in-app on for every type; email IMMEDIATE for assigned, mentioned and waiting on; DAILY for due and watcher updates; OFF for intake (open question 9). A test fails when a type has no default.
- **The digest.** `notification-digest` at 08:10 in `NOTIFICATIONS_TZ` (after the due bells at 08:00): per live workspace (the liveness census in `cross-tenant-recipient-liveness.test.ts` gains it), per ACTIVE member with any DAILY type: their unarchived, unread bell rows of DAILY types created in the last window, plus their due items (assigned or, by part 1, waiting on), as one `NOTIFICATION_DIGEST` email through `enqueueEmail` (dedupe per address and day). This wires 1.6's unused `DUE_DIGEST` path or retires it (open question 10). An email never carries a description or comment text (they are encrypted at rest; the bell row's `body` is generated copy).

## Part 5 — Mentions

### Format (open question 4)

Comments and descriptions are plain text today (`sanitizePlainText`), rendered as text; rich text (Tiptap, MIT) arrives with 4.1 pages. Recommended: keep plain text and store a mention as a token, `<@userId>`, chosen in a picker (`@` in the textarea opens the assignable-members picker, `GET /users/assignable`). `sanitizePlainText` keeps the token as typed; the renderer turns it into a chip showing the person's current name.

### Model and migration (`2026113x150000_mentions`)

- `Mention` (`id`, `tenantId`, `workItemId`, `commentId String?`, `mentionedUserId`, `mentionedById`, `createdAt`), FKs to the item and the comment cascade, `(tenantId, mentionedUserId)` FK to `TenantMembership` cascade (a removed member's mentions go, and render as plain text); partial uniques per source and person; index `(tenantId, mentionedUserId, createdAt)`. RLS, grants, two-tenant test.
- `NotificationType.WORK_ITEM_MENTIONED` and `EmailNotificationType.WORK_ITEM_MENTIONED`, each in its own migration.

### Rules

- **The `Mention` rows are the authority, not the text.** The renderer shows a chip only for a token that has a row for that source; any other `<@…>` renders as literal text. So a token typed by an intake requester (decision 85: the body becomes the description on accept), copied by a template or a repeat, or pasted from elsewhere names nobody and notifies nobody.
- **Parsing** is a pure, property-tested function (`src/app-layer/domain/mention.ts`) run by `addComment`, `editComment` and `updateWorkItem` on the sanitised body, inside the write transaction: it keeps tokens naming ACTIVE members who can see the item's project (`visibleProjects` for their role; a GUEST none until 8.4), writes the rows for the new set, and returns the newly added people. An edit notifies only people not mentioned before; removing a mention deletes the row and notifies nobody.
- **Machine-made text never mentions** (open question 6): `createWorkItemInTx` called by intake accept, a repeat copy or a template writes no `Mention` rows from the projected description. A person's later edit can.
- **Notification**: after the commit, `WORK_ITEM_MENTIONED` to each new person, never the author, through a writer in `src/app-layer/notifications/mention.ts` (preference and ceiling checked); email IMMEDIATE by default. The bell and the email say who mentioned them on which item and link to it; they never carry the comment or description text (open question 7).
- **Watching**: a newly mentioned person is added as a watcher (open question 5), audited as `WORK_ITEM_WATCHER_ADDED` with `metadata.reason: 'mentioned'`.
- **Search** strips mention tokens before tokenising (part 3); the Activity feed still names no comment text.
- **6.3** reuses the grammar with `<@agent:…>` for invocation by mention; the parser rejects that prefix until then.
- **Work-item references** (open question 8): a bare key (`ISL-123`) in a comment renders as a link through `parseKey` at display time, read through the authorised API; nothing stored.

### Tests

Parser properties; the visibility and liveness filter; edit diffing; the authority rule (an unrecorded token renders as text: a rendered test); intake accept with a token in the body notifies nobody; the notification writer's preference check; per-role routes unchanged (no new route: the comment and item routes carry it); `sanitize-rich-text-coverage` unchanged (still plain text).

## Part 6 — Recipient lists (decision 79)

### Model and migration (`2026113x160000_recipient_lists`)

```prisma
model RecipientList {
  id          String    @id @default(cuid())
  tenantId    String
  /// NULL: a workspace list; set: a list of one project.
  projectId   String?
  name        String    // plaintext, sanitizePlainText, ≤ 80
  description String?   // plaintext, ≤ 500
  archivedAt  DateTime?
  createdById String
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt
  @@unique([id, tenantId])
  @@index([tenantId, projectId, archivedAt])
}
model RecipientListMember {
  tenantId  String
  listId    String
  userId    String
  addedById String
  createdAt DateTime @default(now())
  @@id([tenantId, listId, userId])
  @@index([tenantId, userId])
}
```

- Composite FKs: `(projectId, tenantId)` → `Project` cascade; `(listId, tenantId)` → `RecipientList` cascade; `(tenantId, userId)` → `TenantMembership` cascade (a removed member leaves every list). Name unique per scope by two partial uniques (workspace lists; per project). RLS, grants (no `DELETE` on lists if archive-only, open question 18), two-tenant tests for both tables. Names are plaintext and classified; nothing is encrypted (names of lists and member ids only).
- If open question 16 chooses "follow": `WorkItemWatchingList` (`tenantId`, `workItemId`, `listId`, `addedById`) and a per-item opt-out `WorkItemWatchOptOut`; see the question for why it is not recommended.

### One resolver, re-checked at send time

`resolveListRecipients(db, ctx, listIds, { projectId? })` in `src/app-layer/notifications/recipient-list.ts` is the one reader every later feature calls (2.8 reviewers, 4.5 checklist records, 5.1 notify actions, 7.4 reports, 7.6 minutes, and 2.6's notify list if open question 19 says so). It returns ACTIVE members of a live workspace (the census in `cross-tenant-recipient-liveness.test.ts` gains it) who can see the named project (`visibleProjects` for their role), deduplicated, archived lists skipped; each writer then applies the member's preference (part 4). The list's stored membership is never trusted as "may receive".

### Usecases, routes and keys (open question 17)

- Workspace lists managed under `admin.manage`, project lists under `projects.edit`; any member reads them (`projects.view`). Create, rename, change members, archive and restore; every write audited (`RECIPIENT_LIST_*`), sanitised, validated with Zod; a member must be ACTIVE when added.
- Routes: `/api/t/<slug>/recipient-lists` (GET, POST), `/recipient-lists/<id>` (GET, PATCH), `/recipient-lists/<id>/members` (PUT the set), `/recipient-lists/<id>/archive` and `/restore`; each a literal `requirePermission` with a `route-permissions.ts` rule; the usecase asserts the scope's key (workspace vs project) and audits a refusal past the route's key as `AUTHZ_DENIED`.
- **Add to watchers**: `POST /api/t/<slug>/work-items/<id>/watchers/lists { listId }` under `work_items.edit` (the `addWatcher` key): `loadVisibleItem`, then the resolver for the item's project, then one `createMany({ skipDuplicates })` of watchers and one audit entry naming the list and the count; returns who was added and who was skipped (not visible, inactive). A project list can be added only to items of its project.

### UI

Settings → Recipient lists (workspace lists, `settingsPageAccess`); a "Recipient lists" section on a project's page (project lists, offered by `recipientListAffordances` asked on the server); the detail's watchers panel gains "Add a list" (a picker of lists usable on that item). Archive is a typed confirmation, never an undo toast if archive-only. Copy `recipientLists.*`.

### Interactions

Intake's notify list (decision 95: "from 2.7 the list may be a distribution group"): `ProjectIntake.notifyListId` beside the member rows, resolved by the resolver for `intake.view` holders (open question 19). Templates: a project template does not carry lists (lists name people; decision 71's content names none). Repeats: a copy takes no watchers (decision 69), so lists play no part. Field sets: none.

## What makes the prompt harder than it reads

1. **"Full-text search over comments" contradicts "comments are encrypted"** until ADR 0008 decides; Postgres cannot index ciphertext, and a `tsvector` is the words in plaintext (in every backup). Hence two search pull requests: titles now, bodies after the ADR.
2. **Tokens need the plaintext, which only the usecase holds.** The database never sees it (encryption is in the Prisma extension), so tokens cannot come from a trigger or a generated column, and a backfill cannot be a migration: it is a job.
3. **Eight writers of a description or comment** (create, template item, template sub-item, starter item, repeat copy, intake accept, update, comment add/edit) must all write tokens; most go through `createWorkItemInTx`, and a guard pins the rest.
4. **Mentions in plain text can be forged** by anyone who can type, including an outsider on a public form; rendering from stored rows rather than from the text closes that.
5. **The bell row's text is plaintext** (`Notification.body`, classified not sensitive), so a mention or digest that quoted a comment would copy encrypted text into a plaintext column and an email.
6. **Preferences are per member, the mute is per workspace**, and both must be read once per batch inside writers that run in other people's transactions.
7. **Lists are named by five later sub-phases** with send-time re-checks; one resolver, or each will re-implement visibility and liveness differently.
8. **The vocabulary guard** again: the new rows' bans must be qualified.

## ADR amendments (drafts; not applied)

### New: ADR 0008 — Search over encrypted fields

> # 0008 — Search over encrypted fields
>
> Status: Proposed (2026-11-20 drafted).
>
> ## Context
>
> ADR 0002 §11 encrypts `WorkItem.description` and `Comment.body` and decided S1 (titles, keys and plaintext fields only) "until a search ADR chooses between S2 and S3", due before roadmap 2.7. Roadmap 2.7 asks for full-text search over items and comments. ADR 0005 §6.4 defers searching pages' plain-text projection to the same decision. Roadmap 6.5 adds embeddings.
>
> Threat model. Field encryption protects text at rest from anyone who reads the database without the application's keys: a stolen dump or backup, a misused read replica, a database operator. Row-level security protects only against the application's own queries. Any search structure stored in the database is read by the same people encryption is meant to stop.
>
> - **Verified.** inflect-compliance searches plaintext titles by substring (`src/app-layer/usecases/search.ts`); its knowledge store keeps chunk text encrypted and its owner chose a keyed blind-token index for lexical search, recommending against a plaintext `tsvector` (`docs/ai-architecture/weaviate.md`, D-L4-2 and D-L4-7; decided, not built).
>
> ## Decision
>
> ### D1. How encrypted text is searched
>
> - **S3. Keyed word tokens.** Each source stores the set of HMACs of its normalised words under a per-workspace key held outside the database. Finds whole words, all of a query's words in one item; no prefixes, no typos, coarse ranking. Leaks, to a reader without the key, each source's number of distinct words and which sources share words (frequency analysis can guess very common words in a large workspace; a stop list and per-workspace keys reduce it); never the words themselves, and nothing across workspaces.
> - **S3+. S3 plus prefix tokens** (the HMAC of each word's prefixes from 3 letters): as-you-type over bodies; roughly 4× the rows and more frequency signal.
> - **S2. A plaintext `tsvector`** per source. Real full-text search, stemming and ranking in Postgres; the lexemes are the text, readable in every dump and backup, so encryption of these fields protects little.
> - **S1. Unchanged.** Comments stay unsearchable.
> - **Recommendation: S3**, written by the usecase in the text's own transaction through one seam, rebuilt by a job; titles and keys keep a real full-text and trigram index (they are plaintext by ADR 0002 §11).
> - Owner sign-off: ____  Date: ____
>
> ### D2. Normalisation
>
> One tokeniser for documents and queries: NFKC, lower case, accents folded, split on non-letters and digits, tokens of 2+ characters, a short stop list, no stemming; titles use Postgres `'simple'` plus trigrams. **Recommendation: as stated**; English stemming would help English text and harm everything else, and must then match on both sides.
>
> ### D3. The key
>
> - **K1.** `HMAC(deriveSubkey('islestone-search-token-v1'), tenantId)`: stable across master-key and DEK rotations (the subkey material is pinned during a master-key rotation).
> - **K2.** Derived from the workspace DEK: a DEK rotation re-keys tokens, so the DEK sweep rebuilds them.
> - **Recommendation: K1.** Tokens are truncated to 16 bytes.
>
> ### D4. Scope
>
> Covered: work-item descriptions, comment bodies, and (roadmap 4.1) pages' plain-text projection. Not covered: intake request bodies (not work items, ADR 0002 "Consequences"), notification text, audit details. Embeddings (6.5) are a separate decision, by amendment, before 6.5 starts. Tokens are excluded from every export and cascade with their source.
>
> ## Consequences
>
> Search over bodies matches whole words only; the UI says where a hit matched. Every write path of an encrypted searchable field must call the token seam (a guard holds the list). A tokeniser change is a revision number and a rebuild, never a migration. The database holds a derivative of encrypted text whose leakage is stated above, recorded in `docs/encryption.md`.
>
> ## What would change this decision
>
> Customers need prefix or fuzzy search over bodies (S3+ or S2); a workspace large enough that frequency analysis of tokens is realistic (larger stop list, or S1 for it); a regulator or customer contract that forbids any derivative of encrypted text (S1).

## Open questions for the owner

Each gives the options with the recommendation first and a one-line trade-off. Questions 14–17 are the roadmap's own; 1 is the search ADR; the rest are new.

**Search**

1. **How encrypted descriptions and comments are searched (ADR 0008 D1).** A. S3, keyed word tokens. *Recommended*: whole-word search with no readable words in the database; no prefixes or typos on bodies. B. S3 plus prefix tokens: as-you-type on bodies; about 4× the rows and more frequency signal. C. S2, a plaintext `tsvector`: best search, but the words sit readable in every dump and backup. D. S1 only: comments stay unsearchable, contrary to the prompt.
2. **The token key (ADR 0008 D3).** A. Per workspace, from the deployment subkey (`deriveSubkey`) and the workspace id. *Recommended*: survives both key rotations untouched. B. From the workspace DEK: a DEK rotation re-keys tokens too; the DEK sweep must rebuild the index.
3. **Language handling.** A. Language-neutral: lower case, accents folded, no stemming, Postgres `'simple'` for titles. *Recommended*: predictable for any language; "running" does not find "run". B. English stemming on both sides: better recall for English, wrong for other languages. C. A per-workspace language setting: right for each workspace, one more setting and a rebuild on change.

**Mentions**

4. **Text format.** A. Plain text with a `<@userId>` token chosen from a picker, rendered as a chip; rich text with 4.1. *Recommended*: smallest change, no new editor or sanitiser profile. B. Adopt Tiptap for comments and descriptions now, mentions as nodes, stored as sanitised HTML: richer, but pulls 4.1's editor forward and changes every stored body. C. Markdown with `@` handles: familiar, but a renderer and a second sanitiser to secure.
5. **What a mention does.** A. Notifies and adds the person as a watcher. *Recommended*: they hear the replies, as in most trackers. B. Notifies only: less noise, but the person misses the answer to what they were asked.
6. **Machine-made text.** A. Mentions notify only on a person's own write; intake accept, templates and repeat copies record none. *Recommended*: no surprise notifications from a nightly job or an outsider's text. B. Template and repeat text mentions too (as its owner): useful for "@reviewer" in a recurring item; mails people every cycle.
7. **What a mention notification shows.** A. Who mentioned you on which item, with a link; never the text. *Recommended*: encrypted text never lands in plaintext bell rows or email. B. A snippet in the bell, with `Notification.body` added to the encryption manifest: more useful, and every bell read decrypts. C. A snippet in bell and email: most useful; copies encrypted text out by email.
8. **Work-item references in text.** A. A key such as `ISL-123` renders as a link at display time; nothing stored. *Recommended*: cheap, always current. B. Store references as backlinks shown on the target item: richer; the same projection 4.1 needs for pages, so better built once there. C. Nothing in 2.7.

**Inbox, preferences and digests**

9. **Preference granularity.** A. Per type: in-app on/off and email off, immediate or daily; immediate offered only for assigned, mentioned and waiting on. *Recommended*: covers "email me mentions, digest the rest" without a template per type. B. One email choice for everything plus per-type in-app mutes: simplest page, coarse. C. Per type and per project: precise, a large grid and a slower writer path.
10. **The digest.** A. One daily email at 08:10 in `NOTIFICATIONS_TZ` with the day's DAILY notifications and due items, replacing 1.6's separate `DUE_DIGEST`. *Recommended*: one email a day, one dispatcher. B. Keep the due digest and add a notification digest: two emails some days. C. Daily or weekly per member: more choice, two schedules.
11. **Inbox actions.** A. Read/unread and Done (archive), shown as tabs Unread, All, Done. *Recommended*: the familiar inbox model, small. B. As A plus snooze until a date: useful; needs a wake job and another state. C. Read/unread only: smallest; the list never empties.
12. **Retention.** A. Done rows purged after 90 days, read rows after 180, unread kept. *Recommended*: bounded table, nothing unseen lost. B. Keep everything until the workspace is deleted: simplest; the table grows without bound. C. Purge everything after 90 days: smallest table; unread items can vanish.
13. **Admin notification settings page.** A. Settings → Notifications in 2.7c over the existing API (email on/off, sender, BCC, muted types). *Recommended*: members' preferences show a ceiling, so admins need to see and set it. B. Keep it API-only: less work; admins cannot see what their mute does.

**Waiting on (roadmap)**

14. **Due reminders to the person an item waits on** (decision 76 left it open). A. Yes: the same windows and type, worded "waiting on you", also for unassigned items. *Recommended*: whoever must act next hears the deadline; one preference governs both. B. No, assignee only: fewer bells; the person who holds the item up is not told. C. Only on the due day and when overdue: less noise, later warning. D. Yes, under a separate type so it can be muted alone: most control, one more row in the preferences grid.

**Recipient lists (roadmap decision 79)**

15. **The word.** A. "Recipient list" (`RecipientList`). *Recommended*: says what it is for, collides with nothing. B. "Distribution list": familiar from email, but it is the audited product's own term. C. "Audience": short, reads as marketing and odd in "add an audience to watchers".
16. **Copy or follow when added to an item's watchers.** A. Copy: the list's members at that moment become ordinary watchers, each free to stop watching. *Recommended*: no new watcher model; later features that name a list as recipients resolve it at send time anyway. B. Follow: the item watches the list as it changes; needs a list-watch table and a per-item opt-out, and a person cannot simply stop watching. C. Copy now, offer follow later if asked.
17. **Who manages lists.** A. Workspace lists under `admin.manage`, project lists under `projects.edit`. *Recommended*: mirrors decisions 58 and 112; Members manage their projects' lists. B. A new key `notifications.manage_lists` (a new domain): finer for custom roles, one more key everywhere. C. Anyone with `projects.view` creates lists; only the creator or an admin changes them: most open, lists multiply.
18. **Archive or delete.** A. Archive and restore only; no delete (as intake forms). *Recommended*: 2.8, 4.5, 5.1, 7.4 and 7.6 will point at lists, and an archived list keeps their history readable. B. Delete while unreferenced, archive otherwise: tidier list, a reference check per later feature.
19. **Intake's notify list** (decision 95's "may"). A. A project's intake may name one recipient list in addition to its member rows, resolved at send time for `intake.view` holders. *Recommended*: decision 95 as written, nothing removed. B. Replace the member rows with a list: one mechanism, but a migration of 2.6's data. C. Leave intake alone in 2.7.

**Vocabulary and delivery**

20. **ADR 0006 rows.** A. Accept the five rows drafted above (Recipient list, Mention, Notification preference, Digest, Search token) and "Done" as the Inbox's archive verb. *Recommended*: each concept has one word before its model. B. Accept with changes the owner names.
21. **How many pull requests.** A. Six, in the order above, 2.7f after ADR 0008 is signed. *Recommended*: each usable alone; titles search ships without waiting for the ADR. B. Four (a+b, c+d, e, f): fewer reviews, two large pull requests. C. Three (a+b+f, c+d, e): search in one; blocks on the ADR.
