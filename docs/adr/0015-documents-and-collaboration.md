# 0015 — Documents and collaboration

Status: Accepted (owner decisions 338 to 373, 2026-11-27): pages in one tree per project and one for the workspace, ten levels deep, moved with their subtree across trees, soft-deleted in groups and purged after 30 days, never narrower than their tree; the stored Yjs state the source of truth with encrypted JSON and text projections and HTML rendered at use; pages searched through a plaintext `PageSearchVector`; versions as content JSON, compared over Markdown; the core blocks plus toggles, callouts and a table of contents (351, a departure); items by id under visibility and people recorded by claimed client ids; page comments on `Comment`, anchored, with replies and a resolved state, in rich text (356); **work-item descriptions and comments in rich text, converted from plain text and tokens (340, a departure, replacing decision 127's "plain text until 4.1")**; one collaboration server from the worker image with the `access` and `page` notices now; a `pages` permission domain; page watchers; Markdown and a print view; inflect's editor and version diff copied, no deny-list entry for Tiptap's paid packages (366, a departure); seven pull requests; and the six choices under decision 340 (368 to 373): an item-text subset, the old column as the plain-text copy beside an encrypted document, conversion by line breaks only, templates in the same format, plain strings accepted for good (372, a departure), and a counts-only conversion audit

## Context

Roadmap 4.1 asks to "add pages: a tree per project and workspace, the Tiptap editor with slash commands, work-item mentions and embeds, version history, and comments written in-house on the existing comment model. Add collaboration with Yjs and a Hocuspocus server that authenticates the session and checks tenant and page permission on every connection." Hardening H4 adds, for 4.1: a person who loses access is disconnected from open sessions; document size caps and connection and message limits per workspace; collaborative content sanitised on the server before any export or email. The porting map is `docs/porting/maps/4.1.md`; its open questions 1 to 30 were decided by the owner as decisions 338 to 367, and the six choices it then made under decision 340 as decisions 368 to 373 (`docs/HANDOFF.md`; question N is decision 337 + N): every recommendation except questions 3 (decision 340, option C), 14 (decision 351, option B) and 29 (decision 366, option B); question 19 (decision 356) follows decision 340; question 30 (decision 367) is seven pull requests.

ADR 0005 (Accepted, 2026-11-19) already decided most of the architecture: the stored Yjs state is the source of truth (§6.4); the collaboration server is its own Node process (§6.1) and the only writer of that state and its projections (§6.6); every connection carries a signed 60-second collaboration token and is re-checked on every refresh (§6.2); references to work items store the id only (§6.3); client content is untrusted (§6.7); state and versions are encrypted under the workspace key (§6.8); page comments are `Comment` rows anchored by a relative position (§6.10); one audit entry per person per page per 10 minutes (§6.11); agents never connect (§6.12). This ADR holds what is page-specific, names where it departs from ADR 0005, and records rich text in work items.

- **Verified** (Islestone at `0a16570`). `Comment.workItemId` is NOT NULL and `Comment` carries `@@unique([id, workItemId, tenantId])`, which `WorkItem.answerCommentId` and `Mention.commentId` point at; `SearchVector.workItemId` is NOT NULL. The encryption extension encrypts strings only (`src/lib/db/encryption-middleware.ts`). `src/lib/permissions.ts` holds an unused `docs` domain. The stack's six long-running services use the compose test's 4,096 MB ceiling exactly. Descriptions and comments are plain text (`sanitizePlainText`) with `<@userId>` mention tokens (decision 127), encrypted, and vectorised for search by `SearchVectorRepository` (ADR 0008). `sanitizeRichTextHtml` allows headings with an `id`, and no `details`, `summary`, `aside` or `class`.
- **Verified** (npm registry and tarballs, 2026-11-27). Tiptap 3, its collaboration, suggestion, mention, link, table, unique-id, details, table-of-contents and static-renderer packages, `@tiptap/y-tiptap`, `yjs`, `y-protocols`, `@hocuspocus/server` and `@hocuspocus/provider` are MIT; `diff` is BSD-3-Clause. `@tiptap-pro/*` is not on the public registry. `@hocuspocus/extension-redis` 4.6.0 to 4.9.0 depend on `@sesamecare-oss/redlock` 1.4.0, whose `package.json` declares `UNLICENSED`.
- **Verified** (inflect-compliance at `5528464fc54a8681956f3b9ce23ca9c075f0420e`, BUSL-1.1, copying allowed by ADR 0001 D1). `src/components/ui/RichTextEditor.tsx` (a hardened Tiptap 3 editor), its `richtext` copy, its rendered test and `src/components/ui/VersionDiff.tsx` exist; inflect has no Yjs, Hocuspocus, slash menu, mention or comment-anchor code.
- ADR 0006 reserves Page, Page content and Projection and bans Doc, Document, Wiki, Note and Article for a page. No inspiration-only project (roadmap §2.2) was read.

## Decision

1. **Pages and the tree** (decisions 341 to 344). `Page` rows in one table: a project's tree (`projectId` set) and the workspace's (`projectId` NULL), nested at most ten levels by a deferrable parent key in the same scope, ordered by a fractional `sortKey`. Every write that changes the tree takes the per-workspace page-tree lock first, then the page rows in id order, waiting its turn in the process's write queue. A page moves with its live subtree within its tree and across trees; never into an archived or deleted project. Visibility equals the scope's: a project page is readable by whoever reads the project, a workspace page by every holder of `pages.view`; no page is narrower until 8.4. The title is a plaintext row field of at most 200, renamed by a versioned write. Delete soft-deletes the page and its subtree as one group (undo toast), restore through the group's root, purge after `PAGE_PURGE_DAYS` (30); no page archive.
2. **Content and projections** (decision 345). The stored Yjs state (`PageContent.state`) is the source of truth, written only by the collaboration server's store path. Each store writes the projections `contentJson` (validated ProseMirror JSON) and `plainText`, the mention and item-mention rows, the search rows and an automatic version when due. **Departure 1 from ADR 0005 §6.4:** sanitised HTML is not stored; it is rendered from `contentJson` at each export or email and passed through `sanitizeRichTextHtml`. One schema module, shared by browser and server, defines the page node set and the item-text subset (§8); a node the browser can write is a node the server can project. Projections drop and count what the schema does not know, including any link whose scheme is not `http`, `https`, `mailto` or `tel`. A change to the node set bumps `PAGE_SCHEMA_REVISION` and ships a transform and a projection rebuild.
3. **Encryption and search** (decisions 346, 347). The state is stored as base64 text in a `String` column and encrypted by the existing manifest path; the projections, every version's content, comment bodies and every rich-text column are in the manifest; titles, version names and anchors (positions only) are plaintext. Pages are searched: titles, bodies and page comments, through `PageSearchVector`, plaintext stemmed words in the `islestone_bg_en` configuration, written through one seam in the store's and the comment's transaction and read through scoped SECURITY DEFINER functions on decision 245's pattern, bounded like decision 250. **The searchable words of every page and page comment are readable in the database, its dumps and its off-host backups**, as decision 124 accepted for descriptions and comments (ADR 0008, amended).
4. **Versions** (decisions 348 to 350). A version holds the page's content JSON at that moment, encrypted: **departure 2 from ADR 0005 §6.9's "full encoded snapshots"**, since a garbage-collected Yjs document records no usable history. Versions are made automatically when editing goes quiet for 10 minutes and at most hourly while it continues, on "Save version" (named) and before every restore; automatic ones are thinned to all for 7 days, one a day to 90 days, then one a week; saved and before-restore ones are kept for the page's life until 8.3's retention table says otherwise. A restore is a forward change through the server-side write path. Two versions are compared by a block-level line diff of their Markdown.
5. **The editor** (decisions 351, 352). Tiptap 3 loaded on demand behind an error boundary, bound to the provider's document and never given content. Blocks: paragraphs, headings 1 to 3, bullet and numbered lists, quote, plain code block, divider, table, hard break, the marks, links, person and work-item mentions, work-item embeds, page links, and, **by decision 351 (a departure from the recommendation), toggles, callouts and a table of contents**. A toggle's open state is a reader's view state, never stored; a callout is Islestone's own node with a closed `tone`; a table of contents is computed from the headings when shown or exported, never stored as text. Export and print write the three without widening the sanitiser's allowlists. A slash menu written in-house on `@tiptap/suggestion`. No images until 4.4, no external embeds, no checkbox lists: "Create work item" turns a line into a work item and leaves its chip (principle 3).
6. **Mentions and embeds** (decisions 353, 354). A work item in a page is an inline chip or a block embed storing its id only (ADR 0005 §6.3), rendered through a refs read that answers "No access", the same for missing, deleted and invisible items; "Mentioned in pages" on the item from the `PageItemMention` projection; "Link a page" as a `WorkItemLink` of type `PAGE`. A person in a page body is a mention node, recorded on store as a `Mention` row with a page parent for the person whose Yjs client id inserted it: a client id is claimed by the first connection that uses it, and an update claiming another person's is refused and its connection closed, so decision 129 (a person's own write only) holds inside a CRDT. It notifies and makes the person a watcher, as 2.7d does.
7. **Comments** (decisions 355, 356). Page comments are `Comment` rows: `workItemId` nullable, `pageId` added, exactly one by CHECK, each with its own composite unique key; an optional anchor of two Yjs relative positions, drawn as a decoration and never written into the document; a comment survives its anchored text's deletion, marked as such; one level of replies on the same page; resolved and reopened on root comments by anyone who may comment. A page comment can never be a marked answer. **Page comments are rich text, in the same format as item comments** (decision 356, following decision 340), from their first row. Comment authorship rules are decision 53's, unchanged.
8. **Rich text in work items** (decision 340; **a departure from the recommendation, which supersedes decision 127's "plain text until 4.1"**). Work-item descriptions and work-item comments become rich text, without collaboration:
   - *The six choices under it* (decisions 368 to 373, 2026-11-27): the item-text subset with keys as display-time links (368); the existing column as the encrypted plain-text copy, the document in a new encrypted column beside it (369); conversion by line breaks only, never Markdown (370); item templates and project templates' starter items in the same format (371); a plain-string description or comment accepted for good, converted by line breaks, never deprecated or refused (372, a departure); no version bump and one counts-only audit entry per workspace, none per row (373).
   - *Format.* A document of the **item-text** node set (paragraphs, headings 1 to 3, lists, quote, plain code block, divider, hard break, the marks, links, person mentions; no tables, toggles, callouts, table of contents, chips, embeds or page links), stored as canonical ProseMirror JSON in new encrypted columns (`WorkItem.descriptionJson`, `Comment.bodyJson`, `WorkItemTemplate.descriptionJson`). The existing columns keep their names and become the encrypted plain-text projection, written only with the document. Keys typed in text still link at display time (decision 131). A description stays a row field with `If-Match` and a 409 (ADR 0002 §9, ADR 0005 §6.13).
   - *Validation.* `sanitizeRichTextDocument` refuses an unknown node, mark or attribute (400 `RICH_TEXT_INVALID`), sanitises every text node and link, refuses an agent mention until 6.3, and caps depth, nodes, mentions and size; the projection is computed from the sanitised document. Rendering is to React elements only; HTML exists only for an export, through `sanitizeRichTextHtml`.
   - *Mentions.* Mention nodes replace `<@userId>` tokens; the `Mention` rows stay the authority, recorded only for a person's own write (decisions 128 to 131 unchanged); a node with no row renders as plain text and notifies nobody.
   - *Conversion.* Every existing description, comment and item-template description is converted by a job through the decrypting client, page by page, conditionally on the ciphertext it read: line structure only (paragraphs and hard breaks; never read as Markdown), a token becoming a node only where its source has a `Mention` row; no version bump, no notification, no mention row, no per-row audit, one counts-only entry per workspace and run. The search seam keeps each vector's time. A row the previous image wrote as text during the roll is read from its text and converted again.
   - *Every reader.* Search vectorises the projection under a revision bump and a rebuild; notifications and email never carry the text; the detail, the comments panel, the create dialog, the intake accept dialog and the templates manager load the editor on demand; the API carries documents and **accepts a plain string for good**, converted by line breaks and never refused (decision 372, a departure from the map's proposal to refuse it after one release); the marked answer renders as rich text under unchanged rules; a description is present for a field set when its document holds text or a mention; templates and project templates' starter items store documents; an intake request's body stays plain text until it is accepted and converted; repeats copy the document; any later export sanitises on the server.
9. **The collaboration server** (decisions 357 to 363). A `collab` service built from the worker image, at 384 MB, the stack's ceiling raised to 4.5 GB on the shared VM; **one instance** with documents in its memory and no Redis extension (**departure 3 from ADR 0005 §6.1**, deferred until a second instance is measured and its licence question settled). A public WebSocket listener reached on the same origin, `wss://<app host>/collab/…`, routed by Caddy before the app, with an explicit `wss://` origin in `connect-src`; a private port for the app's HMAC-signed server-side writes (restore now, proposals later), applied through a direct connection as the acting person, and a 503 when the server is down. The token is minted under `pages.view`, binds the person, the sign-in session and its version, the workspace, the page and the access level, lives 60 seconds and is refreshed every 45; every authentication and refresh re-reads the session, the membership and its keys and the page. **Departure 4 from ADR 0005 §4's timing:** the `access` notice and a new `page` notice (delete, move, scope) are published from 4.1, after commit, on a per-workspace Redis channel through the one guarded publish function, and the server closes or downgrades the affected connections at once; 4.3 builds the rest on the same function. The caps (ADR 0005 open question 10): a page state at most 4 MB; a message at most 1 MB; per connection 60 messages a second (bursts 120) and 4 MB a minute; awareness 2 KB, 20 a second; 10 connections per person per workspace, 300 per workspace; 30 upgrades a minute per IP; 500 automatic versions per page; H4 sets the final values. Carets and selections with names inside the editor; presence elsewhere is 4.3's.
10. **Keys** (decision 339). The unused `docs` domain becomes `pages`: `view`, `create`, `edit`, `comment`, `delete`; Owners, Admins and Members hold all, Viewers `view`, Guests nothing until 8.4 (decision 204); stored custom roles' `docs` grants are rewritten by a data migration, audited by count. Pages read their affordances from the server.
11. **Notifications and export** (decisions 364, 365). Page watchers (the creator, commenters and mentioned people automatically; anyone may watch or stop); `PAGE_MENTIONED` (immediate email allowed) and `PAGE_COMMENTED` (in-app and digest); nothing for content edits; no bell, email or digest ever carries page, description or comment text. Export is a Markdown download and a print view the browser saves as PDF, both sanitised on the server; no server-side PDF, so no font licence.
12. **Agents** (ADR 0005 §6.12, ADR 0003 §4). Agents and the assistant never connect to the collaboration server; 6.2's read tools (`list_pages`, `get_page`) read projections within the agent's authority; page and description changes are proposals, applied through the server-side write path or validated as a request, as the approver.
13. **Words, sources and delivery** (decisions 338, 366, 367). The words of ADR 0006's "Page words of sub-phase 4.1": Page, Page tree, Page version, Page watcher, Item mention, Comment anchor, Resolved, Reply, Slash menu, Rich text, Toggle, Callout, Table of contents. From inflect-compliance, copied and adapted with `PROVENANCE.md` rows: `RichTextEditor.tsx` (the page editor and its item-text mode), its `richtext` copy, its rendered test and `VersionDiff.tsx`; `PolicyVersion`'s numbering as a pattern only; nothing from inspiration-only projects or Tiptap's templates. **The licence gate gains no deny-list entry for `@tiptap-pro/*`** (decision 366, a departure from the recommendation). Seven pull requests: 4.1a the tree; 4.1b the collaboration server and the editor; 4.1c mentions and embeds; 4.1d comments; 4.1e versions and export; 4.1f search; 4.1g rich text in work items.

## Consequences

- Page content cannot be queried in place: search, export, the diff, backlinks and agents read projections that lag the live document by the store debounce (2 to 10 seconds).
- A change to the editor's node set is a transform of stored states and a rebuild of projections, harder than a row migration; decision 351's three blocks are three more nodes to carry through every such change.
- One collaboration instance is a single point of failure for editing; reading pages, their rows and their comments still works, and the editor shows that it is reconnecting. The stack's memory grows to 4.5 GB.
- The searchable words of pages and page comments join those of descriptions and comments in every dump and backup.
- **Every work-item description and comment is converted once and stored twice** (the document and its plain-text projection, both encrypted); a converter bug would reach every workspace, so the old text is kept as the projection and the document can be rebuilt from it until a person edits it. Once people format text, a return to plain text loses the formatting.
- The work-item views load an editor on demand, so the detail's first paint and the list's latency budgets must hold; rich item text is a larger stored-content attack surface, held by the server's refusal of unknown nodes and the render-to-React rule.
- Anything that writes descriptions or comments later (5.4's replies by email, 5.5's importers, 6.2's proposals) writes documents, or converts through the converter; the `<@userId>` grammar survives only inside it.
- Plain strings stay part of the API for good (decision 372): the request schema accepts a string or a document, both shapes are published with 5.2, and a string never carries a mention or formatting.
- With no deny-list entry, a paid Tiptap package would be kept out by review and exact pins, or by the licence allowlist if its declared licence fails it.

## What would change this decision

- A second collaboration instance (the Redis extension and its `UNLICENSED` dependency).
- 8.4's project grants and per-page sharing, or public read-only pages.
- Measured description conflicts that move descriptions to Yjs (ADR 0002 §9, ADR 0005 §6.13).
- 4.4's images and files in pages and item text.
- A customer, contract or regulator forbidding readable page lexemes in backups (ADR 0008).
- A need for tables, chips or embeds in item text, or for collaborative descriptions.
- Tiptap, Yjs or Hocuspocus going unmaintained or changing licence.
