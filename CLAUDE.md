# CLAUDE.md

Guidance for Claude Code sessions in this repository.

**Islestone** is an AI-enabled project-management SaaS: one work-item table with many views, deterministic planning, and agents that work as delegates of accountable people and write through proposals a person approves, unless a workspace owner raises a rung and the item's assignee started the session (ADR 0003).

Read [docs/ROADMAP.md](docs/ROADMAP.md) (phases, the global preamble in section 4, hardening gates) and [docs/adr/](docs/adr/) before starting. If a step would contradict an ADR, stop and ask.

## Rules that apply now

- **Two env modules.** Server variables live in `src/env.ts`; `NEXT_PUBLIC_` variables live in `src/env-client.ts`. Code a `'use client'` file can reach, directly or through any chain of imports, imports `@/env-client` only. `tests/guards/client-env-boundary.test.ts` walks the import graph from every file Next.js ships to the browser (`'use client'` files, `instrumentation-client.*`, Pages Router files) and fails, naming the chain, if `src/env.ts` is reachable. A `'use server'` module (Server Functions) is a boundary: Next.js sends the client a reference stub, so the walk records the edge and does not descend into it. It has no allowlist. It follows an import of this repository's own workspace packages (`@inflect/ui`) through the package's `exports` map, and fails on one the map cannot resolve. Import them as `@/env` / `@/env-client`, never by a relative path (lint enforces it). No raw `process.env` reads in `src/` outside the env modules (`src/env.ts`, `src/env-client.ts`, `src/env-skip.ts`) and the mirrored UI files: add the variable to the right module and to `.env.example`. The one named exception is `process.env.NEXT_RUNTIME` in `src/instrumentation.ts`, which Next.js inlines per runtime so the Edge bundle drops the Node-only startup checks in `src/instrumentation-node.ts` (owner decision, 2026-11-19). `tests/guards/no-raw-process-env.test.ts` holds both.
- **Lint rules in `src/`:** no `console` (log through `@/lib/observability/logger`, pulled forward from 1.6), no explicit `any`. Type-only imports say `import type`.
- **Production refuses to start without its secrets.** `DATA_ENCRYPTION_KEY` (at least 32 characters, not the published fallback), an authenticated `REDIS_URL` (1.6) and, while `RATE_LIMIT_MODE` is `upstash` (the default), both `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` (issue #17), each refused twice: by the schema in `src/env.ts` and by the startup checks in `src/instrumentation-node.ts` (run from `src/instrumentation.ts` on the Node.js runtime). A deployment that means per-process limits sets `RATE_LIMIT_MODE=memory`. The Playwright server sets a throwaway key, `memory` and the local Redis (`playwright.config.ts`).
- **Exact versions.** `.npmrc` sets `save-exact`; every dependency in `package.json` is pinned.
- **`package.json` overrides** (JSON holds no comments, so each is explained here; remove one when its condition is met): the two Radix entries (`@radix-ui/react-dismissable-layer`, `@radix-ui/react-focus-scope`) hold the versions the shared UI was copied with (1.2); `undici` keeps one copy at the root version; `next-auth` → `nodemailer` lets next-auth's optional 7.x peer resolve to the mailer's 10.x (ADR 0004 question 7); `@prisma/config` → `effect` 3.22.4 moves the Prisma CLI's config loader off `effect` 3.20.0, inside GHSA-7589-6fvf-x4pw (ReDoS, high, `effect` ≤3.22.0), which failed CI's `Audit` job (2026-11-19). Remove that last one once Prisma ships an `@prisma/config` that depends on `effect` ≥3.22.1 (`npm ls effect` then shows no override needed).
- **No AGENTS.md.** `next.config.ts` sets `agentRules: false`, so `next dev` in an agent session does not write one. Agents read this file.
- **Tests ship with behaviour** and must fail when that behaviour regresses. A failing test is fixed, not bypassed.
- **Work-item reads filter `deletedAt` and project visibility explicitly.** No soft-delete extension is ported; a repository method that touches `WorkItem` carries `deletedAt` and `projectVisibilityWhere` in its own `where` (`tests/unit/repositories/work-item-repository-predicates.test.ts`).
- **Every tenant table** gets `tenantId`, a tenant-leading index, row-level-security policies (`tenant_isolation`, `tenant_isolation_insert`, `superuser_bypass`, FORCE) and its own `GRANT … TO app_user` in the migration that creates it, and a two-tenant test listed in `ISOLATION_TESTED`. CI holds each part: `tests/guards/rls-migration-policies.test.ts`, `schema-index-coverage.test.ts`, `tenant-isolation-forward-lock.test.ts` and `tests/integration/rls-coverage.test.ts`.

## Work items

Sub-phases 2.1–2.2 (`docs/porting/maps/2.1-2.2.md`, ADR 0002, ADR 0003 §1). Read [docs/work-items.md](docs/work-items.md) and [docs/pagination.md](docs/pagination.md) before touching it.

- **Model.** `prisma/schema/work.prisma`: `Team`, `WorkflowState` (five categories, `CANCELLED` with two Ls; the category never changes, by trigger), `Project`, `ProjectKeyPrefix`, `ProjectKeySequence`, `WorkItemType`, `WorkItem`, `WorkItemKeyAlias`, `WorkItemRelation`, `Label`, `WorkItemLabel`, `Comment`, `WorkItemWatcher`, `WorkItemLink`. Composite keys keep an item's team equal to its project's, its state of that team with the right category, and its parent in its project. What Prisma cannot declare (`COLLATE "C"` on every `sortKey`, the DEFERRABLE parent link, the relation CHECKs, the partial uniques, the trigger) lives in migration `20261119160100_work_core` with a catalogue test. Key bookkeeping is never deleted (no DELETE for `app_user`).
- **Keys** are `Project.keyPrefix` + `WorkItem.number` from `ProjectKeySequence` (claimed in the item's transaction); prefixes and numbers are never reused, and a moved item keeps its old key as a `WorkItemKeyAlias`. `parseKey`/`formatKey` in `src/app-layer/domain/work-item-key.ts`.
- **Order** is `sortKey`, a fractional index (`src/app-layer/domain/fractional-index.ts`, ADR 0002 F1), computed by the server from "after X / before Y" while the project's sequence row is locked. Compare keys with `<`, never `localeCompare`. A `sortKey` write does not bump `version`.
- **The graph.** Every write to BLOCKS edges or `parentId` takes `lockWorkItemGraph` FIRST (`src/app-layer/usecases/work-item-graph-lock.ts`). BLOCKS cycles are refused by a recursive query over every edge (deleted items included); sub-items nest at most five levels; a sub-item never moves project on its own.
- **Multi-item writes lock in id order first** (owner decision 173, H2; `docs/work-items.md`, "Writes that touch several items"). Every write that changes more than one work item locks them all with one `SELECT … FOR UPDATE … ORDER BY "id"` (`WorkItemRepository.lockForWrite`, or `lockItemsOfPerson`, `lockInState`, `lockPurgeBatch`) BEFORE it reads the rows it plans from; a repository method that can write several rows takes a `LockedWorkItemIds` (`src/app-layer/repositories/work-item-locks.ts`), which only the lock methods mint and `lockedSubset` narrows. Never cast to it, never loop a single-row writer (`updateVersioned`, `bumpVersionOf`, `setSortKey`) over items (`tests/guards/work-item-multi-row-lock.test.ts`). Across kinds the order is the graph lock, then project sequence rows, then item rows; a placement takes the sequence row before writing the item. Creates, reorders and a board drop that places the item wait their turn per project in the process before opening a transaction (`inProjectSequenceQueue`, decision 174: 25 creates at once, `WORK_ITEM_CREATE_BURST_PER_PROJECT`; PgBouncer's 20 server connections are the bound a waiter must not hold). `tests/integration/concurrency/` holds both.
- **Writes.** Usecases in `src/app-layer/usecases/work-item*.ts`, `team.ts`, `workflow-state.ts`, `project.ts`, `work-item-type.ts`, `label.ts`. Every write that changes what an item shows goes through the versioned `updateMany` (`WorkItemRepository.updateVersioned`): 409 `VERSION_CONFLICT` with the current row, 428 for a title or description edit without `If-Match` (`src/lib/http/if-match.ts`). The gate is `loadWritableItem` (404 when missing or invisible, 409 `PROJECT_ARCHIVED`). Delete is a subtree soft delete under one `deletionId`; restore brings that group back.
- **Visibility.** `visibleProjects(ctx)` (`src/app-layer/policies/project-visibility.ts`): every live project for OWNER, ADMIN, MEMBER and VIEWER; none for GUEST until 8.4; fail closed otherwise. Pass it to every repository method; never check one item instead.
- **Permissions.** Work items use 1.4's `work_items.*` keys (delete and restore take `work_items.delete`); projects use `projects.*` (archive, delete and restore take `projects.archive`); teams, workflow states, types and labels are changed under `admin.manage` and read under `projects.view` (owner decision, 2026-11-19: admins configure, and a custom role can grant `admin.manage`). A comment is edited by its author only and deleted by its author or a workspace admin, an admin's delete audited as `COMMENT_MODERATED` (owner decision, 2026-11-19; `src/app-layer/policies/comment.policies.ts`). Every work route is a literal `requirePermission` with a rule; `tests/guards/tenant-crud-authz-coverage.test.ts` pins each key.
- **Side effects.** Keep each path's order (`tests/unit/usecases/work-item-sequence-order.test.ts`): create audits, emits automation and enqueues the email inside its transaction, then rings the bells; a state change audits inside, then emits automation and fans out to watchers after the commit. Notifications go through `work-item-shared.ts` (`emitDueBell`, `emitAssignedBells`, `emitWatcherActivity`, `enqueueAssignedEmail`), never inline.
- **Activity** merges `WORK_ITEM_*` audit entries with live comments; audit entries name changed fields, never description or comment text.
- **Jobs:** `work-item-due-notification` (08:00 in `NOTIFICATIONS_TZ`), `work-item-purge` (`WORK_ITEM_PURGE_DAYS`, 30), `work-item-sortkey-rebalance`. Due dates are date-only: never pass one through a time zone.
- **Queries.** No Prisma read in a loop and no unbounded repository `findMany` (`tests/guards/query-shape-guardrails.test.ts`); a bounded drain says `// guardrail-allow: n+1 — <reason>`.

Sub-phases 2.6a, 2.6b and 2.6c (`docs/porting/maps/2.6.md`, `docs/intake.md`, owner decisions 85 to 99 and 120 to 123).

Pages read `intakeAffordances` on the server; never check a role in a component. `tests/integration/intake-api.test.ts` drives every intake route as each role.
- **Public forms (2.6b; decisions 86, 88, 89 and 98).** A `PUBLIC` form is reached at `/f/<publicId>` with no session, only while `INTAKE_PUBLIC_FORMS` opens them (`isPublicIntakeOpen`: closed in production unless set). `resolvePublicIntakeForm` (`src/app-layer/usecases/intake-public.ts`) is the surface's one pre-tenant read, under `runWithoutRls({ reason: 'public-intake-resolve' })`, and every form that is not open to the public is the same 404; everything after runs in the workspace's context as its system user. Never read a public body with `req.json()` (`capped-body.ts`).
- **The requester (2.6b).** Name and address are PII (`PII_FIELD_MAP`, `requesterEmailHash`); one confirmation email per address per form per day; confirmation is a POST from `/f/confirm/<token>`, never a GET; notices (`enqueueRequesterNotices`, inside the deciding transaction) go only to a confirmed address, never for spam or a snooze, and an email never repeats the request's text or links into the app. The four email types were added in their own migration; their writers are unreachable until an operator opens public forms.
- **Inbound email (2.6c; decisions 120 to 123).** Resend, a sub-processor (`docs/sub-processors.md`), behind `INTAKE_EMAIL` (`isInboundEmailOpen`: closed in production unless set; production refuses it without `RESEND_API_KEY` and a `whsec_` `RESEND_WEBHOOK_SECRET`). `POST /api/intake/email/resend` is a machine caller gated by `acceptResendWebhook` (`src/lib/intake/email/http.ts`): a per-IP bound, a capped body, the Svix signature verified by hand (`svix.ts`); `receiveInboundEmailEvent` resolves the address token under `webhook-ingest`, dedupes on `svix-id` and `email_id`, applies the throttles and blocked senders and records an `IntakeInboundEmail` row, then enqueues `intake-email-fetch`. Never fetch in the webhook. The job (`processInboundEmail`) retrieves the email, downloads the raw message only from a pinned host through `safeFetch` (`resend-download.ts`, an SSRF sink), parses it in-house (`mime.ts`, `text.ts`, `rfc2047.ts`, `content.ts`) and makes the request (deduped by the Message-ID's hash) or a follow-up (`IntakeFollowUp`, the reply address `<token>+r<replyToken>@…`, from the requester's own address only). Only an `Authentication-Results` header from `INTAKE_EMAIL_AUTHSERV_ID` is believed (`auth-results.ts`); only `VERIFIED` (`IntakeSenderCheck`; ADR 0006 bans "Pass") is acknowledged (`INTAKE_RECEIVED_ACK`, Reply-To the reply address), counted as confirmed or attributed to a member; nothing is declined automatically. Auto-replies are dropped and never answered.
- **Blocked senders (2.6c).** `IntakeBlockedSender` holds only the address's lookup hash (ADR 0006), for a project or the workspace (NULL; a partial unique index); its emails and public-form requests are dropped like the trap. Managed under `intake.manage` (`intake-blocked-senders.ts`), including "Block this sender" on a spam decline; a lookup by address is a POST body, never a URL.
- **Copy** is `intake.*` and `settings.intake.*` in `messages/en.json`; a file with several components gives each its own translator name.

Never edit, add or replace a file there without amending E10 (an owner decision); the licence gate does not see it. `PROVENANCE.md` and `NOTICE` carry it.
- **Titles and names** (2.7b, migration `20261203120000_search_titles`, the full-text pair rebuilt by 2.7f): `pg_trgm` and `btree_gin` and four GIN indexes, each `("tenantId", …) WHERE "deletedAt" IS NULL`: `WorkItem_search_title_trgm` / `_fts` and `Project_search_name_trgm` / `_fts`. A query must spell the expression exactly (`to_tsvector('islestone_bg_en', w."title")`). Prisma cannot declare them; the drift check ignores them. `tests/integration/search.test.ts` checks the catalogue and the planner.
- **Descriptions and comments** (2.7f, decision 124). `SearchVector` (migration `20261207120100_search_vectors`): one row per description (`commentId` NULL) or live comment, `lexemes` a plaintext `tsvector` (`Unsupported("tsvector")`, classified in `PLAINTEXT_DERIVATIVES` in `encryption-manifest-coverage.test.ts`), `configName` CHECKed, `revision`; the GIN `SearchVector_search_lexemes` leads with `tenantId` and is partial on the configuration (every match names it). The item, the comment and the workspace cascade. Its readable words are in every dump and backup: that is the decision, not a defect.
- **One seam.** `SearchVectorRepository` is the only module with SQL against the table. Every function that writes a description or a comment's body calls `replaceForSource` (a comment's delete, `removeForSource`) in the same transaction: `createWorkItemInTx`, `insertTemplateItemInTx`, `updateWorkItem`, `addComment`, `editComment`, `deleteComment`; the write-seam guard finds every writer by AST and pins the list. A new writer calls the seam. Mention tokens never become lexemes (`searchableText`). Never index intake requests, template text, project-template content or personal data: a new source is an amendment to ADR 0008.
- **Reads.** `GET /api/t/:slug/search?q=&limit=` (`requirePermission('projects.view')`, `SearchQuerySchema`) calls `searchWorkspace` (`src/app-layer/usecases/search.ts`): titles, keys and names as before, plus `SearchVectorRepository.matchItems` (an item found by its title keeps that hit; the rest score `computeContentScore`, below every title match); each hit says `matchedIn`, and the best five content hits carry a `snippet` (`buildSnippet`, decrypted under the same visibility, never stored). The list's `q` also matches stemmed titles (`WorkItemRepository.titleFullTextIds`) and the vectors, through the internal `WorkItemFilters.fullTextMatchIds` the usecase sets, never the request. Every match is a search function (below) called with typed bind parameters and the visibility input (`projectVisibilityArgs`), never a workspace, and bounded; the rows shown are then read by id under row-level security (`tests/unit/repositories/search-repository-predicates.test.ts`). The query and the text are never logged.
- **The search functions** (owner decision 245, issue #78, migration `20261214120000_search_definer_functions`; `docs/search.md`, "The search functions"; `docs/rls-tenant-isolation.md`, "The search functions: a named exception"). `@@`, `ILIKE` and `%` are not LEAKPROOF, so under row-level security they could not be index conditions (finding F1). Each search read is a SECURITY DEFINER function, `search_work_item_titles`, `search_work_item_title_words`, `search_work_item_title_substring`, `search_project_names` and `search_item_contents`, owned by `app_search_definer` (NOLOGIN, NOINHERIT, BYPASSRLS, column SELECT only, no members): the workspace from `current_setting('app.tenant_id', true)` and never an argument (unset, no rows), `tenantId`, `deletedAt` (the item's and a comment's), the archived filter and visibility in its own `WHERE`, a hard cap, ids and ranks only, `search_path = pg_catalog, public, pg_temp`, schema-qualified tables, EXECUTE for `app_user` alone. Never mark an operator LEAKPROOF, never take the workspace as an argument, never return text. Each is called from one repository; `tests/guards/search-definer-functions.test.ts` pins each body's hash and its predicates (`tests/helpers/search-definer.ts`), `tests/integration/search-definer.test.ts` the catalogue and two-tenant behaviour. A change to a body is a new migration and a new pinned hash. The list's `q` matches title substrings by the ids `search_work_item_title_substring` returns (`WorkItemFilters.titleSubstringMatchIds`) while fewer than 1,000 come back, else by `ILIKE` itself. The plan checks capture the functions' own statements (`auto_explain.log_nested_statements`, the `islestone:search-definer` marker).
- **The bound on content matches** (owner decision 250, issue #89, migration `20261217120000_search_recent_candidates`; `docs/search.md`, "The bound on content matches"). `search_item_contents` ranks only the caller's 2,000 most recently written live, visible matching vectors (`CONTENT_CANDIDATE_BOUND`), read one past the bound, with a fourth column `bounded` when the 2,001st existed, computed after every predicate so it says nothing about rows the caller cannot see. In a workspace of 100,000 vectors or more, for a query matching 100 of the newest 2,000, it walks the newest 50,000 on `SearchVector_search_recent` (tenant-leading, partial on the configuration) and stops at 2,001; otherwise it reads every match on `SearchVector_search_lexemes` (materialised) and keeps the newest. The choice is by measurement, never the planner's estimate (it under-counts phrases); the function sets `plan_cache_mode = force_custom_plan` (a generic plan re-parses the query per row) and `jit = off`. "Recent" is the vector's own `updatedAt`, the time its text was last written: `replaceForSource` stamps it and the rebuild keeps it (`{ keepTime: true }`); never make the rebuild restamp it. `matchItems` returns `{ matches, bounded }`; the route answers `meta.contentMatchesBounded`, the list `contentMatchesBounded`, and the palette and `RecentMatchesNote` show `commandPalette.recentMatches` / `workItems.list.recentMatches`. Titles, keys and project names stay unbounded. `definerProblems` holds the walk (`candidates`) and the settings (`planSettings`) on the spec.
- **The rebuild.** `search-index-rebuild` (02:40 in `NOTIFICATIONS_TZ`): missing or older vectors in every live workspace as its system user, a keyset walk in pages of 500 that each read only their own rows (`staleDescriptionPage` / `staleCommentPage` return the page's stale ids and the next cursor; issue #79), at most 100,000 writes of each kind a run, counts-only `SEARCH_INDEX_REBUILT`; on demand `POST /api/t/:slug/admin/search-index/rebuild` (`admin.manage`, audited, forced, run as the admin re-resolved). A change to the configuration, its dictionary or `searchableText` bumps `SEARCH_VECTOR_REVISION`; never a data migration.
- **Copy** is `commandPalette.*` (`matchedInDescription`, `matchedInComment`, `recentMatches`) and `workItems.list.recentMatches`; the hits' category labels are `SEARCH_TYPE_DEFAULTS`, the headings `commandPalette.entity*`.

Sub-phase 2.7d (`docs/porting/maps/2.7.md`, part 5; `docs/work-items.md`, "Mentions (2.7d)"; `docs/notifications.md`, "Mentions"; owner decisions 127 to 131).

- **Plain text, one grammar.** A mention is the token `<@userId>` in a comment or a description (decision 127; no rich text until 4.1). The grammar is the pure, client-safe `src/app-layer/domain/mention.ts` (`parseMentionIds`, at most `MAX_MENTIONS_PER_TEXT`; `<@agent:…>` refused until 6.3; `segmentText`; the picker's `mentionQueryAt` / `insertMention`). Never parse a token anywhere else.
- **The rows are the authority, not the text.** `Mention` (one row per source and person; `commentId` NULL is the description; cascades with the item, the comment and the membership; migrations `20261205120000` to `20261205120200`). The bell and the email name who and which item and link to it, never the text (decision 130).
- **Keys in text** (`ISL-123`, upper case, a known project prefix) link at display time; nothing is stored (decision 131).
- **UI.** `src/components/work-items/mentions/` (`MentionTextarea`: the `@` picker over `GET /users/assignable`, keys on the text box's own `onKeyDown`; `MentionText`). The description is shown rendered and edited on request. Copy is `workItems.mentions.*`.

## Reviews

Sub-phases 2.8a, 2.8b and 2.8c (`docs/porting/maps/2.8.md`; `docs/work-items.md`, "Reviews (2.8a)", "Reviews (2.8b)" and "Reviews (2.8c)"; `docs/notifications.md`, "Reviews (2.8a)"; ADR 0009; owner decisions 148 to 165).

- **The words** (decision 148, ADR 0006): Review step, Round, Reviewer; Signed off, Returned; "To review". "Review" alone is the proposal page's (6.2); never Approve, Reject, Accept or Decline for a review.
- **Model.** `prisma/schema/reviews.prisma`, migration `20261208120600_reviews` (each new enum value in its own migration before it). One live round per item, one open step per round (partial uniques). `app_user` holds no DELETE on rounds or reviewer rows: a person is withdrawn, never removed. `WorkItemReviewer.responseText` is in the encryption manifest and sanitised.
- **Nothing ended is rewritten** (ADR 0009 §4, H2). The triggers refuse any change to an ended round and every row of it, to an ended step and its responses, to a step's definition once it opened, a response taken back and a direct delete of anything but a step not yet opened; only the key rotations' re-wrap of `responseText` and cascades pass. End children before parents (reviewer rows, the step, the round), or the trigger refuses your own write.
- **One engine.** The usecases are `src/app-layer/usecases/review.ts`; the in-transaction core every path shares is `review-engine.ts` (`openStepInTx`, `settleStepInTx`, `skipStepInTx`, `withdrawRoundsInTx`, `endOpenRoundsOnClose`, `endOpenRoundsInState`, `withdrawReviewerRowsOfUser`, `withdrawNewAssigneeRows`); the pure rules are `domain/review-steps.ts` and `domain/working-days.ts` (date-only, decision 151; from 3.1a over the scheduling engine's calendar module, on the item's working calendar, Monday to Friday when none is saved; never step a due day anywhere else). Every review write takes `ReviewRepository.lockItem` first, and so does `setWorkItemWaitingOn`. The engine returns notices; the caller rings them after its commit through `emitReviewNotices` (`work-item-shared.ts`).
- **Zero is never complete.** An "all" step completes only with every reviewer still asked signed off and at least one; a send refuses a step that resolves to nobody (`NO_REVIEWERS`); a step left with nobody stays open, flagged, until a person skips it (`NO_REVIEWERS_LEFT`), adds a reviewer or withdraws the round.
- **Only people review** (ADR 0009 §10, ADR 0003 §4). Only `respondToReviewStep` writes a response, through `ReviewRepository.recordResponse` (`tests/guards/review-response-seam.test.ts`): a person (`assertActingAsPerson`), the named reviewer, never the item's assignee (decision 158). A response may change while its step is open (decision 162). Never add a job, automation or agent path that responds.
- **The assignee never reviews** (decision 158): refused when steps are edited (`REVIEWER_IS_ASSIGNEE`), dropped from a list at open, refused when responding, and an assignee change withdraws their pending rows (`withdrawNewAssigneeRows` in `assignWorkItem` and `bulkAssignWorkItems`). A new assignee writer calls it too.
- **Every close ends an open round** (decision 149). A state path into a closed category and the subtree delete call `endOpenRoundsOnClose` (a state's delete, `endOpenRoundsInState`) in the same function; `tests/guards/review-close-paths.test.ts` pins the paths. A new state path calls it.
- **Waiting on** (decisions 152, 153): cleared when a round opens, the assignee when it completes or is returned, nothing when withdrawn; a hand write while a round is open is 409 `REVIEW_ROUND_OPEN`. While open, the item waits on the open step's pending reviewers, read from their rows (`reviewerId=me`).
- **Keys** (decision 160): `work_items.view` reads and responds, `work_items.edit` does the rest; skip and removing a pending reviewer from an open step take the assignee, the sender or `admin.manage` (`review.policies.ts`), refused with an audited 403 otherwise. `tests/integration/review-api.test.ts` drives every review route as each role.
- **Notifications** (decision 161): `WORK_ITEM_REVIEW_REQUESTED`, `_DUE`, `_RETURNED`, `_COMPLETED` (`notifications/review.ts`), immediate email for requested and returned (`IMMEDIATE_EMAIL_TYPES` and the preference CHECK), the reminders in `work-item-due-notification`; never the response text.
- **UI (2.8b).** `src/components/work-items/detail/ReviewSteps.tsx` on the detail's Overview (page and sheet); the data hook `data/use-review.ts` (`useWorkItemReview`, `useReviewWrites`: every write that names the round sends its version as `If-Match`, and the work-item views' shared-query guard holds it; removing a reviewer or a step not yet opened goes through the undo toast and is in `SITE_CONTRACTS`; after a write the item is re-read and placed, and lists filtered by reviewer or "waiting on me" are re-read). Every button follows the GET's `viewer` (`reviewAffordances`); never ask a role, a key or who the assignee is in a component. `editSteps` is offered whenever the caller edits work items, so a new round may be planned after one ended. "Changed since signed off" is `changedSinceSignedOff` (open rounds only). While a round is open the detail's waiting on shows the step's reviewers read-only (`useReviewWaitingOn`).
- **The row's summary (2.8b).** `toWorkItemDto` carries `review` (`reviewSummaryOf` in `domain/review-steps.ts`, over the two newest rounds in `workItemListSelect`): the list's `review` column (gear, hidden by default; shown in My Work), the board card's mark (`ReviewBadge`), no lane. `reviewerId` is in `WORK_ITEM_FILTER_KEYS`, the saved-view `FilterKey` and `LIST_FILTER_KEYS`; `rowBelongs` never decides it. My Work's "To review" is the first section (`reviewerId=me`). Copy is `workItems.review.*`.
- **Defaults per type (2.8c, decision 159).** `WorkItemTypeReviewStep` and `WorkItemTypeReviewStepReviewer` (migration `20261209120000_type_review_steps`; a member, by the cascading membership FK, or a workspace list, exactly one by CHECK), read under `projects.view`, replaced as a whole under `admin.manage` (`GET`/`PUT /work-item-types/:typeId/review-steps`, `review-defaults.ts`). `copyTypeReviewDefaultsInTx` is the only path from a type's defaults to an item: both in-transaction creates (`createWorkItemInTx`, `insertTemplateItemInTx`) call it, so every create path copies, as round 1 `PLANNED`, never opened; `tests/guards/review-defaults-copy-paths.test.ts` holds every writer of a new item to it. The item's assignee and members who may not review it are dropped, and named in `WORK_ITEM_CREATED`; a step left naming nobody is kept. A change to the defaults or a type change touches no item. Project templates carry no steps.
- **The Done check (2.8c, decision 149).** Every state path into `DONE` calls `assertReviewAllowsDone` (a state's delete, `assertReviewAllowsDoneInState`; a create into Done is checked by the copy) before it writes; `tests/guards/review-done-paths.test.ts` pins the callers of `stateTransitionEffects`. A new state path calls it. For a type with `reviewRequiredForDone`, the newest round with steps must be `COMPLETED` (`reviewHoldsDone`), else 409 `REVIEW_INCOMPLETE`; an item with no such round is not held; cancelling and a move between Done states never are; nobody overrides it. The check locks the items (`ReviewRepository.lockItems`). Settings → a type → Review steps is `WorkItemTypeReviewStepsSettings` (removal through the undo toast, in `SITE_CONTRACTS`). Copy is `settings.typeReviewSteps.*`.

## Scheduling and working calendars

Copy is `settings.workingCalendars.*`, `settings.projects.dueDate*` and `workItems.projects.dueDate.*`. ## Goals and initiatives

Sub-phases 3.2a, 3.2b and 3.2c (`docs/porting/maps/3.2.md`; `docs/goals.md`; ADR 0002 §2 and §17; ADR 0006 "Goal and roadmap words of sub-phase 3.2"; owner decisions 205 to 224).

- **The words** (ADR 0006): Goal, Initiative, Lead, Health; Planned, Started, Completed, Cancelled. Never Target, Portfolio, Plan, Theme, Objective, Epic or Owner for these, and never "Active" for their status. "Completed" is both a health and a status: show the field's name with the value, and neither sets the other.
- **Model.** `prisma/schema/goals.prisma` (`Goal`, `Initiative`), `Project.initiativeId`, `WorkItem.goalId`; migrations `20261215120000` to `20261215120200`. The four links are composite keys `ON DELETE SET NULL` on their own column (written in SQL; Prisma cannot say the column list), so only the purge deletes a row and the database clears its links. Descriptions are encrypted (manifest) and sanitised, never audited or search-indexed; titles and names plaintext. Not work items: never in the list, board, search or an item read.
- **The tree.** Every write that changes `Goal.parentId` or `Initiative.goalId`, every goal delete and restore and every purge page takes `lockGoalTree` FIRST (`usecases/goal-tree-lock.ts`), before project or item rows. Goals nest at most three levels; a move into its own subtree is `GOAL_WOULD_CYCLE`, past the cap `GOAL_TOO_DEEP`; deleted goals count (`domain/goal-tree.ts`). A deleted target is 404 (`GOAL_NOT_FOUND`, `INITIATIVE_NOT_FOUND`) to every read and write; an archived one takes no new link (409 `GOAL_ARCHIVED`, `INITIATIVE_ARCHIVED`). Targets are read `FOR KEY SHARE`.
- **Archive, delete, restore, purge** (decisions 218 and 219). Archive only Completed or Cancelled (CHECK; `GOAL_NOT_FINISHED`); an archived one is read-only (`ARCHIVED`). Delete is a group under one `deletionId` (a goal, its live descendants, their live initiatives); links are kept; restore only through the group's root (`DELETED_WITH_PARENT`) under a live parent (`PARENT_DELETED`). The nightly `goal-purge` (02:35 UTC, `GOAL_PURGE_DAYS`) locks the items naming a page of goals in id order before deleting them (`lockItemsNamingGoals`), writes no item entry, bumps no version, and writes one counts-only `GOALS_PURGED`.
- **An item's goal** (decision 211). `PUT /work-items/:id/goal` (`work_items.edit`; naming one asks `goals.view` through `assertGoalLinkable`, which every create path calls): a single-field versioned write, `WORK_ITEM_GOAL_CHANGED`; `goal` is a configurable built-in field; a move keeps it; nothing is inherited (a sub-item, a new item, a project's move); repeats copy it through `templateToCreateInput`, skipped and named when it no longer links; templates carry none. The transition trigger does not watch it. A new path that sets `goalId` calls `assertGoalLinkable` and the field set.
- **A project's initiative.** `PUT /projects/:id/initiative` (`projects.edit`; naming one asks `goals.view`), versioned, `PROJECT_UPDATED` naming `initiativeId`; `POST /projects` takes `initiativeId`. Moving a project moves nothing else.
- **Keys** (decision 213): `goals.view`, `goals.manage` (Owners, Admins, Members; Viewers view; a Guest nothing). Pages read `goalAffordances` (`goal.policies.ts`) on the server; never check a role or a key in a component. The Lead is an ACTIVE member, never a Guest, cleared on member removal (`clearLead`, audited).
- **The ancestry** (decision 220). `WorkItemRepository.ancestry` is the one statement (three depth-capped, path-guarded recursive terms with `tenantId`, `deletedAt` and visibility in each); `assembleAncestry` withholds the initiative and goals from a caller without `goals.view`, counting them. `GET /work-items/:id/ancestry` (`work_items.view`); the detail's `AncestryBreadcrumb` ("Also serves" when the item's own goal is off the path). Never a description.
- **Filters.** `goalId` (both paths over each goal's live subtree) and `initiativeId` (the initiatives' projects) are resolved only in `resolveListFiltersInTx` into the internal `goalScope` / `initiativeProjectIds`; `_buildWhere` refuses them unresolved. They ask `goals.view`, 404 a deleted target, refuse more than 1,000 projects (422 `GOAL_SCOPE_TOO_LARGE`), and are in `WORK_ITEM_FILTER_KEYS`, the saved-view `FilterKey` and `LIST_FILTER_KEYS`; the client never decides them.
- **UI.** `GoalPicker` (`pickers.tsx`, over the view configuration's `goals`), `useWorkItemMutations().setGoal`, `useWorkItemAncestry`; the project create dialog's Initiative (`offerInitiative`, asked on the server) and Settings → Projects' column and "Change initiative". Copy is `workItems.goal.*`, `workItems.ancestry.*` and `settings.projects.*initiative*`.
- **Progress (3.2b, decisions 211 and 212).** Derived on every read, never stored: the pure `domain/progress.ts` (`{ scope, done, started }`, cancelled out, zero items never complete; 2.5b's milestones read it too). An initiative counts its live projects' live, visible, non-cancelled items, archived projects included; a goal the same through its subtree's initiatives plus the items naming it or a goal below it directly, each item once (`goalProgress` over `WorkItemRepository.countsByProjects` and `countsByGoals`). `usecases/goal-progress.ts` reads a fixed set whatever the rows shown; more than 1,000 projects for one row is `tooManyProjects`, never a cut count. "Late" is today in the workspace calendar's zone. The project path reads the partial `WorkItem_progress_project_path` (live, non-cancelled; SQL only, migration `20261216120000`): `countsByProjects` is raw SQL naming the `'CANCELLED'` literal, since a bound enum cannot prove the predicate. Never add a plain `[tenantId, projectId, stateCategory]` index: it pulls the list's plans off their indexes.
- **Health (3.2b, decisions 205, 207 and 214).** `PUT /goals/:id/health`, `PUT /initiatives/:id/health` (`goals.manage`, `If-Match` optional): a person only (`setsHealthAsPerson`: no API key, agent, job or system user; the refusal audited `AUTHZ_DENIED`, 403 `NOT_A_PERSON`), never tied to the status either way, audited `GOAL_HEALTH_SET` / `INITIATIVE_HEALTH_SET` with `fromHealth` and `toHealth`; the history is those entries (`ActivityRepository.healthHistory`, no written update). Archived 409 `ARCHIVED`, deleted 404. Show status and health with their names.
- **The pages (3.2b and 3.2c, decisions 221 and 222).** One sidebar entry, Roadmap (`goals.view`, current under `/roadmap` through `activePrefix`; `NAV_PATHS.roadmap` is the Roadmap page, `NAV_PATHS.goals` and `.initiatives` the two lists), over `/roadmap`, `/roadmap/goals` and `/roadmap/initiatives` (main pages, `RoadmapTabs`), and `/roadmap/goals/[goalId]` and `/roadmap/initiatives/[initiativeId]` (subpages). `src/components/goals/` (`use-goals.ts`: deletes and taking a project off an initiative through the undo toast, in `SITE_CONTRACTS`); the server reads are `src/lib/server/goal-pages.server.ts` (`RoadmapAffordances`: `goalAffordances` and `createProject`). The forms read their limits from the client-safe `src/lib/goals/limits.ts`, never `src/lib/schemas/goal.ts`. Copy is `roadmap.*`, `goals.*` and `initiatives.*`.

- **The roadmap (3.2c, decisions 210 and 215 to 217).** A page, not a model, and read-only. `getRoadmap` (`usecases/roadmap.ts`, `GET /roadmap` under `goals.view`, asking `projects.view`) reads in seven statements whatever the size: the goals and initiatives in one (`GoalRepository.roadmapRecords`), the projects (at most `ROADMAP_PROJECT_LIMIT`, 500, archived ones counted; 422 `ROADMAP_TOO_LARGE` with the count above), their dated milestones, ONE aggregate (`WorkItemRepository.roadmapAggregate`: per project, milestone and category the count and the four boundary dates, and grouped by goal the direct path, `UNION ALL`), and the calendars. A bar is derived, never stored: a project's is `spanFromBounds` on its team's calendar (`plannedSpanOf`'s one-date rule, stored dates, no pass), an initiative's or goal's `spanOf` of what is under it; never write a second span. Due dates are diamonds, never engine deadlines (ADR 0010 §3); "finishes after" is a flag only. The chart is the SVAR adapter with `roadmap-model.ts` (records as plain tasks, never `summary`; `gridColumns`, `onSelect`), never editable; a row opens the item timeline (`timelinePathOf`: the project page or the Work items page with `?layout=timeline` and `initiativeId` / `goalId`). The client reads `useRoadmap` (`components/goals/use-roadmap.ts`); goal writes re-read every `/roadmap` key. An initiative's slice is offered by `RoadmapAffordances.roadmap`, asked on the server. The aggregate is plan-checked and the read's statements counted. Copy is `roadmap.page.*` and `roadmap.view.*`.

## Calendar sync

Sub-phase 3.3b (`docs/porting/maps/3.3.md`, its 3.3b part and "Rules no decision names (3.3b, as built)"; `docs/calendar-sync.md`; ADR 0011; owner decisions 225 to 240). The words are ADR 0006's: Calendar connection, Synced event, Calendar sync settings; never Event, Integration, Subscription or Copy for them.

- **Two switches** (decision 234): `CALENDAR_SYNC` (`isCalendarSyncOpen`; closed, every calendar sync route is a 404 before its key and no job does anything; production refuses `1` without a sign-in app pair, twice) and the workspace's `TenantCalendarSettings.syncEnabled` (`integrations.manage`). Off, every connection is torn down.
- **Model.** `prisma/schema/calendar-sync.prisma`, migrations `20261218130000` and `20261218130100`. `CalendarConnection.tokenEncrypted` is in the manifest under the workspace's DEK (decision 238), CHECKed present while CONNECTED and NULL once REVOKED; the connection is keyed to the user, not the membership. `CalendarSyncedEvent` has no FK to the item or the milestone and a NO ACTION key to its connection: a connection goes only after its events. `app_user` holds no DELETE on the settings row. Repository: `CalendarSyncRepository` (the token read only by `tokenOf`).
- **The OAuth flow is hand-written on the sign-in apps** (decision 236), in `src/app-layer/integrations/providers/calendar/token.ts` and `usecases/calendar-connection.ts`, outside the NextAuth seam (ADR 0004 A3): PKCE S256, only the calendar scope (Google `calendar.app.created`, Microsoft `offline_access Calendars.ReadWrite`; never `openid`, `email` or `profile`; no `include_granted_scopes`), its own redirect URIs built on `NEXT_PUBLIC_APP_URL`, Microsoft's authority the consented directory. The state is `src/lib/calendar-sync/oauth-state.ts` (HMAC-sealed, bound to the member and the workspace, carrying the verifier, scoped to `/api/integrations/calendar`, claimed once in Redis). The callbacks (`/api/integrations/calendar/callback`, `/admin-callback`) are signed-in paths, not machine callers: they refuse another person's state and ask `requirePermission` for the state's workspace. Never write `Account`, link an identity or read the external address.
- **Never call Google's revoke endpoint** (decision 236): tokens are destroyed locally. `tests/guards/calendar-sync-egress.test.ts` refuses the endpoint anywhere in `src/`, any `fetch` in calendar sync but `provider-http.ts` (four fixed origins, checked before the request) and any auth-library import in the calendar flow. A server-supplied URL (3.3c's nextLink) goes through `safeFetch` with its origin pinned and a sink row.
- **One generation, one diff.** `generateDesiredEvents` (`usecases/calendar-sync-run.ts`) under the member re-resolved (`resolveMemberContext`; refused: the teardown, never a system context): their open assigned items due from 30 days ago to a year ahead (at most 1,000) and their projects' dated milestones (at most 200, `projects.view`), each a title and one `appLink` (decision 229). The pure `reconcileSyncedEvents` (`domain/calendar-sync.ts`, property-tested) decides inserts, patches and deletes from the rows. An insert is recorded unconfirmed before it is sent and looked up before it is retried. Never push anything else of the workspace.
- **Failures.** A refused credential is terminal (REVOKED, destroyed, rows `PENDING_DELETE`, one `CALENDAR_CONNECTION_REVOKED` as the system user, `NonRetryableJobError`); a throttle is not; one event's failure stays on its row.

Disconnect, `removeTenantMember` (in its transaction, the teardown after the commit), the switch off and the consent withdrawn all use it. A deletion of a workspace or user (8.3) runs it before its cascade.
- **Jobs.** `calendar-sync-dispatch` (every 15 minutes), `calendar-sync-connection`, `calendar-teardown`; after a commit that changes what a calendar shows, call `enqueueCalendarSync` / `enqueueCalendarSyncForItems` (`usecases/calendar-sync-enqueue.ts`, never throwing). A new path that changes an item's title, due date, assignee, state, project or deletion, or a milestone, calls one of them.
- **UI.** Settings → Calendar sync (`src/components/calendar-sync/CalendarSyncSettings.tsx`, `settingsPageAccess().calendarSync`) and the member's section on Inbox → Notification preferences (`CalendarSyncSection.tsx`, offered by `calendarSyncSectionOffered`); data in `use-calendar-sync.ts`, whose disconnect and withdraw go through the undo toast (in `SITE_CONTRACTS`); leaving for a provider is `leaveFor` (a top-level navigation, no CSP change). ## Layer rules

These come from the roadmap's global preamble. The route-handler, usecase, policy and `requirePermission` layers exist since sub-phase 1.4, and the audit, sanitisation and encryption layers since 1.5, and the repository layer since 1.6 (`NotificationRepository`; the work-item repositories since 2.2); their rules bind now.

- Route handlers (`src/app/api/**/route.ts`) parse input, call a usecase and return a response, wrapped in `withApiErrorHandling` (`@/lib/errors/api`). No business logic and no data access in the handler. The 1.4 auth routes under `src/app/api/auth/` are the listed exception that reads the global client (`ROUTE_DIR_ALLOWLIST` in `tests/guards/no-direct-prisma.test.ts`); do not add another without a reason there.
- Usecases (`src/app-layer/usecases/`) hold the logic and take a `RequestContext` as their first argument.
- Policies (`src/app-layer/policies/`) authorise before any data access (`assertCanRead`/`Write`/`Admin`/`Export`, `assertCanManageMembers`, …). Privileged routes are wrapped in `requirePermission('<key>', handler)` from `@/lib/security/permission-middleware`, whose denials write an `AUTHZ_DENIED` audit entry and answer a generic 403; a new privileged route also gets a rule in `src/lib/security/route-permissions.ts` (`tests/guards/api-permission-coverage.test.ts` holds both). The key is a dotted `PermissionSet` path (`admin.members`).
- Every mutation input is validated with Zod (shared schemas in `src/lib/schemas/` and `src/app-layer/schemas/`).
- Free text is sanitised on the server, in the usecase or route that stores it, before it is stored: `sanitizePlainText` for names and descriptions, `sanitizeRichTextHtml` for rich text, `sanitizeUrlText` for a stored URL (`@/lib/security/sanitize`). Encryption is not safety to render: an encrypted field is sanitised too. `tests/guards/sanitize-rich-text-coverage.test.ts` holds the encrypted models to it.
- Every mutation is audited with `logEvent` (`src/app-layer/events/audit.ts`), with the transaction client and a structured `detailsJson` (`category` from `src/lib/audit/event-schema.ts`; a payload that does not parse is refused). It appends a hash-chained `AuditLog` row through `appendAuditEntry`, the only writer; `OrgAuditLog` has `appendOrgAuditEntry`. Never write either table directly, never update or delete a row (triggers and privileges refuse it), and use `appendAuditEntryOrQueue` for an entry whose absence would be worse than a failed request. See [docs/audit-trail.md](docs/audit-trail.md).
- A column that holds personal data or a secret is encrypted: a business or secret field goes in the manifest `src/lib/security/encrypted-fields.ts` (encrypted under the workspace's DEK by `src/lib/db/encryption-middleware.ts`), personal data on a global model in `PII_FIELD_MAP` (`src/lib/security/pii-middleware.ts`). Look a person up by `emailHash: hashForLookup(email)`, never by `email`, which is ciphertext. `tests/guards/encryption-manifest-coverage.test.ts` fails on a free-text column that is in neither and not classified. See [docs/encryption.md](docs/encryption.md).
- An outbound request to a URL a person configured goes through `safeFetch` (`src/app-layer/automation/webhook-safety.ts`); `tests/guards/ssrf-egress-coverage.test.ts` fails on any other sink.
- Repositories filter every query by `tenantId`. (Repositories take the transaction client from `runInTenantContext` and never import `@/lib/prisma`; `tests/guards/no-direct-prisma.test.ts` enforces that half.)

## Auth and permissions

Sub-phase 1.4 (`docs/porting/maps/1.4.md`, ADR 0004, ADR 0006).

- **One seam for the auth library** (ADR 0004 A3). Only the files in `NEXT_AUTH_SEAM` (`eslint.config.mjs`) may load `next-auth` or `@next-auth/*`; `local/next-auth-single-seam` (`eslint-rules/`) refuses it anywhere else in `src/` (`import type` is allowed), and `tests/guards/auth-stack-pinning.test.ts` holds the list equal to the real importers. Everything else reads the session through `@/lib/auth/session` (`getSession`, `getSessionOrThrow`). `next-auth` stays pinned at 4.24.15.
- **Roles and permissions.** `Role` is `OWNER ADMIN MEMBER VIEWER GUEST`; an unresolvable role resolves to VIEWER, never GUEST (`src/lib/auth/session.ts`, `getPermissionsForRole`). `src/lib/permissions.ts` is the `PermissionSet` (fourteen domains, `intake` since 2.6a, `goals` since 3.2a; a VIEWER reads every project and writes nothing but its own personal saved views, decision 60). **A GUEST holds no key until 8.4** (owner decision 204): every keyed route refuses it with an audited 403 and every keyed usecase refuses it, so it reads no configuration, roster or project; it keeps only the key-free self-service routes (its own notifications and preferences, its own MFA and sessions, the workspace MFA policy), which ask the coarse `canRead` alone. A GUEST membership resolves to that empty set and stays GUEST whatever custom role it carries (`permissionsForMembership`, `effectiveRoleOfMembership`; never compute a membership's set or role another way). My Work shows a guest "No access yet"; other pages are 404s; the sidebar shows each workspace row only to a holder of its page's key. 8.4 grants exactly what its project grants need. `src/lib/roles.ts` holds the writers' lists (`ASSIGNABLE_TENANT_ROLES`, which leaves out GUEST until its scope is built; `CUSTOM_ROLE_BASE_ROLES`). An OWNER never carries a custom role and no custom role is built on OWNER (usecases and two CHECKs). A custom role's grants are `TenantCustomRole.grantsJson`: ADR 0006 bans the word "Permissions" in identifiers.
- **Tenant context gates.** `getTenantCtx` (route handlers) and `getTenantServerContext` (pages) run the same workspace MFA gate, `src/lib/auth/workspace-mfa-gate.ts`; keep them on that one module. The edge (`src/middleware.ts`, `src/lib/auth/guard.ts`) admits `/t/<slug>/**` and `/api/t/<slug>/**` only for a slug in the JWT's memberships, refuses non-admins on `/admin` paths, and holds a session that owes an MFA challenge. Public paths are the allowlist in `guard.ts`; `MACHINE_CALLER_PREFIXES` holds the three credential-less beacons (the two CSP report paths and `/api/telemetry/vitals`, 1.6) the two public intake routes (`/api/intake/forms`, `/api/intake/confirm`, 2.6b, decision 98) and the inbound email webhook (`/api/intake/email`, 2.6c), and an entry needs a contract in `tests/guards/machine-caller-paths-self-authenticate.test.ts`; `/f/` is a public page prefix.
- **Public sign-up** at `/api/auth/register` is behind `AUTH_PUBLIC_SIGNUP` (`isPublicSignupOpen`, ADR 0006): unset, closed in production and open otherwise. The invite path on the same route (account only, no workspace) stays open.
- **Email** is stored as ciphertext (`User.email`, written in its normal form, `lookupEmail(x)`) and matched by `emailHash` (`hashForLookup`, which trims and lower-cases). `emailHash` is nullable in the schema and NOT NULL in the database on purpose (the one line in `prisma/fresh-db-schema-drift.expected.sql`; `tests/guards/pii-hash-not-null.test.ts`).
- **Stubs at final paths:** `@/lib/tenant-context-provider` (1.7). It keeps the parent's signatures so 1.7 replaces it without touching callers. Integration suites assert on real `AuditLog` / `OrgAuditLog` rows and verify the chain (`verifyAuditChain`, `verifyOrgAuditChain`); never fake the audit writer. Suites that need a workspace with an owner use `tests/helpers/tenant-fixture.ts`.
- **E2E** signs in as a workspace the spec registers (`isolatedTenant` / `authedPage` from `tests/e2e/fixtures.ts`); there is no seeded tenant. The Playwright server runs with `AUTH_TEST_MODE=1`, `NEXT_TEST_MODE=1`, `AUTH_PUBLIC_SIGNUP=1` and in-memory rate limits; `tests/e2e/README.md` records why there is no real-auth config.

## Security perimeter

Sub-phases 1.5a and 1.5b (`docs/porting/maps/1.5.md`). Read [docs/security-perimeter.md](docs/security-perimeter.md), [docs/encryption.md](docs/encryption.md), [docs/audit-trail.md](docs/audit-trail.md) and [docs/rate-limiting.md](docs/rate-limiting.md) before touching it.

- **Prisma extensions.** `src/lib/prisma.ts` composes, innermost first: the audit extension (an `entity_lifecycle` row with a diff for every write), field encryption, PII, the RLS tripwire. `import * as auditWriterModule` there follows the same dereference-in-a-function rule as the data layer.
- **Keys.** A workspace's DEK is wrapped into `Tenant.encryptedDek` in the write that creates it (`generateAndWrapDek`, as `createTenantWithDek`); `getTenantDek` creates one lazily for a bare `Tenant`. One-way literals (HKDF info and salt, the HMAC domain, the dev fallback) are Islestone's and never change: changing one makes every stored ciphertext and hash unreadable. Set `LOOKUP_HASH_KEY` and `DERIVED_SUBKEY_KEY` to the current key before any master-key rotation; production refuses a rotation without them. A real decrypt failure throws (`ENCRYPTION_DECRYPT_FAIL_CLOSED=0` is the incident lever).
- **The audit trail** is append-only: `app_user` holds SELECT and INSERT only on both logs, and the triggers refuse UPDATE and DELETE except `AuditLog.userId` to NULL (pseudonymisation, 8.3). The chain lock is the bare `hashtext(tenantId)`. `HASH_FIELDS` and the canonical JSON are a wire format: changing either breaks every stored chain.
- **CSP.** The middleware mints a nonce per request and puts the whole policy on the request's `Content-Security-Policy` header (Next.js stamps its scripts from it) and the nonce on `x-csp-nonce` (the root layout's `__webpack_nonce__`); both bridges have guards. No `'unsafe-inline'`/`'unsafe-eval'` in production `script-src`, no third-party host. Violations report to `/api/security/csp-report` (1.6): a per-IP limit and a 16 KB cap in the handler for the POST, the platform key and the edge read tier for the GET; `/api/csp-report` hands off to it in-process.
- **Rate limits.** Mutation tier in `withApiErrorHandling` (60/min), read tier on tenant GETs at the edge after the auth gates (120/min), auth tier on `/api/auth/**` (10/30/60 per min); the public intake paths are metered at the edge at the read tier's budget before the allowlist returns, and the submit and confirmation carry their own per-IP limits (2.6b, see "Intake"); the inbound email webhook is metered per IP in its handler only (2.6c); Upstash or memory by `RATE_LIMIT_MODE`.
- **Secrets in the repository.** `.secret-patterns` feeds the Husky pre-commit hook (`scripts/detect-secrets.sh`, installed by `npm install`) and `tests/guards/no-secrets.test.ts`. Mark a test value `pragma: allowlist secret` on its line, or put it under `tests/fixtures/secrets/`.
- **Key rotation (1.5b).** Two operator-started jobs, never scheduled. `key-rotation` (`POST /api/t/<slug>/admin/key-rotation`, `admin.tenant_lifecycle`, OWNER-only) re-wraps one workspace's DEK and rewrites its `v1:` values (manifest fields and `PII_TENANT_SCOPED_MODELS`) under a newly staged `DATA_ENCRYPTION_KEY`; `scripts/rotate-global-pii.ts` does the tables with no `tenantId` once. `rotateTenantDek` (`POST …/admin/tenant-dek-rotation`, `admin.tenant_lifecycle`, OWNER-only) swaps in a fresh DEK, keeps the old one in `Tenant.previousEncryptedDek` and enqueues `tenant-dek-rotation`, which clears it only after a sweep with zero errors; until then a second rotation is a 409 and reads fall back to the previous DEK. Each sweep pages by `id` and writes conditionally on the ciphertext it read. When a rotation job runs it re-resolves the person who asked (`resolveRotationActor`, `src/app-layer/jobs/rotation-actor.ts`): it acts as them while they are an ACTIVE member holding `admin.tenant_lifecycle`, and otherwise finishes anyway as the workspace system user, recording `requestedByUserId`, `authority: 'SYSTEM'` and the refusal in its audit entries and result. A new PII model goes in `PII_TENANT_SCOPED_MODELS` or `PII_GLOBAL_MODELS` (`tests/guards/pii-rotation-coverage.test.ts`), or no sweep reaches it. A raw write to an interpolated table is refused outside the two sweeps (`tests/unit/audit-trail-guardrails.test.ts`). A future write-once trigger on an encrypted column must admit the sweep's re-wrap.
- **The audit outbox drain (1.5b).** `audit-outbox-flush` replays `AuditOutbox` rows every five minutes, oldest event first, claiming each before its append; a replayed entry carries `occurredAt` and `replayedFromOutbox` in `detailsJson`. A row parks `FAILED` after five attempts and is never deleted.
- **Teardowns.** Audit rows block a delete of their workspace or user (`ON DELETE RESTRICT`, and the trigger). Use `resetDatabase`, or clear them first with `tests/helpers/audit-cleanup.ts`, the only sanctioned raw SQL against the trails; `tests/guards/integration-suite-audit-teardown.test.ts` holds it. `tests/setup/disconnect-after-suite.ts` drops the audit-stream buffers after each integration file.

## Jobs, notifications and observability

Sub-phase 1.6 (`docs/porting/maps/1.6.md`). Read [docs/jobs.md](docs/jobs.md), [docs/notifications.md](docs/notifications.md) and [docs/observability.md](docs/observability.md) before touching it.

- **Jobs.** A job is a key in `JobPayloadMap` with its `JOB_DEFAULTS` entry (`src/app-layer/jobs/types.ts`), one `executorRegistry.register` that names its payload fields (`NamesEveryField`; `tests/guards/executor-payload-forwarding.test.ts` refuses `_payload`), and either a `SCHEDULED_JOBS` entry or an `ON_DEMAND_JOBS` reason (`tests/guards/runtime-wiring-coverage.test.ts`). Enqueue through `enqueue` (`queue.ts`), never a `Queue` of your own. A retry that cannot succeed throws `NonRetryableJobError`. Removing a schedule lists its name in `RETIRED_SCHEDULER_NAMES`.
- **The worker is plain Node.** Nothing it reaches may import the NextAuth seam or `next-auth`, or statically import `next/headers`, `next/navigation` or `server-only` (`tests/guards/worker-import-graph.test.ts`). It bundles with esbuild (`scripts/build-worker.mjs`, CJS shims in its banner).
- **Job identity.** A job writing for nobody uses `buildTenantSystemJobContext` (the `sys_<tenantId>` user; CHECKs refuse it a membership, account, session or password). A job doing what a person asked re-resolves them when it runs (`resolveInitiatorContext`, `resolveMemberContext`); `null` is a refusal, never a fallback to a system context. The one exception, by owner decision (2026-11-19), is the two key rotations: a rotation whose initiator no longer resolves (or no longer holds `admin.tenant_lifecycle`) still finishes, as the workspace system user, with who asked and why recorded and the departed person never named as the actor, because a stopped rotation leaves the workspace's keys half-moved (`src/app-layer/jobs/rotation-actor.ts`). No other job may take that path. The call that first creates `sys_<tenantId>` writes one `SYSTEM_USER_CREATED` entry in the same transaction (`logEvent` with `{ withinTransaction: true }`). A job that resolves people to mail checks the workspace is live (`tests/guards/cross-tenant-recipient-liveness.test.ts`).
- **Notifications.** Email goes through `enqueueEmail` (an outbox row, deduplicated per recipient hash and day with `createMany({ skipDuplicates: true })`, safe inside a transaction) and is sent only by `processOutbox`, which claims each row with a lease before its send. A bell row is written by `createAssignmentNotification` or `createWatcherNotifications`, which ask `isInAppTypeEnabled` before the write and publish the row's real id. Links go through `appLink` (absolute). The outbox address is PII, encrypted in place; `app_user` cannot delete outbox or settings rows. A log line never carries a recipient's address or a message body: the mailer logs `hashForLookup` of each address and the template (`recipientLogFields`, owner decision 2026-11-19). Mail is sent by `nodemailer` when `SMTP_HOST` is set (`SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`), read through `@/env`. `package.json` overrides next-auth's `nodemailer` peer (ADR 0004 question 7), so nothing may import `next-auth/providers/email` (`tests/guards/next-auth-email-provider-unused.test.ts`).
- **Observability.** Log through the logger; trace with `traceUsecase` / `traceOperation`; jobs run in `runJob`. A metric goes in `metrics.ts` or `business-metrics.ts` (one owner per name; no workspace or person id as an attribute). An observable gauge registers through `observable-registry.ts` (`local/observable-gauge-rebinds`). Startup work belongs in `src/instrumentation-node.ts`, shutdown stages in `shutdown.ts` within `shutdown-budget.ts`. Sentry (`sentry.ts`) is server-side and off unless `SENTRY_DSN` is set; its `dataCollection` is pinned off (`tests/guards/sentry-privacy-posture-pinned.test.ts`), and a browser SDK is a new data flow, not a config change.
- **Redis.** `REDIS_URL` is required and authenticated in production; the policy is `noeviction`. The integration project's `jobs-queue-roundtrip` suite needs it (CI runs a Redis service; locally `ALLOW_REDIS_SKIP=1` skips it).

Use `prismaTestClient()` and `resetDatabase()` from `tests/helpers/db.ts` (TRUNCATE fires no row triggers, so the last-owner guards do not block it); never mock Prisma there. Prove isolation through `runInTenantContext`, which runs as `app_user`: the test client connects as the login role and sees every row. The project's per-test timeout is 30 s, set by `jest.setTimeout` in `tests/setup/integration-timeout.ts`: Jest ignores `testTimeout` inside a project entry (`tests/unit/jest-config-timeouts.test.ts`). Every suite under `tests/integration/` must be DB-gated (`tests/guards/integration-suites-execute.test.ts`); one that needs no database goes under `tests/unit/` (the copied middleware and route suites are in `tests/unit/auth-flow/`).
- **Guards** (`tests/guards/`) check source structure. A guard takes its file population from git (`gitFiles()` in `tests/helpers/git-files.ts`, i.e. `git ls-files --cached --others --exclude-standard`), never from a directory walk with a skip list, and proves itself against a planted fixture (a throwaway git repository in a temp directory) so it cannot pass by checking nothing.

Every route and method under `src/app/api/t/[tenantSlug]/` has a hand-written row in `tests/integration/permission-matrix/table.ts` with the outcome for OWNER, ADMIN, MEMBER, VIEWER, GUEST and the two custom roles (`member-no-edit`, `viewer-plus-comment`); `tests/guards/permission-matrix-population.test.ts` fails on a route without a row, and the suites beside the table drive every cell through the real handler. Never compute a cell from `permissions.ts` or `route-permissions.ts`. GUEST cells are `g(...)`, tagged until 8.4; a guest cell on a keyed route is `denied` (decision 204), and the guest tripwire fails the tagged cells once guests' visibility, keys or assignability change; never re-pin `PRE_8_4_VISIBILITY_SHA` without rewriting them. A write that sets or clears a configurable field gets a row in `tests/integration/field-set-routes.test.ts`.
- **Plan checks** (H2a, owner decision 168; `docs/performance.md`): **a new list query joins `PLAN_CHECKED_QUERIES`** (`tests/perf/plan-checked-queries.ts`) with a runner in `tests/perf/plans.test.ts`: its plan on the 10k seed reads no guarded table (`WorkItem`, `Comment`, `SearchVector`, `WorkItemTransition`, `AuditLog`) with a sequential scan, uses the indexes it names (a search index with its operator in the index condition) and stays within its buffer budget. `tests/guards/plan-checked-queries-coverage.test.ts` fails on a repository method that reads `WorkItem`, `Comment` or `SearchVector` and is neither listed nor exempt with a reason. A reported, unfixed finding is a `knownFinding` whose check runs as `it.failing`; remove the marker with the fix. Each query has a 10k buffer budget (`maxBuffers`, every pull request) and a 100k one (`maxBuffers100k`, the nightly run). Budgets (buffers, statements per request in `tests/perf/statements.test.ts`) only go down.
- **Latency** (H2b, owner decisions 166 to 169; `docs/performance.md`, "Latency"): `scripts/perf/budgets.json` is the one owner of the response budgets (decision 167's table; `tests/unit/perf/harness.test.ts` holds every budget at or below it, so a budget only goes down); `scripts/perf/run.mjs` drives the built app, the pure rules are `scripts/perf/lib.mjs`. A scenario that measured nothing (fewer successful samples than asked, an empty histogram, an answer its check refused) fails every run; budgets fail only `--enforce` (the nightly 100k run) after the 25 % tolerance and one re-run. A miss reported and not yet fixed is a scenario's `knownFinding` (its shapes and why): reported, never red, and red the night it stops reproducing until the marker is removed. A new scenario gets its runner, its budget and a line in the docs; writes are marked `write` and run last.

- **E2E** (`tests/e2e/*.spec.ts`) runs Playwright against the standalone server (`npm run start`) on port 3100, so build first. Build with `NEXT_PUBLIC_APP_URL` set to the server's origin (`http://127.0.0.1:3100`, as CI does): the client env module validates in the browser, and a build without it renders the error page. Set `PW_CHROMIUM_PATH` to use a preinstalled Chromium. Traces are off by default. **Isolation** (H2g, owner decision 180; `tests/e2e/README.md`, "Isolation"): `tests/guards/e2e-isolation.test.ts` (ported from inflect-compliance, `BASELINE` empty) fails a top-level `let`/`var` written in one `test()` and read in another, a spec that calls `signInAs`, `goto('/t/…')` or sends to `/api/t/…` without importing `test` from `./fixtures`, and a webServer that loses `AUTH_TEST_MODE=1` / `NEXT_TEST_MODE=1` while every spec shares `127.0.0.1`. Pull requests keep `retries: 1`; the nightly `e2e-isolation` job in `.github/workflows/perf.yml` runs `--repeat-each=2 --retries=0 --workers=4`, then each spec file alone, and a red night opens one issue.
